# 0. 당근 화상면접을 어떻게 봐야 하는가

## 현재까지 수집된 후기에서 반복되는 것

최근 후기와 사용자가 직접 확인한 잡플래닛 후기에서 반복되는 패턴은 크게 세 가지다.

### 1. 이력서 / 포트폴리오 기반 검증

```text
이 프로젝트 왜 했나요?
왜 그 기술을 선택했나요?
본인이 직접 한 건 어디까지인가요?
그 선택 때문에 이런 문제가 생기지 않나요?
그럼 어떻게 해결할 건가요?
다시 한다면 똑같이 할 건가요?
```

### 2. 프론트엔드 기본기


```text

```

을 묻는다.

### 3. 사람 / 동기 / 협업

확인된 후기 질문:

```text

협업하기 어려운 유형은?
서비스를 위해 개발 외에 한 노력은?
```

# 2. 자기소개

## 30초 답변

최근에는 기존 레거시 아파트 커뮤니티 서비스를 신규 프로젝트로 다시 구축하면서 프론트엔드 구조와 인증 흐름, 공통 UI 구조를 설계했습니다. 이 과정에서 AI Agent를 실제 개발 프로세스에 적극적으로 활용하면서 반복적인 구현뿐 아니라 프로젝트 규칙과 검증 방식까지 함께 정리했습니다.

저는 기능을 빠르게 만드는 것뿐 아니라, 이후에 얼마나 쉽게 확장하고 유지할 수 있는지까지 같이 고민하면서 개발하는 편입니다.

# 3. "어떤 개발자이신가요?"

## 이 질문의 의도

기술 스택을 묻는 질문이 아니다.

```text
무엇을 중요하게 보는 사람인가?
어떤 방식으로 일하는가?
어떤 문제에서 강한가?
```

를 묻는다.

## 추천 답변

저는 **문제를 빠르게 구현하는 것과 이후의 유지보수성을 같이 보는 개발자**라고 생각합니다.

최근에는 신규 서비스를 0부터 만드는 경험이 많았는데, 단순히 화면을 빠르게 만드는 것보다 이후 기능이 계속 추가됐을 때 구조가 버틸 수 있는지를 많이 고민했습니다.

또 AI Agent를 적극적으로 활용하면서 반복 작업은 빠르게 처리하되, 아키텍처나 검증 책임은 개발자가 가져가는 방식으로 개발 프로세스를 개선하고 있습니다.

## 키워드

```text
빠른 실행
+
확장성
+
AI를 실행 도구로 활용
+
판단 책임은 개발자
```

## 예상 꼬리

### "빠르게 만드는 것과 유지보수성이 충돌하면요?"

먼저 지금 제품의 단계와 변경 가능성을 봅니다.

초기 검증 단계인데 확장 가능성만 보고 복잡한 구조를 먼저 만들면 오버엔지니어링이 될 수 있고, 반대로 계속 확장될 게 명확한 영역을 임시 구조로 만들면 변경 비용이 커질 수 있습니다.

그래서 **현재 필요한 수준에서 가장 단순한 구조를 선택하되, 변경 가능성이 높은 경계는 명확히 나누는 것**을 기준으로 봅니다.

# 4. "어떤 개발자가 되고 싶나요?"

## 피할 답

```text
잘하는 개발자
시니어 개발자
풀스택 개발자
AI 잘 쓰는 개발자
```

만 말하지 않는다.

## 추천 방향

```text
기능 구현
→ 기술 판단
→ 사용자 문제
→ 제품 결과
```

로 역할을 넓히고 싶다고 말한다.

## 답변

기술적으로 좋은 코드를 만드는 것에서 끝나지 않고, **왜 이 기능을 만드는지와 실제 사용자 행동이 어떻게 달라졌는지까지 보는 개발자**가 되고 싶습니다.

최근에는 아키텍처나 개발 방식에 대한 판단 범위는 많이 넓어졌지만, 앞으로는 데이터와 사용자 반응을 바탕으로 제품의 방향을 결정하는 과정에도 더 깊게 참여하고 싶습니다.

# 5. 이직의 이유는 무엇인가요?

## 원칙

현 회사의 단점을 말하는 질문이 아니다.

```text
현재까지 얻은 것
→ 다음 단계에서 원하는 것
→ Local Jobs와 연결
```

## 추천 답변

현재 회사에서 신규 서비스 구축, 플랫폼 구조 개선, AI Agent 기반 개발 방식처럼 기술적으로 다양한 경험을 할 수 있었습니다.

다만 앞으로는 프론트엔드 개발자가 구현과 기술 구조뿐 아니라 사용자 문제를 정의하고, 데이터를 보면서 제품 방향까지 더 깊게 결정하는 환경에서 일해보고 싶다는 생각이 커졌습니다.

Local Jobs는 작은 팀에서 B2B와 B2C 제품을 함께 만들고, 엔지니어도 제품 성공과 AI 활용 방식에 깊게 관여하는 역할로 보여서 제가 다음 단계에서 경험하고 싶은 방향과 잘 맞는다고 생각했습니다.

## 예상 꼬리

### "현재 회사에서도 하면 되지 않나요?"

현재도 제품 개선 과정에 참여하고 있지만 역할 구조상 가설이나 실험 방향을 PM / 마케팅이 주도하는 경우가 많았습니다.

저도 구현과 계측을 넘어 문제 정의와 결과 해석 단계까지 더 직접적으로 참여해보고 싶습니다.

### 주의

현재 회사를 깎아내리지 않는다.

Local Jobs 공고에서도 0→1, B2B/B2C, Agent 기반 개발 방식과 제품 문제 해결을 강조하고 있었고, 제가 지금까지 해온 경험을 활용하면서도 제품 판단 영역까지 더 확장할 수 있는 팀이라고 느꼈습니다.

# 7. 당근에서 기대하는 점

## 답변

가장 기대하는 것은 **엔지니어가 제품 문제를 정의하는 과정에 깊게 참여하는 경험**입니다.

최근에는 구조나 개발 방식에 대한 기술적 의사결정은 많이 해봤지만, 사용자 데이터와 시장 반응을 기반으로 제품 방향을 결정하는 경험은 상대적으로 부족했습니다.

Local Jobs에서는 엔지니어도 사용자 문제와 지표를 함께 보고 빠르게 실행하는 것으로 알고 있어서, 그 과정에 더 깊게 참여하면서 제가 가진 0→1과 AI 개발 경험도 기여하고 싶습니다.

# 8. 개발할 때 동기부여는 어디서 얻나요?

## 추천 답변 방향

사용자 반응 + 눈에 보이는 개선 + 어려운 문제 해결.

## 답변

제가 만든 기능이 실제 사용자 흐름을 개선하거나, 팀이 반복하던 일을 줄이는 결과로 이어질 때 가장 동기부여를 많이 받습니다.

최근에는 사용자 기능뿐 아니라 AI Agent Harness처럼 개발 방식 자체를 개선하는 작업도 재미있었습니다. 제가 만든 구조가 다음 작업을 더 빠르고 예측 가능하게 만드는 걸 볼 때 성취감을 느끼는 편입니다.

# 9. 최근 가장 성장한 포인트

## 가장 좋은 카드

AI 활용 방식의 변화.

## 답변

최근 가장 성장했다고 느끼는 부분은 AI를 사용하는 방식입니다.

처음에는 AI를 잘 사용하는 걸 많은 작업을 맡기는 것으로 생각해서 간단한 작업까지 Agent에게 위임하기도 했습니다.

그런데 그렇게 하다 보니 제가 직접 코드를 탐색하고 구조를 이해하는 시간이 줄어드는 문제가 생겼습니다.

지금은 AI 활용 능력을 단순한 프롬프트 능력보다 **AI가 예측 가능하게 일할 수 있는 환경을 만드는 능력**으로 보고 있습니다.

# 11. 아파트스토리를 왜 새로 만들었나요?

## 핵심

```text
단지별 DB
PHP 레거시
기능 누적
높은 의존성
변경 영향 파악 어려움
인수인계자 부재
계속되는 신규 기능
```

## 답변

기존 서비스를 그대로 확장하는 방법도 검토했지만 구조적으로 유지보수 비용이 계속 커지는 상황이었습니다.

단지마다 데이터베이스가 분리되어 있었고 PHP 레거시 코드도 오랫동안 기능이 누적되면서 변경 영향 범위를 파악하기 어려웠습니다. 기존 구조를 깊게 알고 있는 인수인계자도 부재한 상태였습니다.

앞으로 관리자와 사용자 기능을 계속 추가해야 했기 때문에 기존 코드를 계속 확장하는 것보다, 유지해야 하는 인증과 기존 데이터는 남기고 신규 애플리케이션 영역을 다시 구축하는 것이 장기적으로 더 효율적이라고 판단했습니다.

## Why 1 — 왜 리팩터링하지 않았나요?

리팩터링도 기존 동작과 영향 범위를 충분히 파악한 상태에서 해야 하는데 당시에는 코드 분석 비용과 변경 리스크가 컸습니다.

신규 기능도 계속 예정되어 있었기 때문에 기존 구조와 신규 구조를 동시에 운영하는 기간이 길어지면 복잡도가 더 커질 가능성이 있다고 판단했습니다.

## Why 2 — 왜 전부 새로 안 만들었나요?

신규 구축 자체가 목적은 아니었습니다.

기존 사용자, 인증, 데이터처럼 이미 사업적으로 연결된 부분은 유지하고 앞으로 확장해야 하는 애플리케이션 영역을 분리했습니다.

## Why 3 — 다시 한다면?

당시 상황이라면 비슷한 결정을 할 것 같습니다.

다만 기존 코드에 테스트가 충분하고 모듈 경계가 잘 잡혀 있었다면 점진적인 migration을 먼저 검토했을 것입니다.

# 12. 신규 프로젝트에서 가장 먼저 고민한 것

## 답변

기술 스택을 먼저 정하기보다 **기존 시스템과 신규 시스템의 경계**를 먼저 정했습니다.

신규 서비스에서도 기존 사용자의 인증과 데이터를 그대로 사용해야 했고, 여러 도메인이 하나의 Backend API를 사용하고 있었기 때문에 인증과 네트워크 구조를 먼저 정리했습니다.

그 다음 여러 앱이 공유해야 하는 UI와 기능의 경계를 모노레포와 디자인 시스템에서 정의했습니다.

# 13. AI Agent를 실제로 어떻게 활용했나요?

## 실제 사용

```text
코드 탐색
반복 UI 구현
리팩터링
테스트 초안
코드 리뷰
Figma MCP
문서화
```

## 답변

신규 프로젝트의 반복적인 구현 속도를 높이기 위해 Claude Code와 Cursor 같은 Agent를 적극적으로 사용했습니다.

초기에는 작업 단위로 프롬프트를 작성했는데 프로젝트가 커질수록 같은 구조와 규칙을 반복해서 전달해야 했고, Agent가 서로 다른 패턴으로 코드를 작성하는 문제가 생겼습니다.

그래서 프로젝트 구조와 도메인, 규칙을 Harness 형태로 명시하고 반드시 지켜야 하는 규칙은 lint나 type 같은 검증 장치로 옮겼습니다.

---

# 14. AI Harness 구조

```text
Global
└─ 공통 개발 원칙

Project
├─ 프로젝트 목적
├─ Architecture
├─ Domain Context
├─ Monorepo package 역할
├─ FSD / import
└─ 금지 영역

Commands
├─ 구현
├─ 리뷰
├─ 리팩터링
└─ 테스트

Memory / Context
└─ 반복적으로 필요한 프로젝트 정보

Validation
├─ lint
├─ type
└─ test
```

## 답변

전역 규칙과 프로젝트 규칙을 분리했습니다.

전역에는 프로젝트가 바뀌어도 유지되는 코드 작성 원칙을 두고, 프로젝트에는 아키텍처, 모노레포 구조, FSD 규칙, 도메인 맥락과 수정하면 안 되는 영역을 넣었습니다.

반복 작업은 Command로 분리했고 반드시 지켜야 하는 규칙은 문서에만 의존하지 않고 lint나 type으로 검증하도록 했습니다.

# 15. 왜 모든 규칙을 문서로 두지 않았나요?

## 답변

Agent가 문서를 항상 완벽하게 준수한다고 보장할 수 없기 때문입니다.

예를 들어 import boundary는 코드만 보면 기계적으로 판정할 수 있기 때문에 문서보다 lint로 강제하는 편이 더 적합했습니다.

반대로 "불필요한 추상화를 하지 않는다"처럼 판단이 필요한 내용은 문서와 리뷰 영역으로 남겼습니다.

# 16. AI가 잘못 구현한 실제 사례

## 사례

```text

→ 기능 정상
→ 구조 일관성 저하
```

## 답변

그런데 Agent가 내부 컴포넌트 파일을 직접 import하는 경우가 반복됐습니다.

기능상 문제는 없지만 내부 구현과 결합되고 import 패턴이 파편화되기 때문에 `no-restricted-imports` 같은 lint 규칙으로 경계를 강제했습니다.

# 17. Monorepo를 왜 선택했나요?

## 답변

마스터 어드민, 단지 어드민, 사용자 서비스가 공통 UI, 인증, 설정과 유틸을 공유해야 했기 때문에 모노레포를 선택했습니다.

각 앱은 독립적으로 개발하고 배포하되 공통 영역은 package로 분리해 재사용할 수 있도록 했습니다.

## Why — 멀티레포는?

멀티레포도 가능하지만 공통 컴포넌트나 설정이 변경될 때 여러 repository의 버전과 배포를 따로 맞춰야 하는 비용이 생길 수 있다고 판단했습니다.

## Trade-off

```text
의존성 경계 관리 필요
빌드 복잡도
package coupling 가능
```

# 18. Design System을 왜 만들었나요?

## 답변

여러 관리자와 사용자 서비스에서 같은 UI 패턴을 반복 구현해야 했기 때문에 공통 토큰과 컴포넌트를 분리했습니다.

목표는 "공통 컴포넌트를 많이 만드는 것"이 아니라 동일한 규칙을 여러 앱에서 재사용하고 변경 시 한 곳에서 관리하는 것이었습니다.

## 꼬리 — 언제 공통으로 올리나요?

한 번 쓰인다고 바로 공통화하지 않습니다.

두 곳 이상에서 동일한 목적과 인터페이스로 반복되고, 변경 방향도 같이 가져갈 가능성이 높은지를 보고 공통화합니다.

# 19. Session / Cookie 인증을 왜 사용했나요?

## 답변

신규 서비스라고 인증까지 새로 만들 필요는 없었고 기존 사용자 인증 체계를 그대로 활용해야 했습니다.

기존 Backend가 세션 기반 인증을 사용하고 있었고 서비스 간 인증 상태를 공유해야 해서 서브도메인 기반의 Session/Cookie 구조를 사용했습니다.

프론트에서 인증 정보를 직접 관리하는 범위를 줄이고 인증 상태와 만료 판단을 서버 중심으로 유지하는 방향이었습니다.

## 주의

```text
Session이 JWT보다 무조건 안전하다 X
```

# 21. Reverse Proxy를 왜 선택했나요?

## 답변

100개가 넘는 도메인이 하나의 Backend API를 사용하는 구조였는데 모든 도메인을 Backend의 CORS allowlist에서 관리하면 도메인 추가 때마다 Backend 설정과 배포가 필요했습니다.

인프라 수준에서 프록시를 구성하는 방법도 있었지만 당시에는 기존 Next 서버를 활용하면 별도 인프라를 추가하지 않고 일관된 API 경로를 만들 수 있었습니다.

API hop과 Next 서버 의존성이 증가하는 단점은 알고 있었지만 당시 규모에서는 운영 단순성의 이점이 더 크다고 판단했습니다.

## Why — CORS가 왜 문제?

CORS 자체가 어려운 문제가 아니라:

```text
프론트 도메인 추가
→ Backend 설정 수정
→ Backend 배포
```

로 변경 주기가 다른 시스템이 묶이는 것이 문제였습니다.

## Trade-off

```text
API hop
Next server 부하
장애 전파
```

# 29. React스럽게 코드를 작성한다는 것

## 답변

```text
→ source of truth 중복 방지

왜 effect 최소?
→ 실행순서 / 동기화 복잡도 감소
```

# 31. React Query queryKey는 어떻게 관리하나요?

## 질문 의도

캐싱의 identity를 이해하는가?

## 핵심

Query Key는:

> **어떤 서버 데이터를 캐시하고 있는지 유일하게 표현하는 식별자**

## 좋은 방식

도메인 단위 key factory를 만든다.

```ts
const userKeys = {
  all: ['users'] as const,
  lists: () => [...userKeys.all, 'list'] as const,
  list: (filters: UserFilters) => [...userKeys.lists(), filters] as const,
  detail: (id: string) => [...userKeys.all, 'detail', id] as const,
};
```

## 왜?

```text
키 문자열 파편화 방지
invalidating 범위 명확
파라미터 누락 방지
재사용
```

## 꼬리

### "filter object 넣어도 되나요?"

직렬화 가능한 값이라면 가능하지만 같은 의미의 필터가 안정적인 구조를 갖도록 관리해야 한다.

### "왜 hierarchy?"

상위 key로 관련 query들을 함께 invalidate할 수 있기 때문.

SPA에서는 `pushState`와 `replaceState`로 페이지 전체 reload 없이 URL과 history entry를 변경할 수 있습니다.

사용자가 뒤로 / 앞으로 이동하면 history entry가 바뀌고 `popstate`를 통해 UI 상태를 맞출 수 있습니다.

검색이나 필터처럼 복원이 필요한 상태를 local state에만 두면 URL과 UI가 어긋날 수 있어서 URL state를 사용합니다.

# 35. Promise 기본기

## 반드시 알아야 할 것

```text
Promise state
pending
fulfilled
rejected
```

## then

Promise의 결과를 이어서 처리한다.

## Promise.all

모두 성공해야 성공.

하나가 reject되면 반환 Promise는 reject.

나머지 네트워크 요청 자체가 자동 취소되는 것은 아니다.

## Promise.allSettled

모든 Promise가 끝날 때까지 기다리고 각각 성공 / 실패 결과 반환.

## race

가장 먼저 settle된 Promise 결과.

## any

가장 먼저 fulfilled된 Promise 결과.

모두 reject되면 AggregateError.

## Event Loop 꼬리 대비

Promise callback은 microtask queue에서 처리된다.

# 41. 앞으로 개발 업무에서 AI를 어떻게 활용할 것인가?

## 답변

앞으로 AI는 코드 생성 도구보다 **개발 프로세스의 실행 주체**로 더 많이 사용될 것이라고 생각합니다.

그래서 저는 Harness, lint, type, test처럼 Agent가 예측 가능한 범위에서 일할 수 있는 환경을 만드는 방향으로 활용하고 있습니다.
