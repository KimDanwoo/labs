# 1. 자기소개

## 30초 답변

안녕하세요. 사용자 경험과 개발 생산성을 함께 고민하는 프론트엔드 엔지니어 김단우입니다.

최근에는 레거시 서비스를 신규로 전환하면서 프론트엔드 구조와 인증 흐름, 공통 UI 구조를 설계하고 구축했습니다.

이 과정에서 AI Agent를 개발 프로세스에 적용해 반복적인 구현과 검증 과정도 개선했습니다.

저는 단순히 기능을 구현하는 데 그치지 않고, 사용자가 더 편하게 서비스를 이용할 수 있도록 개선하면서 팀이 더 빠르고 안정적으로 개발할 수 있는 구조까지 함께 고민하는 개발자입니다.

```text
반복적인 구현과 검증 과정 개선
```

# 2. "어떤 개발자이신가요?"

## 이 질문의 의도

기술 스택을 묻는 질문이 아니다.

```text
무엇을 중요하게 보는 사람인가?
어떤 방식으로 일하는가?
어떤 문제에서 강한가?
```

를 묻는다.

## 추천 답변

저는 **사용자 경험을 개선**하는 것과, 그 개선을 빠르게 **반복할 수 있는 개발 구조**를 같이 고민하는 개발자입니다.

실제로 서비스에서는 **사용자의 탐색이나 사용 흐름을 개선**하는 일을 좋아하고, 개발 과정에서는 **반복적인 개발 비용을 줄이는 구조**를 만드는 데 관심이 많습니다.

## 키워드

```text
사용자 경험
반복할 수 있는 개발 구조
사용자의 탐색이나 사용 흐름을 개선
반복적인 개발 비용을 줄이는 구조
```

## 예상 꼬리

### "빠르게 만드는 것과 유지보수성이 충돌하면요?"

먼저 지금 **제품의 단계**와 **변경 가능성**을 볼것 같아요.

초기 검증 단계인데 확장 가능성만 보고 복잡한 구조를 먼저 만들면 **오버엔지니어링**이 될 수 있고, 반대로 계속 확장될 게 명확한 영역을 **임시 구조**로 만들면 **변경 비용**이 커질 수 있습니다.

그래서 **현재 필요한 수준에서 가장 단순한 구조를 선택**하되, **변경 가능성이 높은 경계는 명확히 나누는 것**을 기준으로 봅니다.

최근에는 아키텍처나 개발 방식에 대한 판단 범위는 많이 넓어졌지만, 앞으로는 데이터와 사용자 반응을 바탕으로 제품의 방향을 결정하는 과정에도 더 깊게 참여하고 싶습니다.

# 4. 이직의 이유는 무엇인가요?

## 원칙

현 회사의 단점을 말하는 질문이 아니다.

```text
현재까지 얻은 것
→ 다음 단계에서 원하는 것
→ Local Jobs와 연결
```

## 추천 답변

현재 회사에서 신규 서비스 구축과 AI Agent 기반 개발 방식을 주도적으로 경험하면서 기술적으로 많이 성장했습니다.
이제는 제가 만들어온 방식과 기준을 더 다양한 경험을 가진 엔지니어들과 검증하고, 기술적인 의사결정을 제품 성과까지 연결하는 경험을 더 깊게 해보고 싶습니다.
당근 알바는 Agent 기반 개발, 그리고 엔지니어의 제품 참여를 중요하게 보고 있어서 제가 원하는 다음 단계와 잘 맞는다고 생각했습니다.

## 예상 꼬리

### "현재 회사에서도 하면 되지 않나요?"

지금 회사에서도 AI 활용과 구조 개선은 계속하고 있습니다. 다만 이 방식들을 제가 만들고 제가 검증하는 구조라서, 제 기준이 맞는지 확인해줄 사람이 많지 않습니다.

잘하는 팀에서는 제 방식이 어디까지 통하는지 검증받고, 더 나은 기준을 훨씬 빠르게 배울 수 있다고 생각합니다.

### 주의

현재 회사를 깎아내리지 않는다.

# 5. 왜 당근인가요?

## 답변 구조

```text
당근이 유명해서 X

내 경험
+
Local Jobs의 일하는 방식
+
내가 앞으로 하고 싶은 역할
```

## 답변

제가 최근 가장 재미있게 해온 일은 신규 서비스를 0부터 만드는 것과 AI Agent를 개발 프로세스에 적용해 일하는 방식을 개선하는 일이었습니다.

당근은 AI를 개인 도구가 아니라 팀의 개발 문화로 쓰는 조직으로 알고 있고, Local Jobs 공고에서도 0→1, B2B/B2C, Agent 기반 개발 방식을 강조하고 있었습니다. 제가 해온 방식을 더 높은 수준의 팀에서 검증받고 확장할 수 있는 곳이라고 느꼈습니다.

---

# 6. 당근에서 기대하는 점

## 답변

가장 기대하는 것은 **잘하는 엔지니어들과 AI 중심 개발 문화 안에서 일해보는 경험**입니다.

지금까지 AI 활용 방식과 구조 설계를 대부분 제가 주도해서 만들어왔는데, 그 기준이 더 높은 수준의 팀에서도 통하는지 검증받고 배우고 싶습니다.

그리고 Local Jobs처럼 작은 팀에서는 엔지니어도 사용자 문제와 지표를 함께 본다고 알고 있어서, 구현을 넘어 제품 판단에 참여하는 경험도 기대하고 있습니다. 제가 가진 0→1과 AI 개발 경험으로 기여할 수 있는 부분도 많다고 생각합니다.

# 7. 개발할 때 동기부여는 어디서 얻나요?

## 추천 답변 방향

사용자 반응 + 눈에 보이는 개선 + 어려운 문제 해결.

## 답변

제가 만든 기능이 실제 사용자 흐름을 개선하거나, 팀이 반복하던 일을 줄이는 결과로 이어질 때 가장 동기부여를 많이 받습니다.

최근에는 사용자 기능뿐 아니라 AI Agent Harness처럼 개발 방식 자체를 개선하는 작업도 재미있었습니다. 제가 만든 구조가 다음 작업을 더 빠르고 예측 가능하게 만드는 걸 볼 때 성취감을 느끼는 편입니다.

그리고 며칠 막혀 있던 문제의 원인을 끝까지 파서 찾아냈을 때의 재미도 큽니다. 문제가 어려울수록 풀었을 때 남는 게 많다고 느낍니다.

# 8. 최근 가장 성장한 포인트

## 가장 좋은 카드

AI 활용 방식의 변화.

## 답변

최근 가장 성장했다고 느끼는 부분은 AI를 사용하는 방식입니다.

처음에는 AI를 잘 사용하는 걸 많은 작업을 맡기는 것으로 생각해서 간단한 작업까지 Agent에게 위임하기도 했습니다.

그런데 그렇게 하다 보니 제가 직접 코드를 탐색하고 구조를 이해하는 시간이 줄어드는 문제가 생겼습니다.

이후에는 반복 실행은 AI에게 적극적으로 맡기되 구조적 판단과 리뷰는 직접 가져가고, Harness와 lint 같은 검증 환경을 만드는 방식으로 바꿨습니다.

지금은 AI 활용 능력을 단순한 프롬프트 능력보다 **AI가 예측 가능하게 일할 수 있는 환경을 만드는 능력**으로 보고 있습니다.

# 9. 아파트스토리를 왜 새로 만들었나요?

## 핵심

```text
단지별 DB
PHP 레거시
기능 누적
높은 의존성
변경 영향 파악 어려움
인수인계자 부재
계속되는 신규 기능
```

## 답변

기존 서비스를 그대로 확장하는 방법도 검토했지만 구조적으로 유지보수 비용이 계속 커지는 상황이었습니다.

단지마다 데이터베이스가 분리되어 있었고 PHP 레거시 코드도 오랫동안 기능이 누적되면서 변경 영향 범위를 파악하기 어려웠습니다. 기존 구조를 깊게 알고 있는 인수인계자도 부재한 상태였습니다.

앞으로 관리자와 사용자 기능을 계속 추가해야 했기 때문에 기존 코드를 계속 확장하는 것보다, 유지해야 하는 인증과 기존 데이터는 남기고 신규 애플리케이션 영역을 다시 구축하는 것이 장기적으로 더 효율적이라고 판단했습니다.

## Why 1 — 왜 리팩터링하지 않았나요?

리팩터링도 기존 동작과 영향 범위를 충분히 파악한 상태에서 해야 하는데 당시에는 코드 분석 비용과 변경 리스크가 컸습니다.

신규 기능도 계속 예정되어 있었기 때문에 기존 구조와 신규 구조를 동시에 운영하는 기간이 길어지면 복잡도가 더 커질 가능성이 있다고 판단했습니다.

# 10. 신규 프로젝트에서 가장 먼저 고민한 것

## 답변

기술 스택을 먼저 정하기보다 **기존 시스템과 신규 시스템의 경계**를 먼저 정했습니다.

신규 서비스에서도 기존 사용자의 인증과 데이터를 그대로 사용해야 했고, 여러 도메인이 하나의 Backend API를 사용하고 있었기 때문에 인증과 네트워크 구조를 먼저 정리했습니다.

그 다음 여러 앱이 공유해야 하는 UI와 기능의 경계를 모노레포와 디자인 시스템에서 정의했습니다.

## 꼬리

### 무엇을 남기고 무엇을 새로 만들었나요?

이미 안정적으로 동작하고 사업적으로 연결된 영역 — 인증, 기존 사용자와 데이터 — 는 남겼습니다. 바꿔서 얻는 이득보다 잘못 건드렸을 때의 리스크가 훨씬 컸습니다.

새로 만든 건 앞으로 계속 확장해야 하는 영역입니다. 마스터 어드민 / 단지 어드민 / 사용자 서비스 화면, 프로젝트 구조와 공통 UI, API 호출 구조입니다.

### Backend와 무엇을 협의했나요?

두 가지입니다.

1. 기존 인증을 신규 앱에서 어떻게 이어받을지 — 쿠키 도메인 범위와 인증 쿠키 공유 범위
2. 여러 도메인이 하나의 API를 바라볼 때 CORS를 어디서 감당할지 — 결과적으로 프론트의 Next 프록시로 흡수하는 쪽으로 정리했습니다

# 11. AI Agent를 실제로 어떻게 활용했나요?

## 실제 사용

```text
코드 탐색
반복 UI 구현
리팩터링
테스트 초안
코드 리뷰
Figma MCP
문서화
```

## 답변

신규 프로젝트의 반복적인 구현 속도를 높이기 위해 Claude Code와 Cursor 같은 Agent를 적극적으로 사용했습니다.

초기에는 작업 단위로 프롬프트를 작성했는데 프로젝트가 커질수록 같은 구조와 규칙을 반복해서 전달해야 했고, Agent가 서로 다른 패턴으로 코드를 작성하는 문제가 생겼습니다.

그래서 프로젝트 구조와 도메인, 규칙을 Harness 형태로 명시하고 반드시 지켜야 하는 규칙은 lint나 type 같은 검증 장치로 옮겼습니다.

## 꼬리

### 어떤 작업은 맡기지 않나요?

되돌리기 어려운 판단입니다. 레이어·패키지 경계 같은 구조 결정, 인증·권한처럼 틀리면 보안 문제가 되는 영역, 스키마 변경, 그리고 Harness 규칙 자체입니다.

반대로 패턴이 정해진 반복 구현, 테스트 케이스 확장, 대량 치환은 적극적으로 맡깁니다.

### 결과를 어떻게 검증하나요?

타입·lint·빌드가 1차 방어선입니다. 존재하지 않는 API나 경계 위반은 대부분 여기서 걸립니다.

리뷰에서는 AI 코드에 자주 나오는 것부터 봅니다 — 요청하지 않은 코드, 기존 코드를 재사용하지 않고 새로 만든 것, 경계 우회. 최종 기준은 하나입니다. **제가 설명할 수 없는 코드는 머지하지 않습니다.**

### 테스트까지 통과하면 믿나요?

아니요. 테스트를 누가 썼는지가 중요합니다.

같은 Agent가 구현과 테스트를 함께 썼다면 구현의 잘못된 가정이 테스트에도 똑같이 들어가 둘 다 통과할 수 있습니다. 중요한 로직은 테스트가 무엇을 보장하는지 직접 읽고, 필요하면 실패해야 하는 케이스를 추가합니다.

```text
└─ 테스트

Memory / Context
└─ 반복적으로 필요한 프로젝트 정보

Validation
├─ lint
├─ type
└─ test
```

## 답변

전역 규칙과 프로젝트 규칙을 분리했습니다.

전역에는 프로젝트가 바뀌어도 유지되는 코드 작성 원칙을 두고, 프로젝트에는 아키텍처, 모노레포 구조, FSD 규칙, 도메인 맥락과 수정하면 안 되는 영역을 넣었습니다.

반복 작업은 Command로 분리했고 반드시 지켜야 하는 규칙은 문서에만 의존하지 않고 lint나 type으로 검증하도록 했습니다.

---

# 13. 왜 모든 규칙을 문서로 두지 않았나요?

## 답변

Agent가 문서를 항상 완벽하게 준수한다고 보장할 수 없기 때문입니다.

예를 들어 import boundary는 코드만 보면 기계적으로 판정할 수 있기 때문에 문서보다 lint로 강제하는 편이 더 적합했습니다.

반대로 "불필요한 추상화를 하지 않는다"처럼 판단이 필요한 내용은 문서와 리뷰 영역으로 남겼습니다.

## 꼬리

### 왜 모든 규칙을 lint로 만들지 않나요?

모든 규칙이 기계적으로 판정되지 않고, lint 룰도 유지보수 비용이기 때문입니다. 규칙이 늘수록 오탐이 늘고, `eslint-disable`이 습관이 되면 규칙이 죽습니다.

기준은 이렇게 잡았습니다. **어겼을 때 되돌리기 어려운 것은 lint로, 판단이 필요한 것은 문서와 리뷰로.**

### Harness가 커지면 어떻게 하나요?

커지는 것 자체가 신호입니다. 길어지면 사람도 Agent도 안 읽습니다.

자주 바뀌는 내용은 코드나 타입으로 옮기고, 특정 작업에서만 필요한 맥락은 전역 문서 대신 그 디렉터리 가까이에 두고, 잘 지켜지는 규칙은 문서에서 지우고 lint만 남깁니다.

### AI가 Harness를 항상 읽는다고 보장할 수 있나요?

보장할 수 없습니다. 그게 lint로 강제하는 이유입니다.

문서는 "읽으면 좋은 것"이고, 반드시 지켜야 하는 건 **읽든 안 읽든 실패하게** 만들어야 합니다. Harness의 목적은 준수 보장이 아니라 어긋났을 때 빨리 드러나게 하는 것에 가깝습니다.

# 14. AI가 잘못 구현한 실제 사례

## 사례

```text
FSD public API
→ 내부 파일 직접 import
→ 기능 정상
→ 구조 일관성 저하
→ lint
```

## 답변

FSD 구조에서 segment의 public API까지만 import하도록 규칙을 두고 있었습니다.

그런데 Agent가 내부 컴포넌트 파일을 직접 import하는 경우가 반복됐습니다.

기능상 문제는 없지만 내부 구현과 결합되고 import 패턴이 파편화되기 때문에 `no-restricted-imports` 같은 lint 규칙으로 경계를 강제했습니다.

## 꼬리

### lint 규칙은 직접 만들었나요?

커스텀 플러그인을 새로 만든 건 아닙니다. 레이어 경계는 `eslint-plugin-boundaries`로 허용 방향을 선언했고, 깊은 import 금지는 `no-restricted-imports` 패턴으로 잡았습니다.

커스텀 룰 직접 작성은 유지보수 비용이 커서 마지막 수단으로 뒀습니다.

만드는 과정도 역할을 나눴습니다 — **어떤 경계를 막을지, 허용 방향이 무엇인지는 제가 정의**하고, 설정 초안 작성은 Agent에게 맡겼습니다. 그리고 위반 케이스를 일부러 만들어서 실제로 lint가 걸리는지 확인한 뒤에 적용했습니다. 규칙의 소유권은 저에게 있고, 작성 노동만 위임한 구조입니다.

### CI 워크플로우는 어떻게 만들었나요?

CI도 같은 방식으로 Agent와 함께 만들었습니다. lint·타입체크·빌드를 PR 단계에서 강제하는 워크플로우를 Agent에게 초안 작성시키고, 제가 **일부러 실패하는 커밋**(경계 위반 import, 타입 에러)을 올려서 실제로 막히는지 검증한 뒤 적용했습니다.

Turborepo 기반이라 CI에서도 캐시가 동작합니다 — 바뀌지 않은 package는 다시 빌드하지 않아서, 모노레포인데도 앱 하나 고친 PR이 전체 빌드를 기다리지 않습니다.

핵심 프레임은 lint와 같습니다: **무엇을 검증할지와 통과 기준은 사람이 정하고, YAML을 쓰는 노동은 AI에게.** CI는 한번 틀리면 조용히 아무것도 안 막는 상태가 되기 때문에, "만들어졌다"가 아니라 "막히는 걸 확인했다"까지가 완성이라고 생각합니다.

> ✍️ 실제 CI에서 도는 잡 목록(lint/type/build 외 테스트·배포 단계 여부)을 면접 전에 확인할 것.

### 동작에는 문제가 없는데 왜 막았나요?

지금 동작이 아니라 **다음 변경의 비용** 때문입니다. 내부 파일 경로가 밖으로 새면 그 순간부터 내부 구조를 바꿀 수 없습니다.

이런 import가 쌓인 뒤에 고치려면 전체를 훑어야 하지만, lint로 막으면 생기는 순간 걸립니다.

# 15. Monorepo를 왜 선택했나요?

## 답변

마스터 어드민, 단지 어드민, 사용자 서비스가 공통 UI, 인증, 설정과 유틸을 공유해야 했기 때문에 모노레포를 선택했습니다.

각 앱은 독립적으로 개발하고 배포하되 공통 영역은 package로 분리해 재사용할 수 있도록 했습니다.

## Why — 멀티레포는?

멀티레포도 가능하지만 공통 컴포넌트나 설정이 변경될 때 여러 repository의 버전과 배포를 따로 맞춰야 하는 비용이 생길 수 있다고 판단했습니다.

## Trade-off

```text
의존성 경계 관리 필요
빌드 복잡도
package coupling 가능
```

## 꼬리

### 공통화 기준은?

두 개 이상의 앱에서 **같은 형태로 실제 반복될 때** 올립니다. "언젠가 쓸 것 같아서" 미리 올리지 않습니다.

한 곳에서만 쓰는 코드를 공통으로 올리면 그 뒤로 모든 변경이 공통 package를 거쳐야 해서, 얻는 것보다 비용이 큽니다.

### Turborepo는 왜?

필요한 게 태스크 의존 그래프와 빌드 캐시 두 가지였고 그 이상은 필요하지 않았습니다.

Turborepo는 태스크의 입력을 해시해서 결과를 캐시하므로 바뀌지 않은 package는 다시 빌드하지 않습니다. 효과가 큰 곳은 CI입니다 — 앱 하나만 고쳤는데 전체를 다시 빌드하는 상황을 막아줍니다.

### 독립 배포가 정말 되나요?

앱 단위 빌드·배포는 분리되어 있습니다. 한 앱을 배포한다고 다른 앱을 같이 올릴 필요는 없습니다.

다만 완전한 독립은 아닙니다. **공통 package를 바꾸면 그걸 쓰는 앱 전부가 영향을 받습니다.** 그래서 공통 package의 변경은 더 신중하게 봅니다.

### 방구해요는 어떤 서비스인가요?

기존 플랫폼에서 확장한 신규 방 구하기 서비스로, 이때 공통 영역과 서비스 영역을 분리하는 모노레포 구조를 처음 잡았고 그 경험이 이후 아파트스토리 플랫폼 설계로 이어졌습니다.

✍️ 방구해요의 정확한 서비스 정의와 현재 상태(운영 중/종료)를 한 줄로 정리해둘 것.

---

# 16. Design System을 왜 만들었나요?

## 답변

여러 관리자와 사용자 서비스에서 같은 UI 패턴을 반복 구현해야 했기 때문에 공통 토큰과 컴포넌트를 분리했습니다.

목표는 "공통 컴포넌트를 많이 만드는 것"이 아니라 동일한 규칙을 여러 앱에서 재사용하고 변경 시 한 곳에서 관리하는 것이었습니다.

## 꼬리 — 언제 공통으로 올리나요?

한 번 쓰인다고 바로 공통화하지 않습니다.

두 곳 이상에서 동일한 목적과 인터페이스로 반복되고, 변경 방향도 같이 가져갈 가능성이 높은지를 보고 공통화합니다.

## Storybook과 컴포넌트 버전 관리는 어떻게 했나요?

Storybook으로 공통 컴포넌트의 상태·변형을 문서화해서, 디자이너·다른 개발자가 코드를 열지 않고도 어떤 컴포넌트가 있고 어떻게 쓰는지 확인할 수 있게 했습니다.

공통 컴포넌트는 별도 패키지로 분리해 각 앱이 의존하는 구조였고, 공통이 바뀌면 그걸 쓰는 앱들이 영향을 받으므로 변경 시 영향 범위를 확인하는 것을 원칙으로 했습니다.

✍️ 버전 관리 방식(semver 배포였는지, workspace 참조로 항상 최신을 쓰는 구조였는지)을 실제와 맞춰 확인할 것.

# 17. 인증은 어떻게 구성했나요?

## 답변

신규 서비스였지만 기존 사용자 인증 체계를 그대로 이어받아야 했기 때문에 인증 시스템 자체를 새로 만들지는 않았습니다.

기존 인증은 JWT 기반이었고, 백엔드가 로그인 성공 시 JWT를 `HttpOnly Cookie`에 담아 내려주는 구조였습니다.

신규 프론트에서도 토큰을 LocalStorage에 저장하거나 직접 `Authorization Header`에 주입하지 않고, 브라우저가 쿠키를 자동으로 전달하도록 구성했습니다.

특히 프론트와 API의 Origin이 달랐기 때문에 요청 시 `credentials: 'include'`를 사용했고, 서버에서도 `Access-Control-Allow-Credentials: true`와 허용 Origin을 명시적으로 설정했습니다.

또한 운영 환경에서는 서브도메인 간 인증 상태를 공유해야 했기 때문에 Cookie의 `Domain`, `SameSite`, `Secure`, `HttpOnly` 옵션을 함께 설정했습니다.

결과적으로 프론트에서는 토큰 자체를 직접 관리하지 않고, 쿠키 전달만 브라우저에 맡기고 실제 토큰 검증과 만료 처리는 서버에서 담당하도록 구성했습니다.

## 주의

```text
"세션 기반 인증"이라고 말하지 않는다
→ Session Store를 조회하는 전통적 세션 인증으로 들린다
→ 정확한 표현: 인증은 JWT, 보관·전달은 HttpOnly Cookie
```

✍️ 실제 쿠키에 `Expires`/`Max-Age`가 있는지 확인할 것 — 없으면 "HttpOnly **Session Cookie** 기반 JWT 인증", 있으면 "HttpOnly Cookie 기반 JWT 인증"이 정확한 명칭이다.

## 꼬리

### 세션 기반인가요, JWT 기반인가요?

인증 자체는 JWT 기반이고, JWT를 전달하고 보관하는 수단으로 HttpOnly Cookie를 사용했습니다.

서버가 Session ID로 별도의 Session Store를 조회하는 전통적인 세션 인증 방식은 아닙니다.

### 왜 localStorage가 아니라 Cookie인가요?

localStorage는 JavaScript로 읽을 수 있어서 XSS가 발생하면 토큰이 그대로 탈취됩니다.

HttpOnly Cookie는 스크립트가 읽을 수 없고 브라우저가 요청에 자동으로 실어주기 때문에, 프론트에 토큰을 다루는 코드 자체가 없어집니다. 서브도메인 간 인증 공유도 쿠키 도메인 설정으로 자연스럽게 해결됩니다.

### JWT는 만료 전 무효화가 어렵지 않나요?

맞습니다. 토큰 자체에 인증 상태가 담겨 있어서 한 번 발급한 토큰을 만료 전에 서버가 되돌리기 어렵습니다.

그래서 만료를 짧게 가져가고 재발급으로 이어가는 방식이 일반적이고, 즉시 차단이 꼭 필요하면 서버 쪽에 블랙리스트 같은 상태를 다시 두게 됩니다. 이 지점이 Session Store 방식과의 실질적인 트레이드오프라고 생각합니다.

### SameSite는?

쿠키를 다른 사이트에서 시작된 요청에 실어 보낼지를 정합니다.

- `Strict`: 크로스 사이트 요청엔 전혀 안 보냄
- `Lax`: 최상위 내비게이션에만 보냄. 요즘 브라우저 기본값
- `None`: 항상 보냄. 반드시 `Secure` 필요

CSRF의 1차 방어선이지만 이것만으로 충분하다고 보진 않습니다.

### CSRF는 어떻게 막나요?

로그인된 상태를 이용해 공격자 사이트가 사용자의 브라우저로 의도하지 않은 요청을 보내게 만드는 공격입니다. 쿠키가 자동으로 실려 나가기 때문에 성립합니다.

방어는 겹쳐서 씁니다 — `SameSite`, CSRF 토큰 대조, 상태를 바꾸는 요청을 GET으로 만들지 않기, Origin/Referer 검증.

### 쿠키 만료와 갱신은?

요청마다 만료를 밀어주는 sliding 방식과, 짧은 만료 + 재발급 방식이 있습니다.

어느 쪽이든 **만료 판단은 서버가 하고 클라이언트는 결과만 반영**하게 두는 게 중요하다고 봤습니다. 프론트가 만료를 추측해서 분기하기 시작하면 서버와 어긋나는 순간이 생깁니다.

### 서브도메인 간 cookie domain은?

`Domain=example.com`으로 설정하면 모든 서브도메인에 전송됩니다. 여러 서비스 도메인이 같은 인증을 공유해야 해서 이 방식이 맞았습니다.

주의할 점은 범위가 넓어질수록 위험도 같이 넓어진다는 것입니다. 서브도메인 하나가 뚫리면 그 쿠키를 공유하는 전체가 영향을 받으므로, 공유 범위를 필요한 만큼만 잡습니다.

# 18. HttpOnly는 왜?

JavaScript에서 쿠키 값을 직접 읽을 수 없게 해서 XSS 상황에서 인증 정보 자체가 탈취되는 경로를 줄일 수 있습니다.

다만 HttpOnly가 XSS 자체를 막는 것은 아닙니다.

## 꼬리

### 그럼 XSS는 뭘로 막나요?

- 사용자 입력을 그대로 HTML로 넣지 않습니다. React는 기본 이스케이프하지만 `dangerouslySetInnerHTML`은 예외입니다
- 마크다운·리치텍스트 렌더링은 sanitize를 거칩니다
- CSP로 실행 가능한 스크립트 출처를 제한합니다

HttpOnly는 피해를 줄이는 장치지 XSS의 해결책이 아닙니다. 스크립트가 실행되면 쿠키를 못 읽어도 사용자 권한으로 요청은 보낼 수 있습니다.

### Secure는?

HTTPS 연결에서만 쿠키를 전송합니다. 평문 HTTP 요청에 쿠키가 실려 중간에서 탈취되는 걸 막습니다. 운영 환경 인증 쿠키에는 기본으로 붙입니다.

---

# 19. 세션과 토큰이 혼재됐다는 게 무슨 뜻인가요?

## 답변

같은 사용자 인증이 **두 체계로 나뉘어 관리되던 상태**였습니다.

실 운영 웹은 기존 PHP 서버 세션으로 인증하고 있었고, 앱 웹뷰 쪽에서는 JWT 방식이 별도로 쓰이고 있었습니다. 같은 사용자인데 환경에 따라 인증 수단이 달라서, 로그인 상태 판단·만료 처리·신규 서비스 연동을 **두 벌로 고민**해야 했습니다.

신규 서비스가 늘어나는 시점이라 이 구조로는 서비스를 추가할 때마다 인증 연동 비용이 반복될 것이 명확했고, 그래서 **JWT를 HttpOnly Cookie에 담아 서브도메인으로 공유하는 방식으로 통일**했습니다. 프론트는 토큰을 직접 다루지 않고, 어떤 서비스든 같은 쿠키로 인증 상태가 이어집니다.

✍️ 통합 후 웹뷰의 인증 처리 방식(같은 쿠키를 쓰는지, 앱에서 주입하는지)과 만료·갱신 정책을 면접 전에 확인할 것.

## 꼬리

### 통합하면서 어려웠던 점은?

인증은 잘못 건드리면 전 서비스 로그인이 깨지는 영역이라, 한 번에 갈아끼우지 않고 **기존 세션이 동작하는 상태를 유지하면서 새 방식을 붙이는 순서**로 갔습니다. Backend와 쿠키 도메인 범위·만료 정책을 먼저 합의하고, 신규 서비스부터 새 방식을 적용했습니다.

### 왜 헤더 방식(Authorization)이 아니라 쿠키인가요?

여러 서브도메인 서비스가 재로그인 없이 인증을 공유해야 했는데, 쿠키는 도메인 설정만으로 이것이 해결됩니다. 헤더 방식은 각 앱이 토큰을 저장하고 실어 보내는 코드를 전부 가져야 하고, 저장 위치가 JavaScript에 노출되는 문제도 있습니다.

# 20. Reverse Proxy를 왜 선택했나요?

## 답변

100개가 넘는 도메인이 하나의 Backend API를 사용하는 구조였는데 모든 도메인을 Backend의 CORS allowlist에서 관리하면 도메인 추가 때마다 Backend 설정과 배포가 필요했습니다.

인프라 수준에서 프록시를 구성하는 방법도 있었지만 당시에는 기존 Next 서버를 활용하면 별도 인프라를 추가하지 않고 일관된 API 경로를 만들 수 있었습니다.

API hop과 Next 서버 의존성이 증가하는 단점은 알고 있었지만 당시 규모에서는 운영 단순성의 이점이 더 크다고 판단했습니다.

## Why — CORS가 왜 문제?

CORS 자체가 어려운 문제가 아니라:

```text
프론트 도메인 추가
→ Backend 설정 수정
→ Backend 배포
```

로 변경 주기가 다른 시스템이 묶이는 것이 문제였습니다.

## Trade-off

```text
API hop
Next server 부하
장애 전파
```

## 꼬리

### Next 서버가 죽으면?

API 호출도 같이 막힙니다. 프록시를 애플리케이션 서버에 얹었을 때의 가장 큰 대가입니다.

사용자 쪽에는 장애 페이지와 재시도 흐름을 제공했지만, 완전한 장애 격리를 만들었다고 말하면 과장입니다. 격리가 중요해지면 프록시를 인프라 레벨로 내리는 게 맞는 방향이라고 봅니다.

### 쿠키는 어떻게 전달되나요?

브라우저→프록시와 프록시→Backend가 별개의 요청이라, 인증 쿠키를 명시적으로 옮겨 붙여야 Backend가 로그인 요청으로 인식합니다.

이때 헤더를 통째로 전달하지 않고 **무엇을 넘길지 명시적으로 정하는 게** 중요합니다. 반대 방향도 같습니다 — Backend의 `Set-Cookie`를 응답에 다시 실어야 하고, 도메인이 바뀌므로 쿠키의 `Domain` 속성이 사용자 도메인에서 유효한지 확인해야 합니다.

### timeout / retry는?

프록시가 무한정 기다리면 Backend 지연이 곧 프론트 전체 장애로 번지므로 Backend 호출에 상한을 둡니다. 프록시의 타임아웃은 Backend보다 짧거나 같아야 프록시가 먼저 정리됩니다.

재시도는 조회성·멱등 요청, 일시적 실패에 한정하고 횟수를 제한합니다. 멱등하지 않은 POST는 기본적으로 재시도하지 않습니다 — 처리는 됐는데 응답만 못 받은 경우 중복 생성이 발생합니다.

### latency는 얼마나 늘었나요?

정확한 수치는 측정해서 관리하지 않았습니다. 숫자를 말하면 지어내는 게 됩니다.

구조적으로 hop이 하나 늘어나는 건 명확하고, 다시 한다면 도입 전후 응답 시간을 남겨서 trade-off를 숫자로 설명할 수 있게 할 것 같습니다.

# 21. 100개가 넘는 도메인을 하나의 앱에서 어떻게 처리했나요?

## 답변

기존 PHP 시스템을 Next.js 기반으로 새로 구축하면서, 100개가 넘는 도메인을 **동일한 애플리케이션**에서 처리해야 했습니다.

핵심은 이 구조가 **서비스 분리가 아니라 테넌트 구분**이라는 점이었습니다. 모든 도메인이 같은 Next.js 앱을 바라보고, 요청된 도메인에 따라 단지(테넌트) 컨텍스트만 달라지면 되는 구조였습니다.

그래서 Nginx나 ALB 같은 인프라 계층에 100개 이상의 라우팅 규칙을 따로 관리하는 대신, **Next.js 서버에서 Host 정보를 기준으로 분기**하는 방식을 선택했습니다. 구현과 운영 모두 이쪽이 단순했습니다.

도메인 분기 로직이 애플리케이션 코드 안에 있으니 변경이 쉽고, 단지별 설정·권한·데이터와 자연스럽게 연결됩니다. 인프라 프록시를 두면 요구사항 대비 별도 인프라 계층과 운영 포인트만 늘어난다고 판단했습니다.

## 꼬리

### 인프라 계층 분기가 더 맞는 경우는 언제인가요?

도메인마다 **서로 다른 서비스나 서버로 보내야 할 때**입니다. 트래픽 분산이나 서비스 간 라우팅은 인프라의 일이고, 애플리케이션은 몰라야 맞습니다.

저희는 목적지가 하나였고 달라지는 건 컨텍스트뿐이라 앱 분기가 맞았습니다. 나중에 도메인별로 다른 앱을 태워야 하는 요구가 생기면 그때 인프라 계층으로 올리는 게 맞는 방향이라고 봅니다.

### 도메인이 계속 늘어나면 어떻게 되나요?

분기가 코드의 조건문이 아니라 **도메인 → 단지 매핑 데이터**를 조회하는 구조라, 도메인이 늘어도 코드 변경 없이 데이터만 추가되면 됩니다. 인프라 규칙로 관리했다면 도메인 추가마다 설정 변경과 배포가 필요했을 것입니다.

✍️ 실제 매핑이 데이터 조회인지 설정 파일인지 확인할 것 — 다르면 이 답을 실제 방식으로 수정.

# 22. A/B 테스트는 어떻게 진행했고, 그중 본인의 역할은 무엇이었나요?

## 가장 먼저 할 일

면접 전 실제 사실을 확인한다.

```text
23%가 어떤 지표인가?
absolute인가 relative인가?
baseline?
실험 기간?
내 역할?
누가 가설을 세움?
누가 분석?
```

실험 전체를 제가 주도한 것은 아닙니다. PM·마케터와 가설을 논의하는 단계에 참여했고, 프론트에서 A/B variant를 구현했습니다.

이벤트 설계와 결과 분석은 제가 주도한 영역이 아니어서, 그 부분까지 제 역할로 말하지 않습니다. 물어보면 "그 부분은 PM과 데이터 파트가 주도했고 저는 구현 관점에서 참여했다"고 정확히 답합니다.

> ✍️ 이력서에 "이벤트 정의 / 공통 logging"이 적혀 있다면 면접 전에 실제 기여 범위와 표현을 맞출 것. 이력서 문장과 면접 답변이 어긋나는 게 최악의 시나리오다.

## 위험

이력서 표현보다 실제 경험이 약하다면 면접에서 오너십을 과장하지 않는다.

# 24. SSR / SSG를 왜 나눴나요?

## 답변

동네생활백서는 검색 유입이 중요한 콘텐츠 서비스였기 때문에 모든 페이지를 하나의 렌더링 방식으로 처리하지 않고 콘텐츠의 변경 주기와 요청 시점 데이터 필요 여부를 기준으로 SSR과 SSG를 나눴습니다.

```text
자주 바뀌고 요청 시 최신값 필요 → SSR
변경 적고 미리 생성 가능 → SSG
```

그리고 URL 구조, metadata, sitemap, indexing 정책을 함께 설계했습니다.

## 꼬리

### SSG 페이지가 계속 늘어나면 빌드는?

전부 빌드 시점에 만들면 페이지 수에 비례해 빌드가 느려집니다.

그래서 자주 조회되는 페이지만 미리 생성하고 나머지는 첫 요청 시 생성해 캐시하거나, 재검증 주기(ISR)를 둬서 배포 없이 갱신되게 하는 방식을 씁니다. 기준은 "얼마나 자주 바뀌고, 첫 요청 지연을 허용할 수 있는가"입니다.

### 색인이 실제로 됐는지 어떻게 확인하나요?

색인 모니터링을 제가 전담하지는 않았습니다. 제 역할은 색인이 가능한 구조를 구현하는 쪽이었고, 구현할 때 색인을 막는 요인이 없는지 — `noindex` 잔존, robots.txt 차단, canonical 충돌 — 을 확인했습니다.

방법 관점에서 답하면, sitemap 제출이 색인을 보장하지 않으므로 제출한 URL 수와 실제 색인된 URL 수를 비교해서 격차가 큰 그룹을 찾는 방식으로 접근합니다.

색인이 안 되는 원인은 보통 정해져 있습니다 — `noindex` 잔존, robots.txt 차단, canonical이 다른 URL을 가리킴, 콘텐츠가 얇거나 중복.

# 25. Vue와 React를 둘 다 썼는데, 비교해주실 수 있나요?

## 답변

둘 다 실무에서 운영해봤습니다. 레거시가 PHP Blade와 Vue 기반이었고, 신규 서비스는 React·Next.js로 만들었습니다.

가장 큰 차이는 **상태 변화를 다루는 방식**이라고 생각합니다. Vue는 반응성 시스템이 의존성을 자동 추적해서 바뀐 곳만 갱신해주고, 템플릿·스타일·로직이 SFC 규칙으로 정리되어 팀 코드가 균일해지기 쉽습니다. React는 상태가 바뀌면 컴포넌트를 다시 실행하는 모델이라 리렌더링을 개발자가 이해하고 제어해야 하는 대신, JSX가 그냥 JavaScript라서 표현의 자유도와 생태계가 넓습니다.

그래서 Vue는 규칙이 정해진 안에서 빠르게 만들기 좋았고, React는 복잡한 UI와 추상화를 설계할 때 더 유연하다고 느꼈습니다. 어느 쪽이 우월하다기보다 **팀과 제품 상황에 맞는 선택**의 문제라고 생각합니다.

## 꼬리

### 왜 신규 서비스는 React로 갔나요?

신규 서비스는 검색 유입이 중요해서 SSR·SEO를 제대로 지원하는 프레임워크가 필요했고, Next.js 생태계가 그 요구에 가장 성숙해 있었습니다. 이후 서비스 확장과 라이브러리·채용 생태계까지 고려하면 신규 기반은 React 쪽이 맞다고 판단했습니다.

### 월 200만 방문 규모에서 프론트가 특별히 신경 쓴 것은?

두 가지입니다. 첫째, 트래픽의 큰 축이 검색 유입이라 **SEO를 깨뜨리지 않는 것** — URL·리다이렉트·인덱싱 정책이 바뀌는 변경은 특히 조심했습니다. 둘째, 레거시와 신규가 병행 운영되는 상태라 **배포가 기존 사용자 흐름을 회귀시키지 않는지**를 확인하는 것이었습니다.

# 26. 이전 회사에서는 어떤 일을 했나요?

## 답변

솔루션 SI 회사에서 2년간 다양한 도메인의 프로젝트를 만들었습니다. 규모가 크지 않아 기획·디자인 단계부터 참여했고, 프론트를 중심으로 백엔드까지 다뤘습니다.

대표적으로 농가 회계·영농일지 CMS를 Next.js와 GraphQL(Apollo) 기반으로 풀스택 개발했고, 소방 안전 점검 문서 시스템에서는 수기로 4시간 걸리던 보고서 작성을 PDF 자동 생성과 전자 서명으로 30분 수준까지 줄였습니다.

여러 도메인을 짧은 주기로 오가며 **낯선 요구사항을 빠르게 구조화하는 훈련**이 된 시기였고, 코드 리뷰와 클린 코드 문화를 팀에 도입하는 일도 주도했습니다.

## 꼬리

# 32. React스럽게 코드를 작성한다는 것

## 답변

UI를 상태와 props의 결과로 선언적으로 표현하는 것이라고 생각합니다.

DOM을 직접 변경하는 대신 state가 바뀌면 UI가 그 결과를 자연스럽게 반영하도록 하고, 계산 가능한 값은 중복 state로 저장하지 않으며 외부 시스템과 동기화가 필요한 경우가 아니라면 effect를 최소화합니다.

## Why Map

```text
왜 선언적?
→ 변경 과정 직접 관리 X

왜 최소 state?
→ 동기화 대상 감소

왜 derived?
→ source of truth 중복 방지

왜 effect 최소?
→ 실행순서 / 동기화 복잡도 감소
```

## 꼬리

### derived state 예를 들어주세요

목록과 검색어가 있을 때 필터링된 목록을 별도 state로 두지 않는 것입니다.

```tsx
// 중복 저장: items나 keyword가 바뀔 때마다 동기화 코드가 필요
const [filtered, setFiltered] = useState(items);

// 파생: 항상 최신이고 동기화할 게 없다
const filtered = items.filter((item) => item.name.includes(keyword));
```

state를 두 개 두면 어긋나는 순간이 반드시 생깁니다. 계산할 수 있는 값은 계산합니다.

### useEffect는 언제 쓰나요?

React 바깥 세계와 동기화할 때만 씁니다 — 구독 등록/해제, 브라우저 API 조작, 외부 저장소 동기화.

반대로 props로 계산 가능한 값은 그냥 계산하고, 사용자 행동에 대한 반응은 이벤트 핸들러에서 처리합니다. 렌더 결과를 보고 다른 state를 맞추는 effect는 구조를 잘못 잡았다는 신호로 봅니다.

### useMemo는 언제 쓰나요?

계산 자체가 무거울 때, 그리고 memo된 자식의 props나 의존성 배열에 들어가는 객체·배열처럼 참조 동일성이 필요할 때입니다.

단순 계산에 붙이는 건 비교 비용과 가독성만 잃습니다. 순서는 **먼저 리렌더의 원인을 없애고, 그래도 남으면 측정한 뒤** 붙입니다.

# 33. 상태관리 경험을 비교해 주세요

## 답변

라이브러리보다 **상태의 성격과 소유권을 먼저 봅니다.**
Local UI State

컴포넌트 내부나 가까운 트리에서만 필요한 상태는 useState를 사용합니다. 예를 들어 모달의 열림/닫힘, 탭 선택, 입력값처럼 특정 화면 안에서만 쓰이는 상태라면 굳이 전역 상태로 올리지 않습니다.

Global Client State

여러 화면이나 컴포넌트에서 공유해야 하는 클라이언트 상태는 Zustand, Jotai, Redux를 고려합니다. Zustand는 단순하게 store를 구성하기 좋고, Jotai는 atom 단위로 상태를 잘게 나눠 관리하기 좋습니다. Redux는 상태 변화 흐름과 규칙을 명확히 가져가야 하는 큰 상태 관리에 적합합니다.

Server State

서버에서 가져오는 데이터는 TanStack Query를 사용합니다. 서버 데이터는 단순히 저장하는 것보다 캐시, stale 상태, refetch, mutation, invalidation 같은 동기화 문제가 중요하기 때문에 별도의 서버 상태로 봅니다.

URL State

검색어, 필터, 정렬 조건, pagination처럼 공유하거나 뒤로가기, 새로고침 이후에도 복원되어야 하는 상태는 URL State로 관리합니다.

이 필요한 상태.

## 꼬리

### Context는 왜 상태관리가 아닌가요?

Context는 상태관리 도구가 아니라 **전달 수단**입니다. 값이 바뀌면 구독하는 모든 컴포넌트가 리렌더됩니다.

그래서 theme·auth처럼 자주 바뀌지 않는 전역 값에 쓰고, 자주 바뀌는 값은 store로 빼서 필요한 컴포넌트만 구독하게 합니다.

### Query가 있으면 전역 store가 필요 없지 않나요?

관리하는 대상이 다릅니다. Query는 원본이 서버에 있는 데이터의 복사본을 관리하고, store는 클라이언트가 소유한 상태를 관리합니다.

서버 데이터를 store에 넣으면 캐시·stale·중복 요청·경쟁 상태를 전부 손으로 짜게 되고, 반대로 순수 client state를 Query에 넣을 이유도 없습니다. 서버 데이터는 Query, 진짜 client state만 store에 남깁니다.

### URL state의 단점은?

- 전부 문자열이라 파싱·검증이 필요하고, 사용자가 직접 고칠 수 있어 신뢰할 수 없는 입력으로 다뤄야 합니다
- 민감한 값은 안 됩니다 — URL은 로그·히스토리·Referer로 새어 나갑니다
- 변경 빈도가 높은 상태에는 부적합합니다

그래서 공유·복원이 필요한 상태만 URL에 둡니다.

# 34. React Query queryKey는 어떻게 관리하나요?

## 답변

캐싱의 identity를 이해하는가?

Query Key는 서버 데이터 캐시의 identity입니다. 그래서 도메인 단위 Key Factory를 만들어 일관되게 관리하고, 응답을 바꾸는 파라미터는 반드시 Key에 포함합니다. 이렇게 하면 키 파편화를 막고 캐시 충돌이나 잘못된 invalidation을 줄일 수 있습니다.

## 꼬리

### "filter object 넣어도 되나요?"

가능합니다. React Query는 key를 구조적으로 해시하기 때문에 객체 property의 순서는 문제가 되지 않습니다.

다만 직렬화 가능한 값이어야 하고, 같은 의미의 필터는 항상 같은 구조로 들어가야 합니다. 그래서 key factory에서 필터 객체의 형태를 한 곳에서 만들어주는 게 안전합니다. `undefined`가 든 property는 해시에서 사라져서 의도와 다른 키가 같아질 수 있는 점도 주의합니다.

### "왜 hierarchy?"

invalidate 범위를 계층으로 제어할 수 있기 때문입니다.

사용자 데이터가 바뀌었을 때 `userKeys.all`로 무효화하면 목록과 상세가 한 번에 갱신되고, 특정 상세만 갱신하고 싶으면 `detail(id)`로 좁힙니다. 키 문자열이 흩어져 있으면 이 범위 제어가 안 되고, 무효화를 하나 놓치는 순간 stale한 화면이 남습니다.

# 35. Hydration이 무엇이고 왜 필요한가요?

## 정의

서버가 생성한 HTML에 클라이언트 React가 상태와 이벤트 핸들러를 연결해 interactive하게 만드는 과정.

## 왜 필요한가?

SSR이 내려주는 건 완성된 HTML 문자열이라 이벤트 핸들러와 상태가 없습니다. 클라이언트 React가 같은 트리를 다시 렌더해서 기존 DOM에 연결해야 상호작용이 가능해집니다.

이때 "서버 렌더 결과와 클라이언트 첫 렌더 결과가 같다"는 전제가 있고, 아래 값들처럼 이 전제가 깨지면 hydration mismatch가 발생합니다.

## 꼬리

### mismatch는 어떻게 해결하나요?

원인은 하나입니다 — 서버 렌더 결과와 클라이언트 첫 렌더 결과가 다른 것.

- 매번 값이 달라지는 것(`Date.now` 등) → 서버에서 만들어 props로 내립니다
- `window`, `localStorage`, timezone → 첫 렌더는 서버와 같은 값을 그리고 마운트 이후에 갱신합니다
- 클라이언트에서만 의미 있는 부분 → dynamic import로 SSR을 끄거나 마운트 후 렌더합니다

`suppressHydrationWarning`은 경고만 숨길 뿐 원인을 고치지 않습니다.

### Client Component와 관계는?

App Router에서 hydration 대상은 Client Component뿐입니다. Server Component는 렌더 결과만 전달되고 클라이언트 번들에 포함되지 않습니다.

`'use client'`를 트리 위쪽에 붙이면 그 아래 전체가 hydration 대상이 되고 번들도 커집니다. 가능한 말단에 두는 이유입니다.

### hydration 비용은?

JS 다운로드·파싱, 트리 재실행, 그리고 그동안 화면은 보이는데 눌러도 반응 없는 구간 — 세 가지가 겹칩니다.

줄이는 방향은 클라이언트 컴포넌트 범위를 좁히고, 무거운 컴포넌트는 필요한 시점에 로드하고, 서버에서 끝낼 수 있는 건 Server Component로 두는 것입니다.

# 36. Sitemap은 어떻게 생성하나요?

## 답변

검색엔진이 크롤링할 URL 목록을 XML로 제공합니다.

정적인 페이지라면 build 시 생성할 수 있고, 동적인 서비스라면 DB나 API에서 공개 가능한 URL을 조회해서 생성합니다.

URL 수가 많다면 sitemap index를 두고 여러 sitemap으로 분리합니다.

Next App Router에서는 `sitemap.ts`를 이용하거나 요구사항에 따라 dynamic route로 생성할 수 있습니다.

## 같이 보는 것

```text
robots.txt
canonical
lastModified
index 여부
```

## 꼬리

### robots.txt와 차이는?

robots.txt는 검색엔진 크롤러가 접근할 수 있는 경로를 제어하는 파일이고,
sitemap.xml은 검색엔진이 사이트의 주요 URL을 더 쉽게 발견할 수 있도록 페이지 목록을 제공하는 파일입니다.

### canonical은?

같은 내용이 여러 URL로 존재할 때 대표 URL을 알려주는 힌트입니다. 파라미터·페이지네이션 때문에 생긴 중복의 평가 분산을 막습니다.

sitemap에는 canonical URL만 넣습니다. 둘이 다른 URL을 가리키면 신호가 충돌합니다.

### 모든 페이지를 넣나요?

색인시키고 싶은 페이지만 넣습니다. 개인화 화면, 조합이 무한한 검색 결과, `noindex` 페이지, canonical이 아닌 중복 URL은 뺍니다. 가치 없는 URL이 많으면 크롤링 예산만 낭비됩니다.

# 37. SPA에서 URL과 뒤로가기는 어떻게 처리하나요?

## 핵심

```text
session history
pushState
replaceState
popstate
```

## 답변

SPA에서는 `pushState`와 `replaceState`로 페이지 전체 reload 없이 URL과 history entry를 변경할 수 있습니다.

사용자가 뒤로 / 앞으로 이동하면 history entry가 바뀌고 `popstate`를 통해 UI 상태를 맞출 수 있습니다.

검색이나 필터처럼 복원이 필요한 상태를 local state에만 두면 URL과 UI가 어긋날 수 있어서 URL state를 사용합니다.

## 꼬리

### pushState와 replaceState 차이?

`pushState`는 history에 새 항목을 추가하고, `replaceState`는 현재 항목을 덮어씁니다.

기준은 "사용자가 뒤로가기로 이 상태로 돌아오고 싶어할까"입니다. 필터 적용은 push, 검색어 타이핑 중간값이나 스크롤 위치는 replace가 맞습니다. 타이핑마다 push하면 뒤로가기를 수십 번 눌러야 이전 화면으로 돌아갑니다.

### popstate는 pushState 때도 발생하나요?

발생하지 않습니다. `popstate`는 사용자가 history를 이동할 때(뒤로/앞으로, `history.back()`)만 발생합니다.

그래서 직접 URL을 바꾼 경우엔 그 시점에 상태를 함께 갱신하고, `popstate`는 "브라우저가 나 대신 이동시켰다"는 신호로 처리합니다.

# 38. Promise의 상태와 all·allSettled·race·any 차이를 설명해주세요

## 반드시 알아야 할 것

```text
Promise state
pending
fulfilled
rejected
```

## then

Promise의 결과를 이어서 처리한다.

## Promise.all

모두 성공해야 성공.

하나가 reject되면 반환 Promise는 reject.

나머지 네트워크 요청 자체가 자동 취소되는 것은 아니다.

## Promise.allSettled

모든 Promise가 끝날 때까지 기다리고 각각 성공 / 실패 결과 반환.

## race

가장 먼저 settle된 Promise 결과.

## any

가장 먼저 fulfilled된 Promise 결과.

모두 reject되면 AggregateError.

## Event Loop 꼬리 대비

Promise callback은 microtask queue에서 처리된다.

```js
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
console.log(4);
// 1 → 4 → 3 → 2
```

microtask(Promise)는 현재 실행 중인 코드가 끝나면 **macrotask(setTimeout)보다 먼저** 전부 비워진다.

## 꼬리

### race는 실무에서 언제 쓰나요?

대표적으로 타임아웃입니다.

```js
const result = await Promise.race([fetchData(), timeout(3000)]);
```

주의할 점은 race에서 진 Promise가 취소되는 게 아니라는 것입니다. 요청은 계속 진행되고 결과만 버려지므로, 실제 취소가 필요하면 `AbortController`를 씁니다.

### await를 연달아 쓰면 어떻게 되나요?

앞 요청이 끝나야 다음이 시작하는 waterfall이 됩니다. 서로 의존하지 않는 요청이라면 `Promise.all`로 동시에 출발시킵니다.

```js
// 순차 — B는 A가 끝난 뒤 시작
const a = await apiA();
const b = await apiB();

// 병렬
const [a, b] = await Promise.all([apiA(), apiB()]);
```

# 39. 브라우저 렌더링 과정과 CSS가 성능에 미치는 영향을 설명해주세요

## Pipeline

```text
HTML → DOM
CSS → CSSOM
DOM + CSSOM → Render Tree
→ Layout
→ Paint
→ Composite
```

## 답변

브라우저는 HTML과 CSS를 각각 DOM과 CSSOM으로 파싱하고, 이를 합친 Render Tree로 Layout(위치·크기 계산) → Paint(픽셀 칠하기) → Composite(레이어 합성) 순서로 화면을 그립니다.

성능 관점에서는 **어느 단계를 다시 실행시키는 변경인가**가 핵심입니다. 레이아웃을 건드리는 변경이 가장 비싸고, 합성만 다시 하는 변경이 가장 쌉니다.

- **Render Tree**: 실제 화면에 그릴 요소들을 결정
- **Layout**: 각 요소의 크기와 위치 계산
- **Paint**: 색상, 테두리, 글자 같은 픽셀 정보를 그림
- **Composite**: 여러 레이어를 최종 화면에 합침

## 꼬리

### reflow와 repaint 차이는?

- **reflow(layout)**: 위치나 크기를 다시 계산합니다. `width`, `top`, `font-size`, DOM 추가·삭제가 유발하고, 한 요소가 바뀌면 주변과 자식까지 영향을 받아 비쌉니다
- **repaint**: 위치는 그대로고 픽셀만 다시 칠합니다. `color`, `background-color` 등

reflow가 일어나면 repaint도 따라옵니다. 반대는 아닙니다.

### layout thrashing이 뭔가요?

쓰기와 읽기를 번갈아 하면서 강제로 레이아웃 계산을 반복시키는 것입니다.

```js
// 매 반복마다 강제 동기 레이아웃
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px';
}
```

브라우저는 스타일 변경을 모아서 처리하려 하는데, `offsetWidth`처럼 레이아웃 결과가 필요한 값을 읽으면 그 자리에서 계산을 강제합니다. 해결은 **읽기를 먼저 다 하고 쓰기를 몰아서** 하는 것입니다.

### transform이 항상 빠른가요?

아닙니다. `transform` / `opacity`가 유리한 이유는 Layout과 Paint를 건너뛰고 합성 단계에서 처리될 **수 있기** 때문이지 항상 그런 건 아닙니다.

레이어 승격 조건에 따라 달라지고, 레이어가 많아지면 합성 비용과 메모리가 늘어 오히려 느려질 수 있습니다. "레이아웃 유발 속성보다 유리한 경우가 많다" 정도로 말하고 실제로는 측정합니다.

### will-change는?

곧 바뀔 속성을 브라우저에 미리 알려 레이어 승격 등을 준비시키는 힌트입니다.

레이어마다 메모리를 쓰기 때문에 상시로 켜두면 오히려 느려집니다. 애니메이션 직전에 켜고 끝나면 제거하는 게 원칙입니다.

### CSS selector가 성능에 중요한가요?

요즘은 대부분 병목이 아닙니다. 실제 병목은 보통 사용하지 않는 CSS 전송량, 과도한 DOM 노드 수, 레이아웃을 유발하는 애니메이션 쪽입니다. 선택자를 다듬기 전에 어디가 느린지 먼저 측정합니다.

# 40. 테스트는 어떻게 작성하나요?

## 답변

전부를 테스트하려 하기보다 **깨지면 아픈 곳부터** 씁니다.

- 파서·계산·변환처럼 **입출력이 명확한 핵심 로직**은 단위 테스트로 고정합니다. 리팩터링할 때 이 테스트가 안전망이 됩니다.
- 컴포넌트는 구현 내부가 아니라 **사용자 관점의 동작**을 테스트합니다 — "버튼을 누르면 목록이 필터된다"처럼요. Testing Library를 쓰는 이유입니다.
- 로그인·결제·핵심 전환처럼 **끊기면 사업에 문제가 되는 흐름**은 Playwright로 E2E를 둡니다.

반대로 스냅샷을 남발하거나 단순 렌더링까지 전부 커버하는 건 유지비만 늘린다고 봅니다. 최근에는 AI가 코드를 많이 작성하기 때문에, 테스트가 **사람이 의도를 고정해두는 장치**로서 더 중요해졌다고 생각합니다.

## 꼬리

### 커버리지 목표를 정해두나요?

숫자 목표는 두지 않습니다. 커버리지는 "실행됐다"를 보장할 뿐 "검증됐다"를 보장하지 않아서, 숫자를 목표로 잡으면 의미 없는 테스트가 늘어납니다. 대신 핵심 로직과 크리티컬 플로우가 커버되는지를 봅니다.

### 테스트를 못 쓰고 넘어간 경험은?

일정이 급한 화면 작업에서는 테스트 없이 나간 경우도 많습니다. 다만 그런 코드도 이후 버그가 나면 **재현 테스트를 먼저 쓰고 고치는 방식**으로 부채를 줄이려고 합니다.

# 41. GraphQL을 써본 경험이 있나요? REST와 비교하면?

## 답변

이전 회사에서 농가 CMS를 **GraphQL(Apollo Client) 기반으로 풀스택 개발**한 경험이 있습니다. 스키마를 정의하고 클라이언트에서 쿼리·뮤테이션으로 데이터를 다루는 흐름을 실무로 다뤘습니다.

REST와의 본질적 차이는 **데이터 요구를 누가 정의하느냐**라고 생각합니다. REST는 서버가 엔드포인트별 응답 형태를 정하고, GraphQL은 클라이언트가 필요한 필드를 질의합니다.

그래서 GraphQL은 화면마다 필요한 데이터가 다를 때 **overfetching(안 쓰는 필드까지 받기)과 underfetching(여러 번 호출)** 문제를 스키마 하나로 풉니다. 스키마가 곧 타입이라 codegen으로 프론트 타입 안전성이 확보되는 것도 큰 장점이었습니다.

대신 대가도 있습니다 — 단일 엔드포인트 POST 중심이라 **HTTP 레벨 캐싱이 어렵고**, 서버는 리졸버 설계와 N+1 문제(DataLoader)를 감당해야 하며, 단순한 CRUD에는 REST보다 초기 비용이 큽니다.

정리하면 **화면이 다양하고 데이터 그래프가 복잡한 제품일수록 GraphQL의 이점이 커지고**, 단순 리소스 CRUD나 HTTP 캐싱이 중요한 공개 API는 REST가 낫다고 봅니다.

GraphQL은 클라이언트가 필요한 데이터 구조를 직접 요청하는 방식이고, 서버는 Schema로 가능한 데이터 구조를 정의합니다. 실제 데이터 조회는 Resolver가 담당합니다. 프론트에서는 Apollo Client를 사용해서 Query와 Mutation을 실행하고 응답을 캐싱합니다. Apollo는 객체를 \_\_typename과 id 기준으로 정규화해서 관리하기 때문에 같은 객체를 여러 화면에서 재사용하기 좋습니다. 서버에서는 중첩 Resolver 때문에 N+1 문제가 생길 수 있어서 DataLoader 같은 batching 전략을 사용할 수 있습니다.

## 꼬리

### 클라이언트 캐싱은 어떻게 다른가요?

Apollo 같은 GraphQL 클라이언트는 응답을 **엔티티 단위로 정규화**해서 캐시합니다. 같은 객체를 여러 쿼리가 공유하므로 한 곳에서 갱신되면 다른 화면에도 반영됩니다. React Query의 키 단위 캐시보다 강력한 대신, 캐시 정책과 무효화를 이해해야 예측 가능하게 동작합니다.

### 최근에는 왜 안 썼나요?

현재 회사 Backend가 REST 기반이라 REST + React Query 조합을 썼습니다. 데이터 레이어의 본질 — 캐싱, 무효화, 서버 상태와 클라이언트 상태의 분리 — 은 같아서, GraphQL 팀에 합류해도 빠르게 적응할 수 있다고 생각합니다.

### Relay는 써봤나요? (당근 스택 — 우대사항에 명시)

실무에서는 Apollo를 썼고 Relay는 써보지 않았습니다. 다만 지원을 준비하면서 Relay가 Apollo와 무엇이 다른지는 학습했습니다.

가장 큰 차이는 **fragment colocation**입니다. 각 컴포넌트가 자기가 필요한 데이터를 fragment로 선언하고, Relay 컴파일러가 빌드 타임에 이를 상위 쿼리 하나로 합칩니다. 데이터 요구가 컴포넌트 파일에 붙어 다니기 때문에, 컴포넌트를 옮기거나 지울 때 데이터 요구도 같이 따라갑니다.

이 방향은 제가 FSD에서 지켜온 원칙 — **부모는 합성만 하고, 컴포넌트가 자기 데이터를 직접 가져간다** — 과 같은 철학이라고 이해했습니다. Apollo는 쿼리를 어디에 둘지 팀 컨벤션에 맡기지만, Relay는 이걸 구조로 강제합니다.

그 외 차이로는:

- **컴파일러가 빌드 타임에 쿼리를 검증·최적화**합니다. 런타임 파싱 비용이 없고, 스키마에 없는 필드는 빌드가 깨집니다.
- 캐시 정규화가 **Global Object Identification**(모든 객체가 전역 유일 `id`를 갖는 Node 인터페이스) 규약 위에서 동작합니다. Apollo의 `__typename + id` 조합보다 규약이 강한 대신 예측 가능합니다.
- 페이지네이션도 `@connection` 규약으로 표준화되어 있습니다.

정리하면 Relay는 **자유도를 줄이고 규약을 강제해서 대규모 팀에서 일관성을 얻는 선택**이라고 이해하고 있고, 규약 기반으로 일하는 방식은 제가 lint·Harness로 해온 것과 같은 방향이라 적응 비용이 크지 않다고 생각합니다.

# 43. 해외 사용자에게 영상을 빠르게 전달하려면?

```text
Object Storage
→ Transcoding
→ HLS / DASH
→ multiple bitrate
→ CDN Edge
→ Adaptive Bitrate
```

## 답변

업로드된 원본을 트랜스코딩해서 여러 비트레이트의 HLS segment로 만들고, CDN 엣지로 전달하는 구조를 생각하겠습니다.

핵심은 두 가지입니다 — **물리적 거리는 CDN 엣지 캐시로 줄이고, 사용자마다 다른 네트워크 품질은 Adaptive Bitrate로 대응합니다.**

원본 영상은 Object Storage에 저장하고, 업로드 이후 트랜스코딩 작업을 통해 여러 해상도의 HLS 파일을 생성하겠습니다. HLS는 영상을 작은 segment 단위로 나누고 master playlist에 여러 bitrate를 정의합니다. 이후 CDN을 앞에 두어 segment를 Edge에 캐싱하고, 플레이어는 현재 네트워크 상태에 따라 적절한 bitrate의 segment를 선택하도록 구성하겠습니다.

## 왜 CDN?

origin 서버가 한 리전에만 있으면 해외 사용자는 물리적 거리만큼의 왕복 지연을 매 요청마다 감수해야 합니다. CDN은 사용자와 가까운 엣지에서 응답해 지연을 줄이고 origin 부하도 낮춥니다.

영상처럼 크고 변하지 않는 파일은 캐시 적중률이 높아서 CDN 효과가 가장 큰 영역입니다.

## 왜 HLS?

영상을 통파일로 내려주면 보지 않을 구간까지 받아야 하고, 재생 중 네트워크 변화에 대응할 수 없습니다.

HLS는 영상을 몇 초 단위 segment로 쪼개고 여러 비트레이트를 준비해두므로, 플레이어가 네트워크 상태를 보며 segment 단위로 품질을 갈아탈 수 있습니다(Adaptive Bitrate). 시작 지점부터 바로 재생할 수 있는 것도 장점입니다.

# 44. 월 200만 방문 서비스에서 성능은 어떻게 측정하고 개선하나요?

## 핵심

```text
측정 먼저
Core Web Vitals (LCP / INP / CLS)
랩 데이터 vs 필드 데이터
이미지 갤러리 개선 사례
```

## 답변

매물 상세처럼 이미지가 많은 화면에서는 LCP가 핵심이었고, A/B 테스트로 개선한 이미지 갤러리 UI도 화면을 예쁘게 바꾸는 것이 아니라 첫 화면에서 사용자가 원하는 정보에 더 빨리 닿게 하는 문제로 접근했습니다.

> ✍️ 실제로 성능 지표를 상시 수집했는지(RUM 도구 유무), Lighthouse를 어느 시점에 돌렸는지 사실관계를 면접 전에 확인할 것. 상시 모니터링이 없었다면 "상시 체계까지는 없었고 개선 시점에 측정했다"고 정확히 말한다.

## 꼬리

### LCP를 개선하려면 뭘 하나요?

LCP 요소(보통 히어로 이미지)를 특정하고 그 요소가 늦는 원인을 나눕니다 — 리소스 자체가 크면 이미지 최적화(포맷·사이즈·CDN), 발견이 늦으면 `priority`/preload, 렌더링이 늦으면 블로킹 리소스 제거. `next/image`의 lazy 기본값 때문에 첫 화면 이미지에 priority를 빠뜨리는 게 흔한 원인입니다.

### 번들 크기는 어떻게 관리하나요?

라우트 단위 코드 스플리팅은 Next가 해주고, 그 위에서 무거운 컴포넌트는 dynamic import로 분리합니다. 번들 분석기로 큰 의존성을 확인하고, 클라이언트에 갈 필요 없는 코드는 Server Component 쪽에 둡니다.

# 45. 프론트엔드 에러 모니터링과 장애 대응은 어떻게 하나요?

## 핵심

```text
에러 수집
Error Boundary
심각도 분류
재발 방지
```

## 답변

프론트 에러는 사용자가 신고하기 전에 아는 것이 목표입니다. 전역 에러 핸들링과 Error Boundary로 화면 전체가 깨지는 것을 막고, 에러를 수집해 발생 빈도와 영향 범위 기준으로 대응 우선순위를 정합니다.

레거시와 신규가 병행 운영되는 환경이라, 배포 직후 기존 사용자 흐름이 회귀하지 않았는지 확인하는 것을 중요하게 봤습니다.

> ✍️ 실제 사용 도구(Sentry 등 에러 트래킹 유무, 없었다면 어떻게 인지했는지 — CS 채널·로그)를 면접 전에 확인할 것. 도구가 없었다면 그 사실을 인정하고 "있었다면 이렇게 구성하겠다"로 전환하는 게 안전하다.

## 꼬리

### 기억에 남는 장애 경험은?

실제 사례 1개를 준비할 것 — 원인, 인지 경로, 조치, 재발 방지까지. 없으면 "AI가 잘못 구현한 실제 사례"(14번)를 운영 관점으로 재구성해 답한다.

### Error Boundary는 어디에 두나요?

전역 1개로 끝내지 않고 화면 블록 단위로 둡니다. 추천 영역 하나가 실패해도 매물 상세 전체가 죽지 않게 — 실패의 반경을 줄이는 도구로 씁니다.

# 46. A/B 테스트는 프론트에서 어떻게 구현했나요?

## 핵심

```text
variant 배정 일관성
플리커(깜빡임)
노출 이벤트
```

## 답변

구현 관점의 핵심은 두 가지였습니다. 첫째, **배정 일관성** — 같은 사용자는 새로고침하거나 다시 방문해도 같은 안을 봐야 결과가 오염되지 않습니다. 둘째, **노출 측정** — variant가 실제로 사용자에게 보인 시점에 노출 이벤트를 남겨야 전환율의 분모가 정확해집니다.

variant 분기 자체는 프론트에서 구현했고, 가설 수립은 PM·마케터와 함께, 결과 분석은 데이터 파트가 주도했습니다.

> ✍️ 배정 방식(Amplitude Experiment 같은 도구였는지, 쿠키/스토리지 기반 자체 구현이었는지)과 SSR 환경에서 플리커를 어떻게 처리했는지 실제 구현을 확인해둘 것.

## 꼬리

### 플리커가 뭐고 왜 문제인가요?

기본안이 먼저 그려진 뒤 variant로 바뀌는 깜빡임입니다. 사용자 경험도 나쁘지만, B안 사용자가 A안을 먼저 보게 되어 실험 자체가 오염됩니다. 서버에서 배정을 결정해 처음부터 variant를 그리거나, 결정 전까지 해당 영역 렌더를 잠깐 보류하는 방식으로 막습니다.

### 두 실험을 동시에 돌리면?

같은 지표에 영향을 주는 실험이 겹치면 원인을 분리할 수 없습니다. 영역이 겹치지 않게 나누거나 기간을 분리하고, 겹쳐야 한다면 상호 배제 그룹으로 나눕니다.

# 47. 공통 이벤트 로깅 구조는 어떻게 설계했나요?

## 핵심

```text
공통 패키지로 분리
사용처는 import만
공통 프로퍼티 자동 부착
네이밍 컨벤션
```

## 답변

문제는 이벤트가 기능마다 제각각 정의되어 비교가 안 되는 것이었습니다. 그래서 로깅을 **하나의 공통 패키지로 분리**해서 이벤트 정의·네이밍 규칙·SDK 초기화를 그 안에서 관리하고, 각 사용처는 패키지를 가져다 호출만 하게 했습니다.

페이지·사용자 상태 같은 공통 프로퍼티는 패키지가 자동으로 붙이므로 호출부는 그 이벤트 고유의 값만 넘깁니다. 이벤트 정의가 한 곳에 모이니 기능별 데이터를 같은 기준으로 비교할 수 있고, 새 기능에 이벤트를 붙이는 비용도 줄었습니다.

> ✍️ 실제 네이밍 규칙(예: `영역_행동` 형태였는지)과 스크롤·노출 측정 구현(IntersectionObserver 등) 구체 사례 1개를 준비할 것.

## 꼬리

### 왜 패키지로 분리했나요?

앱마다 로깅을 따로 구현하면 SDK 초기화·이벤트 이름·프로퍼티 구조가 흩어져서 같은 행동이 다른 이름으로 쌓입니다. 정의를 한 곳에 두면 규칙이 코드로 강제되고, 이벤트를 추가·변경할 때 수정 지점도 한 곳입니다. 여러 앱을 운영하는 모노레포 구조라 공통 패키지로 두는 것이 자연스러웠습니다.

### 이벤트가 제대로 쌓이는지 어떻게 검증하나요?

배포 전 개발 환경에서 이벤트 발생을 직접 확인하고, 배포 후 대시보드에서 볼륨이 예상 범위인지 봅니다. 노출 이벤트는 중복 발화(리렌더마다 발화)가 흔한 함정이라 발화 조건을 명확히 합니다.

### 이벤트 정의는 누가 하나요?

지표가 필요한 쪽(PM)과 구현하는 쪽이 함께 정합니다. 저는 정의된 이벤트를 일관된 구조로 구현하는 쪽을 주도했고, 이벤트 설계 전체를 제가 소유했다고는 말하지 않습니다(이력서 표현과 맞출 것).

# 49. 동네생활백서의 URL 구조는 어떤 기준으로 설계했나요?

## 핵심

```text
계층 = 탐색 단위
검색 의도와 URL 매칭
안 바꿔도 되는 구조
```

## 답변

URL을 사용자의 검색 의도와 맞추는 것을 기준으로 삼았습니다. 지역 정보 콘텐츠는 "지역 + 주제"로 검색되므로 URL 계층도 그 탐색 단위를 따라 설계하고, 한 URL이 하나의 의도에 대응하게 했습니다.

또 URL은 한번 색인되면 바꾸는 비용이 커서(리다이렉트 체인, 평가 분산), 콘텐츠가 늘어나도 구조를 안 바꿔도 되는 형태인지를 먼저 검증했습니다.

> ✍️ 실제 URL 계층(예: `/지역/카테고리/콘텐츠`였는지)과 슬러그 규칙을 확인해둘 것.

## 꼬리

### 좋은 URL의 기준이 뭔가요?

세 가지로 답합니다. **읽힌다** — URL만 보고 무슨 페이지인지 사람과 검색엔진 모두 알 수 있다. **예측된다** — 같은 종류의 페이지는 같은 패턴을 따라서, 하나를 보면 다른 것의 주소를 유추할 수 있다. **안 바뀐다** — 색인·공유·북마크된 URL은 자산이라, 구조 변경 없이 콘텐츠가 늘어날 수 있어야 한다.

### 쿼리 파라미터와 경로의 기준은?

색인시키고 싶은 정체성은 경로에, 정렬·필터처럼 같은 콘텐츠의 변형은 쿼리에 둡니다. 쿼리 조합이 색인되면 중복 페이지가 생기므로 canonical로 대표 URL을 지정합니다.

### 슬러그는 어떻게 만드나요?

의미를 담은 슬러그가 SEO·가독성에 유리하지만, 제목이 바뀌면 URL이 바뀌는 문제가 생깁니다. 그래서 안정적인 ID와 의미 슬러그를 조합하거나(`/post/123-역삼동-맛집`, 조회는 ID로), 슬러그를 생성 시점에 고정하고 제목 변경에 안 따라가게 합니다. 한글 슬러그는 인코딩되면 URL이 길고 흉해지지만 검색 의도 매칭에는 유리해서, 서비스의 유입 채널을 보고 결정합니다.

### URL을 바꿔야 한다면?

301 리다이렉트로 기존 URL의 평가를 새 URL로 넘기고, sitemap과 내부 링크를 함께 갱신합니다. 리다이렉트를 여러 번 거치게 체인을 만들지 않습니다.

## 참고 — URL 설계 학습 노트

이력서의 "IA·URL 구조 설계"를 스스로 설명할 수 있게 정리한 노트.

**IA(Information Architecture)와 URL의 관계** — IA는 콘텐츠를 어떤 단위로 묶고 어떤 계층으로 탐색하게 할지의 설계다. URL은 그 IA가 주소로 드러난 것. 그래서 URL 설계는 "예쁜 주소 만들기"가 아니라 **탐색 단위 정의가 먼저**고 URL은 그 결과다. 동네생활백서라면: 사용자는 "지역"으로 들어와 "주제"로 좁힌다 → `/지역/주제/콘텐츠` 계층이 곧 IA.

**계층 설계의 원칙**

- 계층은 탐색 단위와 일치시킨다. 상위 경로를 잘라내도 유효한 목록 페이지가 나오는 게 이상적 (`/역삼동/맛집/A식당`에서 `/역삼동/맛집`은 목록, `/역삼동`은 지역 홈)
- 깊이는 필요한 만큼만. 계층이 깊다고 SEO에 불리한 건 아니지만, 의미 없는 중간 계층은 유지 비용만 늘린다
- 한 콘텐츠가 여러 분류에 속하면 계층이 무너진다 — 대표 경로 하나를 정하고 나머지는 canonical로 정리

**함정들**

- 트레일링 슬래시(`/a` vs `/a/`)와 대소문자는 서로 다른 URL이다 — 한쪽으로 통일하고 나머지는 리다이렉트
- 페이지네이션은 `?page=2`로 두되 각 페이지가 자기 자신을 canonical로 가리키게 한다 (2페이지를 1페이지로 canonical하면 2페이지 이후 콘텐츠가 색인에서 사라질 수 있음)
- 무한 조합(필터×정렬×페이지)이 색인되면 크롤링 예산 낭비 — 색인 가치 있는 조합만 남기고 나머지는 noindex 또는 robots 제어

**연결 주제** — sitemap·canonical(36번), SSR/SSG 렌더링 전략(24번), 레거시 전환 시 URL 보존(48번)과 이어서 답할 수 있게 해둘 것.

# 50. AI로 개발 리드타임이 줄었다는 걸 어떻게 증명하나요?

## 핵심

```text
비교 기준 제시
1개월 산출물
품질은 사람이 보증
```

## 답변

엄밀한 대조군 실험을 한 것은 아니라서, 그렇게 말하지 않습니다. 대신 비교 가능한 사실을 제시합니다 — 디자인 시스템과 어드민 2종을 약 1개월에 구축했는데, 이전에 비슷한 규모의 어드민을 만들 때의 기간과 비교하면 체감 차이가 분명했다는 식입니다.

그리고 단축의 원천을 구체적으로 말합니다: 반복 UI 구현·CRUD 플로우를 Agent가 패턴으로 재사용하고, 제 시간은 요구사항 정의·아키텍처·검증에 쓰는 구조라서 빨라진 것이지, AI가 알아서 다 만들어서가 아닙니다.

> ✍️ "이전에 비슷한 작업이 얼마나 걸렸는지" 비교 사례 1개를 실제 경험에서 준비할 것. 숫자를 지어내지 말고, 없으면 "정량 비교는 없다"고 인정한다.

## 꼬리

### AI가 만든 코드 품질은 누가 보증하나요?

저입니다. Agent가 만든 코드도 리뷰·테스트를 통과해야 하고, 잘못 구현한 사례(14번)처럼 검증 없이 믿으면 사고가 납니다. 그래서 Harness에 규칙을 축적하고 검증 단계를 플로우에 포함했습니다.

### AI 때문에 오히려 느려진 적은?

있습니다 — 컨텍스트가 부족한 상태로 시키면 잘못된 방향으로 많이 만들어놓고, 그걸 되돌리는 비용이 더 컸습니다. 그래서 규칙·컨텍스트를 Harness에 쌓는 데 투자했고, 그 이후로 같은 실수의 반복이 줄었습니다.

# 51. 웹뷰 환경에서의 웹 개발은 일반 브라우저와 무엇이 다른가요?

## 왜 이 질문이 나오나

당근 제품 대부분은 **앱 안의 웹뷰**로 서빙됩니다. 당근알바(로컬 잡스)도 마찬가지입니다. 면접관 입장에서 "입사하면 바로 하게 될 일"이라 나올 확률이 높습니다.

당근이 웹뷰에서 네이티브 같은 화면 전환을 만들기 위해 **Stackflow**라는 스택 네비게이션 라이브러리를 직접 만들어 오픈소스로 공개했을 정도로, 웹뷰 경험 품질에 투자하는 팀입니다. 이 이름을 아는 것 자체가 준비의 신호가 됩니다.

## 핵심

```text
브라우저가 아니라 "앱 안의 브라우저"
인증 — 앱이 주입한다
네비게이션 — 브라우저 히스토리 ≠ 앱 스택
앱 기능 — 브릿지로 호출
배포 — 앱 심사 없이 웹만 배포
```

## 답변

저희 서비스도 앱 웹뷰로 웹을 서빙하는 영역이 있어서, 일반 브라우저와의 차이를 세 가지로 체감했습니다.

첫째, **인증이 다릅니다.** 웹뷰에는 로그인 화면이 없습니다 — 사용자는 이미 앱에 로그인했기 때문에, 앱이 가진 인증 상태를 웹뷰에 넘겨줘야 합니다. 저희는 웹은 PHP 세션, 앱 웹뷰는 JWT로 인증이 두 벌로 갈라져 있던 게 문제였고, 이걸 HttpOnly Cookie 기반으로 통합하는 작업을 했습니다(19번 참고).

둘째, **네비게이션이 다릅니다.** 브라우저의 히스토리 모델과 앱의 화면 스택 모델이 다르기 때문에, 안드로이드 물리 뒤로가기·iOS 스와이프 백이 웹의 `history`와 자연스럽게 맞물리도록 처리해야 합니다.

셋째, **웹이 할 수 없는 일은 브릿지로 앱에 요청합니다.** 네이티브 공유 시트, 앱 내 다른 화면으로 이동, 권한이 필요한 기능 같은 것들입니다.

정리하면 웹뷰 개발은 "웹을 만든다"기보다 **앱과 웹 사이의 계약(인증·네비게이션·브릿지)을 설계하는 일**이 절반이라고 생각합니다.

> ✍️ 현재 회사에서 본인이 직접 다룬 웹뷰 범위(인증 통합 외에 브릿지 구현·웹뷰 화면 개발 여부)를 면접 전에 정리해둘 것. 안 해본 부분은 "인증 통합 과정에서 웹뷰를 다뤘고, 브릿지 설계는 개념으로 학습했다"고 정직하게 구분한다.

## 브릿지가 무엇인지 설명해주세요

앱과 웹 사이의 **양방향 API**입니다.

- **웹 → 앱**: iOS는 `window.webkit.messageHandlers.<name>.postMessage()`, Android는 `@JavascriptInterface`로 노출된 객체 호출. 앱이 처리할 일(공유, 화면 이동, 토큰 요청)을 메시지로 보냅니다.
- **앱 → 웹**: 앱이 웹뷰에 JavaScript를 주입해서(`evaluateJavascript` 등) 웹의 전역 콜백을 호출합니다.

호출이 비동기 단방향 메시지라서, 실무에서는 **요청에 id를 붙이고 응답 콜백을 매칭해 Promise로 감싸는 래퍼**를 만들어 `await bridge.share(...)`처럼 쓰는 패턴이 일반적입니다.

주의할 점은 브릿지가 **신뢰 경계**라는 것입니다. 웹뷰에 로드된 페이지는 브릿지를 통해 앱 기능에 접근할 수 있으므로, 앱은 허용된 도메인에서만 브릿지를 노출해야 하고, 웹도 브릿지로 받은 데이터를 검증 없이 신뢰하면 안 됩니다.

## 웹뷰 인증은 어떻게 처리하나요

두 가지 방식이 있고, 각각 trade-off가 있습니다.

- **쿠키 주입**: 앱이 로그인 시점에 웹뷰의 쿠키 저장소에 인증 쿠키를 심어줍니다. 웹 입장에서는 일반 브라우저와 코드가 같아지고, HttpOnly라 JS 노출도 없습니다. 저희가 인증을 HttpOnly Cookie로 통일한 것도 웹·웹뷰가 같은 코드 경로를 타게 하려는 목적과 맞닿아 있습니다.
- **브릿지로 토큰 전달**: 웹이 브릿지로 토큰을 받아 Authorization 헤더에 실어 보냅니다. 유연하지만 토큰이 JS 메모리에 존재하므로 XSS 노출면이 생기고, 갱신 타이밍 관리도 웹이 떠안습니다.

가능하면 쿠키 주입 쪽이 낫다고 생각합니다 — **웹과 웹뷰의 인증 코드가 갈라지지 않는 것** 자체가 유지보수에서 가장 큰 이점이기 때문입니다.

## 성능 관점에서는 무엇이 다른가요

웹뷰의 첫 로딩은 **앱 사용자가 느끼는 앱의 속도**입니다. 브라우저 사용자보다 기대 수준이 높습니다 — 네이티브 화면처럼 즉시 뜨길 기대합니다.

- **초기 로딩**: 번들 경량화, 첫 화면 SSR 또는 스켈레톤으로 백지 시간을 없애는 게 우선입니다.
- **웹뷰 프리워밍**: 앱이 웹뷰 인스턴스를 미리 만들어두거나 페이지를 미리 로드해두는 최적화가 가능합니다(앱 팀과의 협업 영역).
- **전환 애니메이션**: 화면 전환이 네이티브처럼 보여야 해서, 당근의 Stackflow 같은 스택 네비게이션 접근이 나옵니다.

## 디버깅은 어떻게 하나요

- iOS: Safari **Web Inspector**로 실기기 웹뷰에 연결
- Android: Chrome `chrome://inspect`로 원격 디버깅
- 환경 차이(앱 UA, 브릿지 유무)가 버그의 원인인 경우가 많아서, 개발 중에는 브릿지 mock을 두고 브라우저에서 개발한 뒤 웹뷰에서 검증하는 흐름이 효율적입니다.

## 꼬리

### 왜 네이티브가 아니라 웹뷰로 만드나요?

**배포 주기의 분리**가 가장 큽니다. 앱 심사 없이 웹 배포만으로 기능이 즉시 반영되고, iOS·Android를 한 코드로 커버합니다. 실험이 잦은 제품(A/B 테스트, 빠른 개선 루프)일수록 이점이 커집니다.

대가는 초기 로딩 속도와 네이티브 수준 인터랙션의 한계입니다. 그래서 진입 빈도가 높고 인터랙션이 무거운 화면은 네이티브로, 변경이 잦고 콘텐츠 중심인 화면은 웹뷰로 가르는 게 일반적인 기준이라고 이해합니다.

### 웹뷰와 일반 브라우저를 한 코드로 어떻게 대응하나요?

환경 감지(브릿지 존재 여부·UA)를 한 곳에 모으고, 기능 단위 어댑터로 격리합니다. 예를 들어 `share()`는 웹뷰면 브릿지, 브라우저면 Web Share API나 URL 복사로 동작하게 하고, 호출부는 환경을 모르게 합니다. 분기가 화면 코드 곳곳에 퍼지는 순간 유지보수가 무너지기 때문입니다.

### 안드로이드 물리 뒤로가기는 어떻게 처리하나요?

기본 동작은 웹뷰 히스토리 back입니다. 문제는 모달·바텀시트가 열린 상태 — 사용자는 "닫힘"을 기대하는데 페이지가 뒤로 갑니다. 그래서 모달을 열 때 히스토리 엔트리를 쌓고(`pushState`) `popstate`에서 모달을 닫는 식으로, **UI 상태를 히스토리와 동기화**해야 합니다. 37번(SPA URL·뒤로가기)과 같은 원리이고, 웹뷰에서는 이게 선택이 아니라 필수가 됩니다.
