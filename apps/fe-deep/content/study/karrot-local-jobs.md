## 0. 이 핸드북 사용법

### 암기 방식

각 주제는 아래 4단계로 반복한다.

1. **키워드만 보고 말하기**
2. **30초 답변**
3. **60초 답변**
4. **꼬꼬무 5~7개**

문장 통암기는 금지한다.

### 모든 경험의 공통 프레임

```text
문제
→ 원인
→ 검토한 대안
→ 내가 선택한 방법
→ 선택 이유
→ 결과
→ 아쉬움 / 다시 한다면
```

1. 왜 그렇게 했나요?
2. 다른 방법은 없었나요?
3. 왜 그 방법은 선택하지 않았나요?
4. 선택한 방식의 단점은 뭐였나요?
5. 실제로 문제는 없었나요?
6. 본인이 직접 판단한 부분은 무엇인가요?
7. 다시 한다면 똑같이 하실 건가요?

# 1. 자기소개

## 핵심 키워드

- 부동산 중개 서비스
- 아파트 커뮤니티
- 프론트엔드
- 0→1 신규 구축
- AI Agent
- 제품 성공
- 사용자 관점

## 30초 답변

안녕하세요. 현재 부동산 중개 서비스와 아파트 커뮤니티 서비스를 개발하고 있는 프론트엔드 엔지니어 김단우입니다.

최근에는 기존 레거시 서비스를 신규 프로젝트로 0부터 다시 구축하면서 프로젝트 구조, 인증, 디자인 시스템, 관리자와 사용자 화면까지 전반적으로 설계하고 개발했습니다.

이 과정에서 AI Agent를 적극적으로 활용하면서 개발 방식 자체도 개선했고, 단순히 기능을 구현하는 것보다 실제 사용자와 제품의 성공까지 고민하며 개발하려고 하고 있습니다.

## 꼬꼬무

### 최근 프로젝트에서 가장 어려웠던 점은?

기술 자체보다 **기존 것과 새 것을 동시에 살려야 한다**는 제약이 가장 어려웠습니다.

레거시 아파트 커뮤니티를 새로 구축하면서도 인증과 도메인 체계는 기존 것을 그대로 써야 했습니다. 화면을 새로 그리는 일은 패턴이 반복돼서 오래 걸리지 않았는데, 기존 인증 흐름에 새 프로젝트를 끼워 넣는 부분은 제약 조건을 먼저 정리하는 데 시간이 많이 들었습니다.

결국 "무엇을 새로 만들고 무엇을 그대로 둘지" 경계를 먼저 긋고 시작한 게 도움이 됐습니다.

### 직접 결정한 기술적 판단은?

크게 세 가지입니다.

1. 레거시를 점진적으로 고치는 대신 신규 프로젝트로 재구축
2. 공통 영역을 모노레포로 묶고 UI를 디자인 시스템으로 분리
3. 100개가 넘는 도메인의 CORS를 백엔드에서 관리하는 대신 기존 Next 서버를 프록시로 사용

특히 세 번째는 API hop이 하나 늘고 Next 서버가 장애 지점이 된다는 단점을 알고 선택했습니다.

### AI Agent가 없었다면 어떻게 했을까?

결과물의 방향은 같았을 거라고 생각합니다. 구조 설계나 인증 흐름 판단은 어차피 제가 했으니까요.

차이가 컸을 부분은 반복적인 관리자 CRUD 화면처럼 **양이 많고 패턴이 동일한 작업**입니다.

반대로 Agent를 쓰면서 생긴 문제도 있었습니다. 제가 직접 코드베이스를 탐색하는 시간이 줄어서 코드 이해도가 얕아졌던 시기가 있었고, 그 뒤로 위임 범위를 좁혔습니다.

### 제품 성공을 고민했다는 구체적 사례는?

프록시를 도입하면 Next 서버가 새로운 장애 지점이 된다는 걸 알고 있었기 때문에, 백엔드 응답이 실패했을 때 **사용자에게 무엇을 보여줄지**를 같이 설계했습니다. 장애 페이지와 재시도 흐름을 준비했습니다.

다만 완전한 장애 격리 구조까지 만든 건 아닙니다. 그 부분은 아직 아쉬움으로 남아 있습니다.

### 본인이 가장 자신 있는 프로젝트는?

아파트 커뮤니티 0→1 재구축입니다.

화면을 옮기는 작업이 아니라 앞으로 기능이 계속 붙는다는 전제로 모노레포, 디자인 시스템, 인증, 관리자/사용자 영역을 함께 설계한 경험이라 이야기할 게 가장 많습니다. 그중에서도 인증과 도메인 구조에 가장 오래 고민했습니다.

# 2. 가장 자신 있는 프로젝트 — 아파트 커뮤니티 0→1

## 암기 키워드

```text
레거시
→ 신규 구축
→ 100개+ 도메인
→ 모노레포
→ 디자인 시스템
→ 인증
→ 관리자/B2C
→ Agent Harness
```

## 문제

- 기존 레거시 서비스
- 확장하기 어려운 구조
- 신규 관리자/사용자 기능이 계속 추가될 예정
- 기존 인증과 도메인 체계를 같이 사용해야 함

## 내가 한 판단

- 신규 프로젝트로 재구축
- 공통 영역은 모노레포에서 공유
- UI는 디자인 시스템으로 재사용
- 인증 흐름 재설계
- AI Agent가 구조를 이해할 수 있도록 Harness 구성

## 결과

- 반복적인 CRUD/관리자 화면 개발 속도 개선
- 코드 구조의 예측 가능성 향상
- 공통 컴포넌트 재사용
- 유지보수와 코드 리뷰가 쉬워짐

## 30초 답변

기존 레거시 아파트 커뮤니티 서비스를 신규 프로젝트로 0부터 재구축한 경험이 가장 자신 있습니다.

단순히 화면을 옮기는 게 아니라 앞으로 계속 기능이 추가되는 걸 고려해서 모노레포, 디자인 시스템, 인증 구조, 관리자와 사용자 영역을 함께 설계했습니다.

특히 AI Agent를 많이 활용했기 때문에 Agent가 프로젝트 구조와 규칙을 이해하도록 Harness를 만들었고, 반복적인 개발 속도뿐 아니라 코드의 예측 가능성과 유지보수성을 높이는 데 집중했습니다.

## 꼬꼬무

### 왜 리팩터링이 아니라 신규 구축이었나요?

기존 구조가 앞으로 추가될 기능을 감당하기 어려운 형태였습니다. 관리자 기능과 사용자 기능이 계속 붙을 예정이었는데, 레거시를 하나씩 뜯어고치면 매번 기존 동작을 깨뜨릴 위험을 안고 가야 했습니다.

다만 **완전히 새로 만든 건 아닙니다.** 인증과 도메인 체계는 기존 것을 그대로 사용했고, 애플리케이션 구조와 화면만 새로 세웠습니다.

리팩터링이 항상 틀렸다는 뜻은 아닙니다. 남은 레거시 코드의 수명이 짧다고 판단했기 때문에 선택한 방식입니다.

### 모노레포가 꼭 필요했나요?

필수는 아니었습니다.

다만 관리자 화면과 사용자 화면이 같은 도메인 지식과 같은 UI를 쓰는데 저장소를 나누면 디자인 시스템과 타입을 복사하거나 별도 패키지로 배포해야 했습니다. 앱이 더 늘어날 가능성이 있어서 공통 부분을 한 저장소에서 공유하는 쪽을 택했습니다.

대신 이런 비용은 감수했습니다.

- 빌드 파이프라인이 복잡해진다
- 패키지 경계를 잘못 잡으면 모든 앱이 같이 느려진다

### FSD는 왜 사용했나요?

폴더 구조가 정갈해서가 아니라 **"이 코드를 어디에 둘 것인가"를 매번 논쟁하지 않기 위해서**였습니다.

레이어가 정해져 있으면 사람이든 AI Agent든 같은 기준으로 위치를 찾습니다. 특히 Agent에게 작업을 맡길 때 구조가 명시적이면 결과가 예측 가능해집니다.

단점은 작은 기능에도 폴더가 여러 개 생긴다는 것이라, 슬라이스를 과하게 쪼개지 않으려고 신경 썼습니다.

### 가장 실패했던 설계는?

AI Agent에게 위임하는 범위를 초기에 너무 넓게 잡은 것입니다.

간단한 문구 수정이나 작은 변경까지 전부 넘기다 보니 코드는 계속 나오는데 제가 코드베이스를 직접 탐색하는 시간이 줄었습니다. 결과적으로 제가 리뷰해야 할 코드에 대한 이해도가 떨어졌습니다.

이후에는 구조적 판단과 리뷰는 직접 하고, 반복 실행만 위임하는 쪽으로 바꿨습니다.

> ✍️ 구조 설계 자체에서 실패한 구체적 사례가 있으면 이걸로 교체하는 게 더 강합니다.

### 가장 많은 시간을 쓴 부분은?

인증과 도메인 구조입니다.

화면은 패턴이 반복되니 빠르게 나오지만, 기존 인증을 새 프로젝트에서 어떻게 재사용할지와 100개가 넘는 도메인이 하나의 백엔드 API를 어떻게 바라보게 할지는 **되돌리기 어려운 결정**이라 대안을 여러 개 놓고 오래 봤습니다.

### AI가 만든 코드 중 가장 문제가 컸던 사례는?

FSD의 public API를 우회한 import였습니다.

`@/features/example/ui`까지만 접근해야 하는데 Agent가 `@/features/example/ui/SomeComponent`처럼 내부 파일을 직접 가져왔습니다. 동작은 정상이라 리뷰에서 놓치기 쉬웠는데, 이런 import가 쌓이면 내부 구조를 바꿀 때 영향 범위가 커집니다.

그래서 이 규칙은 문서에만 두지 않고 lint로 강제했습니다.

### 다시 한다면 바꾸고 싶은 구조는?

프록시 계층입니다. 지금 구조는 Next 서버가 죽으면 API 호출도 같이 막히는데, 당시엔 추가 인프라를 늘리지 않는 단순함을 우선했습니다. 트래픽이 더 커진다면 Gateway나 인프라 레벨 프록시로 분리하는 쪽을 다시 검토할 것 같습니다.

그리고 AI 위임 범위는 처음부터 좁게 시작했을 것 같습니다.

# 3. AI Agent Harness

## 한 줄 정의

> Agent가 프로젝트의 구조, 도메인, 규칙, 금지사항을 이해하고 예측 가능한 범위에서 작업할 수 있게 만든 명시적 개발 환경.

## 암기 키워드

```text
암묵지
→ 명시화
→ 전역 규칙
→ 프로젝트 규칙
→ 금지 영역
→ 검증
→ lint/type
```

## 전역 Harness

프로젝트가 달라도 유지되는 개발 원칙.

예:

- 명확한 네이밍
- 작은 책임 단위
- 불필요한 추상화 지양
- 명시적인 코드
- 읽기 쉬운 구조

## 프로젝트 Harness

프로젝트에만 존재하는 맥락.

예:

- 모노레포 패키지 역할
- FSD 구조
- import 규칙
- 재사용 기준
- 환경변수 등 수정 금지 영역
- 도메인 설명

## 중요한 기준

### Harness에 넣는 것

- 자주 변하지 않는 것
- 여러 작업에서 반복되는 것
- 반드시 알아야 하는 프로젝트 맥락

### Harness만으로 두면 안 되는 것

반드시 지켜야 하는 규칙은 가능하면:

```text
lint
type
test
CI
```

로 강제한다.

## 30초 답변

처음에는 Agent에게 프롬프트로 필요한 규칙을 매번 설명했는데, 작업이 길어질수록 코드 스타일이나 구조가 흔들리는 문제가 있었습니다.

그래서 프로젝트 전반에서 반복되는 구조, 도메인, 금지사항을 Harness로 명시했습니다.

다만 중요한 규칙을 문서에만 의존하면 다시 어길 수 있기 때문에 import boundary 같은 부분은 lint로 강제했습니다.

결과적으로 구현 속도보다도 코드가 제가 예상한 범위에서 만들어져 리뷰와 유지보수가 쉬워진 게 가장 큰 효과였습니다.

## 꼬꼬무

### CLAUDE.md랑 뭐가 다른가요?

CLAUDE.md는 Harness를 담는 **그릇 중 하나**입니다. 제가 말하는 Harness는 파일 하나가 아니라 "Agent가 예측 가능한 범위에서 작업하게 만드는 환경 전체"입니다.

여기엔 규칙 문서뿐 아니라 lint 룰, 타입, 폴더 구조, 금지 영역 표시까지 들어갑니다. 문서는 읽히지 않을 수도 있지만 lint는 반드시 걸리기 때문에, 중요도에 따라 어디에 둘지를 나눴습니다.

### 왜 모든 규칙을 lint로 만들지 않았나요?

두 가지 이유입니다.

1. **모든 규칙이 기계적으로 판정되지 않습니다.** "불필요한 추상화를 하지 마라"는 lint로 표현하기 어렵습니다.
2. **lint 룰도 유지보수 비용입니다.** 규칙이 늘수록 예외 처리와 오탐이 늘고, 개발자가 `eslint-disable`을 습관적으로 붙이기 시작하면 오히려 규칙이 죽습니다.

그래서 기준을 이렇게 잡았습니다. 어겼을 때 되돌리기 어려운 것(import 경계, 레이어 방향)은 lint로, 판단이 필요한 것은 문서와 리뷰로.

### Harness가 너무 커지면 어떻게 하나요?

커지는 것 자체가 신호라고 봅니다. 문서가 길어지면 사람도 Agent도 안 읽습니다.

- 자주 바뀌는 내용은 Harness에서 빼고 코드나 타입으로 옮깁니다
- 특정 작업에서만 필요한 맥락은 전역 문서 대신 그 디렉터리 가까이에 둡니다
- 규칙이 지켜지고 있다면 문서에서 지우고 lint만 남깁니다

### 최신 정보는 어떻게 유지하나요?

원칙은 **"문서를 갱신해야만 유지되는 정보는 최대한 Harness에 넣지 않는다"**입니다. 버전 번호나 파일 목록처럼 금방 낡는 건 문서 대신 코드에서 읽게 합니다.

그래도 남는 부분(도메인 설명, 금지 영역)은 구조를 크게 바꾸는 작업을 할 때 같이 손보는 걸 규칙으로 뒀습니다.

### AI가 Harness를 항상 읽는다고 보장할 수 있나요?

보장할 수 없습니다. 그게 lint로 강제하는 이유입니다.

문서는 "읽으면 좋은 것"이고, 반드시 지켜야 하는 건 **읽든 안 읽든 실패하게** 만들어야 합니다. Harness의 목적은 규칙 준수를 보장하는 게 아니라 어긋났을 때 빨리 드러나게 하는 것에 가깝습니다.

### 사람이 읽기 좋은 코드와 AI가 읽기 좋은 코드가 다른가요?

대부분 같다고 생각합니다. 명시적인 이름, 작은 책임 단위, 예측 가능한 위치는 둘 다에게 좋습니다.

차이가 있다면 AI는 **암묵적 맥락을 추론하기 어렵다**는 점입니다. 사람은 "이 프로젝트에선 원래 이렇게 한다"를 주변 코드에서 눈치채지만 Agent는 자기가 본 범위 안에서만 판단합니다. 그래서 사람에겐 굳이 안 적어도 되는 관례를 명시화한 게 Harness입니다.

### Harness의 성과를 어떻게 측정했나요?

정량 지표를 따로 만들지는 않았습니다. 만들었다고 말하면 과장입니다.

체감한 변화는 **리뷰의 성격이 달라졌다**는 점입니다. 이전에는 "여기는 이 폴더에 있어야 한다", "이 import는 규칙 위반이다" 같은 구조 지적이 많았는데, 그런 것들이 lint에서 걸리기 시작하면서 리뷰에서는 판단이 필요한 부분만 보게 됐습니다.

# 4. AI Agent 실패 경험

## 암기 키워드

```text
과도한 위임
→ 직접 탐색 감소
→ 코드 이해도 저하
→ 리뷰 강화
→ 판단은 사람
```

## 실제 문제

초기에 AI를 적극적으로 쓰면서:

- 간단한 문구 수정
- 작은 코드 변경
- 반복 작업

까지 전부 Agent에게 넘겼다.

문제는 **직접 코드베이스를 탐색하는 시간이 줄었다는 것**.

## 배운 점

> 작업은 위임할 수 있지만 코드에 대한 책임까지 위임할 수는 없다.

## 이후 바꾼 방식

- 구조적 판단은 직접
- Agent 결과 코드 리뷰
- 관련 파일 직접 확인
- Harness 직접 관리
- 반복 실행만 Agent에게 위임

## 꼬꼬무

### 지금은 어떤 작업을 AI에 안 맡기나요?

되돌리기 어려운 판단은 직접 합니다.

- 레이어/패키지 경계 같은 구조 결정
- 인증, 권한처럼 틀리면 보안 문제가 되는 영역
- 스키마 변경이나 마이그레이션
- Harness 자체의 규칙

반대로 패턴이 정해진 반복 구현, 테스트 케이스 확장, 대량 치환 같은 건 적극적으로 맡깁니다.

### AI 코드 리뷰 기준은?

사람 코드를 볼 때와 같은 기준으로 보되, AI 코드에서 유독 자주 나오는 것들을 먼저 확인합니다.

1. **요청하지 않은 코드가 추가됐는가** (쓰지 않는 옵션, 미래를 위한 추상화)
2. **기존 코드를 재사용하지 않고 새로 만들었는가**
3. **경계 규칙을 우회했는가** (내부 import, 레이어 역참조)
4. **동작은 맞는데 이유가 설명되지 않는 부분이 있는가**

가장 중요한 건 마지막입니다. 제가 설명할 수 없는 코드는 머지하지 않습니다.

### hallucination은 어떻게 대응하나요?

없는 패키지나 없는 API를 지어내는 경우가 실제로 있습니다.

- 새 의존성이나 낯선 API가 나오면 공식 문서에서 실재를 확인합니다
- 타입과 빌드가 1차 방어선입니다. 존재하지 않는 API는 대부분 여기서 걸립니다
- Agent에게 "모르면 모른다고 하라"를 규칙으로 명시해 뒀습니다

다만 **타입이 통과한다고 의미가 맞는 건 아니라서** 최종 확인은 사람이 합니다.

### AI가 테스트까지 통과하면 믿나요?

아니요. 테스트를 누가 썼는지가 중요합니다.

같은 Agent가 구현과 테스트를 함께 썼다면 그 테스트는 구현을 그대로 옮긴 것일 수 있습니다. 구현의 잘못된 가정이 테스트에도 똑같이 들어가면 둘 다 통과합니다.

그래서 중요한 로직은 테스트가 **무엇을 보장하는지**를 제가 직접 읽고, 필요하면 실패해야 하는 케이스를 추가합니다.

### 생산성이 정말 좋아졌다고 볼 수 있나요?

작업 종류에 따라 다르다고 답하는 게 정직할 것 같습니다.

패턴이 반복되는 구현에서는 확실히 빨라졌습니다. 반면 구조를 결정하거나 원인을 추적하는 작업은 오히려 제가 직접 보는 게 빠릅니다.

그리고 초기에는 **위임을 늘릴수록 제 코드 이해도가 떨어지는 부작용**이 있었습니다. 그래서 지금은 속도보다 "내가 설명할 수 있는 코드가 남는가"를 기준으로 위임 범위를 정합니다.

# 5. FSD / Public API / lint

## 문제 흐름

```text
FSD 도입
→ segment public API 사용
→ Agent가 내부 파일까지 직접 import
→ 기능은 정상
→ 구조 결합도 증가
→ lint 강제
```

## 핵심

기능이 동작하는가만 문제가 아니다.

```text
@/features/example/ui
```

까지만 접근해야 하는데,

```text
@/features/example/ui/SomeComponent
```

처럼 내부 구현에 직접 접근하면:

- 내부 구조와 결합
- import 파편화
- 리팩터링 영향 증가
- 사람/Agent가 서로 다른 규칙 사용

## 답변 핵심

> 문서로 설명할 수 있는 규칙과 반드시 코드로 강제해야 하는 규칙을 구분했다.

## 꼬꼬무

### barrel export 단점은?

`index.ts`로 모아서 내보내면 public API는 깔끔해지지만 대가가 있습니다.

- **번들에 불필요한 모듈이 딸려 올 수 있습니다.** barrel 하나를 import하면 그 안의 모든 모듈이 평가 대상이 되고, tree-shaking이 항상 완벽하게 걷어내지 못합니다
- **순환 참조가 생기기 쉽습니다.** 서로 다른 파일이 같은 barrel을 거치면 의도치 않은 순환이 만들어집니다
- 파일이 많아지면 빌드/타입 체크가 느려집니다

그래서 barrel은 **경계를 만들고 싶은 지점에만** 두고, 슬라이스 내부에서는 상대 경로로 직접 import했습니다.

### circular dependency는?

가장 흔한 원인은 두 가지입니다. barrel을 서로 참조하는 경우와, 하위 레이어가 상위 레이어를 참조하는 경우입니다.

FSD의 단방향 의존 규칙(`app → views → widgets → features → entities → shared`)은 사실상 순환을 구조적으로 막는 장치입니다. 하위가 상위를 못 보게 하면 사이클이 만들어질 수 없습니다.

그래서 이 방향을 lint로 강제했고, 순환이 필요해 보이면 대부분 **공통으로 내려야 할 코드가 아직 위 레이어에 남아 있다는 신호**로 봤습니다.

### FSD 단점은?

- 작은 기능에도 폴더와 파일이 여러 개 생깁니다. 초기 진입 비용이 있습니다
- 레이어 이름(entities / features / widgets)의 경계가 항상 명확하지 않아서 "이건 feature인가 entity인가" 논쟁이 생깁니다
- 규칙을 강제하지 않으면 폴더만 FSD고 실제 의존성은 뒤엉키기 쉽습니다

세 번째가 실제로 저희에게 일어난 문제라 lint로 막았습니다.

### 왜 FSD가 필요했나요?

기능이 계속 추가될 프로젝트에서 **"이 코드를 어디에 둘지"가 매번 개인 판단이 되는 걸 막고 싶었습니다.**

특히 AI Agent에게 작업을 맡기는 비중이 커지면서 이유가 하나 더 생겼습니다. 구조가 암묵적이면 Agent는 매번 다른 위치에 코드를 만듭니다. 레이어와 import 규칙이 명시적이면 사람과 Agent가 같은 기준을 씁니다.

### lint rule은 직접 만들었나요?

경계 규칙은 `eslint-plugin-boundaries`로 레이어와 허용 방향을 선언해서 강제했고, "세그먼트보다 깊이 import하지 않는다"는 부분은 `no-restricted-imports`의 패턴으로 잡았습니다.

즉 **플러그인 하나를 새로 만든 게 아니라 기존 룰을 프로젝트 규칙에 맞게 설정한 쪽**에 가깝습니다. 커스텀 룰을 직접 작성하는 건 유지보수 비용이 커서 마지막 수단으로 뒀습니다.

### 폴더 구조가 너무 복잡해지지 않나요?

복잡해질 수 있어서 두 가지를 지켰습니다.

1. **슬라이스를 미리 쪼개지 않습니다.** 재사용이 실제로 생겼을 때 내립니다
2. **레이어는 늘리지 않습니다.** 정해진 레이어 안에서만 해결합니다

그리고 구조의 목적은 파일 개수를 줄이는 게 아니라 **찾는 시간을 줄이는 것**이라고 봅니다. 파일이 몇 개 더 생기더라도 위치가 예측 가능하면 이득이라고 판단했습니다.

# 6. 인증 — 세션 쿠키

## 암기 키워드

```text
기존 인증 재사용
→ 서브도메인
→ 세션 쿠키
→ JS 토큰 관리 최소화
→ 서버 중심 인증
```

## 핵심

주의:

> "세션 인증이 토큰 인증보다 무조건 안전하다"라고 말하지 않는다.

정확한 방향:

- 프론트 JS에서 인증 정보를 직접 관리하는 범위를 줄임
- HttpOnly/Secure cookie 사용 가능
- 인증 상태를 서버 중심으로 관리

## 꼬꼬무

### JWT와 비교하면?

무엇이 더 안전하냐가 아니라 **상태를 어디에 두느냐**의 차이라고 봅니다.

|        | 세션                  | JWT                                           |
| ------ | --------------------- | --------------------------------------------- |
| 상태   | 서버가 보관           | 토큰 자체에 담김                              |
| 무효화 | 서버에서 즉시 가능    | 만료 전 무효화가 어려움(별도 블랙리스트 필요) |
| 확장   | 세션 저장소 공유 필요 | 서버가 상태를 안 가져도 됨                    |

저희는 기존 인증 체계를 그대로 재사용해야 했고, 로그아웃·강제 만료 같은 제어가 서버에서 즉시 되는 게 중요해서 세션 쪽이 자연스러웠습니다. JWT가 틀렸다는 뜻은 아닙니다.

### HttpOnly의 장점은?

`HttpOnly` 쿠키는 **JavaScript에서 읽을 수 없습니다**(`document.cookie`로 접근 불가).

XSS가 발생했을 때 공격 스크립트가 토큰을 그대로 긁어가는 경로를 막아줍니다. 반대로 `localStorage`에 토큰을 두면 XSS 한 번에 그대로 유출됩니다.

주의할 점은 **XSS 자체를 막아주진 않는다**는 것입니다. 스크립트가 실행되면 쿠키를 못 읽어도 사용자의 권한으로 요청을 보낼 수는 있습니다.

### Secure는?

`Secure` 속성이 붙은 쿠키는 **HTTPS 연결에서만 전송**됩니다.

평문 HTTP로 나가는 요청에 쿠키가 실려서 중간에서 탈취되는 상황을 막습니다. 운영 환경에서는 인증 쿠키에 기본으로 붙인다고 보면 됩니다.

### SameSite는?

쿠키를 **다른 사이트에서 시작된 요청에 실어 보낼지**를 정합니다.

- `Strict`: 크로스 사이트 요청엔 전혀 안 보냄. 외부 링크로 들어오면 로그인 안 된 것처럼 보일 수 있음
- `Lax`: 최상위 내비게이션(링크 클릭 등)에만 보냄. 요즘 브라우저 기본값
- `None`: 항상 보냄. 반드시 `Secure` 필요

CSRF에 대한 1차 방어선이지만 이것만으로 충분하다고 보진 않습니다.

### CSRF는?

사용자가 이미 로그인된 상태를 이용해, 공격자 사이트가 사용자의 브라우저로 **의도하지 않은 요청**을 보내게 만드는 공격입니다. 쿠키가 자동으로 실려 나가기 때문에 성립합니다.

방어는 보통 겹쳐서 씁니다.

1. `SameSite=Lax/Strict`
2. CSRF 토큰(요청 본문/헤더에 넣고 서버에서 대조)
3. 상태를 바꾸는 요청은 GET으로 만들지 않기
4. Origin/Referer 검증

### XSS는?

공격자가 주입한 스크립트가 **우리 오리진에서 실행**되는 문제입니다. 실행되는 순간 사실상 그 사용자로서 무엇이든 할 수 있습니다.

- 사용자 입력을 그대로 HTML로 넣지 않습니다. React는 기본적으로 이스케이프하지만 `dangerouslySetInnerHTML`은 예외입니다
- 마크다운/리치텍스트를 렌더링해야 하면 sanitize를 거칩니다
- CSP로 실행 가능한 스크립트 출처를 제한합니다

`HttpOnly`는 피해를 줄여주는 장치지 XSS의 해결책은 아닙니다.

### 쿠키 만료와 갱신은?

만료는 두 가지가 있습니다. 브라우저를 닫으면 사라지는 **세션 쿠키**와, `Max-Age`/`Expires`가 붙은 **영속 쿠키**입니다.

갱신은 보통 두 방식입니다.

- 요청이 있을 때마다 만료를 밀어주는 sliding 방식 — 계속 쓰면 로그인이 유지됨
- 짧은 액세스 + 별도 갱신 수단 — 만료를 짧게 가져가되 재발급으로 이어붙임

어느 쪽이든 **만료를 서버가 판단하고 클라이언트는 결과만 반영하게** 두는 게 중요하다고 봤습니다.

### 서브도메인 간 cookie domain은?

`Domain=example.com`으로 설정하면 `a.example.com`, `b.example.com` 모두에 전송됩니다. 저희는 여러 서비스 도메인이 같은 인증을 공유해야 해서 이 방식이 맞았습니다.

주의할 점은 **범위가 넓어질수록 위험도 같이 넓어진다**는 것입니다. 서브도메인 하나가 뚫리면 그 쿠키를 공유하는 전체가 영향을 받습니다. 그래서 쿠키를 공유해야 하는 범위를 필요한 만큼만 잡는 게 중요합니다.

# 7. Reverse Proxy

## 암기 흐름

```text
100개+ 도메인
→ 하나의 Backend API
→ CORS 관리 복잡
→ 대안 검토
→ Next proxy
→ 단순성 선택
→ hop/장애 trade-off
```

## 문제

- 100개가 넘는 서비스 도메인
- 하나의 Backend API
- Backend CORS allowlist에서 계속 관리하면 운영 포인트 증가

## 대안

1. Backend CORS 관리
2. Nginx / Gateway 등 인프라 프록시
3. 기존 Next 서버 proxy

## 선택 이유

- 기존 Next 서버 활용
- 추가 인프라 구성 최소화
- 일관된 API 경로
- Backend 설정 변경 감소

## Trade-off

- API hop 증가
- Next 서버 부하
- 장애 지점 증가

## 솔직한 한계

사용자 측에서는 장애 페이지와 재시도 흐름을 제공했지만, 완전한 장애 격리 구조까지 만들었다고 과장하지 않는다.

## 꼬꼬무

### 왜 CORS 100개 관리가 문제인가요?

기술적으로 어려워서가 아니라 **운영 포인트가 계속 늘어나기 때문**입니다.

도메인이 하나 추가될 때마다 백엔드 allowlist를 수정하고 배포해야 합니다. 프론트에서 도메인을 붙이는 작업인데 백엔드 배포가 선행 조건이 되고, 누락되면 그 도메인만 조용히 실패합니다.

즉 "설정이 어렵다"가 아니라 **변경 주기가 다른 두 시스템이 서로 묶인다**는 게 문제였습니다.

### API Gateway는 왜 안 썼나요?

기능적으로는 더 맞는 선택일 수 있습니다. 인증, 레이트 리밋, 라우팅을 한 곳에서 다루기 좋으니까요.

선택하지 않은 이유는 **추가 인프라와 그 운영 비용**이었습니다. Gateway를 하나 세우면 설정·배포·모니터링·장애 대응이 새로 생깁니다. 당시엔 이미 Next 서버가 모든 도메인 앞단에 있었고, 프록시로 쓰면 새 컴포넌트 없이 목적을 달성할 수 있었습니다.

규모가 더 커지거나 인증·정책이 복잡해지면 다시 검토할 지점이라고 생각합니다.

### Nginx는?

같은 이유입니다. Nginx나 인프라 레벨 프록시가 성능과 격리 면에서는 유리합니다. 애플리케이션 서버를 거치지 않으니 hop이 애플리케이션 런타임을 타지 않습니다.

다만 그 설정을 관리할 주체와 배포 파이프라인이 따로 필요했고, 당시 규모에서는 **단순함의 이득이 더 크다**고 판단했습니다.

### latency는 얼마나 늘었나요?

정확한 수치는 측정해서 관리하지 않았습니다. 숫자를 말하면 지어내는 게 됩니다.

구조적으로 늘어나는 건 명확합니다. 브라우저 → Next 서버 → 백엔드로 hop이 하나 늘고, Next 서버가 같은 리전에 있느냐에 따라 왕복 시간이 더해집니다.

다시 한다면 프록시 도입 전후로 API 응답 시간을 남겨서 근거를 갖고 말할 수 있게 할 것 같습니다.

### Next 서버 죽으면?

**API 호출도 같이 막힙니다.** 프록시를 애플리케이션 서버에 얹었을 때의 가장 큰 대가입니다.

사용자 쪽에서는 장애 페이지와 재시도 흐름을 제공했지만, 완전한 장애 격리 구조를 만들었다고 말하면 과장입니다.

격리가 중요해지면 프록시를 애플리케이션에서 떼어내 인프라 레벨로 내리는 게 맞는 방향이라고 봅니다.

### cookie forwarding은?

프록시가 중간에 끼면 **브라우저 → 프록시**와 **프록시 → 백엔드**가 별개의 요청이라, 인증 쿠키를 그대로 넘겨주지 않으면 백엔드는 비로그인 요청으로 봅니다.

그래서 들어온 요청의 인증 관련 헤더를 백엔드 요청에 옮겨 붙여야 합니다. 이때 주의할 점은 **무엇을 넘길지 명시적으로 정하는 것**입니다. 요청 헤더를 통째로 전달하면 `host` 같은 헤더 때문에 백엔드가 다르게 동작하거나, 넘기면 안 되는 정보가 같이 나갈 수 있습니다.

### Set-Cookie는?

반대 방향에도 같은 문제가 있습니다. 백엔드가 내려준 `Set-Cookie`를 프록시가 브라우저 응답으로 다시 내려주지 않으면 로그인이 성립하지 않습니다.

그리고 도메인이 바뀌기 때문에 쿠키의 `Domain`/`Path` 속성이 브라우저에서 그대로 유효한지 확인해야 합니다. 백엔드 도메인 기준으로 내려온 쿠키는 사용자 도메인에서 저장되지 않을 수 있습니다.

### timeout은?

프록시가 무한정 기다리면 Next 서버의 커넥션이 묶여서, 백엔드 지연이 곧 프론트 전체 장애로 번집니다.

그래서 백엔드 호출에 상한을 두고, 초과하면 실패로 처리해 사용자에게 재시도 흐름을 보여주는 쪽이 낫다고 봅니다. **프록시의 타임아웃은 백엔드보다 짧거나 같아야** 프록시 쪽이 먼저 정리됩니다.

### retry는 어디까지 하나요?

기준은 두 가지입니다.

1. **재시도해도 안전한 요청인가** (조회성 요청, 멱등한 요청)
2. **재시도로 해결될 수 있는 실패인가** (네트워크 오류, 일시적 5xx / 4xx는 재시도해도 그대로)

그리고 무한 재시도는 백엔드가 힘들 때 부하를 더 얹는 방향이라, 횟수를 제한하고 간격을 벌리는 형태가 안전합니다.

### idempotent 요청이 아닌 POST도 retry하나요?

기본적으로 하지 않습니다. 요청이 실제로는 처리됐는데 응답만 못 받은 경우 **중복 생성**이 발생합니다.

꼭 재시도해야 한다면 서버가 중복을 식별할 수 있어야 합니다. 클라이언트가 요청마다 고유 키를 만들어 보내고 서버가 같은 키의 요청을 한 번만 처리하는 방식(idempotency key)이 일반적인 해법입니다.

그런 장치가 없다면 재시도는 사용자에게 맡기고, UI에서 무슨 일이 있었는지 알려주는 편이 낫다고 봤습니다.

### 다시 만든다면 구조를 바꿀 건가요?

지금 규모에서 같은 상황이라면 같은 선택을 할 것 같습니다. 추가 인프라 없이 문제를 해결한 게 당시엔 합리적이었습니다.

다만 두 가지는 처음부터 다르게 하겠습니다.

1. **프록시 전후 응답 시간을 남겨서** trade-off를 숫자로 설명할 수 있게 만들기
2. 트래픽이 커지는 시점을 미리 정해두고, 그때 프록시를 인프라 레벨로 내리는 계획을 같이 잡기

# 8. React스럽게 코드를 작성한다는 것

## 한 줄

> UI를 직접 조작하는 것이 아니라 상태와 props의 결과로 선언적으로 표현하는 것.

## 핵심 키워드

```text
선언적
단방향 데이터 흐름
최소 상태
derived state
effect 최소화
composition
```

## 답변

저는 React스럽게 코드를 작성한다는 건 UI를 상태의 결과로 표현하는 것이라고 생각합니다.

DOM을 직접 변경해서 화면을 맞추기보다 state와 props를 기준으로 어떤 UI가 보여야 하는지를 선언적으로 작성합니다.

또 계산할 수 있는 값을 별도 state로 중복 저장하지 않고, 외부 시스템과 동기화가 필요한 경우가 아니라면 useEffect를 최소화합니다.

컴포넌트도 하나가 너무 많은 책임을 가지기보다는 합성과 역할 분리를 통해 재사용 가능한 구조를 만드는 걸 중요하게 생각합니다.

## 꼬꼬무

### 선언적이라는 게 정확히 뭔가요?

**"어떻게 바꿀지"가 아니라 "지금 상태면 무엇이 보여야 하는지"를 쓰는 것**입니다.

명령형은 `if (열림) modal.style.display = 'block'`처럼 변화 과정을 직접 지시합니다. 이러면 상태 조합이 늘어날 때마다 "이 경우엔 무엇을 되돌려야 하지"를 사람이 추적해야 합니다.

선언적으로 쓰면 `{isOpen && <Modal />}`처럼 결과만 기술하고, 이전 상태에서 지금 상태로 가는 과정은 React가 처리합니다. 상태가 늘어나도 사람이 추적할 게 늘지 않는다는 게 핵심 이점입니다.

### derived state 예를 들어보세요.

목록과 검색어가 있을 때, 필터링된 목록을 **별도 state로 두지 않는 것**입니다.

```tsx
// 중복 저장: items나 keyword가 바뀔 때마다 동기화 코드가 필요하다
const [filtered, setFiltered] = useState(items);

// 파생: 항상 최신이고 동기화할 게 없다
const filtered = items.filter((item) => item.name.includes(keyword));
```

state를 두 개 두면 둘이 어긋나는 순간이 반드시 생깁니다. 계산할 수 있는 값은 계산합니다.

### useEffect는 언제 쓰나요?

**React 바깥 세계와 동기화할 때**만 씁니다.

- 구독 등록/해제 (`addEventListener`, WebSocket, `IntersectionObserver`)
- 브라우저 API 조작 (문서 타이틀, 포커스)
- 외부 저장소 동기화

반대로 이런 건 effect가 아닙니다.

- props/state로 계산 가능한 값 → 그냥 계산
- 사용자 행동에 대한 반응 → 이벤트 핸들러
- 렌더링 결과에 따라 다른 state를 맞추는 것 → 구조를 잘못 잡은 신호

### useEffect 없이 API 호출 가능한가요?

가능하고, 지금은 그쪽이 기본에 가깝습니다.

- **서버 컴포넌트**에서 렌더링 시점에 직접 가져오기
- **React Query** 같은 라이브러리에 위임하기. 캐시, 중복 제거, 재시도, 무효화를 직접 짜지 않아도 됩니다
- 사용자 행동으로 발생하는 요청은 **이벤트 핸들러**에서

`useEffect` + `fetch`를 직접 쓰면 경쟁 상태, 취소, 중복 요청, 로딩/에러 상태를 전부 직접 관리해야 해서 실수가 나기 쉽습니다.

### state colocation이 뭔가요?

**상태를 그 상태를 쓰는 곳에서 가장 가까이 두는 것**입니다.

모달 열림 여부처럼 한 컴포넌트 안에서 끝나는 상태를 최상위로 올려두면, 관련 없는 컴포넌트까지 리렌더 대상이 되고 그 상태가 어디서 쓰이는지 추적하기 어려워집니다.

기본값은 "일단 가장 가까운 곳에 두고, 공유가 필요해지면 그때 올린다"입니다.

### lifting state up은?

두 형제 컴포넌트가 같은 상태를 봐야 할 때 **공통 부모로 상태를 올리는 것**입니다.

주의할 점은 무한정 올리면 안 된다는 것입니다. 계속 올리다 보면 최상위가 모든 상태를 들고 있게 되고 prop drilling이 시작됩니다.

그 선을 넘어야 한다면 상태의 성격을 다시 봅니다. 서버 데이터면 React Query, 여러 화면이 공유하는 client state면 전역 스토어, 공유·복원이 필요하면 URL이 더 맞는 자리일 수 있습니다.

### controlled / uncontrolled 차이는?

값의 **주인이 누구인가**의 차이입니다.

- **controlled**: React state가 값을 소유하고 `value` + `onChange`로 관리. 입력을 즉시 검증·변형하거나 다른 UI와 연동해야 할 때
- **uncontrolled**: DOM이 값을 소유하고 필요할 때 `ref`나 폼 제출로 읽음. 입력마다 리렌더가 없어서 큰 폼에서 유리

한 입력에 두 방식을 섞으면(초기엔 `defaultValue`, 나중에 `value`) 경고가 나고 동작이 꼬입니다.

### custom hook은 언제 만드나요?

**상태 로직이 반복될 때** 만듭니다. UI를 묶으려고 만들지 않습니다.

기준은 두 가지입니다.

1. 같은 상태 + effect 조합이 두 곳 이상에서 반복되는가
2. 훅 이름으로 그 로직의 의도를 설명할 수 있는가 (`useDebounce`, `useIntersection`)

한 곳에서만 쓰는 로직을 미리 훅으로 빼는 건 추상화만 늘어나는 경우가 많아서 하지 않습니다.

### useMemo는 언제 쓰나요?

두 경우입니다.

1. **계산 자체가 무거울 때** (큰 배열 정렬/필터)
2. **참조 동일성이 필요할 때** — `memo`된 자식의 props나 다른 훅의 의존성 배열로 들어가는 객체/배열

반대로 단순 계산에 붙이는 건 의미가 없습니다. `useMemo`도 비교 비용과 메모리를 쓰고, 무엇보다 코드를 읽기 어렵게 만듭니다.

순서는 **먼저 불필요한 리렌더의 원인을 없애고, 그래도 남으면 측정한 뒤 붙이는 것**이라고 생각합니다.

# 9. 상태관리

## 먼저 나누기

```text
Local State
Global Client State
Server State
URL State
```

## useState

- 해당 컴포넌트 또는 가까운 트리에서만 사용
- 가장 먼저 고려

## Context

- theme
- auth context
- 저빈도 전역값

주의:

> 모든 전역 상태를 Context로 처리하지 않는다.

## Zustand

- 가벼운 global client state
- 비교적 간단한 API
- 자유도가 높음

단점:

- 기준 없이 쓰면 store 비대화
- server state까지 넣기 쉬움

## Redux

장점:

- 명확한 흐름
- tooling
- 큰 규모의 상태 관리

단점:

- 구조와 boilerplate 증가 가능

## TanStack Query

> client global state 라이브러리라기보다 server state 관리 도구로 설명.

- cache
- stale
- refetch
- retry
- mutation
- invalidation

## URL State

- 검색 조건
- filter
- pagination
- 공유 가능한 상태
- 뒤로가기 복원

## 좋은 답변

라이브러리부터 고르기보다 상태가 어디에서 생성되고 누가 소유해야 하는지를 먼저 봅니다.

서버에서 오는 데이터는 TanStack Query, 여러 화면에서 공유해야 하는 client state는 Zustand, 특정 UI 안에서 끝나는 상태는 useState처럼 상태의 성격에 따라 선택합니다.

# 10. 브라우저 뒤로가기 / History API

## 핵심 키워드

```text
session history
pushState
replaceState
popstate
URL state
SPA
```

## 개념

브라우저는 현재 탭의 탐색 이력을 session history로 관리한다.

SPA에서는:

```js
history.pushState();
history.replaceState();
```

로 페이지 전체 reload 없이 URL과 history entry를 변경할 수 있다.

사용자가 뒤로가기를 하면 이전 history entry로 이동하고 상황에 따라 `popstate`가 발생한다.

## 실무 포인트

검색/필터 상태를 local state에만 두면:

- URL과 UI 불일치
- 뒤로가기 복원 실패
- 공유 불가능

그래서 공유/복원이 필요한 상태는 URL을 source of truth로 둘 수 있다.

## 꼬꼬무

### pushState와 replaceState 차이?

- `pushState`: history에 **새 항목을 추가**합니다. 뒤로가기를 누르면 이전 상태로 돌아옵니다
- `replaceState`: **현재 항목을 덮어씁니다**. 뒤로가기 스택이 늘지 않습니다

기준은 "사용자가 뒤로가기로 이 상태로 돌아오고 싶어할까"입니다. 페이지 이동이나 필터 적용은 `push`, 검색어 타이핑 중간값이나 스크롤 위치 저장은 `replace`가 맞습니다.

타이핑마다 `pushState`를 하면 뒤로가기를 스무 번 눌러야 이전 화면으로 돌아가는 상황이 됩니다.

### popstate는 pushState 때도 발생하나요?

**발생하지 않습니다.** `pushState`/`replaceState`는 `popstate`를 트리거하지 않습니다.

`popstate`는 사용자가 history를 **이동할 때**(뒤로/앞으로, `history.back()` 등) 발생합니다. 그래서 직접 URL을 바꾼 경우엔 그 시점에 상태를 함께 갱신해줘야 하고, `popstate`는 "브라우저가 나 대신 이동시켰다"는 신호로 처리합니다.

### hashchange와 차이는?

`hashchange`는 URL의 `#` 뒤 부분이 바뀔 때만 발생합니다. History API 이전에 SPA 라우팅을 하던 방식입니다.

차이는 두 가지입니다.

- **서버가 해시를 못 봅니다.** `#` 뒤는 요청에 포함되지 않아서 SSR이나 서버 라우팅이 불가능합니다
- History API는 실제 경로를 바꾸므로 SEO·공유·서버 렌더링에 모두 유리합니다

대신 History API를 쓰면 어떤 경로로 직접 들어와도 서버가 응답할 수 있어야 합니다.

### Next router는 무엇을 해주나요?

History API를 직접 다루지 않아도 되게 감싸줍니다.

- `<Link>`/`router.push`가 내부적으로 history 항목을 관리하고 `popstate`를 처리합니다
- 이동할 페이지의 코드와 데이터를 **미리 가져옵니다**(prefetch)
- App Router에서는 이동 시 필요한 서버 컴포넌트 부분만 받아와서 갈아끼웁니다
- 스크롤 위치 복원을 기본 처리합니다

직접 구현하면 이 중 상당수를 손으로 만들어야 합니다.

### URL state의 단점은?

- **길이 제한과 가독성.** 상태가 많아지면 URL이 지저분해지고 브라우저·서버마다 상한이 있습니다
- **민감한 값을 넣으면 안 됩니다.** URL은 로그, 히스토리, Referer로 새어 나갑니다
- **타입이 없습니다.** 전부 문자열이라 파싱과 검증이 필요하고, 사용자가 손으로 고칠 수 있으니 신뢰할 수 없는 입력으로 다뤄야 합니다
- 변경 빈도가 높은 상태에는 부적합합니다

그래서 **공유·복원이 필요한 상태만** URL에 둡니다.

### history.state에는 뭘 넣을 수 있나요?

structured clone이 가능한 값이면 들어갑니다. 객체, 배열, 원시값은 되고 함수나 DOM 노드, 클래스 인스턴스는 안 됩니다.

브라우저마다 크기 제한이 있어서 **데이터 저장소로 쓰기엔 적합하지 않습니다.** 목록 데이터를 통째로 넣기보다 스크롤 위치나 직전 화면 식별자처럼 복원에 필요한 최소 정보만 두는 게 안전합니다.

# 11. Hydration

## 한 줄

> 서버에서 만들어진 HTML에 클라이언트 React가 상태와 이벤트를 연결해 interactive하게 만드는 과정.

## 흐름

```text
Server
→ HTML 생성
→ Browser 표시
→ JS 다운로드
→ React 실행
→ 기존 HTML과 연결
→ interactive
```

## Hydration mismatch 원인

서버 렌더링 결과와 클라이언트 최초 렌더 결과가 다르면 발생.

예:

- Date.now()
- Math.random()
- window
- localStorage 값
- timezone 기반 값

## 꼬꼬무

### SSR과 hydration 차이?

SSR은 **서버에서 HTML을 만드는 단계**이고, hydration은 그 HTML에 **클라이언트 React가 붙는 단계**입니다.

SSR만 끝난 시점의 화면은 보이지만 눌러도 반응하지 않습니다. hydration이 끝나야 이벤트 핸들러와 상태가 연결되어 상호작용이 됩니다.

즉 순서상 SSR → (HTML 표시) → JS 로드 → hydration → interactive입니다.

### hydration이 필요한 이유?

서버가 만든 건 **결과 HTML일 뿐 상태와 핸들러가 없기 때문**입니다.

React는 클라이언트에서 같은 컴포넌트 트리를 한 번 더 그려보고, 이미 있는 DOM과 대응시켜서 이벤트 핸들러를 붙이고 상태를 연결합니다. 이 과정을 건너뛰면 화면은 보이는데 아무것도 동작하지 않습니다.

이렇게 하는 이유는 **첫 화면을 빨리 보여주면서도 상호작용을 포기하지 않기 위해서**입니다.

### CSR에는 hydration이 있나요?

없습니다. CSR은 빈 HTML을 받고 JS가 DOM을 처음부터 만들기 때문에 맞춰야 할 기존 DOM이 없습니다.

그래서 CSR엔 mismatch 문제도 없지만, 대신 JS가 실행되기 전까지 아무것도 보이지 않습니다.

### mismatch를 어떻게 해결하나요?

원인은 항상 하나입니다. **서버 렌더 결과와 클라이언트 첫 렌더 결과가 다른 것.**

- `Date.now()`, `Math.random()`처럼 매번 값이 달라지는 것 → 값을 서버에서 만들어 props로 내려보냅니다
- `window`, `localStorage`, 타임존 기반 값 → 첫 렌더에서는 서버와 같은 값을 그리고, `useEffect` 이후에 갱신합니다
- 정말 클라이언트에서만 의미 있는 부분은 dynamic import로 SSR을 끄거나 마운트 이후 렌더합니다

주의할 건 `suppressHydrationWarning`은 경고만 숨길 뿐 원인을 고치지 않는다는 점입니다.

### Client Component와 관계는?

App Router에서 hydration 대상은 **Client Component뿐**입니다.

Server Component는 서버에서 렌더된 결과만 전달되고 클라이언트 번들에 포함되지 않습니다. 그래서 `'use client'`를 트리 위쪽에 붙이면 그 아래 전체가 클라이언트 컴포넌트가 되어 hydration 대상과 번들이 같이 커집니다.

`'use client'`를 가능한 말단에 두는 이유가 이것입니다.

### hydration 비용은?

세 가지가 겹칩니다.

1. **JS 다운로드/파싱** — 번들이 클수록 늦어집니다
2. **트리 재실행** — 클라이언트에서 컴포넌트를 한 번 더 렌더합니다
3. **그동안의 입력 무반응** — 화면은 보이는데 눌러도 안 되는 구간이 생깁니다

줄이는 방향은 클라이언트 컴포넌트 범위를 좁히는 것, 무거운 컴포넌트를 필요한 시점에 로드하는 것, 그리고 애초에 서버에서 끝낼 수 있는 부분을 Server Component로 두는 것입니다.

# 12. 브라우저 렌더링 / CSS 성능

## 렌더링 파이프라인

```text
HTML → DOM
CSS → CSSOM
DOM + CSSOM → Render Tree
→ Layout
→ Paint
→ Composite
```

## 성능 개선 방향

- 불필요한 DOM 줄이기
- unused CSS 줄이기
- layout thrashing 피하기
- 애니메이션은 가능하면 transform / opacity 활용
- 큰 화면은 content-visibility 고려
- 측정 후 최적화

## 주의

```text
transform = 무조건 GPU
```

라고 말하지 않는다.

## 꼬꼬무

### reflow와 repaint 차이는?

- **reflow(layout)**: 요소의 위치나 크기를 다시 계산합니다. `width`, `height`, `top`, `font-size`, DOM 추가/삭제 등이 유발합니다. 한 요소가 바뀌면 주변·자식까지 영향을 받아 비용이 큽니다
- **repaint**: 위치는 그대로고 픽셀만 다시 칠합니다. `color`, `background-color`, `visibility` 등

reflow가 일어나면 repaint도 따라옵니다. 반대는 아닙니다. 그래서 애니메이션에서 레이아웃을 건드리는 속성을 바꾸는 걸 피합니다.

### layout thrashing이 뭔가요?

**쓰기와 읽기를 번갈아 하면서 강제로 레이아웃 계산을 반복시키는 것**입니다.

```js
// 나쁨: 매 반복마다 강제 동기 레이아웃
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px';
}
```

브라우저는 스타일 변경을 모아서 처리하려 하는데, `offsetWidth`처럼 레이아웃 결과가 필요한 값을 읽으면 그 자리에서 계산을 강제합니다.

해결은 **읽기를 먼저 다 하고, 쓰기를 나중에 몰아서** 하는 것입니다.

### requestAnimationFrame은?

브라우저의 **다음 화면 갱신 직전에 콜백을 실행**해 달라고 예약하는 API입니다.

`setTimeout(fn, 16)`과 달리 화면 주사율에 맞춰 호출되고, 탭이 백그라운드면 호출되지 않아 불필요한 작업을 하지 않습니다.

용도는 두 가지입니다. JS로 프레임 단위 애니메이션을 만들 때, 그리고 여러 DOM 쓰기를 한 프레임으로 모을 때.

### will-change는?

"이 속성이 곧 바뀔 테니 미리 준비해라"라고 브라우저에 알리는 힌트입니다. 보통 해당 요소를 별도 레이어로 승격시킵니다.

주의할 점이 많습니다.

- **레이어마다 메모리를 씁니다.** 남발하면 오히려 느려집니다
- 상시로 켜두면 안 되고, 애니메이션 직전에 켜고 끝나면 제거하는 게 원칙입니다
- 이미 부드럽게 도는 애니메이션에 붙일 이유는 없습니다

### transform이 항상 빠른가요?

아닙니다. **"transform은 무조건 GPU라 빠르다"는 과장입니다.**

`transform`/`opacity`가 유리한 이유는 레이아웃과 페인트를 건너뛰고 합성 단계에서 처리될 **수 있기** 때문이지, 항상 그렇게 되는 건 아닙니다. 레이어 승격 조건에 따라 달라지고, 레이어가 많아지면 합성 비용과 메모리가 늘어 오히려 느려질 수 있습니다.

정확하게는 "레이아웃을 유발하는 속성보다 유리한 경우가 많다" 정도로 말하고, 실제로는 측정해서 확인합니다.

### CSS selector가 성능에 얼마나 중요한가요?

**요즘은 대부분 병목이 아닙니다.**

과거엔 후손 선택자가 느리다는 얘기가 많았지만, 브라우저 최적화가 좋아져서 일반적인 규모에서는 체감 차이가 나지 않습니다.

실제 병목은 보통 다른 곳입니다.

- 사용하지 않는 CSS가 잔뜩 실려서 전송·파싱 비용이 큰 것
- DOM 노드 수가 지나치게 많은 것
- 레이아웃을 유발하는 애니메이션

그래서 선택자를 다듬기 전에 **어디가 느린지 먼저 측정한다**고 답하는 게 맞다고 봅니다.

# 13. 외부 API를 3번 호출할 때

## 첫 질문

> 세 요청이 서로 의존적인가?

## 독립적

```js
await Promise.all([apiA(), apiB(), apiC()]);
```

## 의존적

A의 결과가 B에 필요하다면 완전 병렬화 불가.

## 개선 순서

```text
의존성 확인
→ 병렬화
→ 중복 호출 제거
→ cache
→ prefetch
→ BFF aggregation
→ progressive UI
```

## 꼬꼬무

### Promise.all 중 하나 실패하면?

**즉시 reject됩니다.** 첫 번째 실패가 그대로 전체 결과가 됩니다.

주의할 점은 나머지 요청이 취소되지는 않는다는 것입니다. 이미 보낸 요청은 계속 진행되고 결과만 버려집니다. 그래서 처리되지 않은 rejection이 남지 않게 신경 써야 합니다.

세 API 중 하나가 실패해도 화면의 나머지는 보여줘야 한다면 `Promise.all`은 맞지 않습니다.

### Promise.allSettled는?

**모든 프로미스가 끝날 때까지 기다리고, 각각의 성공/실패를 배열로 돌려줍니다.**

```js
const results = await Promise.allSettled([apiA(), apiB(), apiC()]);
// [{status:'fulfilled', value}, {status:'rejected', reason}, ...]
```

일부가 실패해도 나머지를 렌더링해야 하는 화면에 적합합니다. 대신 호출한 쪽에서 각 결과의 상태를 직접 확인해야 하고, 실패한 영역을 UI에서 어떻게 보여줄지 결정해야 합니다.

### API 하나만 느리면?

먼저 그 응답이 **첫 화면에 꼭 필요한지**를 봅니다.

- 필요 없다면 → 나머지를 먼저 렌더하고 느린 부분만 나중에 채웁니다 (Suspense, 스트리밍, 로딩 스켈레톤)
- 필요하다면 → 왜 느린지 봅니다. 백엔드 쿼리 문제인지, 응답이 과하게 큰지, 네트워크 왕복이 많은지

그리고 **타임아웃을 둡니다.** 하나가 무한정 기다리면 전체 화면이 인질이 됩니다.

전부 다 모아서 한 번에 보여주는 것보다 **먼저 보여줄 수 있는 걸 먼저 보여주는 게** 체감상 훨씬 빠릅니다.

### BFF를 만들면 장점/단점?

**장점**

- 클라이언트가 요청 한 번으로 필요한 데이터를 받습니다. 왕복 횟수와 waterfall이 줄어듭니다
- 화면에 필요한 형태로 가공해서 내려줄 수 있어 클라이언트가 가벼워집니다
- 여러 백엔드의 차이를 한 곳에서 흡수합니다

**단점**

- 배포하고 운영할 서버가 하나 늘어납니다. 장애 지점도 늘어납니다
- 화면이 바뀔 때마다 BFF도 같이 바꿔야 해서 배포 결합이 생깁니다
- 캐시 전략이 한 겹 더 복잡해집니다

저희가 프록시를 도입할 때와 같은 종류의 판단입니다. 단순함과 통제력 사이의 trade-off입니다.

### cache stale 문제는?

캐시는 **오래된 데이터를 보여줄 위험을 감수하고 속도를 얻는 것**입니다. 그래서 데이터마다 허용 가능한 낡음의 정도를 정하는 게 먼저입니다.

- 거의 안 바뀌는 데이터(카테고리 목록) → 길게 캐시
- 자주 바뀌지만 조금 늦어도 되는 데이터 → stale-while-revalidate. 캐시를 먼저 주고 뒤에서 갱신
- 항상 최신이어야 하는 데이터(잔액, 재고) → 캐시하지 않거나 매우 짧게

그리고 **변경이 일어난 쪽에서 무효화**하는 게 핵심입니다. 시간 만료에만 의존하면 사용자가 방금 수정한 값이 이전 값으로 보이는 상황이 생깁니다.

### retry는?

기준은 두 가지입니다.

1. **재시도해도 안전한가** — 조회는 안전하고, 생성/결제 같은 요청은 중복 위험이 있습니다
2. **재시도로 해결될 실패인가** — 네트워크 오류나 일시적 5xx는 가능하고, 4xx는 몇 번을 보내도 같습니다

그리고 즉시 반복하면 이미 힘든 서버에 부하를 더 얹으므로 간격을 점점 벌리는 형태가 안전합니다. 횟수 제한은 반드시 둡니다.

### waterfall을 어떻게 찾나요?

브라우저 개발자도구 Network 탭에서 요청들의 **시작 시점이 계단처럼 밀려 있는지**를 봅니다. 동시에 출발했어야 할 요청들이 순차적으로 시작하고 있으면 waterfall입니다.

코드에서 자주 나오는 원인은 두 가지입니다.

```js
// 순차: B는 A가 끝난 뒤에 시작한다
const a = await apiA();
const b = await apiB();

// 병렬: 동시에 출발한다
const [a, b] = await Promise.all([apiA(), apiB()]);
```

그리고 **컴포넌트 계층에 의한 waterfall**도 있습니다. 부모가 데이터를 받아 렌더한 뒤에야 자식이 자기 데이터를 요청하는 구조입니다. 이 경우 요청을 위로 올리거나 미리 가져오는 방식으로 풉니다.

# 14. 이미지 최적화

## 문제를 둘로 나눈다

### 저장 비용

- 업로드 resize
- compression
- EXIF 제거
- 필요 시 원본 보관 정책

### 전송 비용

- WebP / AVIF
- responsive image
- srcset / sizes
- lazy loading
- CDN
- cache

## 답변 흐름

```text
원본 정책
→ 저장 시 최적화
→ 용도별 size 생성
→ modern format
→ CDN
→ device별 적절한 이미지 전달
```

## 꼬꼬무

### WebP와 AVIF 차이?

둘 다 JPEG/PNG보다 같은 화질에서 용량이 작은 최신 포맷입니다.

- **WebP**: 더 오래됐고 지원 범위가 넓습니다. 인코딩이 빠릅니다
- **AVIF**: 압축률이 더 좋습니다(특히 저용량 구간). 대신 **인코딩이 훨씬 느리고 CPU를 많이 씁니다**

그래서 보통 둘 중 하나를 고르기보다 `<picture>`나 CDN의 콘텐츠 협상으로 **브라우저가 지원하는 최적 포맷을 내려주고 원본 포맷을 fallback으로** 둡니다.

### 원본은 버릴 건가요?

버리지 않는 쪽을 기본으로 봅니다. 원본을 버리면 나중에 새 포맷이나 새 사이즈가 필요할 때 다시 만들 수 없습니다.

다만 저장 비용이 있으니 절충합니다.

- 업로드 시 과도하게 큰 이미지는 **상한 해상도로 한 번 줄여서** 원본으로 삼습니다
- EXIF의 위치 정보 같은 민감 메타데이터는 제거합니다
- 오래된 원본은 저렴한 스토리지 계층으로 옮깁니다

### 썸네일은 언제 생성하나요?

두 가지 방식이고 트레이드오프가 다릅니다.

- **업로드 시 미리 생성**: 조회가 항상 빠릅니다. 대신 안 쓰일 사이즈까지 만들고 저장하며, 사이즈 정책이 바뀌면 전부 다시 만들어야 합니다
- **요청 시 생성 후 캐시(on-demand)**: 실제 필요한 것만 만듭니다. 대신 첫 요청이 느리고, 임의 파라미터로 무한히 생성되지 않도록 허용 사이즈를 제한해야 합니다

트래픽 패턴이 예측되고 사이즈가 고정이면 미리 생성, 사이즈가 자주 바뀌면 on-demand가 낫다고 봅니다.

### 서버에서 변환하면 CPU 비용은?

이미지 인코딩은 CPU를 많이 씁니다. 특히 AVIF는 눈에 띄게 무겁습니다.

그래서 고려할 점은 이렇습니다.

- 변환을 **요청 처리 경로에서 동기로 하지 않습니다.** 큐로 넘기거나 별도 워커에서 처리합니다
- 한 번 만든 결과는 반드시 캐시해서 재변환을 막습니다
- 동시 변환 수에 상한을 둡니다. 안 그러면 업로드가 몰릴 때 서버 전체가 느려집니다

직접 운영하기 부담되면 CDN이나 이미지 서비스에 위임하는 게 현실적인 선택입니다.

### CDN image transformation은?

URL 파라미터로 사이즈·포맷·품질을 지정하면 **엣지에서 변환하고 캐시해주는** 기능입니다.

- 장점: 변환 인프라를 직접 운영하지 않아도 되고, 결과가 엣지에 캐시돼 사용자와 가깝습니다
- 단점: 비용이 변환/요청 수에 비례하고, 특정 벤더에 URL 형식이 묶입니다. 파라미터 조합이 무한이라 **허용 값을 제한하지 않으면 캐시 미스와 비용이 폭증**합니다

### lazy loading 단점은?

- **스크롤 직후 이미지가 비어 보이는 구간**이 생깁니다. 특히 느린 네트워크에서 체감이 큽니다
- 로드 전 크기를 모르면 이미지가 뜰 때 레이아웃이 밀립니다(CLS). `width`/`height`나 `aspect-ratio`를 지정해야 합니다
- 화면에 곧 들어올 이미지까지 늦게 시작하면 오히려 느려 보입니다

즉 "전부 lazy"는 답이 아니고, **처음 화면 밖에 있는 것에만** 적용하는 게 맞습니다.

### LCP 이미지는 lazy loading 해도 되나요?

**하면 안 됩니다.** LCP 이미지는 첫 화면에서 가장 큰 콘텐츠라, lazy로 두면 발견 자체가 늦어져서 LCP가 직접 나빠집니다.

오히려 반대로 우선순위를 올려줍니다.

- `loading="eager"` (기본값)
- `fetchpriority="high"` 또는 Next의 `priority`
- 필요하면 `<link rel="preload">`로 더 일찍 발견되게 합니다

정리하면 **첫 화면 이미지는 우선 로드, 나머지는 lazy**입니다.

# 15. 해외 사용자에게 동영상 빠르게 전달

## 핵심

```text
Object Storage
→ Transcoding
→ HLS/DASH
→ 여러 bitrate
→ CDN Edge
→ Adaptive Bitrate
```

## 설명

원본 동영상을 그대로 전송하지 않고 다양한 bitrate와 해상도로 transcoding한다.

HLS 또는 DASH처럼 segment 기반 스트리밍으로 제공하고 글로벌 CDN을 사용해 사용자와 가까운 edge에서 segment를 전달한다.

클라이언트는 네트워크 환경에 따라 bitrate를 조정하는 adaptive bitrate streaming을 사용한다.

## 꼬꼬무

### 왜 mp4 한 파일로 안 주나요?

세 가지 문제가 있습니다.

1. **화질이 고정됩니다.** 네트워크가 나빠져도 같은 용량을 계속 받아야 해서 버퍼링이 납니다
2. **시작이 느립니다.** 파일 전체를 받는 구조면 재생까지 대기가 깁니다
3. **모든 사용자에게 같은 품질을 강요합니다.** 모바일 LTE와 유선 환경이 같은 파일을 받습니다

세그먼트 기반 스트리밍은 상황에 따라 중간에 품질을 바꿀 수 있어서 이 문제들이 해결됩니다.

### HLS가 뭔가요?

**HTTP 기반의 적응형 스트리밍 방식**입니다. 영상을 짧은 조각으로 나누고, 어떤 조각들이 있는지 적어둔 플레이리스트(`.m3u8`)를 먼저 내려줍니다.

플레이어는 플레이리스트를 읽고 현재 네트워크에 맞는 품질의 조각부터 순서대로 받아 재생합니다. 일반 HTTP를 쓰기 때문에 **기존 CDN을 그대로 활용**할 수 있다는 게 큰 장점입니다.

DASH도 같은 개념이고 표준과 컨테이너가 다릅니다.

### segment란?

영상을 잘라놓은 **짧은 조각 파일**입니다. 보통 수 초 단위입니다.

조각 길이가 성능을 좌우합니다.

- 짧으면: 품질 전환이 빠르고 시작이 빠릅니다. 대신 요청 수가 많아집니다
- 길면: 요청 수가 줄지만 네트워크가 나빠졌을 때 대응이 늦습니다

그리고 조각 단위이기 때문에 **자주 보는 앞부분만 엣지에 캐시되는** 효과도 자연스럽게 생깁니다.

### CDN cache miss면?

엣지에 없으면 원본(또는 상위 캐시)까지 가져와야 해서 그 조각만 느려집니다. 재생 중이면 버퍼링으로 나타납니다.

완화 방법은 이렇습니다.

- **인기 콘텐츠의 앞부분 조각을 미리 채워둡니다**(prewarm). 시작 구간이 가장 자주 요청됩니다
- 엣지와 원본 사이에 중간 캐시 계층을 둡니다
- 조각 URL을 안정적으로 유지해서 캐시 키가 분산되지 않게 합니다. 쿼리 파라미터가 매번 달라지면 전부 miss가 됩니다

마지막 항목은 signed URL을 쓸 때 특히 주의해야 하는 부분입니다.

### bitrate는 몇 개 만들 건가요?

정답은 없고 **타깃 사용자 환경에 맞춰** 정합니다. 보통 3~5개 정도의 사다리를 만듭니다.

고려할 점은 두 가지입니다.

- 단계가 촘촘하면 전환이 부드럽지만 **인코딩·저장 비용이 배수로** 늘어납니다
- 단계 간 차이가 너무 크면 전환이 눈에 띄게 튑니다

해외 사용자가 많다면 낮은 대역폭 구간을 반드시 포함시켜야 합니다. 그리고 실제 재생 로그를 보고 안 쓰이는 단계는 줄이는 게 맞다고 봅니다.

### 최초 재생 속도는 어떻게 개선?

- **첫 조각을 짧게** 만들어서 재생 시작에 필요한 데이터를 줄입니다
- **낮은 품질로 시작**해서 바로 틀고, 이후 올립니다
- 플레이리스트와 첫 조각을 미리 가져옵니다(preload)
- 인기 콘텐츠의 시작 구간을 엣지에 미리 올려둡니다

핵심은 "좋은 화질로 늦게 시작"보다 **"낮은 화질로 빨리 시작"이 체감이 훨씬 낫다**는 점입니다.

### signed URL은 왜 필요?

영상 파일 URL이 그대로 노출되면 **누구나 퍼가서 재생**할 수 있습니다. 대역폭 비용이 그대로 새고, 유료·비공개 콘텐츠라면 접근 제어가 무너집니다.

signed URL은 만료 시각과 서명을 URL에 넣어서, 정해진 시간 동안 그 사용자에게만 유효하게 만듭니다.

주의할 점은 **서명이 매번 달라지면 CDN 캐시 키도 달라진다**는 것입니다. 그래서 서명을 쿠키로 분리하거나 캐시 키에서 서명 파라미터를 제외하도록 CDN을 설정합니다.

### DRM은?

signed URL은 **접근**을 막지만 다운로드된 뒤의 복제는 막지 못합니다. DRM은 콘텐츠 자체를 암호화하고 재생 시점에 라이선스를 받아야 복호화되도록 해서 그 지점을 막습니다.

다만 비용이 큽니다. 라이선스 서버 운영, 플랫폼별 대응(Widevine/FairPlay/PlayReady), 플레이어 제약이 따라옵니다.

그래서 판단 기준은 **콘텐츠의 가치**입니다. 유료 콘텐츠가 아니라면 signed URL과 짧은 만료로 충분한 경우가 많습니다. 제가 직접 DRM을 구축해본 경험은 없어서, 도입한다면 요구 수준을 먼저 확인할 것 같습니다.

# 16. Sitemap

## 한 줄

> 검색엔진에게 크롤링 대상 URL을 알려주는 XML 목록.

## 정적 사이트

build 시 생성 가능.

## 동적 사이트

DB/API에서 SEO 대상 URL을 가져와 생성.

## URL이 매우 많을 때

```text
sitemap index
→ sitemap-1.xml
→ sitemap-2.xml
...
```

## 같이 생각할 것

- robots.txt
- canonical
- lastModified
- index 대상 여부

## 주의

> sitemap 제출 = 검색 노출 보장 아님.

## 꼬꼬무

### robots.txt와 차이는?

역할이 반대에 가깝습니다.

- **robots.txt**: "여기는 크롤링하지 마라"는 **제한**
- **sitemap**: "여기 있으니 와서 봐라"는 **안내**

그리고 robots.txt로 막은 경로는 크롤러가 접근하지 않으므로, 그 안의 `noindex`도 읽히지 않습니다. **색인에서 빼고 싶으면 robots.txt로 막는 게 아니라 페이지에 `noindex`를 두고 크롤링은 허용**해야 합니다. 이 부분이 자주 혼동됩니다.

### canonical은?

같은 내용이 여러 URL로 존재할 때 **어떤 URL이 대표인지** 알려주는 표시입니다.

정렬 파라미터, 페이지네이션, 추적 파라미터(`?utm_...`), www 유무처럼 사실상 같은 페이지가 여러 주소를 갖는 경우가 흔합니다. 그대로 두면 평가가 분산됩니다.

주의할 점은 canonical은 **강제가 아니라 힌트**라는 것과, sitemap에는 canonical URL만 넣는 게 맞다는 것입니다. sitemap과 canonical이 서로 다른 URL을 가리키면 신호가 충돌합니다.

### 페이지가 백만 개면?

sitemap 한 파일에는 URL 5만 개, 압축 전 50MB라는 상한이 있습니다. 그래서 나눕니다.

```text
sitemap index (최상위)
→ sitemap-1.xml
→ sitemap-2.xml
...
```

실무적으로는 단순히 쪼개는 것보다 **의미 단위로 나누는 게** 낫습니다. 카테고리별, 갱신 주기별로 나누면 어떤 그룹이 색인되고 있는지 파악하기 쉽고, 자주 바뀌는 그룹만 다시 만들면 됩니다.

### 모든 페이지를 sitemap에 넣나요?

아니요. **색인시키고 싶은 페이지만** 넣습니다.

빼는 대상은 이런 것들입니다.

- 로그인, 마이페이지처럼 개인화된 화면
- 검색 결과처럼 조합이 무한한 페이지
- `noindex`를 건 페이지 (sitemap에 넣으면 신호가 모순됩니다)
- 중복 URL (canonical이 아닌 쪽)

가치 없는 URL을 많이 넣으면 크롤링 예산만 낭비됩니다.

### 실시간으로 생성하나요?

요청마다 DB를 전부 훑어 만드는 건 위험합니다. 크롤러가 자주 요청하면 그대로 부하가 됩니다.

보통은 이렇게 합니다.

- 정적/준정적 사이트: **빌드 시 생성**
- 동적 사이트: 주기적으로 생성해서 캐시하거나, 데이터 변경 시 갱신

핵심은 sitemap이 **최신일 필요는 있어도 실시간일 필요는 없다**는 점입니다. 검색엔진이 반영하는 데 어차피 시간이 걸립니다.

### sitemap 변경은 언제 검색엔진이 알게 되나요?

즉시는 아닙니다. 크롤러가 다시 방문할 때 알게 됩니다.

빨리 알리는 방법은 있습니다.

- robots.txt에 sitemap 위치를 적어두기
- Search Console 등 검색엔진 도구에 제출하기
- `lastmod`를 정확하게 유지하기 — **실제로 바뀌지 않았는데 매번 갱신하면 신뢰를 잃어서 무시됩니다**

그리고 중요한 전제로, **sitemap에 넣었다고 색인이 보장되지는 않습니다.** 어디까지나 발견을 돕는 장치입니다.

# 17. AI를 앞으로 어떻게 활용할 것인가

## 개발 업무

```text
코드 생성
→ 탐색
→ 설계 보조
→ 구현
→ 테스트
→ 리뷰 보조
→ 문서
→ PR
→ 반복 업무 자동화
```

## 내 관점

AI를 단순 autocomplete가 아니라 **개발 workflow에 참여하는 Agent**로 본다.

하지만:

```text
구조
판단
검증
책임
```

은 개발자가 가진다.

## 서비스 도입

AI 기능을 먼저 찾지 않는다.

```text
사용자 문제
→ 기존 UX의 friction
→ AI가 실제로 개선 가능한가
→ 실패 시 UX
→ deterministic 영역 분리
→ 비용/latency/품질 검증
```

## 좋은 한 줄

> 개발에서는 AI가 더 많은 실행을 담당하도록 하되 검증 가능한 환경을 만들고, 제품에서는 AI 자체보다 사용자의 실제 문제를 얼마나 더 잘 해결할 수 있는지를 먼저 보겠습니다.

## 꼬꼬무

### 모든 서비스에 AI가 필요한가요?

필요하지 않다고 생각합니다.

기준은 **"사용자가 지금 겪는 불편이 무엇인가"**입니다. 그 불편이 규칙으로 풀리면 규칙이 낫습니다. 규칙은 결과가 일정하고, 싸고, 틀렸을 때 원인을 찾을 수 있습니다.

AI가 유리한 건 입력이 자유롭고 정답이 하나로 정해지지 않는 영역입니다. 반대로 정확도가 100%여야 하는 곳에 AI를 넣으면 불편이 줄어드는 게 아니라 **불편의 종류가 바뀔 뿐**입니다.

### hallucination 대응은?

없앨 수는 없다고 보고, **틀렸을 때의 비용을 줄이는 쪽**으로 설계합니다.

- 모델이 자유롭게 생성하게 두지 않고 **출처가 있는 데이터 안에서** 답하게 합니다
- 출력 형식을 스키마로 강제하고 검증합니다. 형식이 어긋나면 사용자에게 보여주지 않습니다
- 사실 확인이 가능한 부분은 코드로 검증합니다 (존재하는 ID인지, 계산이 맞는지)
- 결과에 **근거를 함께 보여줘서** 사용자가 판단할 수 있게 합니다

그리고 되돌릴 수 없는 동작(결제, 삭제, 발송)은 모델 출력만으로 실행되지 않게 합니다.

### 비용은?

기능을 붙이기 전에 **요청 단가 × 예상 호출 수**를 먼저 계산해야 한다고 봅니다. 사용자가 늘수록 선형으로 늘어나는 비용이라 무료 기능에 무제한으로 붙이면 감당이 안 됩니다.

줄이는 방법은 이렇습니다.

- 같은 입력에 대한 결과는 캐시합니다
- 쉬운 요청은 작은 모델로, 어려운 것만 큰 모델로 보냅니다
- 프롬프트의 고정 부분을 재사용해서 반복 비용을 낮춥니다
- 사용자당 호출 상한을 둡니다

### latency는?

LLM 호출은 기존 API보다 느립니다. 그래서 **기다림을 어떻게 다룰지가 UX의 일부**가 됩니다.

- 스트리밍으로 첫 글자를 빨리 보여줍니다. 총 시간이 같아도 체감이 크게 다릅니다
- 사용자를 막지 않아도 되는 작업은 비동기로 처리하고 완료를 알립니다
- 예측 가능한 요청은 미리 계산해둡니다
- 타임아웃과 그때 보여줄 화면을 반드시 정합니다

### deterministic logic과 LLM 역할은?

역할을 나눕니다.

- **LLM**: 자연어 이해, 분류, 요약, 초안 생성처럼 **모호한 입력을 다루는 부분**
- **코드**: 계산, 권한 확인, 상태 변경, 검증처럼 **틀리면 안 되는 부분**

예를 들어 사용자의 문장에서 조건을 뽑아내는 건 LLM에 맡기고, 그 조건으로 실제 검색과 필터링을 하는 건 코드가 합니다. 이렇게 하면 모델이 틀려도 **잘못된 조건이 나올 뿐 시스템이 잘못 동작하지는 않습니다.**

### 개인정보는?

외부 모델 API로 데이터를 보내는 순간 **제3자에게 데이터를 전송하는 것**이라는 전제로 시작해야 합니다.

- 필요한 최소한만 보냅니다. 식별자·연락처처럼 없어도 되는 값은 제거하거나 치환합니다
- 학습에 사용되지 않는 조건인지 계약·설정을 확인합니다
- 로그에 프롬프트 원문이 남지 않도록 합니다. 여기서 새는 경우가 실제로 많습니다
- 사용자에게 어떤 데이터가 처리되는지 알리고 동의 범위를 넘지 않습니다

이 부분은 프론트엔드만의 판단으로 정할 수 없어서, 도입 전에 법무·보안과 함께 확인해야 하는 영역이라고 봅니다.

### AI 기능의 성공 지표는?

"AI를 얼마나 썼는가"는 지표가 아니라고 생각합니다. 호출 수가 늘었다고 제품이 좋아진 건 아닙니다.

봐야 할 건 **원래 풀려던 사용자 문제가 실제로 줄었는가**입니다.

- 그 작업을 끝내는 데 걸리는 시간이 줄었는가
- 중간에 이탈하던 단계에서 이탈이 줄었는가
- 결과를 그대로 채택한 비율(수정 없이 쓴 비율)
- 재시도·되돌리기 비율. 높다면 결과 품질이 낮다는 신호입니다

그리고 비용과 지연을 같이 봐야 합니다. 지표가 좋아져도 단가가 감당 안 되면 유지할 수 없습니다.

### AI가 틀리면 UX는?

**틀린다는 전제로 화면을 설계합니다.**

- 결과를 **확정이 아니라 제안으로** 보여줍니다. 사용자가 수정하고 확정합니다
- 되돌릴 수 있게 만듭니다. 실행 전 확인이나 실행 후 취소
- 근거를 함께 보여줍니다. 사용자가 맞는지 판단할 수 있어야 합니다
- 확신이 낮으면 **틀린 답을 내놓기보다 "찾지 못했다"고 말하게** 합니다
- 사용자가 틀렸다고 알릴 수 있는 경로를 둡니다

가장 나쁜 건 틀린 결과를 확신에 찬 형태로 보여주고 되돌릴 방법을 주지 않는 것이라고 생각합니다.

# 마지막으로 기억할 것

면접관이 원하는 건 완벽한 정답 암기가 아니다.

계속 파고들었을 때:

```text
내가 실제로 해본 일인가?
왜 그렇게 판단했는가?
다른 방법을 생각해봤는가?
단점을 알고 선택했는가?
결과에 책임질 수 있는가?
```
