# 1. 사주 추천을 4분 동안 네 번 설명했다

## 키워드

```text
예산·지역은 하드 제약
사주는 정렬 기준, 필터 아님
입력 → 제약 → 랭킹 → 검증
4문장
```

## 답변

> 예산과 희망 지역을 하드 제약으로 먼저 걸러내고, 사주는 그 안에서 **순위를 매기는 데만** 씁니다.
> 사주에서 뽑는 건 용신과 길방 두 가지고, 매물 등록 때 받는 향(남동향 등) 필드에 매핑해 가점을 줍니다.
> 그래서 "동쪽이 좋다"가 나와도 예산 밖 지역은 후보에 아예 오르지 않습니다.
> AI는 사주 해석을 구조화된 속성으로 바꾸는 단계에만 쓰고, 매물 매칭은 ⟨DB 쿼리 / 룰 — 확인 필요⟩입니다.

네 문장이다. 이 이상은 꼬리질문 몫이다.

## 오답 — 실제 발화 08:35~12:35

같은 구간에서 **여섯 번** 되물음을 받았고, 여섯 번 다 사주 도메인을 다시 설명했다.

| 시각  | 내가 한 말                                                          | 실제로 답한 것       |
| ----- | ------------------------------------------------------------------- | -------------------- |
| 08:35 | "사용자 연령대나 성별 그리고 뭐 직장 위치 등을 기반으로…"           | 서비스 소개          |
| 09:22 | "원하는 금액과 사주에 필요한 용신 정보들을 결합해서"                | 처음으로 설계에 근접 |
| 09:55 | "나무나 금 흙 이런 어떤 화 이런 속성들을 조금 축약해서"             | 사주 도메인 재설명   |
| 10:44 | "7억에 살 수 있는 광명부터 송내 뭐 그 쪽을 신중동"                  | 예시 나열            |
| 11:35 | "나무에 좀 길한 방향이 동쪽이거든요"                                | 사주 도메인 재설명   |
| 12:35 | "사주와 융합할 수 있는 그런 부동산을 추천하는 게 저희 목표였습니다" | 목표 재진술          |

**왜 오답인가.** 09:22에 한 번 나온 핵심(예산 ∧ 용신 결합)을 09:55에 다시 도메인으로 후퇴시켰다. 면접관이 알고 싶은 건 사주가 무엇인지가 아니라 **비결정적 입력을 어떻게 결정적 랭킹으로 바꿨는가**다. 4분을 쓰고도 그 답이 한 문장으로 나오지 않았다.

## 꼬리

### 추천이 맞았는지는 어떻게 검증했나요?

키워드: 정답 없음, 대리 지표, 클릭·문의

사주 추천에 정답 레이블이 없다. 그래서 **대리 지표**로 봤다 — ⟨추천 매물 클릭률 / 문의 전환 — 확인 필요⟩. 정답률이 아니라 "이 추천이 탐색을 늘렸는가"로 판단했다.

### 사주를 믿지 않는 사용자에게는 어떤 가치가 있나요?

키워드: 탐색 진입점, 기본 필터로 동일, 재미

믿지 않아도 손해가 없다. 예산·지역 필터 결과는 그대로고, 사주는 정렬 가중치만 바꾼다. 진입 장벽이 아니라 **탐색을 시작하게 만드는 훅**이었다.

### AI가 잘못된 용신을 뽑으면요?

키워드: 하드 제약이 안전망, 예산 밖 노출 없음

랭킹만 바꾸므로 최악의 경우도 "순서가 이상한 후보 목록"이다. 예산 밖 매물이 뜨는 사고는 구조적으로 안 난다. 사주를 필터가 아니라 정렬에 둔 이유가 이거다.

## 확인할 것

- 매칭이 DB 쿼리인지 AI 응답인지. 09:22에 "AI를 통해서 검증하고", 09:55에 "저희 데이터베이스와 연동해서"라고 둘 다 말했다.
- 용신 → 매물 속성 매핑이 몇 개인지 (향 말고 더 있나).

## 보완할 점 — 다음 면접에서 바꿀 한 가지

**도메인 설명은 한 문장까지만.** 사주가 뭔지, 용신이 뭔지는 면접관이 물어본 게 아니다.

한 문장 쓰고 곧바로 "그래서 시스템에서는 ○○로 다뤘습니다"로 넘어간다. 그리고 **두 번째 되물음에서 멈추고 질문을 확인한다** — "제가 사주 쪽을 길게 말씀드린 것 같은데, 추천 로직 쪽을 여쭤보시는 걸까요?"

# 2. A/B 성공 지표를 차트 종류로 세 번 답했다

## 키워드

```text
노출 대비 클릭률이 1차 지표
전환까지 이어지는지 함께 본다
클릭률만 올랐으면 성공 아님
두 그룹 비율 비교 = 막대
```

## 답변

> CTA 실험이라면 **노출 대비 클릭률**을 1차 지표로 보고, 클릭 이후 문의나 전환까지 이어지는지를 함께 봅니다.
> 클릭률만 올랐는데 전환이 그대로면 성공으로 보지 않습니다.

차트 형태를 따로 물으면 그때 답한다:

> 두 그룹 비율 비교라 막대가 맞다고 생각합니다.

## 오답 — 실제 발화 19:19~19:57

| 시각  | 발화                                                                       |
| ----- | -------------------------------------------------------------------------- |
| 19:19 | "a와 b의 클릭률을 직접 비교할 수 있는 **바 차트**나 한눈에 보기 쉬운 형태" |
| 19:36 | "명확하게 볼 수 있는 형태의 차트면은 좋을 것 같은데 **네 그렇습니다**"     |
| 19:57 | "**원형 차트**의 퍼센트로 a와 b의 클릭률을 보여줄 수도"                    |

**왜 오답인가.** 두 가지가 겹쳤다.

1. **질문을 못 알아들었다.** 세 번 다 시각화로 답했다. 세 번 물었다는 건 지표를 물었다는 뜻이다.
2. **답 자체가 틀렸다.** 두 그룹의 비율 비교에 원형 차트는 쓰지 않는다. 원형은 전체를 100%로 쪼갤 때 쓰는 것이고, A군 12% vs B군 15%는 서로 다른 두 모집단이라 한 원 안에 들어가지 않는다. 데이터를 매일 보는 사람 앞에서 나오면 추가 감점이다.

19:36의 "네 그렇습니다"는 할 말이 없는데 문장을 닫아야 해서 나온 소리다.

## 꼬리

### 클릭률이 올랐는데 전환이 떨어지면요?

키워드: 실패로 본다, 낚시성 CTA, 1차·2차 지표 순서

실패로 본다. 클릭을 유도했지만 기대와 다른 화면이 나왔다는 뜻이라 장기적으로 신뢰를 깎는다. 그래서 1차 지표만으로 종료 판정을 하지 않는다.

### 유의성은 어떻게 판단했나요?

키워드: 미확인, 최소 표본, 조기 종료 위험

⟨실제로 유의성 검정을 했는지 확인 필요⟩ — 안 했다면 그렇게 말한다. "표본 크기와 기간을 사전에 정하지 않고 지표 차이만 봤습니다. 지금이라면 최소 표본과 기간을 먼저 합의합니다"가 정직하고, 조기 종료 위험을 안다는 신호가 된다.

## 보완할 점 — 다음 면접에서 바꿀 한 가지

**"성공을 어떻게 판단했나"에는 반드시 분자와 분모를 말한다.**

지표 질문에 시각화로 답하면 데이터를 안 본 사람으로 읽힌다. 위 두 문장은 통째로 외운다.

# 3. A/B 트래픽 분배 방식을 답하지 못했다

## 키워드

```text
분배는 Amplitude, 쿼리는 QA 강제 진입
사용자 단위 고정 배정
같은 사람은 항상 같은 그룹
```

## 답변

> 분배는 ⟨Amplitude Experiment — 확인 필요⟩가 사용자 단위로 고정 배정했습니다.
> 쿼리스트링은 QA가 특정 그룹으로 강제 진입할 때만 쓰는 우회로였고, 실제 사용자 분배에는 쓰지 않았습니다.
> 같은 사용자는 세션이 바뀌어도 같은 그룹에 들어가야 지표가 의미를 갖기 때문입니다.

## 오답 — 실제 발화 13:17 / 14:52 / 17:14

전사본 안에서 답이 서로 충돌한다.

| 시각  | 발화                                                                                                                   | 문제               |
| ----- | ---------------------------------------------------------------------------------------------------------------------- | ------------------ |
| 13:17 | "앰플리튜드 기능으로 a 환경을 볼 사용자 그리고 b 환경을 볼 사용자를 나눠서"                                            | 분배 = Amplitude   |
| 14:52 | "저희는 그 쿼리를 붙여서 이제 진입점에 쿼리를 붙여서 테스트를 진행했습니다"                                            | 분배 = 쿼리스트링? |
| 17:14 | "앰플리튜드 툴에 분리하는 게 있어가지고 그 기능을 활용했던 것 같습니다. **제가 지금 정확하게 기억은 나지 않아가지고**" | 확신 없음          |

**왜 오답인가.** "기억이 안 난다"는 것 자체는 감점이 크지 않다. 문제는 **직전 두 답변이 서로 다른 설명이었다는 것**이다. 면접관 입장에서는 이 지원자가 실제로 그 부분을 만들었는지가 흐려진다. 17:53에 "차트·대시보드는 마케터·기획자가 했고 저는 베리언트를 나눴다"고 스스로 역할을 좁혀놨는데, 그 좁힌 영역조차 설명이 흔들린 셈이다.

## 꼬리

### 사용자 단위 고정이 왜 중요한가요?

키워드: 같은 사람 다른 화면, 지표 오염, 재방문

같은 사람이 재방문할 때마다 다른 그룹에 들어가면 지표가 섞여서 어느 쪽이 나은지 판단할 수 없다. 사용성도 깨진다.

### 로그인 전 사용자는 어떻게 고정하나요?

키워드: 디바이스 ID, 로그인 시 승계

디바이스 ID 기준으로 배정하고, 로그인 시점에 사용자 ID로 승계한다. ⟨실제 구현이 이랬는지 확인 필요⟩

## 보완할 점 — 다음 면접에서 바꿀 한 가지

**내가 만들었다고 말한 것은 한 문장으로 정리해서 외워둔다.**

특히 "내가 한 건 여기까지"라고 경계를 그은 영역은 더 정확해야 한다. 경계를 긋는 건 좋은 습관인데, 그 안쪽이 흐리면 경계를 그은 게 회피로 읽힌다.

# 4. 가장 강한 카드를 "자연스럽게"로 끝냈다

## 키워드

```text
매물 밀도 편차가 문제
클러스터링 + 이전 결과 유지
요청 취소로 깜빡임 제거
숫자 하나
```

## 답변

> 지역별 매물 밀도 편차가 커서, 밀집 지역에서 지도를 움직이면 응답이 늦고 화면이 비었다가 다시 그려졌습니다.
> 세 가지를 했습니다. 밀도에 따라 ⟨클러스터링/그리드 집계 — 확인 필요⟩로 그릴 개수를 줄이고, 새 응답이 오기 전까지 이전 결과를 유지해 빈 화면을 없앴고, 이동 중 발생한 이전 요청은 취소해서 늦게 온 응답이 화면을 덮지 않게 했습니다.
> 결과로 ⟨체감 지연 / 렌더 시간 / 이탈률 — 숫자 하나 확인 필요⟩가 개선됐습니다.

## 오답 — 실제 발화 07:51

> "매물이 많은 지역이 있고 적은 지역이 있지만 많은 지역일수록 매물을 빠르게 보여줘야 되는데 그런 부분을 제가 좀 **고도화**해서 화면에 그릴 때 **깜빡거리지 않고** 좀 더 **자연스럽게** 보이고 그런 노출 과정을 고민 많이 했습니다."

**왜 오답인가.** 이 답에는 **기술이 하나도 없다.** "고도화", "자연스럽게", "고민 많이 했습니다" 세 단어가 내용을 다 대체했다.

지도 위 대량 마커 렌더링은 프론트엔드 면접에서 가장 파고들기 좋은 주제고, 이 사람이 실제로 성능을 만져봤는지가 여기서 갈린다. 문제 정의(밀도 편차)까지는 스스로 꺼내놓고, 해결 방법과 결과를 말하지 않아서 **면접관이 더 물을 실마리도 남기지 않았다.** 07:51 이후 지도 얘기는 다시 안 나왔다.

## 꼬리

### 마커가 몇 개까지 늘어나면 문제가 되나요?

키워드: 임계 개수, DOM vs 캔버스

⟨실제 임계값 확인 필요⟩. 개수를 모르면 "정확한 수치는 기억나지 않지만 밀집 지역에서 눈에 띄게 느려지는 지점이 있었습니다"까지만 말하고, 대신 대응 방식을 말한다.

### 이전 결과를 유지하면 낡은 데이터가 보이지 않나요?

키워드: 짧은 구간, 빈 화면과의 교환, 로딩 표시

보인다. 다만 수백 ms 구간이고, 빈 화면이 번쩍이는 것보다 낫다고 판단했다. 대신 갱신 중이라는 표시를 남겼다. ⟨표시를 실제로 넣었는지 확인 필요⟩

### 요청 취소는 어떻게 했나요?

키워드: AbortController, 최신 요청만 반영

⟨AbortController인지 응답 순서 비교인지 확인 필요⟩. 지도 이동은 요청이 연속으로 나가서, 취소를 안 하면 늦게 온 옛 응답이 최신 화면을 덮는다.

## 보완할 점 — 다음 면접에서 바꿀 한 가지

**"고도화했습니다", "자연스럽게", "고민 많이 했습니다"를 답변에서 뺀다.**

이 세 표현이 들어갈 자리에는 항상 구체적인 기술 이름이나 숫자가 들어갈 수 있다. 없으면 그건 아직 정리가 안 된 경험이다. 면접 전에 **성과 숫자 세 개**를 확보한다.

# 5. 되물어놓고 대답을 듣지 않았다

## 키워드

```text
묻고 나서 침묵
확인 → 대답 듣기 → 답변
추측으로 진행 금지
```

## 답변

되묻기는 두 동작이다. **묻는 것**과 **듣는 것**. 물음표 뒤에 말을 이으면 되물은 게 아니라 추측한 것이다.

> 제가 질문을 다르게 이해한 것 같은데, ○○을 말씀하시는 걸까요?

여기서 문장을 끝내고 기다린다.

## 오답 — 실제 발화 26:17 → 27:09

26:17:

> "혹시 제가 죄송한데 도메인 컨텍스트를 작성한 게 그 동네 생활 백서 탭이 맞을까요? **네** 저희가 그 의미론적으로 유추할 수 있는 시멘틱 URL을 구축을 했습니다."

물음표와 다음 문장 사이에 아무것도 없다. 그리고 27:03 "아 네", 27:09 "네 죄송합니다" — 정정당한 뒤 도메인 타입·상수 중앙화 얘기로 다시 시작했다.

**왜 오답인가.** 되묻기는 이번 면접에서 **유일하게 나온 좋은 습관**이었는데, 그걸 스스로 무효로 만들었다. 결과적으로 한 질문에 두 번 답했고 그중 한 번은 완전히 다른 주제였다. 확인을 안 한 것보다 나쁜 인상이 될 수 있다 — "묻는 시늉만 한다"로 읽히기 때문이다.

## 꼬리

### 침묵이 어색하지 않나요?

키워드: 2초, 면접관이 채운다

2초면 된다. 되물음 뒤의 침묵은 면접관이 채우게 되어 있다. 어색한 건 말하는 쪽뿐이다.

### 확인했는데도 못 알아들으면요?

키워드: 아는 범위 선언, 정직

거기서 아는 범위를 선언하고 끝낸다. "제가 이해한 범위에서 말씀드리면 ○○입니다. 방향이 다르면 말씀해 주세요."

## 보완할 점 — 다음 면접에서 바꿀 한 가지

**물음표를 찍으면 입을 닫는다.**

되묻기 자체는 이미 할 줄 안다. 부족한 건 그 다음 2초다.

# 6. "획기적"을 "획기적"으로 답했다

## 키워드

```text
정의 요청 = 내 단어를 설명하라
동어반복 금지
구체적 장면 하나
```

## 답변

> 제가 "획기적"이라고 말씀드린 건 정확히는 **요청 때마다 개발이 붙지 않는 상태**를 뜻했습니다.
> 지금은 단지마다 다른 리포트 요구가 오면 매번 쿼리를 새로 짜야 하는데, 운영자가 항목과 기간을 직접 골라 뽑을 수 있으면 그 사이클이 사라집니다.

## 오답 — 실제 발화 23:07 → 23:34

23:07:

> "데이터 팀에 데이터 마트를 통해서 그런 기능을 좀 **쉽고 획기적으로** 뽑을 수 있게끔 요청을 한다든지"

23:34 (면접관이 "획기적이라는 게 뭔가요"를 되물은 것으로 추정):

> "**쉽고 획기적으로** 뽑을 수 있는 거는 사용자가 원하는 속성을 직접 선택하고 그 속성을 편리하게 압축해서 한눈에 볼 수 있는 형태로 보여주는 게 **획기적인 것 같습니다.**"

**왜 오답인가.** 정의를 물었는데 같은 단어로 답을 닫았다. 게다가 "편리하게", "한눈에" 같은 또 다른 미정의 단어를 얹어서 모호함이 늘었다.

되물음이 오는 단어는 대부분 **내가 무심코 쓴 형용사**다. 형용사에는 정의가 없으니 되물을 수밖에 없고, 그때 같은 형용사로 답하면 대화가 제자리를 돈다.

## 꼬리

### 그럼 처음부터 그 단어를 안 쓰면 되나요?

키워드: 형용사 대신 동작, 누가 무엇을 안 해도 되는가

그게 낫다. "획기적" 자리에 항상 **누가 무엇을 안 해도 되는지**가 들어갈 수 있다. "개발자가 매번 쿼리를 짜지 않아도 된다"가 그 자리에 맞는 문장이다.

### 정의를 못 대겠으면요?

키워드: 철회, 다시 말씀드리면

철회한다. "제가 단어를 잘못 골랐습니다. 다시 말씀드리면 ○○입니다."

## 보완할 점 — 다음 면접에서 바꿀 한 가지

**면접관이 내 단어를 되물으면, 그 단어를 다시 쓰지 않고 답한다.**

같은 단어가 답에 또 나오면 그건 답이 아니다.

# 7. 디자인 시스템 확장을 "묶어서 쓴다"로 세 번 답했다

## 키워드

```text
variant는 열거 가능할 때
합성(children/slot)은 조합이 열릴 때
프로젝트 shared에 래퍼
디자인 팀과 기준 합의
```

## 답변

> 두 갈래로 나눕니다. 경우의 수가 **닫혀 있으면 variant로** 시스템 안에 넣고, 조합이 계속 열리는 성격이면 **합성으로** 풀어서 바깥에서 조립하게 합니다.
> 한 프로젝트에만 필요한 형태면 그 프로젝트 shared에 래퍼를 두고, 두 번째 프로젝트에서 같은 요구가 나오면 그때 시스템으로 올립니다.
> 판단이 반복되지 않게 디자인 팀과 "어떤 변형까지를 시스템이 책임지는지" 기준을 먼저 맞췄습니다.

## 오답 — 실제 발화 30:04~31:19

| 시각  | 발화                                                                       | 실질           |
| ----- | -------------------------------------------------------------------------- | -------------- |
| 30:04 | "디자인 팀과 조율을 해서 명확한 기준을 가지고"                             | 조직 얘기      |
| 30:30 | "디자인 시스템을 한 번 더 **묶어서** 커스텀하게 사용할 수 있게끔"          | 래퍼           |
| 30:52 | "그거를 사용하는 쪽에서 한 번 더 **묶어서** 사용을 할 수 있을 것 같습니다" | 같은 말        |
| 31:19 | "쉐어드 폴더를 따로 둬서 커스텀한 버튼을 컴포넌트로 만들어서"              | 같은 말 + 위치 |

**왜 오답인가.** 세 번의 답이 사실상 한 문장이다. "바깥에서 한 번 더 감싼다" — 이건 방법이 아니라 **위치**다. 어떤 경우에 감싸고 어떤 경우에 시스템을 고치는지, 그 기준이 없다.

28:47에 이미 좋은 원칙을 말해뒀다 — "프롭스를 늘려서 하나의 컴포넌트에 많은 책임을 전가하는 시스템은 좋지 않다", "원자에서 분자 단위로 합성될 수 있어야 한다". **그 답을 30:04에서 다시 쓰지 않았다.** 이미 가진 카드를 안 꺼낸 오답이다.

## 꼬리

### variant와 합성의 경계는 어디인가요?

키워드: 열거 가능성, prop 증가 속도

경우의 수를 다 적을 수 있으면 variant, 요구가 올 때마다 prop이 하나씩 붙는 조짐이 보이면 합성이다. prop이 늘어나는 속도가 신호다.

### 래퍼가 프로젝트마다 생기면 파편화되지 않나요?

키워드: 두 번째 요구가 승격 신호, 중복은 허용

한 번은 중복을 허용하고, **같은 래퍼가 두 번째 프로젝트에 생기면** 그때 시스템으로 올린다. 첫 등장에 추상화하면 대개 틀린 추상화가 된다.

### 시스템 컴포넌트를 고쳐야만 하는 경우는요?

키워드: 접근성, 포커스, 키보드

접근성·포커스·키보드 동작처럼 **모든 사용처가 같아야 하는 것**은 래퍼로 우회하지 않고 시스템을 고친다.

## 보완할 점 — 다음 면접에서 바꿀 한 가지

**같은 답이 두 번 나오면 답이 아니라 판단 기준을 요구받고 있는 것이다.**

"어떻게 하나요"에 방법을 말했는데 또 물으면, 다음 답은 방법이 아니라 **"이럴 땐 A, 저럴 땐 B"** 형태여야 한다.

# 8. 답을 "우선은"으로 열었다 — 30분 동안 14회

## 키워드

```text
우선은 → 금지
첫 문장은 질문에 대한 직접 답
한 답변 한 논점
```

## 답변

**"우선은"으로 답을 시작하지 않는다.** 금지어는 이것 하나면 된다.

말버릇이 아니라 **문장 구조를 결정하는 단어**다. "우선은"으로 열면 뒤에 나열이 와야 해서 결론이 앞으로 나올 수가 없다. "첫 문장은 결론"과 이 단어는 물리적으로 양립하지 않는다.

## 오답 — 실제 발화 전 구간

06:12 · 06:41 · 07:04 · 07:51 · 08:35 · 09:22 · 13:17 · 15:40 · 21:57 · 22:41 · 27:09 · 28:47 · 30:04 …

가장 나쁜 예 — 21:57:

> "**우선** B2B에서 다른 데이터를 받기보다는 **우선은** 제가 지금 신규로 만들고 있는 개발을 먼저 완성하는 과정이 중요했기 때문에 네 그렇습니다."

한 문장에 두 번 나오고, 결론 없이 "네 그렇습니다"로 닫혔다. 내용상으로도 "그건 제 일이 아니었다"로 읽혀서 오너십 질문에 최악의 답이 됐다.

12:35도 같은 구조다:

> "네 그래서 이제 사용자가 원하는 위치 기반을 어느 정도 받아가지고 그에 맞게 어느 정도 사주와 융합할 수 있는 그런 부동산을 추천하는 게 저희 목표였습니다."

결론부터 쓰면:

> 목표는 예산과 희망 지역을 먼저 확정하고, 사주는 순위를 매기는 데만 쓰는 것이었습니다.

## 꼬리

### 다른 말버릇도 같이 고쳐야 하나요?

키워드: 하나만, 인지부하, filler는 증상

하나만 잡는다. 여섯 개를 동시에 의식하면 인지부하가 늘어서 오히려 더 끊긴다. filler는 원인이 아니라 증상이고, 문장을 짧게 끝내면 자동으로 준다.

### `~것 같습니다`도 없애야 하나요?

키워드: 의견과 사실 구분, 정직함

구분한다. **의견**을 물었으면 "~라고 생각합니다"가 맞고, **불확실한 사실**에는 "~것 같습니다"가 오히려 정직하다. 싸잡아 지우면 아는 척하는 사람이 된다.

## 보완할 점 — 다음 면접에서 바꿀 한 가지

**첫 단어를 "우선은"이 아닌 것으로 시작한다. 이것만 지킨다.**

이 하나를 막으면 첫 문장이 강제로 결론이 된다. 나머지는 따라온다.
