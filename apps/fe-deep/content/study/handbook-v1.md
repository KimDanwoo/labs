# 자기소개

## 30초 답변

안녕하세요. 사용자 경험과 개발 생산성을 함께 고민하는 프론트엔드 엔지니어 김단우입니다.

최근에는 레거시 서비스를 신규로 전환하면서 프론트엔드 구조와 인증 흐름, 공통 UI 구조를 설계하고 구축했습니다.

이 과정에서 AI Agent를 개발 프로세스에 적용해 반복적인 구현과 검증 과정도 개선했습니다.

저는 단순히 기능을 구현하는 데 그치지 않고, 사용자가 더 편하게 서비스를 이용할 수 있도록 개선하면서 팀이 더 빠르고 안정적으로 개발할 수 있는 구조까지 함께 고민하는 개발자입니다.

## 키워드

```text
사용자 경험
개발 생산성
프론트 구조와 인증 흐름
공통 UI 구조 설계
확장 / 유지보수
반복적인 구현과 검증 과정 개선
```

# "어떤 개발자이신가요?"

를 묻는다.

## 추천 답변

저는 **사용자 경험을 개선**하는 것과, 그 개선을 빠르게 **반복할 수 있는 개발 구조**를 같이 고민하는 개발자입니다.

실제로 서비스에서는 **사용자의 탐색이나 사용 흐름을 개선**하는 일을 좋아하고, 개발 과정에서는 **반복적인 개발 비용을 줄이는 구조**를 만드는 데 관심이 많습니다.

## 키워드

```text
사용자 불편 고민
바른 개선 구조
제품 완성도
```

## 예상 꼬리

### "빠르게 만드는 것과 유지보수성이 충돌하면요?"

키워드: 제품 단계, 변경 가능성, 오버엔지니어링, 가장 단순한 구조

먼저 지금 **제품의 단계**와 **변경 가능성**을 볼것 같아요.

초기 검증 단계인데 확장 가능성만 보고 복잡한 구조를 먼저 만들면 **오버엔지니어링**이 될 수 있고, 반대로 계속 확장될 게 명확한 영역을 **임시 구조**로 만들면 **변경 비용**이 커질 수 있습니다.

그래서 **현재 필요한 수준에서 가장 단순한 구조를 선택**하되, **변경 가능성이 높은 경계는 명확히 나누는 것**을 기준으로 봅니다.

```
코드
목적

제품 방향
```

# 이직의 이유는 무엇인가요?

## 추천 답변

현재 회사에서 신규 서비스 구축과 AI Agent 기반 개발 방식을 주도적으로 경험하면서 기술적으로 많이 성장했습니다.
이제는 제가 만들어온 방식과 기준을 더 다양한 경험을 가진 엔지니어들과 검증하고, 기술적인 의사결정을 제품 성과까지 연결하는 경험을 더 깊게 해보고 싶습니다.
당근 알바는 Agent 기반 개발, 그리고 엔지니어의 제품 참여를 중요하게 보고 있어서 제가 원하는 다음 단계와 잘 맞는다고 생각했습니다.

## 키워드

```
주도적 경험으로 기술 성장
다향한 경험을 가진 엔지니어와 검증
기술적 의사결정을 제품성과에 연결
```

## 예상 꼬리

### "현재 회사에서도 하면 되지 않나요?"

키워드: 제품 성장, 검증, 함께 성장

지금 회사에서도 AI 활용이나 구조 개선은 계속하고 있습니다.

다만 앞으로는 이런 기술적인 역량을 넘어서, 당근처럼 프로덕트 성장에 몰두하는 사람들과 함께 일하면서 제가 가진 기술과 경험을 실제 제품 성장에 더 많이 녹여보고 싶습니다.

그 과정에서 제 방식도 검증받고, 다른 사람들의 좋은 기준도 배우면서 더 빠르게 성장하고 싶습니다.

# 왜 당근인가요? (기대하는 점 포함)

## 답변

제가 최근 가장 재미있게 해온 일은 신규 서비스를 0부터 만드는 것과 AI Agent를 개발 프로세스에 적용해 일하는 방식을 개선하는 일이었습니다.

당근은 AI를 개인 도구가 아니라 팀의 개발 문화로 쓰는 조직으로 알고 있고, Local Jobs 공고에서도 0→1, B2B/B2C, Agent 기반 개발 방식을 강조하고 있었습니다. 제가 해온 방식을 더 높은 수준의 팀에서 검증받고 확장할 수 있는 곳이라고 느꼈습니다.

기대하는 점도 같은 결입니다 — **프로덕트 성장에 몰두하는 사람들과 함께 제 역량을 제품 성장에 녹이면서 더 성장**하고 싶습니다.

# 개발할 때 동기부여는 어디서 얻나요?

## 답변

제가 만든 기능이 실제 사용자 흐름을 개선하거나, 팀이 반복하던 일을 줄이는 결과로 이어질 때 가장 동기부여를 많이 받습니다.

최근에는 사용자 기능뿐 아니라 AI Agent Harness처럼 개발 방식 자체를 개선하는 작업도 재미있었습니다. 제가 만든 구조가 다음 작업을 더 빠르고 예측 가능하게 만드는 걸 볼 때 성취감을 느끼는 편입니다.

그리고 며칠 막혀 있던 문제의 원인을 끝까지 파서 찾아냈을 때의 재미도 큽니다. 문제가 어려울수록 풀었을 때 남는 게 많다고 느낍니다.

## 키워드

```
사용자 흐름을 개선
반복하던 일을 줄이기
Harness처럼 개발방식 개선
```

# 최근 가장 성장한 포인트

## 답변

최근 가장 성장했다고 느끼는 부분은 AI를 사용하는 방식입니다.

처음에는 AI를 잘 사용하는 걸 많은 작업을 맡기는 것으로 생각해서 간단한 작업까지 Agent에게 위임하기도 했습니다.

그런데 그렇게 하다 보니 제가 직접 코드를 탐색하고 구조를 이해하는 시간이 줄어드는 문제가 생겼습니다.

이후에는 반복 실행은 AI에게 적극적으로 맡기되 구조적 판단과 리뷰는 직접 가져가고, Harness와 lint 같은 검증 환경을 만드는 방식으로 바꿨습니다.

지금은 AI 활용 능력을 단순한 프롬프트 능력보다 **AI가 예측 가능하게 일할 수 있는 환경을 만드는 능력**으로 보고 있습니다.

# 아파트스토리를 왜 새로 만들었나요?

## 핵심

```text
단지별 DB
PHP 레거시
기능 누적
높은 의존성
변경 영향 파악 어려움
인수인계자 부재
계속되는 신규 기능
```

## 답변

기존 서비스를 그대로 확장하는 방법도 검토했지만 구조적으로 유지보수 비용이 계속 커지는 상황이었습니다.

단지마다 데이터베이스가 분리되어 있었고 PHP 레거시 코드도 오랫동안 기능이 누적되면서 변경 영향 범위를 파악하기 어려웠습니다. 기존 구조를 깊게 알고 있는 인수인계자도 부재한 상태였습니다.

앞으로 관리자와 사용자 기능을 계속 추가해야 했기 때문에 기존 코드를 계속 확장하는 것보다, 유지해야 하는 인증과 기존 데이터는 남기고 신규 애플리케이션 영역을 다시 구축하는 것이 장기적으로 더 효율적이라고 판단했습니다.

## Why 1 — 왜 리팩터링하지 않았나요?

키워드: 코드 분석 비용, 변경 리스크, 동시 운영 복잡도

리팩터링도 기존 동작과 영향 범위를 충분히 파악한 상태에서 해야 하는데 당시에는 코드 분석 비용과 변경 리스크가 컸습니다.

신규 기능도 계속 예정되어 있었기 때문에 기존 구조와 신규 구조를 동시에 운영하는 기간이 길어지면 복잡도가 더 커질 가능성이 있다고 판단했습니다.

# 신규 프로젝트에서 가장 먼저 고민한 것

## 답변

기술 스택을 먼저 정하기보다 **기존 시스템과 신규 시스템의 경계**를 먼저 정했습니다.

신규 서비스에서도 기존 사용자의 인증과 데이터를 그대로 사용해야 했고, 여러 도메인이 하나의 Backend API를 사용하고 있었기 때문에 인증과 네트워크 구조를 먼저 정리했습니다.

그 다음 여러 앱이 공유해야 하는 UI와 기능의 경계를 모노레포와 디자인 시스템에서 정의했습니다.

## 꼬리

### 무엇을 남기고 무엇을 새로 만들었나요?

키워드: 인증·데이터 유지, 리스크 비교, 확장 영역만 신규

이미 안정적으로 동작하고 사업적으로 연결된 영역 — 인증, 기존 사용자와 데이터 — 는 남겼습니다. 바꿔서 얻는 이득보다 잘못 건드렸을 때의 리스크가 훨씬 컸습니다.

새로 만든 건 앞으로 계속 확장해야 하는 영역입니다. 마스터 어드민 / 단지 어드민 / 사용자 서비스 화면, 프로젝트 구조와 공통 UI, API 호출 구조입니다.

### Backend와 무엇을 협의했나요?

키워드: 쿠키 도메인 범위, 인증 쿠키 공유, CORS, Next 프록시

두 가지입니다.

1. 기존 인증을 신규 앱에서 어떻게 이어받을지 — 쿠키 도메인 범위와 인증 쿠키 공유 범위
2. 여러 도메인이 하나의 API를 바라볼 때 CORS를 어디서 감당할지 — 결과적으로 프론트의 Next 프록시로 흡수하는 쪽으로 정리했습니다

# AI Agent를 실제로 어떻게 활용했나요?

## 실제 사용

```text
코드 탐색
반복 UI 구현
리팩터링
테스트 초안
코드 리뷰
Figma MCP
문서화
```

## 답변

신규 프로젝트의 반복적인 구현 속도를 높이기 위해 Claude Code와 Cursor 같은 Agent를 적극적으로 사용했습니다.

초기에는 작업 단위로 프롬프트를 작성했는데 프로젝트가 커질수록 같은 구조와 규칙을 반복해서 전달해야 했고, Agent가 서로 다른 패턴으로 코드를 작성하는 문제가 생겼습니다.

그래서 프로젝트 구조와 도메인, 규칙을 Harness 형태로 명시하고 반드시 지켜야 하는 규칙은 lint나 type 같은 검증 장치로 옮겼습니다.

## 꼬리

### 어떤 작업은 맡기지 않나요?

키워드: 되돌리기 어려운 판단, 구조 결정, 인증·권한, 반복 구현은 위임

되돌리기 어려운 판단입니다. 레이어·패키지 경계 같은 구조 결정, 인증·권한처럼 틀리면 보안 문제가 되는 영역, 스키마 변경, 그리고 Harness 규칙 자체입니다.

반대로 패턴이 정해진 반복 구현, 테스트 케이스 확장, 대량 치환은 적극적으로 맡깁니다.

### 결과를 어떻게 검증하나요?

키워드: 타입·lint·빌드, 리뷰, 설명할 수 없는 코드는 머지 금지

타입·lint·빌드가 1차 방어선입니다. 존재하지 않는 API나 경계 위반은 대부분 여기서 걸립니다.

리뷰에서는 AI 코드에 자주 나오는 것부터 봅니다 — 요청하지 않은 코드, 기존 코드를 재사용하지 않고 새로 만든 것, 경계 우회. 최종 기준은 하나입니다. **제가 설명할 수 없는 코드는 머지하지 않습니다.**

### 테스트까지 통과하면 믿나요?

키워드: 같은 Agent, 잘못된 가정 공유, 직접 읽기, 실패 케이스 추가

아니요. 테스트를 누가 썼는지가 중요합니다.

같은 Agent가 구현과 테스트를 함께 썼다면 구현의 잘못된 가정이 테스트에도 똑같이 들어가 둘 다 통과할 수 있습니다. 중요한 로직은 테스트가 무엇을 보장하는지 직접 읽고, 필요하면 실패해야 하는 케이스를 추가합니다.

# AI Harness 구조

```text
Global
└─ 공통 개발 원칙

Project
├─ 프로젝트 목적
├─ Architecture
├─ Domain Context
├─ Monorepo package 역할
├─ FSD / import
└─ 금지 영역

Commands
├─ 구현
├─ 리뷰
├─ 리팩터링
└─ 테스트

Memory / Context
└─ 반복적으로 필요한 프로젝트 정보

Validation
├─ lint
├─ type
└─ test
```

## 답변

전역 규칙과 프로젝트 규칙을 분리했습니다.

전역에는 프로젝트가 바뀌어도 유지되는 코드 작성 원칙을 두고, 프로젝트에는 아키텍처, 모노레포 구조, FSD 규칙, 도메인 맥락과 수정하면 안 되는 영역을 넣었습니다.

반복 작업은 Command로 분리했고 반드시 지켜야 하는 규칙은 문서에만 의존하지 않고 lint나 type으로 검증하도록 했습니다.

# 왜 모든 규칙을 문서로 두지 않았나요?

## 답변

Agent가 문서를 항상 완벽하게 준수한다고 보장할 수 없기 때문입니다.

예를 들어 import boundary는 코드만 보면 기계적으로 판정할 수 있기 때문에 문서보다 lint로 강제하는 편이 더 적합했습니다.

반대로 "불필요한 추상화를 하지 않는다"처럼 판단이 필요한 내용은 문서와 리뷰 영역으로 남겼습니다.

## 꼬리

### 왜 모든 규칙을 lint로 만들지 않나요?

키워드: 기계적 판정 불가, 룰 유지보수 비용, 오탐, 되돌리기 어려운 것만 lint

모든 규칙이 기계적으로 판정되지 않고, lint 룰도 유지보수 비용이기 때문입니다. 규칙이 늘수록 오탐이 늘고, `eslint-disable`이 습관이 되면 규칙이 죽습니다.

기준은 이렇게 잡았습니다. **어겼을 때 되돌리기 어려운 것은 lint로, 판단이 필요한 것은 문서와 리뷰로.**

### Harness가 커지면 어떻게 하나요?

키워드: 커지는 게 신호, 코드·타입으로 이동, 디렉터리 가까이, 지켜지는 규칙은 삭제

커지는 것 자체가 신호입니다. 길어지면 사람도 Agent도 안 읽습니다.

자주 바뀌는 내용은 코드나 타입으로 옮기고, 특정 작업에서만 필요한 맥락은 전역 문서 대신 그 디렉터리 가까이에 두고, 잘 지켜지는 규칙은 문서에서 지우고 lint만 남깁니다.

---

# AI가 잘못 구현한 실제 사례

## 사례

```text
FSD public API
→ 내부 파일 직접 import
→ 기능 정상
→ 구조 일관성 저하
→ lint
```

## 답변

FSD 구조에서 segment의 public API까지만 import하도록 규칙을 두고 있었습니다.

그런데 Agent가 내부 컴포넌트 파일을 직접 import하는 경우가 반복됐습니다.

기능상 문제는 없지만 내부 구현과 결합되고 import 패턴이 파편화되기 때문에 `no-restricted-imports` 같은 lint 규칙으로 경계를 강제했습니다.

## 꼬리

### lint 규칙은 직접 만들었나요?

키워드: eslint-plugin-boundaries, no-restricted-imports, 경계 정의는 직접, 위반 케이스로 검증

커스텀 플러그인을 새로 만든 건 아닙니다. 레이어 경계는 `eslint-plugin-boundaries`로 허용 방향을 선언했고, 깊은 import 금지는 `no-restricted-imports` 패턴으로 잡았습니다.

커스텀 룰 직접 작성은 유지보수 비용이 커서 마지막 수단으로 뒀습니다.

만드는 과정도 역할을 나눴습니다 — **어떤 경계를 막을지, 허용 방향이 무엇인지는 제가 정의**하고, 설정 초안 작성은 Agent에게 맡겼습니다. 그리고 위반 케이스를 일부러 만들어서 실제로 lint가 걸리는지 확인한 뒤에 적용했습니다. 규칙의 소유권은 저에게 있고, 작성 노동만 위임한 구조입니다.

### CI 워크플로우는 어떻게 만들었나요?

키워드: 초안은 Agent, 일부러 실패하는 커밋, Turborepo 캐시, 막히는 걸 확인

CI도 같은 방식으로 Agent와 함께 만들었습니다. lint·타입체크·빌드를 PR 단계에서 강제하는 워크플로우를 Agent에게 초안 작성시키고, 제가 **일부러 실패하는 커밋**(경계 위반 import, 타입 에러)을 올려서 실제로 막히는지 검증한 뒤 적용했습니다.

Turborepo 기반이라 CI에서도 캐시가 동작합니다 — 바뀌지 않은 package는 다시 빌드하지 않아서, 모노레포인데도 앱 하나 고친 PR이 전체 빌드를 기다리지 않습니다.

핵심 프레임은 lint와 같습니다: **무엇을 검증할지와 통과 기준은 사람이 정하고, YAML을 쓰는 노동은 AI에게.** CI는 한번 틀리면 조용히 아무것도 안 막는 상태가 되기 때문에, "만들어졌다"가 아니라 "막히는 걸 확인했다"까지가 완성이라고 생각합니다.

> ✍️ **확정(2026-08-28)** — CI에서 도는 것은 **lint·type check·build와 Slack 알림·브랜치 병합 자동화**이고, **테스트를 게이트로 두지는 않았다.** 과장하지 말고 그대로 말한다.
>
> 즉 AI 결과의 검증은 **정적 검사(lint·타입) + 사람 리뷰**가 축이었고, 자동 테스트 게이트는 없었다. 이어서 *"규칙으로 막을 수 있는 건 lint로 내리고, 나머지는 리뷰로 봤습니다. 테스트를 게이트로 두는 건 아직 못 한 부분입니다"*로 한계를 스스로 짚는다.

### 동작에는 문제가 없는데 왜 막았나요?

키워드: 다음 변경의 비용, 내부 구조 결합, 생기는 순간 걸림

지금 동작이 아니라 **다음 변경의 비용** 때문입니다. 내부 파일 경로가 밖으로 새면 그 순간부터 내부 구조를 바꿀 수 없습니다.

이런 import가 쌓인 뒤에 고치려면 전체를 훑어야 하지만, lint로 막으면 생기는 순간 걸립니다.

---

# Monorepo를 왜 선택했나요?

## 답변

마스터 어드민, 단지 어드민, 사용자 서비스가 공통 UI, 인증, 설정과 유틸을 공유해야 했기 때문에 모노레포를 선택했습니다.

각 앱은 독립적으로 개발하고 배포하되 공통 영역은 package로 분리해 재사용할 수 있도록 했습니다.

## Why — 멀티레포는?

키워드: 여러 repo 버전 동기화, 배포 맞추는 비용

멀티레포도 가능하지만 공통 컴포넌트나 설정이 변경될 때 여러 repository의 버전과 배포를 따로 맞춰야 하는 비용이 생길 수 있다고 판단했습니다.

## Trade-off

```text
의존성 경계 관리 필요
빌드 복잡도
package coupling 가능
```

## 꼬리

### 공통화 기준은?

키워드: 두 개 이상 실제 반복, 미리 올리지 않음, 변경이 공통을 거치는 비용

두 개 이상의 앱에서 **같은 형태로 실제 반복될 때** 올립니다. "언젠가 쓸 것 같아서" 미리 올리지 않습니다.

한 곳에서만 쓰는 코드를 공통으로 올리면 그 뒤로 모든 변경이 공통 package를 거쳐야 해서, 얻는 것보다 비용이 큽니다.

### Turborepo는 왜?

키워드: 태스크 의존성, 빌드 캐시, 앱별 독립 배포 CI, npm script 호환

Turborepo를 선택한 이유는 모노레포에서 필요한 기능이 태스크 의존성 관리와 빌드 캐시였기 때문입니다.

각 앱과 패키지의 의존 관계를 기준으로 필요한 작업만 실행하고, 변경되지 않은 작업은 캐시된 결과를 재사용해서 불필요한 빌드를 줄일 수 있었습니다.

또 앱별로 독립 배포할 수 있도록 CI를 구성해서, 실제 변경사항이 있는 앱만 배포되도록 했습니다.

추가로 기존 package.json의 npm script 기반 워크플로우를 그대로 활용할 수 있어서 프론트엔드 생태계와도 잘 맞았습니다.

### 독립 배포가 정말 되나요?

키워드: 앱 단위 빌드·배포 분리, 공통 package 변경은 전체 영향

앱 단위 빌드·배포는 분리되어 있습니다. 한 앱을 배포한다고 다른 앱을 같이 올릴 필요는 없습니다.

다만 완전한 독립은 아닙니다. **공통 package를 바꾸면 그걸 쓰는 앱 전부가 영향을 받습니다.** 그래서 공통 package의 변경은 더 신중하게 봅니다.

---

# 마이크로 프론트엔드는 검토하지 않으셨나요?

## 왜 이 질문이 나오나

모노레포·독립 배포를 이야기하면 자연스럽게 따라오는 질문입니다. **도입하지 않은 기술에 대해서도 왜 안 했는지 말할 수 있어야** 선택이 판단으로 인정됩니다. 안 해본 걸 해본 것처럼 말하는 게 최악이고, 아예 모른다고 하는 게 그다음입니다.

## 핵심

```text
모노레포  빌드 시점에 코드를 공유한다 — 배포 단위는 나눌 수 있다
MFE      런타임에 독립 배포된 조각을 조합한다
대가     공유 의존성 버전, 런타임 로딩 실패, 스타일 격리, 통합 테스트
팀 경계가 배포 경계여야 할 만큼 커졌을 때 값을 한다
```

## 답변

검토했지만 도입하지 않았습니다. 저희가 풀려던 문제는 **"서로 다른 팀이 서로의 배포를 기다린다"**가 아니라 **"같은 것을 여러 번 다시 만든다"**였기 때문입니다.

둘의 차이는 통합 시점에 있습니다. 모노레포는 빌드 시점에 코드를 공유하고 애플리케이션은 각자 배포됩니다. 마이크로 프론트엔드는 각 조각이 독립적으로 배포된 뒤 **런타임에 조립**됩니다. 조직이 커서 팀 경계가 곧 배포 경계여야 할 때 이 런타임 독립성이 값을 합니다.

대신 비용이 큽니다. 조각들이 공유하는 라이브러리의 버전을 맞춰야 하고 — React가 두 벌 로드되면 훅이 깨집니다 — 한 조각이 로딩에 실패했을 때의 화면을 설계해야 하고, 스타일 격리와 전역 상태 공유, 통합 테스트가 전부 새 문제로 올라옵니다.

저희는 애플리케이션이 세 개였고 한 팀이 다뤘습니다. 이 규모에서 런타임 조립의 이점은 거의 없고 비용만 남는다고 판단해서, **모노레포로 코드를 공유하고 배포 단위만 나누는 선까지** 갔습니다. 지금도 그 판단이 맞았다고 생각합니다.

> ✍️ Module Federation을 직접 써본 적이 없다면 그렇게 말할 것. "개념은 알고, 우리 규모에선 필요 없다고 판단했다"가 정직하면서도 충분히 좋은 답이다.

## 꼬리

### 그럼 언제 도입을 고려하시겠어요?

키워드: 팀 수와 배포 주기, 기술 스택이 갈릴 때, 레거시 점진 대체

세 가지 신호를 봅니다. **배포가 서로를 기다리는 일이 반복될 때**, 조각마다 기술 스택이나 교체 시점이 달라야 할 때, 그리고 레거시를 화면 단위로 조금씩 대체해야 할 때입니다.

마지막 경우는 실제로 저희 상황과 가까웠습니다. PHP 기반 레거시와 새 React 서비스가 공존했으니까요. 다만 저희는 조각을 런타임에 섞는 대신 **경로 단위로 서비스를 가르는 방식**을 택했습니다. 훨씬 단순하고, 이 정도 규모에서는 같은 효과를 냅니다.

### 독립 배포는 모노레포로도 되나요?

키워드: 저장소와 배포 단위는 별개, 변경 감지 빌드, 공유 패키지 변경 시 영향 범위

됩니다 — **저장소가 하나인 것과 배포 단위가 하나인 것은 별개 문제**입니다. Turborepo로 변경된 앱만 빌드·배포하도록 구성했습니다.

다만 완전한 독립은 아닙니다. 공유 패키지를 고치면 그걸 쓰는 앱들이 함께 영향을 받고 함께 나가야 합니다. 그래서 공유 영역의 변경은 더 보수적으로 다루고, 호환을 깨는 변경은 나눠서 반영합니다. 이 점을 "완전히 독립적입니다"라고 말하면 과장이라고 생각합니다.

# Design System을 왜 만들었나요?

## 답변

여러 관리자와 사용자 서비스에서 같은 UI 패턴을 반복 구현해야 했기 때문에 공통 토큰과 컴포넌트를 분리했습니다.

목표는 "공통 컴포넌트를 많이 만드는 것"이 아니라 동일한 규칙을 여러 앱에서 재사용하고 변경 시 한 곳에서 관리하는 것이었습니다.

## Storybook과 컴포넌트 버전 관리는 어떻게 했나요?

키워드: 상태·변형 문서화, 코드 없이 확인, 별도 패키지, 영향 범위 확인

Storybook으로 공통 컴포넌트의 상태·변형을 문서화해서, 디자이너·다른 개발자가 코드를 열지 않고도 어떤 컴포넌트가 있고 어떻게 쓰는지 확인할 수 있게 했습니다.

공통 컴포넌트는 별도 패키지로 분리해 각 앱이 의존하는 구조였고, 공통이 바뀌면 그걸 쓰는 앱들이 영향을 받으므로 변경 시 영향 범위를 확인하는 것을 원칙으로 했습니다.

> ✍️ **확정(2026-08-28)** — 공유 패키지에 **버전을 붙여 배포**했고 수정이 있을 때마다 올렸다. workspace 참조로 항상 최신을 쓰는 구조가 아니었다. 따라서 "각 앱이 자기 시점의 버전을 쓰고, 올릴 때 의도적으로 올린다"고 말할 수 있다.

# 디자인 시스템의 토큰과 컴포넌트 API는 어떻게 설계했나요?

## 왜 이 질문이 나오나

이력서에 Design System이 **두 회사 모두**에 등장하고 Design Tokens·Storybook이 Skill에도 있습니다. "왜 만들었나"(앞 문항)는 답이 되어 있지만, 이 팀은 디자인 시스템을 실제로 운영하는 조직이라 **"어떻게 설계했고 어떻게 바꿔왔나"**까지 들어옵니다.

## 핵심

```text
토큰은 2단계 — 팔레트(원자) → 의미(semantic)
컴포넌트는 표시만, 도메인을 모른다
variant는 boolean 나열이 아니라 union 하나로
바꾸는 것보다 "바꿔도 안 깨지게 하는 것"이 어렵다
```

## 답변

토큰을 **두 단계**로 나눕니다. 먼저 색 스케일 같은 원자 팔레트를 두고, 그 위에 `primary`·`danger`처럼 **의미 기반 이름**을 얹어 팔레트를 참조하게 합니다.

이렇게 하면 다크 모드나 브랜드 색 변경이 **의미 층의 매핑만 바꾸는 일**이 됩니다. 컴포넌트는 `blue-500`이 아니라 `primary`를 쓰기 때문에 손댈 필요가 없습니다. 반대로 컴포넌트가 팔레트를 직접 쓰기 시작하면 이 층이 무의미해져서, 그건 린트로 막는 게 낫다고 봅니다.

컴포넌트 API에서는 두 가지를 지킵니다. **표시 컴포넌트는 도메인을 모르게** 하는 것 — Button은 "공고 지원 버튼"을 알면 안 되고 표시에 필요한 것만 받습니다. 그리고 **상태를 boolean으로 나열하지 않는 것** — `isPrimary`·`isDanger`가 따로 있으면 둘 다 true인 불가능한 조합이 생기므로 `variant` 하나로 묶습니다.

실제로 가장 어려운 건 만드는 게 아니라 **바꾸는 것**이었습니다. 여러 앱이 쓰는 컴포넌트의 props를 바꾸면 전부 영향을 받기 때문에, 호환을 깨는 변경은 한 번에 하지 않고 새 것을 추가한 뒤 기존 것을 사용 중단으로 표시하고 옮기는 순서로 갑니다.

## 꼬리

### Storybook은 실제로 어떻게 쓰셨나요?

키워드: 문서이자 합의 도구, 상태 조합 확인, 디자이너 리뷰, 방치되면 부채

**"이 컴포넌트가 어떤 상태를 가지는가"를 합의하는 자리**로 씁니다. 코드에서는 잘 안 보이는 로딩·비활성·긴 텍스트·에러 같은 조합을 한 화면에 늘어놓고 디자이너와 함께 봅니다.

주의할 점은 스토리가 실제 컴포넌트와 따로 놀기 시작하면 **읽는 사람을 속이는 문서**가 된다는 것입니다. 그래서 스토리를 별도 산출물이 아니라 컴포넌트 작업의 일부로 붙여두는 게 중요하다고 봅니다.

### 디자인 시스템에서 접근성은 어디까지 책임지나요?

키워드: 한 번 잡으면 전 앱이 이득, 역할·포커스·대비, 앱에서 매번 챙기면 실패

**여기서 잡는 게 가장 싸다**고 생각합니다. 앱마다 챙기면 반드시 빠지지만, Button·Modal·Input 같은 기본 컴포넌트에서 역할·키보드 포커스·포커스 트랩·대비를 한 번 해결하면 그 위에 만드는 화면은 자동으로 따라옵니다.

토큰 층도 여기에 기여합니다. 색 대비를 팔레트 단계에서 검증해두면 조합을 잘못 써서 대비가 무너지는 경우를 줄일 수 있습니다.

### 여러 앱이 쓰는 컴포넌트의 변경은 어떻게 배포했나요?

키워드: 추가 후 이전, deprecate 표시, 한 번에 다 바꾸지 않음, 영향 범위 확인

**깨는 변경을 한 번에 하지 않는 것**이 원칙입니다. 새 props를 추가해 공존시키고, 기존 것에 사용 중단 표시를 남기고, 앱을 하나씩 옮긴 뒤 마지막에 제거합니다.

모노레포라 어떤 앱이 무엇을 쓰는지 검색으로 바로 확인할 수 있다는 점이 도움이 됐습니다. 다만 그 편의 때문에 **"어차피 다 고치면 되지"라고 한 번에 바꾸려는 유혹**이 생기는데, 앱이 늘어날수록 그 방식은 안 됩니다.

# 인증은 어떻게 구성했나요?

## 답변

신규 서비스였지만 기존 사용자 인증 체계를 그대로 이어받아야 했기 때문에 인증 시스템 자체를 새로 만들지는 않았습니다.

기존 인증은 JWT 기반이었고, 백엔드가 로그인 성공 시 JWT를 `HttpOnly Cookie`에 담아 내려주는 구조였습니다.

신규 프론트에서도 토큰을 LocalStorage에 저장하거나 직접 `Authorization Header`에 주입하지 않고, 브라우저가 쿠키를 자동으로 전달하도록 구성했습니다.

특히 프론트와 API의 Origin이 달랐기 때문에 요청 시 `credentials: 'include'`를 사용했고, 서버에서도 `Access-Control-Allow-Credentials: true`와 허용 Origin을 명시적으로 설정했습니다.

또한 운영 환경에서는 서브도메인 간 인증 상태를 공유해야 했기 때문에 Cookie의 `Domain`, `SameSite`, `Secure`, `HttpOnly` 옵션을 함께 설정했습니다.

결과적으로 프론트에서는 토큰 자체를 직접 관리하지 않고, 쿠키 전달만 브라우저에 맡기고 실제 토큰 검증과 만료 처리는 서버에서 담당하도록 구성했습니다.

## 주의

```text
"세션 기반 인증"이라고 말하지 않는다
→ Session Store를 조회하는 전통적 세션 인증으로 들린다
→ 정확한 표현: 인증은 JWT, 보관·전달은 HttpOnly Cookie
```

## 확정된 사실 — 실제 쿠키 (2026-08-28 확인)

```text
Expires / Max-Age   없음      → Session Cookie
SameSite            Lax
Domain              .○○○.net  (앞의 점 = 서브도메인 포함)
Path                /
HttpOnly            O
Secure              O
```

정확한 명칭은 **"HttpOnly Session Cookie에 담긴 JWT 인증"**이다. 쿠키에 만료가 없고, 만료 판단은 서버가 JWT로 한다.

## 꼬리

### 세션 기반인가요, JWT 기반인가요?

키워드: 인증은 JWT, 보관·전달은 HttpOnly Cookie, Session Store 아님

인증 자체는 JWT 기반이고, JWT를 전달하고 보관하는 수단으로 HttpOnly Cookie를 사용했습니다.

서버가 Session ID로 별도의 Session Store를 조회하는 전통적인 세션 인증 방식은 아닙니다.

### 왜 localStorage가 아니라 Cookie인가요?

키워드: XSS 탈취, 스크립트 접근 불가, 브라우저 자동 전송, 서브도메인 공유

localStorage는 JavaScript로 읽을 수 있어서 XSS가 발생하면 토큰이 그대로 탈취됩니다.

HttpOnly Cookie는 스크립트가 읽을 수 없고 브라우저가 요청에 자동으로 실어주기 때문에, 프론트에 토큰을 다루는 코드 자체가 없어집니다. 서브도메인 간 인증 공유도 쿠키 도메인 설정으로 자연스럽게 해결됩니다.

### JWT는 만료 전 무효화가 어렵지 않나요?

키워드: 짧은 만료, 재발급, 블랙리스트, Session Store와의 트레이드오프

맞습니다. 토큰 자체에 인증 상태가 담겨 있어서 한 번 발급한 토큰을 만료 전에 서버가 되돌리기 어렵습니다.

그래서 만료를 짧게 가져가고 재발급으로 이어가는 방식이 일반적이고, 즉시 차단이 꼭 필요하면 서버 쪽에 블랙리스트 같은 상태를 다시 두게 됩니다. 이 지점이 Session Store 방식과의 실질적인 트레이드오프라고 생각합니다.

### SameSite는?

키워드: Strict, Lax, None은 Secure 필수, Lax는 GET 이동만 통과, 서브도메인끼리는 same-site

쿠키를 다른 사이트에서 시작된 요청에 실어 보낼지를 정합니다.

- `Strict`: 크로스 사이트 요청엔 전혀 안 보냄
- `Lax`: 최상위 내비게이션에만 보냄. 요즘 브라우저 기본값
- `None`: 항상 보냄. 반드시 `Secure` 필요

저희는 `Lax`입니다. 그래서 **외부 사이트에서 시작된 POST·fetch·iframe 요청에는 쿠키가 실리지 않고**, 링크를 눌러 들어오는 최상위 GET 이동에만 실립니다. 여기서 "상태를 바꾸는 요청을 GET으로 만들지 않는다"는 원칙이 짝이 됩니다 — Lax가 열어두는 유일한 통로가 GET 이동이라, 그 통로로 상태가 바뀌지 않으면 남는 구멍이 크게 줄어듭니다.

한 가지 더 — **서브도메인끼리는 same-site로 취급**됩니다. `a.○○○.net`과 `b.○○○.net`은 등록 도메인이 같아서 `Lax`여도 쿠키가 그대로 오갑니다. SameSite를 조여도 서브도메인 SSO가 깨지지 않는 이유입니다.

CSRF의 1차 방어선이지만 이것만으로 충분하다고 보진 않습니다.

### CSRF는 어떻게 막나요?

키워드: 쿠키 자동 전송으로 성립, SameSite, CSRF 토큰, Origin·Referer 검증

로그인된 상태를 이용해 공격자 사이트가 사용자의 브라우저로 의도하지 않은 요청을 보내게 만드는 공격입니다. 쿠키가 자동으로 실려 나가기 때문에 성립합니다.

방어는 겹쳐서 씁니다 — `SameSite`, CSRF 토큰 대조, 상태를 바꾸는 요청을 GET으로 만들지 않기, Origin/Referer 검증.

### 서브도메인 간 cookie domain은?

키워드: Domain 속성, 지정하면 서브도메인 포함·생략하면 host-only, 앞의 점은 무시됨, 공유 범위만큼 위험

쿠키의 **`Domain` 속성**이 결정합니다. `Domain=example.com`처럼 **지정하면** 그 도메인과 **모든 서브도메인**으로 전송되고, **아예 주지 않으면 host-only**가 되어 쿠키를 내려준 그 호스트에만 갑니다. 여러 서비스가 같은 인증을 공유해야 해서 지정하는 쪽이 맞았습니다.

값 앞의 점(`.example.com`)은 옛 표기이고 요즘 브라우저는 **무시합니다** — 점이 있어서 서브도메인이 포함되는 게 아니라, `Domain`을 지정한 것 자체로 포함됩니다.

주의할 점은 범위가 넓어질수록 위험도 같이 넓어진다는 것입니다. 서브도메인 하나가 뚫리면 그 쿠키를 공유하는 전체가 영향을 받으므로, 공유 범위를 필요한 만큼만 잡습니다.

### HttpOnly는 왜?

키워드: JS 접근 차단, 탈취 경로 축소, XSS 자체는 못 막음

JavaScript에서 쿠키 값을 직접 읽을 수 없게 해서 XSS 상황에서 인증 정보 자체가 탈취되는 경로를 줄일 수 있습니다.

다만 HttpOnly가 XSS 자체를 막는 것은 아닙니다.

### 그럼 XSS는 뭘로 막나요?

키워드: 기본 이스케이프, dangerouslySetInnerHTML, sanitize, CSP

- 사용자 입력을 그대로 HTML로 넣지 않습니다. React는 기본 이스케이프하지만 `dangerouslySetInnerHTML`은 예외입니다
- 마크다운·리치텍스트 렌더링은 sanitize를 거칩니다
- CSP로 실행 가능한 스크립트 출처를 제한합니다

HttpOnly는 피해를 줄이는 장치지 XSS의 해결책이 아닙니다. 스크립트가 실행되면 쿠키를 못 읽어도 사용자 권한으로 요청은 보낼 수 있습니다.

### Secure는?

키워드: HTTPS에서만 전송, 평문 탈취 방지

HTTPS 연결에서만 쿠키를 전송합니다. 평문 HTTP 요청에 쿠키가 실려 중간에서 탈취되는 걸 막습니다. 운영 환경 인증 쿠키에는 기본으로 붙입니다.

# 세션과 토큰이 혼재됐다는 게 무슨 뜻인가요?

## 답변

같은 사용자 인증이 **두 체계로 나뉘어 관리되던 상태**였습니다.

실 운영 웹은 기존 PHP 서버 세션으로 인증하고 있었고, 앱 웹뷰 쪽에서는 JWT 방식이 별도로 쓰이고 있었습니다. 같은 사용자인데 환경에 따라 인증 수단이 달라서, 로그인 상태 판단·만료 처리·신규 서비스 연동을 **두 벌로 고민**해야 했습니다.

신규 서비스가 늘어나는 시점이라 이 구조로는 서비스를 추가할 때마다 인증 연동 비용이 반복될 것이 명확했고, 그래서 **JWT를 HttpOnly Cookie에 담아 서브도메인으로 공유하는 방식으로 통일**했습니다. 프론트는 토큰을 직접 다루지 않고, 어떤 서비스든 같은 쿠키로 인증 상태가 이어집니다.

> ✍️ **확정(2026-08-28)** — 당시에는 **브릿지로 토큰을 넘기는 방식**이었고, 지금 기준으로는 미성숙한 구조였다. 감추지 말고 그대로 말한 뒤 **"지금 다시 한다면 쿠키 주입으로 갈 것 같습니다 — 웹과 웹뷰의 인증 코드가 갈라지지 않는 게 가장 큰 이점이라"**로 닫는다. 개선 방향을 말할 수 있으면 오히려 가점이다.

## 꼬리

### 통합하면서 어려웠던 점은?

키워드: 한 번에 안 갈아끼움, 기존 세션 유지, 쿠키 도메인·만료 선합의, 신규부터 적용

인증은 잘못 건드리면 전 서비스 로그인이 깨지는 영역이라, 한 번에 갈아끼우지 않고 **기존 세션이 동작하는 상태를 유지하면서 새 방식을 붙이는 순서**로 갔습니다. Backend와 쿠키 도메인 범위·만료 정책을 먼저 합의하고, 신규 서비스부터 새 방식을 적용했습니다.

### 왜 헤더 방식(Authorization)이 아니라 쿠키인가요?

키워드: 서브도메인 인증 공유, 도메인 설정으로 해결, 토큰 저장 코드, JS 노출

여러 서브도메인 서비스가 재로그인 없이 인증을 공유해야 했는데, 쿠키는 도메인 설정만으로 이것이 해결됩니다. 헤더 방식은 각 앱이 토큰을 저장하고 실어 보내는 코드를 전부 가져야 하고, 저장 위치가 JavaScript에 노출되는 문제도 있습니다.

# Reverse Proxy를 왜 선택했나요?

## 답변

100개가 넘는 도메인이 하나의 Backend API를 사용하는 구조였는데 모든 도메인을 Backend의 CORS allowlist에서 관리하면 도메인 추가 때마다 Backend 설정과 배포가 필요했습니다.

인프라 수준에서 프록시를 구성하는 방법도 있었지만 당시에는 기존 Next 서버를 활용하면 별도 인프라를 추가하지 않고 일관된 API 경로를 만들 수 있었습니다.

API hop과 Next 서버 의존성이 증가하는 단점은 알고 있었지만 당시 규모에서는 운영 단순성의 이점이 더 크다고 판단했습니다.

## Why — CORS가 왜 문제?

키워드: 도메인 추가마다 Backend 설정·배포, 변경 주기가 다른 시스템의 결합

CORS 자체가 어려운 문제가 아니라:

```text
프론트 도메인 추가
→ Backend 설정 수정
→ Backend 배포
```

로 변경 주기가 다른 시스템이 묶이는 것이 문제였습니다.

## Trade-off

```text
API hop
Next server 부하
장애 전파
```

## 꼬리

### Next 서버가 죽으면?

키워드: API도 같이 막힘, 완전한 격리 아님, 인프라 레벨 프록시로 전환

API 호출도 같이 막힙니다. 프록시를 애플리케이션 서버에 얹었을 때의 가장 큰 대가입니다.

사용자 쪽에는 장애 페이지와 재시도 흐름을 제공했지만, 완전한 장애 격리를 만들었다고 말하면 과장입니다. 격리가 중요해지면 프록시를 인프라 레벨로 내리는 게 맞는 방향이라고 봅니다.

### 쿠키는 어떻게 전달되나요?

키워드: 별개의 요청, 명시적으로 옮겨 붙임, Set-Cookie 반환, Domain 유효성

브라우저→프록시와 프록시→Backend가 별개의 요청이라, 인증 쿠키를 명시적으로 옮겨 붙여야 Backend가 로그인 요청으로 인식합니다.

이때 헤더를 통째로 전달하지 않고 **무엇을 넘길지 명시적으로 정하는 게** 중요합니다. 반대 방향도 같습니다 — Backend의 `Set-Cookie`를 응답에 다시 실어야 하고, 도메인이 바뀌므로 쿠키의 `Domain` 속성이 사용자 도메인에서 유효한지 확인해야 합니다.

### timeout / retry는?

키워드: 프록시 타임아웃 ≤ Backend, 멱등 요청만 재시도, POST 중복 생성

프록시가 무한정 기다리면 Backend 지연이 곧 프론트 전체 장애로 번지므로 Backend 호출에 상한을 둡니다. 프록시의 타임아웃은 Backend보다 짧거나 같아야 프록시가 먼저 정리됩니다.

재시도는 조회성·멱등 요청, 일시적 실패에 한정하고 횟수를 제한합니다. 멱등하지 않은 POST는 기본적으로 재시도하지 않습니다 — 처리는 됐는데 응답만 못 받은 경우 중복 생성이 발생합니다.

# SSR / SSG를 왜 나눴나요?

## 답변

동네생활백서는 검색 유입이 중요한 콘텐츠 서비스였기 때문에 모든 페이지를 하나의 렌더링 방식으로 처리하지 않고 콘텐츠의 변경 주기와 요청 시점 데이터 필요 여부를 기준으로 SSR과 SSG를 나눴습니다.

```text
자주 바뀌고 요청 시 최신값 필요 → SSR
변경 적고 미리 생성 가능 → SSG
```

그리고 URL 구조, metadata, sitemap, indexing 정책을 함께 설계했습니다.

## 꼬리

### SSG 페이지가 계속 늘어나면 빌드는?

키워드: 페이지 수에 비례, 자주 조회만 미리 생성, 첫 요청 시 생성, ISR

전부 빌드 시점에 만들면 페이지 수에 비례해 빌드가 느려집니다.

그래서 자주 조회되는 페이지만 미리 생성하고 나머지는 첫 요청 시 생성해 캐시하거나, 재검증 주기(ISR)를 둬서 배포 없이 갱신되게 하는 방식을 씁니다. 기준은 "얼마나 자주 바뀌고, 첫 요청 지연을 허용할 수 있는가"입니다.

### 색인이 실제로 됐는지 어떻게 확인하나요?

키워드: 제출 URL vs 색인 URL 비교, noindex 잔존, robots.txt, canonical 충돌

색인 모니터링을 제가 전담하지는 않았습니다. 제 역할은 색인이 가능한 구조를 구현하는 쪽이었고, 구현할 때 색인을 막는 요인이 없는지 — `noindex` 잔존, robots.txt 차단, canonical 충돌 — 을 확인했습니다.

방법 관점에서 답하면, sitemap 제출이 색인을 보장하지 않으므로 제출한 URL 수와 실제 색인된 URL 수를 비교해서 격차가 큰 그룹을 찾는 방식으로 접근합니다.

색인이 안 되는 원인은 보통 정해져 있습니다 — `noindex` 잔존, robots.txt 차단, canonical이 다른 URL을 가리킴, 콘텐츠가 얇거나 중복.

# Vue와 React를 둘 다 썼는데, 비교해주실 수 있나요?

## 답변

둘 다 실무에서 운영해봤습니다. 레거시가 PHP Blade와 Vue 기반이었고, 신규 서비스는 React·Next.js로 만들었습니다.

가장 큰 차이는 **상태 변화를 다루는 방식**이라고 생각합니다. Vue는 반응성 시스템이 의존성을 자동 추적해서 바뀐 곳만 갱신해주고, 템플릿·스타일·로직이 SFC 규칙으로 정리되어 팀 코드가 균일해지기 쉽습니다. React는 상태가 바뀌면 컴포넌트를 다시 실행하는 모델이라 리렌더링을 개발자가 이해하고 제어해야 하는 대신, JSX가 그냥 JavaScript라서 표현의 자유도와 생태계가 넓습니다.

그래서 Vue는 규칙이 정해진 안에서 빠르게 만들기 좋았고, React는 복잡한 UI와 추상화를 설계할 때 더 유연하다고 느꼈습니다. 어느 쪽이 우월하다기보다 **팀과 제품 상황에 맞는 선택**의 문제라고 생각합니다.

## 꼬리

### 왜 신규 서비스는 React로 갔나요?

키워드: SSR·SEO 요구, Next.js 생태계 성숙, 라이브러리·채용 생태계

신규 서비스는 검색 유입이 중요해서 SSR·SEO를 제대로 지원하는 프레임워크가 필요했고, Next.js 생태계가 그 요구에 가장 성숙해 있었습니다. 이후 서비스 확장과 라이브러리·채용 생태계까지 고려하면 신규 기반은 React 쪽이 맞다고 판단했습니다.

### 월 200만 방문 규모에서 프론트가 특별히 신경 쓴 것은?

키워드: SEO 안 깨뜨리기, URL·리다이렉트·인덱싱, 배포 회귀 확인

두 가지입니다. 첫째, 트래픽의 큰 축이 검색 유입이라 **SEO를 깨뜨리지 않는 것** — URL·리다이렉트·인덱싱 정책이 바뀌는 변경은 특히 조심했습니다. 둘째, 레거시와 신규가 병행 운영되는 상태라 **배포가 기존 사용자 흐름을 회귀시키지 않는지**를 확인하는 것이었습니다.

# 기술 스터디와 블로그 모임을 계속 운영하시는 이유가 뭔가요?

## 왜 이 질문이 나오나

이력서 Education에 **프론트엔드 기술 서적 스터디 운영(24.11~)**, **기술 블로그 모임(25.01~)**, 방통대 재학, 항해플러스 수료가 적혀 있습니다. 이건 "성실함"을 보려는 질문이 아니라 **학습을 실제 업무 결과로 어떻게 바꾸는지**를 보는 질문입니다.

## 핵심

```text
읽는 것과 설명하는 것은 다르다 — 설명해야 구멍이 드러난다
운영까지 하는 이유는 강제로 마감을 만들기 위해서
학습 → 실제 도입까지 이어진 사례를 하나는 준비
```

## 답변

혼자 읽으면 이해했다고 착각하기 쉬운데, **남에게 설명하려고 하면 어디를 모르는지가 바로 드러납니다.** 스터디를 참여만 하지 않고 운영까지 하는 이유는 스스로에게 마감을 만들기 위해서입니다.

블로그 모임도 같은 이유입니다. 글로 쓰려면 "왜 그렇게 동작하는지"까지 확인해야 해서, 업무에서 그냥 넘어갔던 것들을 다시 파게 됩니다.

방통대 컴퓨터과학과에 다니는 것도 비슷한 판단이었습니다. 실무에서는 필요한 부분만 골라 배우게 되는데, **기초를 순서대로 훑는 경험은 따로 만들지 않으면 안 생긴다**고 봤습니다.

## 꼬리

### 새 기술을 팀에 도입할 때는 어떤 기준으로 판단하나요?

키워드: 문제가 먼저, 작은 범위 검증, 되돌릴 수 있는가, 팀이 유지 가능한가

**해결하려는 문제가 먼저 있어야** 합니다. 좋아 보여서 도입하면 대개 그 기술이 문제로 바뀝니다.

그다음은 되돌릴 수 있는지를 봅니다. 한 화면이나 한 패키지처럼 작은 범위에서 먼저 써보고, 아니다 싶으면 걷어낼 수 있는 형태로 시작합니다. 마지막이 **팀이 유지할 수 있는가**입니다. 저만 이해하는 구조는 제가 자리를 비우는 순간 부채가 되기 때문에, 도입할 거라면 문서와 규칙까지 같이 남기는 걸 조건으로 봅니다. AI Harness에 규칙을 축적한 것도 같은 생각에서 나온 선택이었습니다.

### 학습한 것 중 실제로 업무를 바꾼 사례가 있나요?

# 클로저를 실무에서 언제 마주치나요?

## 왜 이 질문이 나오나

"클로저가 뭔가요"는 암기 질문이라 요즘 잘 안 나오지만, **"useEffect 의존성 배열이 왜 필요한가요"**나 **"왜 옛날 값이 찍히나요"**는 자주 나옵니다. 둘 다 클로저 질문입니다. 개념이 아니라 **증상에서 출발해 설명할 수 있는지**가 핵심입니다.

## 핵심

```text
함수는 자기가 만들어진 시점의 환경을 기억한다
React 훅은 이 성질 위에 서 있다 — 렌더마다 새 함수, 새 환경
증상 1  타이머·구독 안에서 옛날 state를 본다 (stale closure)
증상 2  구독을 정리 안 하면 잡고 있던 값이 안 풀린다 (누수)
```

## 답변

클로저는 **함수가 자기가 만들어진 자리의 변수를 계속 들고 다니는 성질**입니다. 실무에서 이걸 의식하게 되는 건 대부분 "왜 옛날 값이 보이지?" 하는 순간입니다.

React 함수 컴포넌트는 렌더마다 함수가 통째로 다시 만들어지고, 그 안의 핸들러들은 **그 회차의 값을 붙잡은 채로** 밖으로 나갑니다. 그래서 한 번만 등록되는 타이머나 구독 안에서는 등록 시점의 값이 영원히 고정됩니다.

```js
useEffect(() => {
  const id = setInterval(() => {
    setCount(count + 1); // count는 첫 렌더의 0에 고정 → 계속 1
  }, 1000);
  return () => clearInterval(id);
}, []);
```

해결은 두 가지입니다. **이전 값 기준으로 갱신하거나**(`setCount(prev => prev + 1)`), 최신 값을 계속 봐야 하면 ref처럼 렌더와 무관하게 유지되는 그릇을 쓰는 것입니다. 의존성 배열에 값을 넣으면 effect가 다시 실행되면서 새 클로저로 교체되는데, 타이머라면 매번 재등록되는 부작용이 생기므로 상황에 따라 고릅니다.

정리하면 의존성 배열은 린트를 만족시키려고 있는 게 아니라 **"이 함수가 어느 시점의 값을 봐야 하는가"를 선언하는 자리**라고 이해하고 있습니다.

## 꼬리

### 클로저 때문에 메모리 누수가 나는 경우가 있나요?

키워드: 구독·리스너 정리 안 함, 참조가 살아 있으면 회수 안 됨, cleanup

있습니다. 이벤트 리스너나 구독을 등록해두고 정리하지 않으면, **그 콜백이 붙잡고 있는 값들이 통째로 살아남습니다.** 컴포넌트는 화면에서 사라졌는데 콜백이 그 시점의 상태와 DOM 참조를 계속 잡고 있는 상태가 됩니다.

그래서 effect에서 등록한 것은 반드시 cleanup에서 해제합니다. SPA는 페이지가 새로고침되지 않아서 이런 누수가 세션 내내 쌓인다는 점이 일반 페이지와 다릅니다. 웹뷰처럼 앱과 메모리를 나눠 쓰는 환경에서는 더 직접적인 문제가 됩니다.

### 렌더마다 함수가 새로 만들어지면 낭비 아닌가요?

키워드: 함수 생성 비용은 작다, 문제는 참조가 바뀌는 것, memo·의존성 깨짐

함수를 만드는 비용 자체는 거의 문제가 안 됩니다. 실제 문제는 **참조가 매번 달라진다**는 것입니다.

그 함수를 memo된 자식에게 props로 내려보내면 얕은 비교가 항상 실패해서 memo가 무의미해지고, effect 의존성에 넣으면 매 렌더마다 effect가 다시 돕니다. `useCallback`은 성능 최적화라기보다 **참조를 안정시키는 도구**에 가깝고, 그래서 받는 쪽이 참조에 민감할 때만 의미가 있다고 봅니다.

# this와 프로토타입은 요즘도 알아야 하나요?

## 왜 이 질문이 나오나

함수 컴포넌트만 쓰면 직접 마주칠 일은 줄었습니다. 하지만 **라이브러리 코드를 읽을 때, 레거시(Vue Options API·클래스 컴포넌트)를 만질 때, 그리고 "왜 여기서 undefined가 나오지" 하는 순간**에 반드시 걸립니다. 저는 실제로 PHP·Vue 레거시와 React를 함께 다뤘기 때문에 피해갈 수 없는 영역이었습니다.

## 핵심

```text
this는 정의 위치가 아니라 "어떻게 호출됐는가"로 정해진다
화살표 함수는 자기 this가 없다 — 바깥 걸 그대로 쓴다
class는 프로토타입의 문법 설탕
instanceof는 프로토타입 체인을 따라 올라가며 확인한다
```

## 답변

`this`에서 헷갈리는 이유는 **선언된 위치가 아니라 호출 방식으로 정해지기 때문**입니다. 객체의 메서드로 부르면 그 객체가 되고, 그냥 함수로 부르면 잃어버립니다. 그래서 메서드를 콜백으로 넘기는 순간 끊깁니다.

```js
const timer = {
  sec: 0,
  tick() {
    this.sec++;
  },
};
setInterval(timer.tick, 1000); // this가 timer가 아님
setInterval(() => timer.tick(), 1000); // 호출 형태를 유지
```

화살표 함수는 **자기 `this`를 만들지 않고 바깥 스코프의 것을 그대로 씁니다.** 그래서 콜백 안에서 상위 컨텍스트를 유지하고 싶을 때 편하고, 클래스 컴포넌트 시절의 `bind` 보일러플레이트가 사라진 것도 이 덕분입니다.

프로토타입은 **객체가 다른 객체에게 "없으면 저쪽에 물어봐"라고 위임하는 구조**입니다. `class` 문법은 이 위에 얹힌 표현이고, 메서드는 인스턴스마다 복사되지 않고 프로토타입에 한 벌만 있습니다. `instanceof`가 이 체인을 따라 올라가며 확인하는 것도 같은 구조 위에서 동작합니다.

실무에서 이걸 알아야 하는 이유는 새로 그런 코드를 짜기 위해서가 아니라, **남의 코드를 읽고 디버깅하기 위해서**라고 생각합니다.

## 꼬리

### 그럼 항상 화살표 함수를 쓰면 되나요?

키워드: 동적 this가 필요한 자리, 프로토타입에 안 올라감, 인스턴스마다 생성

아닙니다. **`this`가 호출 대상에 따라 달라져야 하는 자리**에서는 오히려 틀립니다. 예를 들어 DOM 이벤트 핸들러에서 `this`로 해당 엘리먼트를 받거나, Vue Options API의 메서드처럼 프레임워크가 `this`를 주입해주는 구조에서는 화살표 함수를 쓰면 깨집니다.

클래스에서 화살표 함수를 필드로 선언하면 프로토타입이 아니라 **인스턴스마다 하나씩 생깁니다.** 인스턴스가 아주 많은 경우엔 차이가 생길 수 있어서, 자동 바인딩의 편의와 맞바꾸는 선택이라고 이해하고 있습니다.

### 라이브러리 프로토타입을 확장해도 되나요?

키워드: 전역 오염, 다른 코드와 충돌, 표준 추가 시 깨짐, 유틸 함수로

내장 객체의 프로토타입을 건드리는 건 피합니다. 전역에 영향을 주기 때문에 다른 라이브러리와 같은 이름으로 충돌할 수 있고, **나중에 표준에 같은 이름의 메서드가 들어오면 조용히 동작이 달라집니다.**

필요한 기능은 그냥 유틸 함수로 두는 게 안전합니다. 확장이 주는 편의보다 나중에 원인을 못 찾는 버그의 비용이 훨씬 큽니다.

# 객체 상태를 다룰 때 무엇을 조심하나요?

## 왜 이 질문이 나오나

"상태를 바꾸면 React는 무엇을 하나요" 문항에서 **참조 비교**를 이야기하면 곧바로 여기로 이어집니다. 화면이 안 바뀌는 버그와 이상하게 같이 바뀌는 버그가 전부 이 지점에서 나옵니다.

## 핵심

```text
전개 연산자는 한 겹만 복사한다 — 안쪽은 참조를 공유한다
직접 수정하면 참조가 그대로라 React가 변화를 모른다
깊은 복사는 필요할 때만 — 대부분은 바뀐 경로만 새로 만들면 된다
```

## 답변

가장 자주 나오는 사고는 **얕은 복사를 깊은 복사로 착각하는 것**입니다.

```js
const next = { ...user }; // 한 겹만 새로 만든다
next.profile.name = 'x'; // 안쪽은 원본과 같은 객체 → 원본도 바뀐다
```

React 상태에서 이게 문제가 되는 이유는 두 방향입니다. 원본을 직접 수정하면 **참조가 그대로라 변화를 감지하지 못해 화면이 안 바뀌고**, 반대로 여러 상태가 같은 안쪽 객체를 공유하면 **하나만 고쳤는데 다른 쪽도 같이 바뀝니다.**

그렇다고 매번 통째로 깊은 복사할 필요는 없습니다. 원칙은 **바뀐 경로만 새로 만들고 나머지는 참조를 재사용하는 것**입니다. 안 바뀐 부분의 참조가 유지되면 memo나 selector의 얕은 비교도 그대로 이득을 봅니다.

중첩이 깊어져서 이 작업이 지저분해지면, 그건 대개 **상태 구조 자체가 잘못 잡혔다는 신호**로 봅니다. 평평하게 펴거나 조각을 나누는 쪽을 먼저 검토합니다.

## 꼬리

### 깊은 복사가 정말 필요하면 뭘 쓰나요?

키워드: structuredClone, JSON 왕복의 손실, 함수·DOM은 복제 불가

`structuredClone`이 표준으로 있습니다. 순환 참조도 처리하고 `Date`·`Map`·`Set`도 유지합니다.

예전에 많이 쓰던 `JSON.parse(JSON.stringify(...))`는 **`undefined`가 사라지고 `Date`가 문자열이 되는 등 조용히 값이 변형**되기 때문에 피합니다. 다만 `structuredClone`도 함수나 DOM 노드는 복제하지 못하므로, 순수한 데이터에만 쓴다는 전제가 붙습니다.

### 원본을 못 바꾸게 강제할 수도 있나요?

키워드: Object.freeze는 얕음, 개발 환경 가드, 타입으로 readonly

`Object.freeze`가 있지만 **한 겹만 얼어서** 중첩 객체는 그대로 수정됩니다. 런타임에 전부 얼리는 건 비용도 있어서 저는 두 가지를 씁니다.

타입 레벨에서 `readonly`로 막아 **컴파일 시점에 잡는 것**이 우선이고, 정말 사고가 잦은 영역이라면 개발 환경에서만 freeze를 걸어 위반을 빨리 드러냅니다. 프로덕션 런타임 비용 없이 실수를 잡는 쪽이 낫다고 봅니다.

# React스럽게 코드를 작성한다는 것

## 답변

UI를 상태와 props의 결과로 선언적으로 표현하는 것이라고 생각합니다.

DOM을 직접 변경하는 대신 state가 바뀌면 UI가 그 결과를 자연스럽게 반영하도록 하고, 계산 가능한 값은 중복 state로 저장하지 않으며 외부 시스템과 동기화가 필요한 경우가 아니라면 effect를 최소화합니다.

## Why Map

```text
왜 선언적?
→ 변경 과정 직접 관리 X

왜 최소 state?
→ 동기화 대상 감소

왜 derived?
→ source of truth 중복 방지

왜 effect 최소?
→ 실행순서 / 동기화 복잡도 감소
```

## 꼬리

### derived state 예를 들어주세요

키워드: 필터링 목록, 중복 state 동기화, 계산 가능한 값은 계산

목록과 검색어가 있을 때 필터링된 목록을 별도 state로 두지 않는 것입니다.

```tsx
// 중복 저장: items나 keyword가 바뀔 때마다 동기화 코드가 필요
const [filtered, setFiltered] = useState(items);

// 파생: 항상 최신이고 동기화할 게 없다
const filtered = items.filter((item) => item.name.includes(keyword));
```

state를 두 개 두면 어긋나는 순간이 반드시 생깁니다. 계산할 수 있는 값은 계산합니다.

### useEffect는 언제 쓰나요?

키워드: 외부 세계 동기화, 구독 등록·해제, 이벤트 핸들러, 파생값

React 바깥 세계와 동기화할 때만 씁니다 — 구독 등록/해제, 브라우저 API 조작, 외부 저장소 동기화.

반대로 props로 계산 가능한 값은 그냥 계산하고, 사용자 행동에 대한 반응은 이벤트 핸들러에서 처리합니다. 렌더 결과를 보고 다른 state를 맞추는 effect는 구조를 잘못 잡았다는 신호로 봅니다.

### useMemo는 언제 쓰나요?

키워드: 무거운 계산, 참조 동일성, 원인 먼저 제거, 측정 후 적용

계산 자체가 무거울 때, 그리고 memo된 자식의 props나 의존성 배열에 들어가는 객체·배열처럼 참조 동일성이 필요할 때입니다.

단순 계산에 붙이는 건 비교 비용과 가독성만 잃습니다. 순서는 **먼저 리렌더의 원인을 없애고, 그래도 남으면 측정한 뒤** 붙입니다.

# 상태를 바꾸면 React는 무엇을 하나요?

## 왜 이 질문이 나오나

"React스럽게"와 "상태관리 비교"는 **어떻게 쓰는가**입니다. 이 문항은 그 아래 — **왜 그렇게 동작하는가**입니다. 리렌더를 줄였다거나 memo를 썼다는 이야기를 하는 순간 바로 여기로 내려옵니다.

## 핵심

```text
setState → 다시 그릴 대상으로 표시 → 렌더 예약
렌더  컴포넌트 함수를 다시 실행해 새 엘리먼트 트리를 만든다 (DOM 아님)
비교  같은 위치·같은 타입이면 갱신, 타입이 다르면 버리고 새로 만든다
커밋  달라진 부분만 실제 DOM에 반영
부모가 리렌더되면 자식도 기본적으로 리렌더된다
```

## 답변

상태를 바꾸면 DOM이 즉시 바뀌는 게 아니라 **"다시 그려야 한다"고 예약**만 됩니다.

이후 렌더 단계에서 해당 컴포넌트 함수를 다시 실행해 새 엘리먼트 트리를 만듭니다. 이건 아직 DOM이 아니라 "이렇게 생겨야 한다"는 설명서에 가깝습니다. React는 이 새 트리를 이전 트리와 같은 위치끼리 비교해서, **타입이 같으면 속성만 갱신하고 타입이 다르면 그 자리를 버리고 새로 만듭니다.** 그리고 실제로 달라진 부분만 DOM에 반영합니다.

여기서 실무에 직접 영향을 주는 사실이 두 가지입니다.

첫째, **부모가 리렌더되면 자식은 props가 그대로여도 기본적으로 리렌더됩니다.** 자식 함수를 다시 실행해봐야 결과가 같은지 알 수 있기 때문입니다. 그래서 리렌더 비용이 실제로 문제가 될 때 `memo`로 "props가 얕은 비교로 같으면 건너뛰라"고 알려주는 것이고, 반대로 말하면 **memo를 붙였는데 매 렌더마다 새 객체나 새 함수를 props로 내려보내면 아무 효과가 없습니다.**

둘째, **상태는 컴포넌트가 아니라 트리에서의 위치에 붙습니다.** 같은 위치에 같은 타입이 계속 있으면 상태가 유지되고, 조건 분기로 위치가 달라지면 상태가 초기화됩니다. 리스트에서 `key`가 중요한 것도 같은 이유입니다 — key가 "이건 아까 그 항목"이라고 알려주는 신분증이라, 인덱스를 key로 쓰면 중간에 항목을 지웠을 때 신분증이 밀려서 **엉뚱한 항목에 입력값이 남는** 버그가 납니다.

## 꼬리

### 왜 setState 직후에 값을 읽으면 옛날 값이 나오나요?

키워드: 렌더 단위 스냅샷, 클로저, 즉시 반영 아님, 함수형 업데이트

상태 값이 **그 렌더 시점의 스냅샷으로 고정**되어 있기 때문입니다. 컴포넌트 함수가 실행될 때 그 안의 변수는 그 회차의 값을 클로저로 잡고 있고, `setState`는 다음 렌더를 예약할 뿐 진행 중인 함수의 변수를 바꾸지 않습니다.

```js
const [n, setN] = useState(0);
setN(n + 1);
setN(n + 1); // n은 여전히 0 → 결과는 1
setN((prev) => prev + 1); // 이전 값 기준 → 안전
```

그래서 **이전 값에 기반해 갱신할 때는 함수형 업데이트**를 씁니다. 이게 "React가 이상하게 동작한다"고 느끼는 지점의 대부분인데, 사실은 렌더를 값의 스냅샷 단위로 다룬다는 모델이 일관되게 적용된 결과라고 이해하고 있습니다.

### 상태를 여러 번 바꾸면 렌더도 여러 번 되나요?

키워드: 자동 배칭, 한 번에 묶어서 한 번 렌더, React 18부터 범위 확대

아닙니다. 여러 상태 변경을 **한 덩어리로 묶어서 한 번만 렌더**합니다. 중간 상태로 화면을 그리면 깜빡임이 생기고 낭비이기 때문입니다.

React 18 이전에는 이 묶음이 이벤트 핸들러 안에서만 적용돼서, `setTimeout`이나 비동기 콜백 안에서는 각각 렌더되는 차이가 있었습니다. 지금은 그런 경우도 자동으로 묶입니다.

### 같은 값으로 setState를 하면 어떻게 되나요?

키워드: Object.is 비교, 같으면 건너뜀, 객체는 참조가 달라짐, 불변 갱신

값이 같으면 렌더를 건너뜁니다. 비교는 `Object.is` 기준의 참조 비교입니다.

그래서 객체나 배열을 다룰 때 **기존 객체를 직접 수정하면 참조가 그대로라 화면이 안 바뀌고**, 반대로 내용이 같아도 매번 새 객체를 만들면 항상 리렌더됩니다. 불변 갱신을 하는 이유가 코딩 취향이 아니라 이 비교 방식 때문이라고 봅니다.

### 렌더가 중간에 멈출 수도 있나요?

키워드: 작업 단위로 쪼갬, 급한 업데이트 우선, useTransition, 렌더 함수는 순수해야

렌더 작업을 작은 단위로 쪼개서 처리하기 때문에, 더 급한 일이 생기면 **진행 중인 렌더를 중단하고 나중에 다시 시작할 수 있습니다.** 무거운 목록을 그리는 도중에도 입력 반응이 먼저 처리되게 하려는 구조입니다.

`useTransition`으로 "이 업데이트는 급하지 않다"고 표시하면 그 렌더는 뒤로 밀립니다. 검색어 입력은 즉시 반영하고 결과 목록 갱신은 양보하는 식입니다.

전제가 하나 있습니다 — **렌더 함수가 순수해야 합니다.** 중단·재시작될 수 있으니 렌더 중에 외부 값을 바꾸거나 요청을 보내면 그 작업이 두 번 일어날 수 있습니다. 개발 환경에서 effect를 두 번 실행해 보여주는 것도 이걸 미리 잡으라는 의도라고 이해하고 있습니다.

# 상태관리 경험을 비교해 주세요

## 답변

라이브러리보다 **상태의 성격과 소유권을 먼저 봅니다.**
Local UI State

컴포넌트 내부나 가까운 트리에서만 필요한 상태는 useState를 사용합니다. 예를 들어 모달의 열림/닫힘, 탭 선택, 입력값처럼 특정 화면 안에서만 쓰이는 상태라면 굳이 전역 상태로 올리지 않습니다.

Global Client State

여러 화면이나 컴포넌트에서 공유해야 하는 클라이언트 상태는 Zustand, Jotai, Redux를 고려합니다. Zustand는 단순하게 store를 구성하기 좋고, Jotai는 atom 단위로 상태를 잘게 나눠 관리하기 좋습니다. Redux는 상태 변화 흐름과 규칙을 명확히 가져가야 하는 큰 상태 관리에 적합합니다.

Server State

서버에서 가져오는 데이터는 TanStack Query를 사용합니다. 서버 데이터는 단순히 저장하는 것보다 캐시, stale 상태, refetch, mutation, invalidation 같은 동기화 문제가 중요하기 때문에 별도의 서버 상태로 봅니다.

URL State

검색어, 필터, 정렬 조건, pagination처럼 공유하거나 뒤로가기, 새로고침 이후에도 복원되어야 하는 상태는 URL State로 관리합니다.

## 꼬리

### Context는 왜 상태관리가 아닌가요?

키워드: 전달 수단, 구독 전체 리렌더, theme·auth처럼 드물게 변하는 값

Context는 상태관리 도구가 아니라 **전달 수단**입니다. 값이 바뀌면 구독하는 모든 컴포넌트가 리렌더됩니다.

그래서 theme·auth처럼 자주 바뀌지 않는 전역 값에 쓰고, 자주 바뀌는 값은 store로 빼서 필요한 컴포넌트만 구독하게 합니다.

### Query가 있으면 전역 store가 필요 없지 않나요?

키워드: 관리 대상이 다름, 서버 데이터 복사본, 클라이언트 소유 상태

관리하는 대상이 다릅니다. Query는 원본이 서버에 있는 데이터의 복사본을 관리하고, store는 클라이언트가 소유한 상태를 관리합니다.

서버 데이터를 store에 넣으면 캐시·stale·중복 요청·경쟁 상태를 전부 손으로 짜게 되고, 반대로 순수 client state를 Query에 넣을 이유도 없습니다. 서버 데이터는 Query, 진짜 client state만 store에 남깁니다.

### URL state의 단점은?

키워드: 문자열 파싱·검증, 신뢰할 수 없는 입력, 민감한 값 금지, 변경 빈도

- 전부 문자열이라 파싱·검증이 필요하고, 사용자가 직접 고칠 수 있어 신뢰할 수 없는 입력으로 다뤄야 합니다
- 민감한 값은 안 됩니다 — URL은 로그·히스토리·Referer로 새어 나갑니다
- 변경 빈도가 높은 상태에는 부적합합니다

그래서 공유·복원이 필요한 상태만 URL에 둡니다.

# 전역 상태 라이브러리는 리렌더를 어떻게 줄이나요?

## 왜 이 질문이 나오나

이력서에 Zustand·Jotai·Redux·Pinia·Apollo가 나열되어 있습니다. "언제 뭘 쓰나"(앞 문항)를 답하면 다음은 반드시 **"그럼 그게 어떻게 동작해서 Context보다 나은가"**입니다.

## 핵심

```text
Context  값이 바뀌면 구독하는 컴포넌트가 전부 리렌더 — 선택 구독이 없다
외부 store  상태를 React 밖에 두고, 컴포넌트가 필요한 조각만 구독
Zustand  selector로 조각 선택 + 얕은 비교
Jotai    atom 자체가 구독 단위
```

## 답변

핵심 차이는 **"바뀐 걸 누가 어떻게 아느냐"**입니다.

Context는 값이 바뀌면 그 Context를 쓰는 컴포넌트가 **전부** 다시 그려집니다. "이 필드만 볼게요"라고 말할 방법이 없습니다. 그래서 theme이나 로그인 사용자처럼 **드물게 바뀌는 값의 전달 통로**로는 훌륭하지만, 자주 바뀌는 상태를 담으면 리렌더가 넓게 퍼집니다.

외부 store 라이브러리는 상태를 React 트리 밖에 두고, 컴포넌트가 **필요한 조각만 골라 구독**합니다. 상태가 바뀌면 store가 구독자에게 알리고, 각 컴포넌트는 자기가 고른 조각이 실제로 달라졌을 때만 리렌더됩니다.

```js
// 전체 구독 — 어떤 값이 바뀌어도 리렌더
const state = useStore();
// 조각 구독 — count가 바뀔 때만 리렌더
const count = useStore((s) => s.count);
```

Zustand는 이 selector 방식이고, Jotai는 atom 하나하나가 구독 단위라서 상태를 잘게 나누는 것 자체가 리렌더를 나누는 일이 됩니다. 접근이 다를 뿐 **"구독 범위를 좁힌다"**는 목적은 같습니다.

그리고 서버 데이터는 아예 이 층에 두지 않습니다. 캐시·stale·재요청·무효화는 성격이 다른 문제라 React Query가 담당하고, 전역 store에는 정말 클라이언트 상태만 남기는 게 제 기준입니다.

## 꼬리

### selector를 쓰는데도 리렌더가 계속되면 원인이 뭘까요?

키워드: 매번 새 객체 반환, 얕은 비교 실패, 필드 단위로 쪼개기

selector가 **매번 새 객체를 만들어 반환**하는 경우가 대부분입니다.

```js
// 매 호출마다 새 객체 → 항상 "달라졌다"고 판단
const { a, b } = useStore((s) => ({ a: s.a, b: s.b }));
```

기본 비교가 참조 비교라서, 내용이 같아도 새 참조면 리렌더됩니다. 필드 단위로 각각 구독하거나, 얕은 비교 옵션을 명시해서 해결합니다. selector를 썼다는 사실만으로 최적화가 되는 게 아니라 **반환값의 참조가 안정적이어야** 의미가 있습니다.

### 외부 store를 React가 안전하게 읽는 방법이 따로 있나요?

키워드: useSyncExternalStore, tearing, 동시성 렌더링 중 값 변경

`useSyncExternalStore`라는 전용 훅이 있고, 요즘 라이브러리들은 이걸 씁니다.

렌더가 중단·재시작될 수 있다 보니, 한 번의 렌더 안에서 어떤 컴포넌트는 옛 값을 다른 컴포넌트는 새 값을 읽어서 **화면이 서로 다른 시점의 상태로 조각나는 문제**(tearing)가 생길 수 있습니다. 이 훅은 구독과 스냅샷 읽기를 React가 정한 방식으로 통일해 그걸 막습니다.

직접 `useEffect`로 store를 구독하는 코드를 짜면 이 보장이 없다는 점이 실질적인 차이입니다.

### 그럼 Redux를 쓸 이유는 뭔가요?

키워드: 흐름의 추적 가능성, 액션 로그·devtools, 팀 규모와 규칙

번들 크기나 코드량만 보면 요즘 선택지가 더 가볍습니다. Redux의 남는 가치는 **상태가 왜 그렇게 바뀌었는지를 추적할 수 있다는 것**이라고 봅니다. 모든 변경이 액션으로 남아서 devtools로 되짚을 수 있고, 여러 명이 손대는 큰 상태에서 규칙을 강제하기 좋습니다.

반대로 말하면 그 추적이 필요 없는 규모에서는 보일러플레이트만 남습니다. 저는 전역 상태를 최대한 줄이고 서버 상태와 URL 상태로 밀어내는 쪽을 먼저 시도합니다.

# React Query queryKey는 어떻게 관리하나요?

## 답변

캐싱의 identity를 이해하는가?

Query Key는 서버 데이터 캐시의 identity입니다. 그래서 도메인 단위 Key Factory를 만들어 일관되게 관리하고, 응답을 바꾸는 파라미터는 반드시 Key에 포함합니다. 이렇게 하면 키 파편화를 막고 캐시 충돌이나 잘못된 invalidation을 줄일 수 있습니다.

## 꼬리

### "filter object 넣어도 되나요?"

키워드: 구조적 해시, 직렬화 가능, key factory, undefined 주의

가능합니다. React Query는 key를 구조적으로 해시하기 때문에 객체 property의 순서는 문제가 되지 않습니다.

다만 직렬화 가능한 값이어야 하고, 같은 의미의 필터는 항상 같은 구조로 들어가야 합니다. 그래서 key factory에서 필터 객체의 형태를 한 곳에서 만들어주는 게 안전합니다. `undefined`가 든 property는 해시에서 사라져서 의도와 다른 키가 같아질 수 있는 점도 주의합니다.

### "왜 hierarchy?"

키워드: invalidate 범위 제어, all→detail 계층, 놓치면 stale 화면

invalidate 범위를 계층으로 제어할 수 있기 때문입니다.

사용자 데이터가 바뀌었을 때 `userKeys.all`로 무효화하면 목록과 상세가 한 번에 갱신되고, 특정 상세만 갱신하고 싶으면 `detail(id)`로 좁힙니다. 키 문자열이 흩어져 있으면 이 범위 제어가 안 되고, 무효화를 하나 놓치는 순간 stale한 화면이 남습니다.

# Hydration이 무엇이고 왜 필요한가요?

## 정의

서버가 생성한 HTML에 클라이언트 React가 상태와 이벤트 핸들러를 연결해 interactive하게 만드는 과정.

## 왜 필요한가?

키워드: 완성된 HTML 문자열, 이벤트 핸들러 없음, 같은 트리 재렌더·연결

SSR이 내려주는 건 완성된 HTML 문자열이라 이벤트 핸들러와 상태가 없습니다. 클라이언트 React가 같은 트리를 다시 렌더해서 기존 DOM에 연결해야 상호작용이 가능해집니다.

이때 "서버 렌더 결과와 클라이언트 첫 렌더 결과가 같다"는 전제가 있고, 아래 값들처럼 이 전제가 깨지면 hydration mismatch가 발생합니다.

## 꼬리

### mismatch는 어떻게 해결하나요?

키워드: 서버·클라 첫 렌더 불일치, props로 내리기, 마운트 후 갱신, SSR 끄기

원인은 하나입니다 — 서버 렌더 결과와 클라이언트 첫 렌더 결과가 다른 것.

- 매번 값이 달라지는 것(`Date.now` 등) → 서버에서 만들어 props로 내립니다
- `window`, `localStorage`, timezone → 첫 렌더는 서버와 같은 값을 그리고 마운트 이후에 갱신합니다
- 클라이언트에서만 의미 있는 부분 → dynamic import로 SSR을 끄거나 마운트 후 렌더합니다

`suppressHydrationWarning`은 경고만 숨길 뿐 원인을 고치지 않습니다.

### Client Component와 관계는?

키워드: hydration 대상은 Client만, use client는 말단에, 번들 크기

App Router에서 hydration 대상은 Client Component뿐입니다. Server Component는 렌더 결과만 전달되고 클라이언트 번들에 포함되지 않습니다.

`'use client'`를 트리 위쪽에 붙이면 그 아래 전체가 hydration 대상이 되고 번들도 커집니다. 가능한 말단에 두는 이유입니다.

### hydration 비용은?

키워드: JS 다운로드·파싱, 트리 재실행, 반응 없는 구간, 범위 좁히기

JS 다운로드·파싱, 트리 재실행, 그리고 그동안 화면은 보이는데 눌러도 반응 없는 구간 — 세 가지가 겹칩니다.

줄이는 방향은 클라이언트 컴포넌트 범위를 좁히고, 무거운 컴포넌트는 필요한 시점에 로드하고, 서버에서 끝낼 수 있는 건 Server Component로 두는 것입니다.

# App Router에서 서버와 클라이언트 사이에 실제로 무엇이 오가나요?

## 왜 이 질문이 나오나

이력서 첫 줄이 Next.js App Router입니다. "왜 App Router를 썼나요"(1단계)는 답할 수 있어도, **"그러면 서버에서 클라이언트로 뭐가 어떤 형태로 넘어가나요"**(2단계)에서 막히면 그 위에 쌓은 모든 설계 이야기가 추상론이 됩니다. Hydration 문항이 "왜 필요한가"라면, 이 문항은 "무엇이 오가는가"입니다.

## 핵심

```text
서버가 보내는 것은 HTML 하나가 아니다
HTML — 즉시 보여줄 비대화형 화면
RSC Payload — 서버 컴포넌트 트리의 렌더 결과 + 클라이언트 컴포넌트 자리 표시
JS 청크 — 클라이언트 컴포넌트 코드
이 셋이 만나 hydration
```

## 답변

서버가 응답 하나에 **두 가지**를 실어 보낸다고 이해하고 있습니다.

하나는 **HTML**입니다. 사용자가 JS를 기다리지 않고 즉시 보는, 아직 상호작용이 안 되는 화면입니다.

다른 하나는 **RSC Payload**입니다. 서버 컴포넌트를 실행한 결과를 직렬화한 데이터인데, 여기에는 서버 컴포넌트의 렌더 결과와 함께 **클라이언트 컴포넌트가 들어갈 자리 표시, 그 컴포넌트의 JS 파일 참조, 서버가 넘겨준 props**가 담깁니다. 서버 컴포넌트의 코드 자체는 클라이언트로 가지 않습니다 — 결과만 갑니다.

클라이언트에서는 HTML로 먼저 화면을 보여주고, RSC Payload로 서버·클라이언트 트리를 맞춘 뒤, 클라이언트 컴포넌트의 JS가 도착하면 hydration으로 이벤트 핸들러를 붙여 상호작용이 열립니다.

이 구조에서 얻는 실질적인 이점은 **서버 컴포넌트에 있는 코드와 의존성이 클라이언트 번들에 포함되지 않는다**는 것입니다. 무거운 마크다운 파서나 날짜 라이브러리를 서버 컴포넌트 안에서만 쓰면 사용자는 그걸 내려받지 않습니다. 웹뷰처럼 초기 로딩이 곧 체감 속도인 환경에서 이 차이가 큽니다.

이후 페이지 이동에서는 HTML을 다시 받지 않고 **RSC Payload만 받아서** 트리를 갱신합니다.

## 꼬리

### `'use client'`는 정확히 무엇을 바꾸나요?

키워드: 경계 선언, 파일이 아니라 경계, import 그래프가 클라이언트로, 아래는 전부 클라이언트

"이 컴포넌트를 클라이언트에서 실행한다"는 선언이 아니라 **경계 선언**입니다. 그 파일부터 시작해 import로 딸려오는 모듈들이 클라이언트 번들에 포함되고, 그 아래에 import된 컴포넌트들은 따로 표시하지 않아도 클라이언트 컴포넌트가 됩니다.

그래서 실무에서 중요한 건 **경계를 트리의 어디에 두느냐**입니다. 상태가 필요한 작은 컴포넌트 하나 때문에 페이지 최상단에 `'use client'`를 붙이면 그 아래 전부가 클라이언트로 내려가서, 서버 컴포넌트를 쓰는 이유가 사라집니다. 경계는 가능한 한 **잎사귀 쪽으로 밀어서** 붙이는 게 원칙이라고 봅니다.

### 클라이언트 컴포넌트 안에 서버 컴포넌트를 넣을 수 있나요?

키워드: import은 불가, children으로 주입은 가능, 이미 렌더된 결과를 전달

`'use client'` 파일에서 서버 컴포넌트를 직접 import 하면 그건 클라이언트 컴포넌트가 됩니다. 하지만 **`children`이나 props로 넘기는 것은 가능합니다.**

서버에서 이미 렌더된 결과를 클라이언트 컴포넌트가 그냥 자리에 꽂아 넣는 형태이기 때문입니다. 그래서 Provider나 레이아웃 껍데기처럼 상태만 가진 클라이언트 컴포넌트를 만들고, 안쪽 내용은 서버 컴포넌트로 유지하는 패턴을 씁니다. 이게 경계를 잎사귀로 미는 실질적인 방법입니다.

### 서버에서 클라이언트로 넘기는 props에 제약이 있나요?

키워드: 직렬화 가능해야 함, 함수·클래스 인스턴스 불가, 경계를 넘는 순간 네트워크

직렬화 가능한 값이어야 합니다. 함수나 클래스 인스턴스는 그대로 넘길 수 없습니다 — RSC Payload에 실려 네트워크를 건너가야 하기 때문입니다.

그리고 **넘기는 props가 곧 전송량**이라는 점도 중요합니다. 서버에서 받은 큰 응답을 통째로 클라이언트 컴포넌트에 내려보내면, 렌더링은 서버에서 했는데 데이터는 다 내려가는 상황이 됩니다. 경계에서 필요한 필드만 추려서 넘기는 게 맞다고 봅니다.

### Suspense를 걸면 서버가 어떻게 동작하나요?

키워드: 스트리밍, fallback 먼저 전송, 준비되면 이어서 전송, TTFB와 LCP 분리

준비된 부분부터 **먼저 흘려보냅니다.** 페이지 전체가 완성될 때까지 기다리지 않고, 느린 부분은 fallback을 먼저 보내고 데이터가 준비되면 나머지를 이어 보내 그 자리를 채웁니다.

효과는 **느린 데이터 하나가 전체 페이지의 첫 응답을 잡아먹지 않게 되는 것**입니다. 목록은 바로 보이고 추천 영역만 늦게 채워지는 식입니다.

다만 만능은 아닙니다. 스트리밍은 응답 시작을 앞당길 뿐 전체 완료 시간을 줄이지는 않고, fallback과 실제 콘텐츠의 높이가 다르면 레이아웃 이동(CLS)이 생깁니다. 그래서 스켈레톤은 실제 콘텐츠와 크기를 맞춰서 만듭니다.

### Next의 캐시는 어디에 걸리나요?

키워드: 계층이 여러 개, 요청 단위 중복 제거·데이터 캐시·라우트 캐시·클라이언트 라우터 캐시, Next 16은 use cache로 모델 변경 중

한 덩어리가 아니라 **계층이 여러 개**라는 게 핵심이고, 버그의 대부분은 "어느 계층이 안 지워졌는지"를 착각해서 생깁니다.

기존 모델에서는 같은 요청 안의 중복 fetch 제거, 요청 간 공유되는 데이터 캐시, 렌더 결과를 통째로 저장하는 라우트 캐시, 그리고 브라우저 쪽 라우터 캐시가 층을 이룹니다. 무효화는 시간 기반(revalidate)과 태그·경로 기반(on-demand) 두 축입니다.

Next 16에서는 이 모델이 **Cache Components 방향으로 정리되는 중**입니다. `use cache`로 함수나 컴포넌트 단위로 캐시를 명시하고, `cacheLife`로 수명을, `cacheTag`로 무효화 단위를 지정합니다. 캐시가 "기본으로 켜져 있어서 언제 꺼지는지 외워야 하는 것"에서 **"명시적으로 켜는 것"**으로 바뀌는 흐름이라고 이해하고 있습니다.

> ✍️ 지원하는 팀이 어느 모델을 쓰는지는 알 수 없다. "예전 모델은 이랬고 지금은 이 방향으로 가고 있다"까지 말하면 충분하고, 확신 없는 옵션 이름을 단정하지 말 것.

### 당근알바 같은 서비스라면 이 구조에서 무엇을 조심하시겠어요?

키워드: 개인화 데이터는 캐시 금지, 사용자군별 경계, 웹뷰 저사양 hydration 비용

두 가지입니다.

첫째, **개인화된 데이터가 공유 캐시에 섞이지 않게 하는 것**입니다. 공고 목록처럼 모두가 같은 걸 보는 화면과 내 지원 현황처럼 나만 보는 화면은 캐시 단위가 완전히 달라야 하고, 이 경계를 잘못 잡으면 남의 데이터가 보이는 사고로 이어집니다. 성능 문제가 아니라 보안 문제입니다.

둘째, **웹뷰에서의 hydration 비용**입니다. 서버가 HTML을 아무리 빨리 보내도 클라이언트 컴포넌트가 많으면 저사양 안드로이드에서 "보이는데 눌리지 않는" 구간이 길어집니다. 그래서 경계를 잎사귀로 미는 작업이 웹뷰에서는 취향이 아니라 성능 요구사항이 된다고 봅니다.

# Sitemap은 어떻게 생성하나요?

## 답변

검색엔진이 크롤링할 URL 목록을 XML로 제공합니다.

정적인 페이지라면 build 시 생성할 수 있고, 동적인 서비스라면 DB나 API에서 공개 가능한 URL을 조회해서 생성합니다.

URL 수가 많다면 sitemap index를 두고 여러 sitemap으로 분리합니다.

Next App Router에서는 `sitemap.ts`를 이용하거나 요구사항에 따라 dynamic route로 생성할 수 있습니다.

## 같이 보는 것

```text
robots.txt
canonical
lastModified
index 여부
```

## 꼬리

### robots.txt와 차이는?

키워드: 크롤러 접근 제어, URL 발견 돕기

robots.txt는 검색엔진 크롤러가 접근할 수 있는 경로를 제어하는 파일이고,
sitemap.xml은 검색엔진이 사이트의 주요 URL을 더 쉽게 발견할 수 있도록 페이지 목록을 제공하는 파일입니다.

### canonical은?

키워드: 대표 URL 힌트, 중복 평가 분산 방지, sitemap과 일치

같은 내용이 여러 URL로 존재할 때 대표 URL을 알려주는 힌트입니다. 파라미터·페이지네이션 때문에 생긴 중복의 평가 분산을 막습니다.

sitemap에는 canonical URL만 넣습니다. 둘이 다른 URL을 가리키면 신호가 충돌합니다.

### 모든 페이지를 넣나요?

키워드: 색인 대상만, noindex·중복 제외, 크롤링 예산

색인시키고 싶은 페이지만 넣습니다. 개인화 화면, 조합이 무한한 검색 결과, `noindex` 페이지, canonical이 아닌 중복 URL은 뺍니다. 가치 없는 URL이 많으면 크롤링 예산만 낭비됩니다.

# SPA에서 URL과 뒤로가기는 어떻게 처리하나요?

## 핵심

```text
session history
pushState
replaceState
popstate
```

## 답변

SPA에서는 `pushState`와 `replaceState`로 페이지 전체 reload 없이 URL과 history entry를 변경할 수 있습니다.

사용자가 뒤로 / 앞으로 이동하면 history entry가 바뀌고 `popstate`를 통해 UI 상태를 맞출 수 있습니다.

검색이나 필터처럼 복원이 필요한 상태를 local state에만 두면 URL과 UI가 어긋날 수 있어서 URL state를 사용합니다.

## 꼬리

### pushState와 replaceState 차이?

키워드: 새 항목 vs 덮어쓰기, 뒤로가기로 돌아오고 싶은가, 필터는 push 타이핑은 replace

`pushState`는 history에 새 항목을 추가하고, `replaceState`는 현재 항목을 덮어씁니다.

기준은 "사용자가 뒤로가기로 이 상태로 돌아오고 싶어할까"입니다. 필터 적용은 push, 검색어 타이핑 중간값이나 스크롤 위치는 replace가 맞습니다. 타이핑마다 push하면 뒤로가기를 수십 번 눌러야 이전 화면으로 돌아갑니다.

# Promise의 상태와 all·allSettled·race·any 차이를 설명해주세요

## 반드시 알아야 할 것

```text
Promise state
pending
fulfilled
rejected
```

## then

Promise의 결과를 이어서 처리한다.

## Promise.all

모두 성공해야 성공.

하나가 reject되면 반환 Promise는 reject.

나머지 네트워크 요청 자체가 자동 취소되는 것은 아니다.

## Promise.allSettled

모든 Promise가 끝날 때까지 기다리고 각각 성공 / 실패 결과 반환.

## race

가장 먼저 settle된 Promise 결과.

## any

가장 먼저 fulfilled된 Promise 결과.

모두 reject되면 AggregateError.

## Event Loop 꼬리 대비

Promise callback은 microtask queue에서 처리된다.

```js
console.log(1);
setTimeout(() => console.log(2), 0);
Promise.resolve().then(() => console.log(3));
console.log(4);
// 1 → 4 → 3 → 2
```

microtask(Promise)는 현재 실행 중인 코드가 끝나면 **macrotask(setTimeout)보다 먼저** 전부 비워진다.

## 꼬리

### race는 실무에서 언제 쓰나요?

키워드: 타임아웃, 진 Promise 취소 아님, AbortController

대표적으로 타임아웃입니다.

```js
const result = await Promise.race([fetchData(), timeout(3000)]);
```

주의할 점은 race에서 진 Promise가 취소되는 게 아니라는 것입니다. 요청은 계속 진행되고 결과만 버려지므로, 실제 취소가 필요하면 `AbortController`를 씁니다.

### await를 연달아 쓰면 어떻게 되나요?

키워드: waterfall, 의존 없으면 Promise.all 병렬

앞 요청이 끝나야 다음이 시작하는 waterfall이 됩니다. 서로 의존하지 않는 요청이라면 `Promise.all`로 동시에 출발시킵니다.

```js
// 순차 — B는 A가 끝난 뒤 시작
const a = await apiA();
const b = await apiB();

// 병렬
const [a, b] = await Promise.all([apiA(), apiB()]);
```

# 이벤트 루프는 실제로 어떤 순서로 도나요?

## 왜 이 질문이 나오나

Promise 문항에서 출력 순서를 맞히면 다음은 반드시 **"왜 그 순서인가"**입니다. 그리고 이 원리는 성능 문항(INP)과 곧바로 이어집니다 — 답답한 화면의 원인은 대부분 **한 태스크가 너무 길어서 루프가 다음 일을 못 하는 것**이기 때문입니다.

## 핵심

```text
1. 콜스택의 현재 작업을 끝까지 실행 (중간에 못 끊는다)
2. 마이크로태스크 큐를 "전부" 비운다  ← Promise 콜백
3. 필요하면 렌더링 (스타일→레이아웃→페인트)
4. 다음 매크로태스크 하나를 꺼낸다  ← setTimeout, 클릭 이벤트
```

## 답변

JS는 한 번에 하나의 작업만 실행하고, **실행 중인 작업은 중간에 끊지 않는 것**이 대전제입니다. 이벤트 루프는 이 작업들을 어떤 순서로 꺼낼지 정하는 규칙입니다.

핵심은 큐가 **두 종류**라는 점입니다. `setTimeout`이나 사용자 이벤트 같은 매크로태스크는 루프를 한 바퀴 돌 때 하나씩 꺼내지만, Promise 콜백 같은 마이크로태스크는 **현재 작업이 끝나는 즉시 큐가 빌 때까지 전부** 처리됩니다. `setTimeout(fn, 0)`보다 `Promise.then`이 항상 먼저 실행되는 이유가 이것입니다.

여기서 두 가지가 따라옵니다.

첫째, **렌더링도 루프의 한 단계입니다.** 화면 갱신은 마이크로태스크를 다 비운 뒤에 일어납니다. 그래서 마이크로태스크가 계속 새 마이크로태스크를 만들어내면 렌더링 차례가 영영 오지 않아서 화면이 완전히 멈춥니다 — 무한 루프와 증상이 같은데 원인은 다릅니다.

둘째, **긴 작업 하나가 모든 것을 막습니다.** 클릭 핸들러 안에서 무거운 계산을 50ms 이상 돌리면 그동안 들어온 입력·스크롤·애니메이션이 전부 대기합니다. INP가 나쁜 화면의 원인 대부분이 이 "긴 태스크"이고, 해결책은 계산을 잘게 쪼개 사이사이 루프에 양보하거나 워커로 넘기는 것입니다.

## 꼬리

### setTimeout(fn, 0)은 정말 0ms 뒤에 실행되나요?

키워드: 최소 지연, 큐에 등록될 뿐, 앞의 작업이 끝나야 실행, 중첩 시 최소값 상향

아닙니다. **"0ms 뒤에 큐에 넣어라"**는 의미이고, 실제 실행은 콜스택이 비고 앞선 마이크로태스크가 전부 끝난 뒤입니다. 앞 작업이 500ms 걸렸다면 그 뒤입니다.

명세상 최소 지연도 있어서, 타이머가 여러 겹 중첩되면 브라우저가 최소값을 4ms 정도로 올립니다. 그래서 setTimeout은 **정확한 시간 도구가 아니라 "지금 말고 나중에" 표시**로 이해하는 게 맞다고 봅니다.

### requestAnimationFrame은 어디에 끼나요?

키워드: 다음 페인트 직전, 프레임에 맞춤, 애니메이션은 rAF, 백그라운드 탭에서 멈춤

**다음 렌더링 직전**에 실행됩니다. 화면 주사율에 맞춰 호출되므로 애니메이션을 setTimeout으로 돌리는 것보다 프레임이 안정적이고, 탭이 백그라운드로 가면 호출이 멈춰서 자원도 아낍니다.

한 프레임 안에서 여러 요소의 위치를 읽고 쓰는 작업을 여기에 모아두면, 읽기·쓰기가 뒤섞여 생기는 강제 동기 레이아웃(layout thrashing)도 줄일 수 있습니다.

### async/await는 이 그림의 어디에 있나요?

키워드: Promise의 문법, await 이후가 마이크로태스크, 함수는 그 자리에서 반환

Promise를 다르게 쓴 문법일 뿐 별도의 메커니즘이 아닙니다. `await`를 만나면 함수는 그 자리에서 일단 반환되고, **나머지 코드는 마이크로태스크로 예약**됐다가 이어집니다.

그래서 `await` 뒤의 코드는 항상 마이크로태스크 순서를 따르고, 앞 문항에서 본 "연달아 await하면 직렬로 기다린다"는 것도 같은 이유입니다.

### 긴 계산을 어떻게 쪼개나요?

키워드: 루프에 양보, 청크 단위 처리, Web Worker, 사용자 입력 우선

원칙은 **중간중간 루프에 제어권을 돌려주는 것**입니다. 큰 배열을 한 번에 도는 대신 일정 개수씩 처리하고 다음 태스크로 넘기면, 그 사이에 입력과 렌더링이 처리됩니다.

계산 자체가 무겁고 DOM이 필요 없다면 **Web Worker로 다른 스레드에 넘기는 게 정석**입니다. 메인 스레드는 사용자 입력에 응답하는 데 쓰는 게 우선이라고 봅니다.

# 브라우저 렌더링 과정과 CSS가 성능에 미치는 영향을 설명해주세요

## Pipeline

```text
HTML → DOM
CSS → CSSOM
DOM + CSSOM → Render Tree
→ Layout
→ Paint
→ Composite
```

## 답변

브라우저는 HTML과 CSS를 각각 DOM과 CSSOM으로 파싱하고, 이를 합친 Render Tree로 Layout(위치·크기 계산) → Paint(픽셀 칠하기) → Composite(레이어 합성) 순서로 화면을 그립니다.

성능 관점에서는 **어느 단계를 다시 실행시키는 변경인가**가 핵심입니다. 레이아웃을 건드리는 변경이 가장 비싸고, 합성만 다시 하는 변경이 가장 쌉니다.

- **Render Tree**: 실제 화면에 그릴 요소들을 결정
- **Layout**: 각 요소의 크기와 위치 계산
- **Paint**: 색상, 테두리, 글자 같은 픽셀 정보를 그림
- **Composite**: 여러 레이어를 최종 화면에 합침

## 꼬리

### reflow와 repaint 차이는?

키워드: 위치·크기 재계산, 픽셀만 다시 칠함, reflow는 repaint 동반

- **reflow(layout)**: 위치나 크기를 다시 계산합니다. `width`, `top`, `font-size`, DOM 추가·삭제가 유발하고, 한 요소가 바뀌면 주변과 자식까지 영향을 받아 비쌉니다
- **repaint**: 위치는 그대로고 픽셀만 다시 칠합니다. `color`, `background-color` 등

reflow가 일어나면 repaint도 따라옵니다. 반대는 아닙니다.

### layout thrashing이 뭔가요?

키워드: 읽기·쓰기 교차, 강제 동기 레이아웃, 읽기 먼저 쓰기 몰아서

쓰기와 읽기를 번갈아 하면서 강제로 레이아웃 계산을 반복시키는 것입니다.

```js
// 매 반복마다 강제 동기 레이아웃
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px';
}
```

브라우저는 스타일 변경을 모아서 처리하려 하는데, `offsetWidth`처럼 레이아웃 결과가 필요한 값을 읽으면 그 자리에서 계산을 강제합니다. 해결은 **읽기를 먼저 다 하고 쓰기를 몰아서** 하는 것입니다.

### transform이 항상 빠른가요?

키워드: 합성 단계 처리 가능성, 레이어 승격 조건, 레이어 과다 비용, 측정

아닙니다. `transform` / `opacity`가 유리한 이유는 Layout과 Paint를 건너뛰고 합성 단계에서 처리될 **수 있기** 때문이지 항상 그런 건 아닙니다.

레이어 승격 조건에 따라 달라지고, 레이어가 많아지면 합성 비용과 메모리가 늘어 오히려 느려질 수 있습니다. "레이아웃 유발 속성보다 유리한 경우가 많다" 정도로 말하고 실제로는 측정합니다.

### will-change는?

키워드: 미리 알리는 힌트, 레이어 메모리, 직전에 켜고 끝나면 제거

곧 바뀔 속성을 브라우저에 미리 알려 레이어 승격 등을 준비시키는 힌트입니다.

레이어마다 메모리를 쓰기 때문에 상시로 켜두면 오히려 느려집니다. 애니메이션 직전에 켜고 끝나면 제거하는 게 원칙입니다.

### CSS selector가 성능에 중요한가요?

키워드: 대부분 병목 아님, CSS 전송량, DOM 노드 수, 측정 먼저

요즘은 대부분 병목이 아닙니다. 실제 병목은 보통 사용하지 않는 CSS 전송량, 과도한 DOM 노드 수, 레이아웃을 유발하는 애니메이션 쪽입니다. 선택자를 다듬기 전에 어디가 느린지 먼저 측정합니다.

# 성능을 개선했다면 무엇을 어떤 수치로 측정했나요?

## 왜 이 질문이 나오나

렌더링 파이프라인을 설명할 수 있는 것과, **개선을 숫자로 말할 수 있는 것**은 다른 능력입니다. "월 200만 방문"과 "웹뷰"를 이력서에 쓴 이상, 무엇을 재서 무엇이 좋아졌는지 언어가 없으면 앞의 모든 최적화 이야기가 추상론이 됩니다.

## 핵심

```text
LCP  주요 콘텐츠가 보이기까지        좋음 2.5초 이하
INP  상호작용 → 다음 프레임까지      좋음 200ms 이하
CLS  누적 레이아웃 이동             좋음 0.1 이하
Lab(Lighthouse)는 재현, Field(실사용자)는 진실
```

## 답변

사용자가 체감하는 것을 세 구간으로 나눠서 봅니다 — **보이기까지, 눌렀을 때 반응하기까지, 보는 동안 흔들리지 않기**.

**LCP**는 뷰포트에서 가장 큰 콘텐츠 요소가 그려지는 시점입니다. 보통 히어로 이미지나 제목이 그 대상이라, 서버 응답 시간(TTFB), 렌더 차단 리소스, 그리고 그 이미지의 로딩 우선순위가 지배합니다. 목록 상단 이미지에 lazy loading을 걸어버려서 LCP가 나빠지는 게 아주 흔한 실수입니다.

**INP**는 사용자의 입력부터 화면이 실제로 바뀔 때까지를 봅니다. 2024년에 FID를 대체했는데, FID가 "첫 입력이 처리되기 시작할 때까지"만 재서 실제 답답함과 어긋났기 때문입니다. INP는 **처리와 렌더링까지 포함**해서 훨씬 정직합니다. 원인은 대부분 메인 스레드를 오래 잡는 작업 — 큰 목록의 리렌더, 무거운 동기 계산입니다.

**CLS**는 콘텐츠가 뒤늦게 들어오면서 화면이 밀리는 정도입니다. 이미지·광고 영역에 크기를 미리 잡아두지 않거나, 스켈레톤과 실제 콘텐츠의 높이가 다를 때 생깁니다.

측정은 두 종류를 구분해서 씁니다. Lighthouse 같은 **lab 측정**은 조건이 고정돼 재현과 회귀 확인에 좋고, 실제 사용자에게서 수집하는 **field 측정**은 저사양 기기·느린 네트워크가 섞인 진짜 분포를 보여줍니다. 개선 여부의 판단은 field 쪽 값으로 하는 게 맞다고 생각합니다 — lab에서 좋아졌는데 실사용자 값이 그대로인 경우가 실제로 있습니다.

> ✍️ **확정(2026-08-28): 성능을 수치로 측정한 경험은 없다.** 지어내지 말고 *"지표로 관리해본 경험은 없고, 이 지표들로 봐야 한다고 이해하고 있습니다"*까지만 말한다. 이 문항은 B티어이고, 원리를 설명할 수 있으면 충분하다.

## 꼬리

### LCP를 나쁘게 만드는 원인을 순서대로 짚어주세요

키워드: TTFB, 렌더 차단 리소스, 리소스 로딩 우선순위, 요소 렌더 지연

네 구간으로 쪼개서 봅니다. **서버 응답이 늦거나**(TTFB), **CSS·동기 스크립트가 렌더를 막거나**, **LCP 이미지의 발견·다운로드가 늦거나**, **데이터를 기다리느라 요소 자체가 늦게 그려지는** 경우입니다.

실무에서 가장 자주 걸리는 건 세 번째입니다. LCP 이미지가 JS 실행 후에야 DOM에 들어가면 브라우저가 그 존재를 늦게 알게 됩니다. 그래서 첫 화면 이미지는 서버 렌더 결과에 포함시키고 우선순위를 명시하는 게 기본이고, 반대로 화면 밖 이미지는 lazy로 미룹니다.

### INP가 나쁜데 원인을 어떻게 찾나요?

키워드: 롱태스크, 입력 지연·처리·렌더 3구간, 상태 변경 범위 축소

INP는 **입력 지연 → 이벤트 처리 → 다음 프레임 렌더** 세 구간의 합이라, 어디가 긴지부터 봅니다. 메인 스레드가 이미 다른 작업으로 막혀 있으면 첫 구간이, 핸들러가 무거우면 두 번째가, 상태 변경으로 큰 트리가 다시 그려지면 세 번째가 깁니다.

프론트엔드에서 가장 흔한 건 세 번째입니다. 입력 하나에 목록 전체가 리렌더되는 구조라면 상태를 잘게 나누거나 렌더 범위를 좁히는 게 우선이고, 무거운 계산은 잘라서 넘기거나 뒤로 미룹니다.

### 웹뷰에서는 이 수치가 왜 더 나빠지나요?

키워드: 저사양 기기 비중, 앱 메모리 공유, 앱 속도로 체감

기기 분포가 다릅니다. 앱 사용자에는 저사양 안드로이드 비중이 있어서, 개발 기기에서 괜찮은 INP가 현장에서 몇 배로 나옵니다. 웹뷰는 앱과 자원을 나눠 쓰기 때문에 여유도 더 적습니다.

그리고 사용자가 이걸 **웹이 아니라 앱이 느린 것**으로 인식한다는 게 중요합니다. 그래서 웹뷰 화면은 lab 수치보다 **하위 구간(예: 75·95 퍼센타일) 실사용자 값**을 기준으로 잡는 게 맞다고 봅니다.

### 번들 크기는 어떻게 관리하나요?

키워드: 무엇이 왜 들어갔는지, 경계 축소, 코드 분할, 예산 설정

크기 자체보다 **무엇이 왜 들어갔는지**를 봅니다. 번들 분석으로 큰 덩어리를 찾고, 그게 정말 첫 화면에 필요한지부터 따집니다.

App Router 환경에서는 클라이언트 경계를 좁히는 것이 가장 효과가 큽니다 — 서버 컴포넌트에만 있는 의존성은 애초에 내려가지 않기 때문입니다. 그다음이 라우트·모달 단위 코드 분할이고, 마지막으로 CI에 크기 예산을 걸어 회귀를 막습니다.

# 코드 스플리팅은 실제로 어떻게 동작하나요?

## 왜 이 질문이 나오나

"번들을 줄였다"는 말은 누구나 합니다. 면접에서 갈리는 건 **분할점이 어떻게 정해지고, 과하게 쪼개면 왜 오히려 느려지는지**를 아는가입니다.

## 핵심

```text
동적 import가 분할점 — 번들러가 그 지점에서 파일을 가른다
lazy + Suspense — 컴포넌트 단위로 늦게 불러오기
트리셰이킹은 다른 개념 — 안 쓰는 코드를 빌드 때 제거
과하게 쪼개면 요청이 줄줄이 이어지는 폭포수가 된다
```

## 답변

번들러는 정적 `import`를 따라가며 하나로 합치지만, **동적 `import()`를 만나면 거기를 경계로 파일을 나눕니다.** 그 지점의 코드는 별도 청크가 되고, 실제 호출 시점에 네트워크로 받아옵니다. React에서는 `lazy`와 `Suspense`를 얹어 로딩 중 대체 화면을 보여주는 형태로 씁니다.

자주 헷갈리는 게 트리셰이킹인데, 이건 **빌드 시점에 아무도 안 쓰는 코드를 지우는 것**이라 다른 개념입니다. 정적 분석이 가능해야 동작하므로 ESM 형태여야 하고, 부수효과가 있는 모듈은 지우지 못합니다. 코드 스플리팅이 "언제 받을지"를 나누는 거라면 트리셰이킹은 "아예 안 받을 것"을 지우는 겁니다.

기준은 **"첫 화면에 필요한가"**입니다. 라우트 단위 분할은 거의 항상 이득이고, 모달·에디터·차트처럼 열어야만 쓰는 무거운 UI도 좋은 후보입니다. 반대로 대부분의 사용자가 결국 여는 화면을 굳이 쪼개면 클릭 후 대기만 생깁니다.

## 꼬리

### 과하게 쪼개면 왜 느려지나요?

키워드: 요청 폭포수, 청크당 오버헤드, 캐시 파편화, 배포마다 해시 변경

**요청이 줄줄이 이어지기 때문입니다.** A를 받아야 그 안의 B를 알고, B를 받아야 C를 아는 구조가 되면 왕복이 누적됩니다. 특히 웹뷰·모바일 네트워크에서는 요청 하나하나의 지연이 커서 손해가 큽니다.

캐시 측면도 있습니다. 청크가 잘게 흩어지면 배포 때마다 바뀌는 파일이 늘어 캐시 적중률이 떨어집니다. 그래서 자주 바뀌는 앱 코드와 잘 안 바뀌는 라이브러리를 갈라두는 편이 낫습니다.

### 클릭한 뒤에 받으면 늦지 않나요?

키워드: 미리 불러오기, 호버·뷰포트 진입 시점, 유휴 시간 활용

그래서 **필요하다고 확신하기 전에 미리 받아둡니다.** 링크에 마우스를 올리거나 버튼이 화면에 들어온 시점에 청크를 미리 요청해두면, 실제 클릭 때는 이미 받아진 상태가 됩니다.

Next는 화면에 보이는 링크의 코드를 미리 가져오는 동작이 기본이라, 라우트 단위에서는 이 이점을 자동으로 얻습니다. 직접 만든 지연 로딩 컴포넌트라면 이 프리페치를 손으로 붙여야 합니다.

### 로딩 상태는 어떻게 보여주나요?

키워드: 레이아웃 이동 방지, 크기 맞춘 스켈레톤, 빠른 네트워크에선 깜빡임

빈 화면 대신 **실제 콘텐츠와 크기가 같은 스켈레톤**을 둡니다. 크기가 다르면 콘텐츠가 도착할 때 화면이 밀려서 CLS가 나빠집니다.

반대 문제도 있습니다 — 청크가 50ms 만에 도착하면 스켈레톤이 깜빡하고 사라져서 오히려 거슬립니다. 이럴 땐 스켈레톤 표시를 살짝 늦추거나, 한번 보여줬으면 최소 시간은 유지하는 식으로 다듬습니다.

### 웹뷰에서는 분할 기준이 달라지나요?

키워드: 첫 화면 최소화, 요청 왕복 비용 큼, 진입 경로가 정해져 있음

첫 화면을 최소로 만드는 게 더 중요해집니다. 웹뷰의 첫 로딩은 사용자가 **앱의 속도로 인식**하기 때문입니다.

대신 왕복 비용이 크니 잘게 쪼개기보다 **"첫 화면 / 나머지"로 굵게 가르는 편**이 낫다고 봅니다. 그리고 앱에서 웹뷰로 들어오는 진입 경로는 대체로 정해져 있어서, 그 경로의 코드를 미리 받아두는 최적화가 잘 먹히는 환경이라고 생각합니다.

# GraphQL을 써본 경험이 있나요? REST와 비교하면?

## 답변

이전 회사에서 농가 CMS를 **GraphQL(Apollo Client) 기반으로 풀스택 개발**한 경험이 있습니다. 스키마를 정의하고 클라이언트에서 쿼리·뮤테이션으로 데이터를 다루는 흐름을 실무로 다뤘습니다.

REST와의 본질적 차이는 **데이터 요구를 누가 정의하느냐**라고 생각합니다. REST는 서버가 엔드포인트별 응답 형태를 정하고, GraphQL은 클라이언트가 필요한 필드를 질의합니다.

그래서 GraphQL은 화면마다 필요한 데이터가 다를 때 **overfetching(안 쓰는 필드까지 받기)과 underfetching(여러 번 호출)** 문제를 스키마 하나로 풉니다. 스키마가 곧 타입이라 codegen으로 프론트 타입 안전성이 확보되는 것도 큰 장점이었습니다.

대신 대가도 있습니다 — 단일 엔드포인트 POST 중심이라 **HTTP 레벨 캐싱이 어렵고**, 서버는 리졸버 설계와 N+1 문제(DataLoader)를 감당해야 하며, 단순한 CRUD에는 REST보다 초기 비용이 큽니다.

정리하면 **화면이 다양하고 데이터 그래프가 복잡한 제품일수록 GraphQL의 이점이 커지고**, 단순 리소스 CRUD나 HTTP 캐싱이 중요한 공개 API는 REST가 낫다고 봅니다.

GraphQL은 클라이언트가 필요한 데이터 구조를 직접 요청하는 방식이고, 서버는 Schema로 가능한 데이터 구조를 정의합니다. 실제 데이터 조회는 Resolver가 담당합니다. 프론트에서는 Apollo Client를 사용해서 Query와 Mutation을 실행하고 응답을 캐싱합니다. Apollo는 객체를 \_\_typename과 id 기준으로 정규화해서 관리하기 때문에 같은 객체를 여러 화면에서 재사용하기 좋습니다. 서버에서는 중첩 Resolver 때문에 N+1 문제가 생길 수 있어서 DataLoader 같은 batching 전략을 사용할 수 있습니다.

## 꼬리

### 클라이언트 캐싱은 어떻게 다른가요?

키워드: 엔티티 단위 정규화, 쿼리 간 공유, React Query는 키 단위

Apollo 같은 GraphQL 클라이언트는 응답을 **엔티티 단위로 정규화**해서 캐시합니다. 같은 객체를 여러 쿼리가 공유하므로 한 곳에서 갱신되면 다른 화면에도 반영됩니다. React Query의 키 단위 캐시보다 강력한 대신, 캐시 정책과 무효화를 이해해야 예측 가능하게 동작합니다.

### 최근에는 왜 안 썼나요?

키워드: Backend가 REST, 데이터 레이어 본질 동일, 빠른 적응

현재 회사 Backend가 REST 기반이라 REST + React Query 조합을 썼습니다. 데이터 레이어의 본질 — 캐싱, 무효화, 서버 상태와 클라이언트 상태의 분리 — 은 같아서, GraphQL 팀에 합류해도 빠르게 적응할 수 있다고 생각합니다.

### Relay는 써봤나요? (당근 스택 — 우대사항에 명시)

키워드: 안 써봤음 정직하게, fragment colocation, 컴파일러 빌드 검증, 규약 강제

실무에서는 Apollo를 썼고 Relay는 써보지 않았습니다. 다만 지원을 준비하면서 Relay가 Apollo와 무엇이 다른지는 학습했습니다.

가장 큰 차이는 **fragment colocation**입니다. 각 컴포넌트가 자기가 필요한 데이터를 fragment로 선언하고, Relay 컴파일러가 빌드 타임에 이를 상위 쿼리 하나로 합칩니다. 데이터 요구가 컴포넌트 파일에 붙어 다니기 때문에, 컴포넌트를 옮기거나 지울 때 데이터 요구도 같이 따라갑니다.

이 방향은 제가 FSD에서 지켜온 원칙 — **부모는 합성만 하고, 컴포넌트가 자기 데이터를 직접 가져간다** — 과 같은 철학이라고 이해했습니다. Apollo는 쿼리를 어디에 둘지 팀 컨벤션에 맡기지만, Relay는 이걸 구조로 강제합니다.

그 외 차이로는:

- **컴파일러가 빌드 타임에 쿼리를 검증·최적화**합니다. 런타임 파싱 비용이 없고, 스키마에 없는 필드는 빌드가 깨집니다.
- 캐시 정규화가 **Global Object Identification**(모든 객체가 전역 유일 `id`를 갖는 Node 인터페이스) 규약 위에서 동작합니다. Apollo의 `__typename + id` 조합보다 규약이 강한 대신 예측 가능합니다.
- 페이지네이션도 `@connection` 규약으로 표준화되어 있습니다.

정리하면 Relay는 **자유도를 줄이고 규약을 강제해서 대규모 팀에서 일관성을 얻는 선택**이라고 이해하고 있고, 규약 기반으로 일하는 방식은 제가 lint·Harness로 해온 것과 같은 방향이라 적응 비용이 크지 않다고 생각합니다.

# 이미지가 너무 크다면?

## 답변

저장 비용과 전송 비용을 나눠서 보겠습니다.

저장 쪽은 업로드 시점에 처리합니다 — 용도별 크기로 resize하고, 압축하고, EXIF 같은 메타데이터를 제거하고, 원본을 어디까지 보관할지 정책을 정합니다.

전송 쪽 핵심은 **사용자가 실제로 보는 크기와 포맷만 보내는 것**입니다. `srcset`/`sizes`로 화면에 맞는 해상도를 고르게 하고, WebP·AVIF로 용량을 줄이고, CDN 캐시를 태우고, 뷰포트 밖 이미지는 lazy loading으로 미룹니다.

```text
저장 비용
전송 비용
```

## 저장

```text

compression
EXIF 제거
원본 정책
```

## 전송

```text
WebP
AVIF
responsive image
srcset
sizes
CDN
cache
lazy loading
```

> 원본을 빨리 보내는 게 아니라 사용자가 실제로 필요한 크기와 포맷만 전달한다.

# 브라우저에서 파일을 만들어 내려주는 건 어떻게 처리하나요?

## 왜 이 질문이 나오나

이력서에 **엑셀 다운로드·인쇄 기능으로 업무 자동화**(팜스태프), **보고서 PDF 자동 생성·전자 서명**(한국소방안전)이 핵심 구현으로 적혀 있고, "수기 작성 4시간 → 30분"이라는 수치까지 붙어 있습니다. 실제로 어떻게 만들었는지 물어보기 딱 좋은 소재입니다.

## 핵심

```text
클라이언트 생성  빠르고 서버 부담 없음 — 대신 메모리 한계, 결과가 기기마다 다를 수 있음
서버 생성        무겁지만 결과가 일정하다 — 정합성이 중요하면 이쪽
인쇄            print용 CSS는 화면 CSS와 다른 매체
서명            좌표를 받아 그리고, 이미지로 고정
```

## 답변

기준은 **결과물이 정확히 같아야 하는가, 그리고 데이터가 얼마나 큰가**입니다.

엑셀 같은 내려받기는 데이터가 크지 않으면 클라이언트에서 만들어 `Blob`으로 내려주는 게 빠르고 서버 부담도 없습니다. 다만 브라우저 메모리에 전부 올라가므로 **행이 수만 건으로 늘어나면 탭이 멈춥니다.** 그래서 규모가 커지면 서버에서 스트리밍으로 만들어 내려보내는 쪽으로 옮기는 게 맞다고 봅니다.

PDF·보고서처럼 **양식이 정해져 있고 누가 뽑아도 같아야 하는 문서**는 서버에서 만드는 편이 안전합니다. 브라우저마다 폰트와 렌더링이 미묘하게 달라서 클라이언트에서 만들면 사용자마다 결과가 달라질 수 있고, 공식 문서에서는 그게 곧 사고입니다.

인쇄는 별도 매체로 다룹니다. 화면용 레이아웃을 그대로 인쇄하면 잘리거나 불필요한 UI가 같이 나오므로, 인쇄용 스타일에서 **페이지 나눔 위치와 숨길 요소를 따로 지정**합니다.

전자 서명은 캔버스에 포인터 좌표를 받아 선을 그리고, 완료 시점에 이미지로 고정해 전송하는 형태로 구현했습니다. 터치와 마우스를 같은 코드로 다루려면 포인터 이벤트로 통일하는 게 편했습니다.

> ✍️ 3년 전 프로젝트라 세부 구현이 흐릿하면 "이런 판단 기준으로 만들었다"까지만 말하고, 라이브러리 이름을 확실하지 않게 대지 말 것.

## 꼬리

### 다운로드 중에 사용자가 기다려야 하는 문제는요?

키워드: 큰 파일은 비동기 생성, 완료 알림, 진행 상태 노출

작은 파일은 즉시 내려주면 되지만, 오래 걸리는 생성은 **요청과 내려받기를 분리**합니다. 서버에 생성을 맡기고 끝나면 알려주는 방식입니다.

동기로 붙잡아두면 그동안 브라우저가 멈춘 것처럼 보이고, 타임아웃에도 걸립니다. 최소한 진행 중이라는 표시와 실패했을 때 다시 시도할 경로는 있어야 한다고 봅니다.

### 민감한 문서를 다룰 때 주의할 점은요?

키워드: 접근 권한은 서버에서, URL 추측 방지, 캐시 금지, 만료되는 링크

**권한 검사는 반드시 서버에서** 합니다. 프론트에서 버튼을 숨기는 건 UI일 뿐이고, 파일 URL을 직접 치면 열리는 구조면 아무 의미가 없습니다.

파일 주소를 추측 가능한 순번으로 두지 않고, 가능하면 만료되는 링크로 발급합니다. 그리고 개인정보가 담긴 응답은 캐시되지 않게 헤더를 지정합니다. 부동산·소방 문서처럼 개인정보가 들어가는 문서에서는 이 부분이 기능보다 중요하다고 생각합니다.

# 해외 사용자에게 영상을 빠르게 전달하려면?

```text
Object Storage
→ Transcoding
→ HLS / DASH
→ multiple bitrate
→ CDN Edge
→ Adaptive Bitrate
```

## 답변

업로드된 원본을 트랜스코딩해서 여러 비트레이트의 HLS segment로 만들고, CDN 엣지로 전달하는 구조를 생각하겠습니다.

핵심은 두 가지입니다 — **물리적 거리는 CDN 엣지 캐시로 줄이고, 사용자마다 다른 네트워크 품질은 Adaptive Bitrate로 대응합니다.**

원본 영상은 Object Storage에 저장하고, 업로드 이후 트랜스코딩 작업을 통해 여러 해상도의 HLS 파일을 생성하겠습니다. HLS는 영상을 작은 segment 단위로 나누고 master playlist에 여러 bitrate를 정의합니다. 이후 CDN을 앞에 두어 segment를 Edge에 캐싱하고, 플레이어는 현재 네트워크 상태에 따라 적절한 bitrate의 segment를 선택하도록 구성하겠습니다.

## 왜 CDN?

키워드: 물리적 거리, 엣지 캐시, origin 부하, 캐시 적중률

origin 서버가 한 리전에만 있으면 해외 사용자는 물리적 거리만큼의 왕복 지연을 매 요청마다 감수해야 합니다. CDN은 사용자와 가까운 엣지에서 응답해 지연을 줄이고 origin 부하도 낮춥니다.

영상처럼 크고 변하지 않는 파일은 캐시 적중률이 높아서 CDN 효과가 가장 큰 영역입니다.

## 왜 HLS?

키워드: segment 분할, 여러 비트레이트, Adaptive Bitrate, 즉시 재생

영상을 통파일로 내려주면 보지 않을 구간까지 받아야 하고, 재생 중 네트워크 변화에 대응할 수 없습니다.

HLS는 영상을 몇 초 단위 segment로 쪼개고 여러 비트레이트를 준비해두므로, 플레이어가 네트워크 상태를 보며 segment 단위로 품질을 갈아탈 수 있습니다(Adaptive Bitrate). 시작 지점부터 바로 재생할 수 있는 것도 장점입니다.

# 프론트엔드 에러 모니터링과 장애 대응은 어떻게 하나요?

## 핵심

```text
에러 수집
Error Boundary
심각도 분류
재발 방지
```

## 답변

프론트 에러는 사용자가 신고하기 전에 아는 것이 목표입니다. 전역 에러 핸들링과 Error Boundary로 화면 전체가 깨지는 것을 막고, 에러를 수집해 발생 빈도와 영향 범위 기준으로 대응 우선순위를 정합니다.

레거시와 신규가 병행 운영되는 환경이라, 배포 직후 기존 사용자 흐름이 회귀하지 않았는지 확인하는 것을 중요하게 봤습니다.

> ✍️ **확정(2026-08-28): 에러 트래킹 도구는 없었다. 장애 인지 경로는 CS 문의였다.**
>
> 그대로 말한다: _"별도 에러 트래킹 도구는 두지 않았고, 대부분 CS 문의로 인지했습니다. 사용자가 먼저 아는 구조였다는 게 이 방식의 명확한 한계입니다."_
>
> 그리고 **바로 "있었다면 이렇게 하겠다"로 이동한다** — 에러 수집 도구를 붙여 배포 단위로 에러율을 보고, 급증 시 알림을 받고, Error Boundary로 화면 전체가 죽지 않게 하는 순서. 없었다는 사실보다 **한계를 정확히 아는지**를 본다.

## 꼬리

### 그럼 사용자가 먼저 알게 되는 구조 아니었나요?

키워드: 맞다, 인지까지 지연, CS가 사실상 모니터링, 탐지 자동화가 다음 과제

맞습니다. CS 문의가 사실상 모니터링 역할을 했고, **문제가 생긴 시점과 저희가 아는 시점 사이에 지연이 있었습니다.** 그게 이 방식의 한계입니다.

다만 인지한 뒤의 대응은 갖춰져 있었습니다 — 재현 경로를 좁히고 배포 이력과 대조해서 원인을 찾는 흐름입니다. 부족했던 건 대응이 아니라 **탐지**였고, 다시 만든다면 에러 수집과 배포 단위 에러율 알림을 먼저 붙이겠습니다.

### Error Boundary는 어디에 두나요?

키워드: 화면 블록 단위, 실패의 반경 축소

전역 1개로 끝내지 않고 화면 블록 단위로 둡니다. 추천 영역 하나가 실패해도 매물 상세 전체가 죽지 않게 — 실패의 반경을 줄이는 도구로 씁니다.

# A/B 테스트는 어떻게 구현했고, 본인의 역할은 무엇이었나요?

## 핵심

```text
variant 배정 일관성
플리커(깜빡임)
노출 이벤트
```

## 답변

구현 관점의 핵심은 두 가지였습니다. 첫째, **배정 일관성** — 같은 사용자는 새로고침하거나 다시 방문해도 같은 안을 봐야 결과가 오염되지 않습니다. 둘째, **노출 측정** — variant가 실제로 사용자에게 보인 시점에 노출 이벤트를 남겨야 전환율의 분모가 정확해집니다.

variant 분기 자체는 프론트에서 구현했고, 가설 수립은 PM·마케터와 함께, 결과 분석은 데이터 파트가 주도했습니다.

> ✍️ **미확인(2026-08-28)** — 배정 방식과 SSR 플리커 처리는 실제 구현이 기억나지 않는다. 위 답변의 "핵심 두 가지"는 **원리로서 아는 내용**이지 본인이 구현한 사실이 아니므로 구현 사실처럼 말하지 않는다. 물어보면 *"variant 분기를 프론트에서 구현했고, 배정과 플리커 처리의 세부는 지금 정확히 기억나지 않습니다"*로 답한다.

## 오너십 표현 (실제 역할 기준)

실험 전체를 제가 주도한 것은 아닙니다. PM·마케터와 가설을 논의하는 단계에 참여했고, 프론트에서 A/B variant를 구현했습니다.

이벤트 설계와 결과 분석은 제가 주도한 영역이 아니어서, 그 부분까지 제 역할로 말하지 않습니다. 물어보면 "그 부분은 PM과 데이터 파트가 주도했고 저는 구현 관점에서 참여했다"고 정확히 답합니다. 이력서 표현보다 실제 경험이 약하다면 오너십을 과장하지 않는다.

> ✍️ **확정(2026-08-28)** — 이벤트명은 PM과 **협의해서 정했고**, 그 위치에 실제로 심을 수 있는지 검증한 뒤 삽입했다. 따라서 "이벤트 정의를 주도했다"가 아니라 **"PM과 이벤트를 협의해 확정하고, 구현 가능성을 검증해 심었다"**가 정확한 표현이다. 공통 로깅 구조 설계는 본인 기여로 말해도 된다.

## 23% 수치는 어떻게 설명할 것인가 — **B안 확정**

Amplitude 재확인은 포기했다. 지어내지 않는다. **3문장 구조로 간다 — 인정 → 내가 한 일 → 지금이라면.**

```text
1문장  수치의 한계를 먼저, 짧게 인정한다 (변명 없이)
2문장  실제로 내가 한 일로 즉시 이동한다 (구체적으로)
3문장  지금이라면 어떻게 측정하겠다 (여기가 강한 구간)
```

### 그대로 쓰는 답변

> "그 값은 실험 이후 문의 클릭이 개선된 폭을 이력서 작성 당시 자료에서 옮겨 적은 것인데, **정확한 지표 정의와 기간은 지금 기억나지 않습니다.** 확인하지 못한 채로 말씀드리는 게 맞다고 생각합니다.
>
> 제가 실제로 한 일은 PM과 이벤트를 협의해 확정하고 구현 가능성을 검증해 심는 것, 그리고 variant를 프론트에서 구현하는 것이었습니다. 그 결과로 CTA 위치와 이미지 갤러리 UI를 바꿨습니다. 실험 설계와 결과 해석은 PM·데이터 파트가 주도했습니다.
>
> 지금 같은 실험을 맡는다면 **시작 전에** 성공 지표의 분자·분모, 최소 기간, 중단 기준을 먼저 합의하고 들어가겠습니다. 그때는 그 부분이 제 역할이 아니라고 생각했는데, 구현하는 사람이 분모를 정확히 알아야 노출 이벤트를 제대로 심을 수 있다는 걸 나중에 알았습니다."

**핵심은 2·3문장이다.** 1문장만 말하고 멈추면 침묵이 생기고 면접관이 그 침묵을 채운다. 인정은 짧게, 이동은 빠르게.

### 절대 하지 말 것

```text
분모·기간을 추측해서 대기
"통계적으로 유의했다" — 검정한 적 없으면 말하지 않는다
"PM이 준 숫자입니다" — 책임 떠넘기기로 들린다
길게 변명하기 — 인정은 한 문장이면 충분하다
```

## 꼬리

### 확인하지 않고 이력서에 쓰신 건가요?

키워드: 변명하지 않는다, 당시 자료 기준으로 옮겨 적었다, 관리 소홀 인정, 한 문장으로 끝낸다

**가장 아픈 질문이고 반드시 준비해야 한다.** 방어하려 들면 더 나빠진다.

> "당시 정리해둔 자료를 기준으로 적었습니다. 다만 그 근거를 지금 재구성하지 못하는 건 제가 관리하지 못한 부분이 맞습니다. 앞으로는 수치를 쓸 때 산출 근거를 같이 남기겠습니다."

한 문장으로 인정하고 끝낸다. 이력서를 옹호하거나 "다들 그렇게 쓰지 않나요" 류로 가면 그 순간 신뢰가 무너진다.

### 그럼 그 실험이 성공이라고 판단한 근거는 뭐였나요?

키워드: 판단 주체는 PM·데이터 파트, 나는 구현과 이벤트, 지금이라면 사전 기준 합의

정직하게 역할을 긋습니다 — 성공 판단은 PM과 데이터 파트가 했고, 저는 variant 구현과 이벤트 삽입을 맡았습니다.

그리고 여기서 멈추지 말고 이어갑니다. 지금이라면 실험을 시작하기 전에 성공 지표와 최소 기간, 중단 기준을 먼저 합의하고 들어가겠다고 말합니다. **아쉬웠던 지점을 스스로 짚는 게 "몰랐습니다"보다 훨씬 낫습니다.**

### 플리커가 뭐고 왜 문제인가요?

키워드: 기본안→variant 깜빡임, 실험 오염, 서버에서 배정, 렌더 보류

기본안이 먼저 그려진 뒤 variant로 바뀌는 깜빡임입니다. 사용자 경험도 나쁘지만, B안 사용자가 A안을 먼저 보게 되어 실험 자체가 오염됩니다. 서버에서 배정을 결정해 처음부터 variant를 그리거나, 결정 전까지 해당 영역 렌더를 잠깐 보류하는 방식으로 막습니다.

# 공통 이벤트 로깅 구조는 어떻게 설계했나요?

## 핵심

```text
공통 패키지로 분리
사용처는 import만
공통 프로퍼티 자동 부착
네이밍 컨벤션
```

## 답변

문제는 이벤트가 기능마다 제각각 정의되어 비교가 안 되는 것이었습니다. 그래서 로깅을 **하나의 공통 패키지로 분리**해서 이벤트 정의·네이밍 규칙·SDK 초기화를 그 안에서 관리하고, 각 사용처는 패키지를 가져다 호출만 하게 했습니다.

페이지·사용자 상태 같은 공통 프로퍼티는 패키지가 자동으로 붙이므로 호출부는 그 이벤트 고유의 값만 넘깁니다. 이벤트 정의가 한 곳에 모이니 기능별 데이터를 같은 기준으로 비교할 수 있고, 새 기능에 이벤트를 붙이는 비용도 줄었습니다.

> ✍️ **확정(2026-08-28)** — 네이밍은 **`영역_행동`** 형태였다. 예: `매물상세_문의클릭`. 이름만으로 어디서 무엇을 했는지 읽히게 하는 게 목적이고, 이 규칙이 있어야 나중에 이벤트가 수백 개가 돼도 찾을 수 있다.
>
> **⚠️ 미확인 — 스크롤 측정.** 이력서에 "페이지 방문, 스크롤, CTA 클릭"이 이벤트로 적혀 있는데 **스크롤을 어떻게 측정했는지 기억나지 않는 상태다.** 물어보면 정직하게 말하고, 아래 꼬리("스크롤은 어떻게 측정하나요")의 원리 수준으로 답한다. 구현했다고 단정하지 말 것.

## 꼬리

### 스크롤은 어떻게 측정하나요?

키워드: 스크롤 깊이 구간, 25·50·75%, IntersectionObserver로 요소 노출, 중복 발화 방지

두 가지 방식이 있습니다. **스크롤 깊이**를 25·50·75·100% 같은 구간으로 끊어 그 지점을 처음 넘을 때 한 번씩 남기거나, **특정 요소가 화면에 들어온 시점**을 `IntersectionObserver`로 잡아 노출 이벤트를 남기는 방식입니다.

스크롤 이벤트에 직접 붙이면 초당 수십 번 발화하므로 반드시 구간을 끊고 한 번만 남게 가드를 둡니다. 요소 노출 쪽은 A/B 테스트에서 특히 중요합니다 — **variant가 실제로 보인 시점**이 전환율의 분모가 되기 때문입니다.

### 왜 패키지로 분리했나요?

키워드: 정의 한 곳, 규칙 코드로 강제, 수정 지점 하나, 모노레포

앱마다 로깅을 따로 구현하면 SDK 초기화·이벤트 이름·프로퍼티 구조가 흩어져서 같은 행동이 다른 이름으로 쌓입니다. 정의를 한 곳에 두면 규칙이 코드로 강제되고, 이벤트를 추가·변경할 때 수정 지점도 한 곳입니다. 여러 앱을 운영하는 모노레포 구조라 공통 패키지로 두는 것이 자연스러웠습니다.

### 이벤트가 제대로 쌓이는지 어떻게 검증하나요?

키워드: 배포 전 직접 확인, 볼륨 예상 범위, 노출 중복 발화

배포 전 개발 환경에서 이벤트 발생을 직접 확인하고, 배포 후 대시보드에서 볼륨이 예상 범위인지 봅니다. 노출 이벤트는 중복 발화(리렌더마다 발화)가 흔한 함정이라 발화 조건을 명확히 합니다.

# 로깅한 이벤트는 실제로 어떤 경로로 서버에 도착하나요?

## 왜 이 질문이 나오나

이벤트 설계와 A/B 테스트 문항은 **왜·무엇을**에 답합니다. 이 문항은 그 위의 2단계 — **어떻게 동작하는가**입니다. "이벤트를 심었다"는 사람은 많고, "이벤트가 유실되는 지점을 안다"는 사람은 적습니다. 23%라는 숫자를 이력서에 쓴 이상 여기까지는 준비되어 있어야 합니다.

## 핵심

```text
호출 즉시 전송되지 않는다 — 큐에 쌓아 배치로 보낸다
그래서 이탈 직전 이벤트는 유실될 수 있다
익명 식별자(device) + 로그인 식별자(user)를 잇는 문제가 항상 있다
SPA는 페이지뷰가 자동으로 안 잡힌다
```

## 답변

`track()` 호출이 곧 네트워크 요청은 아닙니다. 대부분의 분석 SDK는 이벤트를 **큐에 쌓았다가 개수나 시간 조건으로 묶어서 전송**합니다. 매 클릭마다 요청을 보내면 사용자 기기의 네트워크와 배터리를 갉아먹기 때문입니다.

이 구조에서 나오는 문제가 세 가지입니다.

첫째, **이탈 직전 이벤트의 유실**입니다. 큐에 남은 상태로 탭이 닫히거나 다른 페이지로 이동하면 그 요청은 중간에 끊깁니다. 그래서 페이지 언로드 시점에는 일반 요청 대신 `navigator.sendBeacon`처럼 **문서가 사라진 뒤에도 브라우저가 대신 보내주는 방식**을 쓰는 게 안전합니다. 하필 유실되는 게 "이탈"이라는, 퍼널에서 가장 중요한 이벤트라는 게 문제입니다.

둘째, **사용자 식별**입니다. 로그인 전에는 익명 기기 식별자로 쌓이고 로그인 후에는 사용자 식별자로 쌓이는데, 이 둘을 잇지 않으면 "가입 전 탐색 → 가입 → 지원"이라는 한 사람의 여정이 두 사람으로 쪼개져서 퍼널이 전부 틀어집니다. 그래서 로그인 시점에 식별자를 연결하는 처리를 반드시 넣습니다.

셋째, **SPA의 페이지뷰**입니다. 클라이언트 라우팅은 문서를 다시 로드하지 않으므로 브라우저 기준 페이지뷰가 발생하지 않습니다. 라우트 변경을 직접 감지해서 발화시켜야 하고, 이때 중복 발화를 조심해야 합니다.

> ✍️ 구체적인 SDK 옵션 이름을 단정하지 말 것. "배치 전송이 기본이고 언로드 시점에는 beacon 방식을 쓴다"는 **동작 원리 수준**으로 말하고, 정확한 옵션명을 물으면 "설정으로 조정한 기억이 있지만 이름은 확실하지 않다"고 답하는 게 낫다.

## 꼬리

### 이벤트가 제대로 쌓이는지 어떻게 검증하나요?

키워드: 개발 단계 디버그 모드, 배포 후 실시간 확인, 스키마 검증, 볼륨 모니터링

세 단계로 봅니다. 개발 중에는 디버그 모드로 실제 전송되는 payload를 눈으로 확인하고, 배포 직후에는 실시간 스트림에서 해당 이벤트가 들어오는지 봅니다.

그다음이 실무에서 더 중요합니다 — **이벤트 볼륨의 추이를 지켜보는 것**입니다. 이벤트가 안 오는 사고는 대부분 배포 며칠 뒤에 조용히 발생합니다. 컴포넌트를 리팩터링하면서 로깅 호출이 빠지는 식인데, 아무도 에러를 보지 않기 때문에 지표가 이상해진 뒤에야 발견합니다. 그래서 핵심 이벤트는 볼륨이 급감하면 알 수 있게 해두는 게 맞다고 봅니다.

### 같은 이벤트가 두 번 찍히는 문제는 왜 생기나요?

키워드: effect 재실행, StrictMode 이중 실행, 리렌더마다 발화, 상태로 가드

렌더 흐름에 로깅을 붙였을 때 생깁니다. 개발 환경의 StrictMode는 effect를 의도적으로 두 번 실행하고, 의존성이 잘못 잡힌 effect는 리렌더마다 다시 돕니다.

그래서 **"화면이 그려졌다"가 아니라 "사용자가 무엇을 했다"에 붙이는 것**을 기본으로 합니다. 노출 이벤트처럼 불가피하게 렌더에 붙여야 하면 한 번만 발화하도록 가드를 둡니다. 개발 환경에서만 두 번 찍히는 걸 보고 코드를 잘못 고치는 경우도 있어서, 원인을 아는 게 중요합니다.

### 이벤트 스키마는 누가 어떻게 관리하나요?

키워드: 이름 규칙, 속성 표준화, 공통 속성 자동 주입, 나중에 못 고침

이름과 속성 규칙을 먼저 정하고 **공통 속성은 개별 호출에서 빼서 자동으로 붙입니다.** 로그인 여부, 사용자군, 화면 정보 같은 것을 매번 손으로 넣게 하면 반드시 빠지거나 달라집니다.

가장 중요한 건 **이벤트는 나중에 소급해서 고칠 수 없다**는 점입니다. 잘못 쌓인 3개월치 데이터는 되살릴 수 없어서, 이름과 속성 설계는 코드 리뷰 대상으로 삼는 게 맞다고 생각합니다. 저희에서 로깅 구조를 공통 패키지로 분리한 것도 이 규칙이 서비스마다 갈라지지 않게 하려는 목적이었습니다.

### 양면시장이라면 이벤트 설계에서 뭘 다르게 하시겠어요?

키워드: 사용자군 속성 필수, 같은 이름 다른 의미 금지, 매칭까지 잇는 퍼널

**모든 이벤트에 사용자군을 속성으로 넣는 것**이 출발점입니다. 이게 없으면 나중에 어떤 지표도 쪼갤 수 없습니다.

그리고 같은 이벤트 이름을 양쪽에서 다른 의미로 쓰지 않게 합니다 — 구직자의 "지원"과 사장님의 "지원자 확인"은 별개 이벤트여야 합니다. 마지막으로 두 쪽을 잇는 퍼널, 즉 지원부터 사장님의 응답까지를 하나로 볼 수 있게 공통 식별자(공고 ID 등)를 이벤트에 함께 실어 두는 게 중요하다고 봅니다. 한쪽 퍼널만 보면 양면시장의 진짜 성과를 못 봅니다.

# 동네생활백서의 URL 구조는 어떤 기준으로 설계했나요?

## 핵심

```text
계층 = 탐색 단위
검색 의도와 URL 매칭
안 바꿔도 되는 구조
```

## 답변

URL을 사용자의 검색 의도와 맞추는 것을 기준으로 삼았습니다. 지역 정보 콘텐츠는 "지역 + 주제"로 검색되므로 URL 계층도 그 탐색 단위를 따라 설계하고, 한 URL이 하나의 의도에 대응하게 했습니다.

또 URL은 한번 색인되면 바꾸는 비용이 커서(리다이렉트 체인, 평가 분산), 콘텐츠가 늘어나도 구조를 안 바꿔도 되는 형태인지를 먼저 검증했습니다.

> ✍️ **확정(2026-08-28)** — 지역이 가장 중요한 축이라 **`지역 → 건물명 / 단지코드`** 계층으로 잡았다. 지역을 상위 경로에 둔 이유(검색 유입이 지역 단위로 발생, 상위 경로가 곧 색인 단위)를 함께 말한다.

## 꼬리

### 좋은 URL의 기준이 뭔가요?

키워드: 읽힌다, 예측된다, 안 바뀐다

세 가지로 답합니다. **읽힌다** — URL만 보고 무슨 페이지인지 사람과 검색엔진 모두 알 수 있다. **예측된다** — 같은 종류의 페이지는 같은 패턴을 따라서, 하나를 보면 다른 것의 주소를 유추할 수 있다. **안 바뀐다** — 색인·공유·북마크된 URL은 자산이라, 구조 변경 없이 콘텐츠가 늘어날 수 있어야 한다.

### 쿼리 파라미터와 경로의 기준은?

키워드: 정체성은 경로, 정렬·필터는 쿼리, canonical로 대표 지정

색인시키고 싶은 정체성은 경로에, 정렬·필터처럼 같은 콘텐츠의 변형은 쿼리에 둡니다. 쿼리 조합이 색인되면 중복 페이지가 생기므로 canonical로 대표 URL을 지정합니다.

### 슬러그는 어떻게 만드나요?

키워드: ID+의미 슬러그 조합, 생성 시점 고정, 유입 채널 보고 결정

의미를 담은 슬러그가 SEO·가독성에 유리하지만, 제목이 바뀌면 URL이 바뀌는 문제가 생깁니다. 그래서 안정적인 ID와 의미 슬러그를 조합하거나(`/post/123-역삼동-맛집`, 조회는 ID로), 슬러그를 생성 시점에 고정하고 제목 변경에 안 따라가게 합니다. 한글 슬러그는 인코딩되면 URL이 길고 흉해지지만 검색 의도 매칭에는 유리해서, 서비스의 유입 채널을 보고 결정합니다.

### URL을 바꿔야 한다면?

키워드: 301 리다이렉트, sitemap·내부 링크 갱신, 체인 금지

301 리다이렉트로 기존 URL의 평가를 새 URL로 넘기고, sitemap과 내부 링크를 함께 갱신합니다. 리다이렉트를 여러 번 거치게 체인을 만들지 않습니다.

## 참고 — URL 설계 학습 노트

이력서의 "IA·URL 구조 설계"를 스스로 설명할 수 있게 정리한 노트.

**IA(Information Architecture)와 URL의 관계** — IA는 콘텐츠를 어떤 단위로 묶고 어떤 계층으로 탐색하게 할지의 설계다. URL은 그 IA가 주소로 드러난 것. 그래서 URL 설계는 "예쁜 주소 만들기"가 아니라 **탐색 단위 정의가 먼저**고 URL은 그 결과다. 동네생활백서라면: 사용자는 "지역"으로 들어와 "주제"로 좁힌다 → `/지역/주제/콘텐츠` 계층이 곧 IA.

**계층 설계의 원칙**

- 계층은 탐색 단위와 일치시킨다. 상위 경로를 잘라내도 유효한 목록 페이지가 나오는 게 이상적 (`/역삼동/맛집/A식당`에서 `/역삼동/맛집`은 목록, `/역삼동`은 지역 홈)
- 깊이는 필요한 만큼만. 계층이 깊다고 SEO에 불리한 건 아니지만, 의미 없는 중간 계층은 유지 비용만 늘린다
- 한 콘텐츠가 여러 분류에 속하면 계층이 무너진다 — 대표 경로 하나를 정하고 나머지는 canonical로 정리

**함정들**

- 트레일링 슬래시(`/a` vs `/a/`)와 대소문자는 서로 다른 URL이다 — 한쪽으로 통일하고 나머지는 리다이렉트
- 페이지네이션은 `?page=2`로 두되 각 페이지가 자기 자신을 canonical로 가리키게 한다 (2페이지를 1페이지로 canonical하면 2페이지 이후 콘텐츠가 색인에서 사라질 수 있음)
- 무한 조합(필터×정렬×페이지)이 색인되면 크롤링 예산 낭비 — 색인 가치 있는 조합만 남기고 나머지는 noindex 또는 robots 제어

**연결 주제** — sitemap·canonical, SSR/SSG 렌더링 전략 문항과 이어서 답할 수 있게 해둘 것.

# 테스트는 어떤 기준으로 무엇까지 작성하나요?

## 왜 이 질문이 나오나

이력서 Skill에 Vitest·Jest·Playwright·React Testing Library가 나열되어 있고, **"AI가 만든 코드를 테스트로 검증한다"**고 적었습니다. 즉 테스트는 제 개발 방식의 전제로 선언되어 있어서, 여기서 막히면 AI Harness 이야기 전체가 흔들립니다.

## 핵심

```text
기준은 커버리지 숫자가 아니라 "깨지면 사용자가 아픈가"
순수 로직   단위 테스트 — 싸고 빠르다
컴포넌트    사용자 관점으로 — 구현이 아니라 보이는 것·누르는 것
핵심 플로우  e2e 소수 — 비싸고 잘 깨진다
```

## 답변

테스트를 **회귀를 막는 비용**으로 보고, 비용 대비 효과 순으로 씁니다.

가장 먼저 쓰는 건 **순수 로직**입니다. 금액 계산, 날짜·포맷 변환, 상태 전이 규칙처럼 입력과 출력이 분명한 것들입니다. 싸고 빠르고 안 깨지기 때문에 여기서 가장 많이 회수합니다. 그래서 로직을 컴포넌트 안에 묻어두지 않고 밖으로 빼는 게 테스트 이전에 설계 문제이기도 합니다.

**컴포넌트 테스트는 사용자 관점으로** 씁니다. 내부 state가 무엇인지가 아니라 "무엇이 보이고 무엇을 누를 수 있는가"를 검증합니다. 그래서 역할(role)과 화면에 보이는 텍스트로 요소를 찾습니다. 이렇게 쓰면 리팩터링해도 테스트가 살아남고, 덤으로 **접근성 속성이 제대로 붙어 있어야 테스트가 통과**하는 효과도 있습니다.

**e2e는 정말 핵심 플로우만** 둡니다. 로그인, 문의·지원처럼 깨지면 매출이 멈추는 경로입니다. 느리고 환경에 민감해서 많이 만들면 아무도 안 믿는 빨간 불이 됩니다.

AI Agent 활용과 직접 연결되는 부분이 여기입니다. **Agent가 만든 코드를 사람이 한 줄씩 읽어서 검증하는 건 확장되지 않습니다.** 대신 요구사항을 테스트로 먼저 고정해두면 결과를 기계적으로 판정할 수 있습니다. 저는 이걸 "AI에게 정답지를 주는 것"에 가깝다고 봅니다.

> ✍️ **확정(2026-08-28)** — 실제로는 **유닛 테스트 위주**이고 컴포넌트 테스트·e2e는 갖추지 않았다. 그대로 말한다: _"핵심 로직 위주로 유닛 테스트를 두는 정도이고, 컴포넌트 테스트나 e2e까지 체계적으로 갖추지는 못했습니다."_
>
> **주의 — 이력서 Skill의 Testing 항목(Vitest·Jest·Playwright·RTL)이 실제보다 넓게 읽힌다.** 특히 Playwright는 **개인 프로젝트에서 크롤링 용도로** 쓴 것이지 e2e 테스트로 쓴 게 아니다. 물어보면 그렇게 정확히 구분해서 답한다 — 거짓이 아니고, 구분해서 말하는 것 자체가 신뢰를 준다.

## 꼬리

### e2e가 자꾸 깨지면 어떻게 하나요?

키워드: 고정 대기 금지, 조건 대기, 네트워크 모킹, 테스트 격리

원인은 대부분 **타이밍과 데이터 공유**입니다.

`sleep` 같은 고정 시간 대기는 빠르면 낭비고 느리면 실패하므로, "이 요소가 보일 때까지"처럼 조건으로 기다립니다. 그리고 외부 API에 의존하면 남의 사정으로 빨간 불이 켜지므로 네트워크를 모킹하거나 전용 데이터를 씁니다. 테스트끼리 같은 계정·같은 데이터를 공유하면 순서에 따라 결과가 달라져서, 각 테스트가 자기 데이터를 만들고 치우게 합니다.

깨지는 걸 방치하면 **아무도 안 보는 테스트**가 되는 게 진짜 손실이라고 봅니다.

### 무엇은 테스트하지 않나요?

키워드: 구현 세부, 스냅샷 남용, 라이브러리 동작, 유지비가 가치보다 큰 것

내부 구현 세부와 라이브러리 자체의 동작은 안 합니다. 리팩터링할 때마다 같이 고쳐야 하는 테스트는 회귀를 막는 게 아니라 **변경을 막습니다.**

큰 스냅샷도 피합니다. 바뀌면 사람이 검토하지 않고 그냥 갱신하게 돼서 통과 여부에 의미가 없어집니다. 유지비가 잡아주는 가치보다 크면 안 쓰는 게 맞다고 봅니다.

### 커버리지 목표를 두시나요?

키워드: 지표가 목표가 되면 왜곡, 핵심 경로 우선, 낮은 곳 확인용

숫자를 목표로 두지는 않습니다. 목표가 되는 순간 **의미 없는 테스트로 채우게 되기 때문**입니다.

대신 커버리지는 "핵심 로직인데 아무도 안 건드리는 영역"을 찾는 **탐지 도구**로 씁니다. 결제나 인증처럼 중요한 모듈이 비어 있으면 그건 신호로 보고 채웁니다.

# AI로 개발 리드타임이 줄었다는 걸 어떻게 증명하나요?

## 핵심

```text
비교 기준 제시
1개월 산출물
품질은 사람이 보증
```

## 답변

엄밀한 대조군 실험을 한 것은 아니라서, 그렇게 말하지 않습니다. 대신 비교 가능한 사실을 제시합니다 — 디자인 시스템과 어드민 2종을 약 1개월에 구축했는데, 이전에 비슷한 규모의 어드민을 만들 때의 기간과 비교하면 체감 차이가 분명했다는 식입니다.

그리고 단축의 원천을 구체적으로 말합니다: 반복 UI 구현·CRUD 플로우를 Agent가 패턴으로 재사용하고, 제 시간은 요구사항 정의·아키텍처·검증에 쓰는 구조라서 빨라진 것이지, AI가 알아서 다 만들어서가 아닙니다.

> ✍️ **확정(2026-08-28): 정량 A/B 비교는 없다.** 지어내지 말고 인정한 뒤, **절대 산출물로 이동한다.**
>
> - 말할 것: _"이전 작업과 나란히 놓고 잰 정량 비교는 없습니다. 다만 실제로 **약 한 달 동안 디자인 시스템과 마스터 어드민·단지 어드민을 새로 구축**했고, 그 전 같은 규모의 작업에서는 이런 속도가 나오지 않았습니다."_
> - 이어서 **무엇이 빨라졌는지**를 구체화한다 — 반복되는 CRUD 화면과 폼, 구조가 정해진 UI 구현, 그리고 같은 패턴을 다음 앱에 재사용하는 구간.
> - 반대로 **안 빨라진 것**도 말한다: 요구사항 정의, 아키텍처 판단, 도메인이 얽힌 로직. 양쪽을 다 말하면 과장으로 안 들린다.

## 꼬리

### AI가 만든 코드 품질은 누가 보증하나요?

키워드: 내가 보증, 리뷰·테스트 필수, Harness에 규칙 축적

저입니다. Agent가 만든 코드도 리뷰·테스트를 통과해야 하고, 잘못 구현한 사례처럼 검증 없이 믿으면 사고가 납니다. 그래서 Harness에 규칙을 축적하고 검증 단계를 플로우에 포함했습니다.

### AI 때문에 오히려 느려진 적은?

키워드: 컨텍스트 부족, 되돌리는 비용, Harness에 투자

있습니다 — 컨텍스트가 부족한 상태로 시키면 잘못된 방향으로 많이 만들어놓고, 그걸 되돌리는 비용이 더 컸습니다. 그래서 규칙·컨텍스트를 Harness에 쌓는 데 투자했고, 그 이후로 같은 실수의 반복이 줄었습니다.

# 웹뷰 환경에서의 웹 개발은 일반 브라우저와 무엇이 다른가요?

## 왜 이 질문이 나오나

당근 제품 대부분은 **앱 안의 웹뷰**로 서빙됩니다. 당근알바(로컬 잡스)도 마찬가지입니다. 면접관 입장에서 "입사하면 바로 하게 될 일"이라 나올 확률이 높습니다.

당근이 웹뷰에서 네이티브 같은 화면 전환을 만들기 위해 **Stackflow**라는 스택 네비게이션 라이브러리를 직접 만들어 오픈소스로 공개했을 정도로, 웹뷰 경험 품질에 투자하는 팀입니다. 이 이름을 아는 것 자체가 준비의 신호가 됩니다.

## 핵심

```text
브라우저가 아니라 "앱 안의 브라우저"
인증 — 앱이 주입한다
네비게이션 — 브라우저 히스토리 ≠ 앱 스택
앱 기능 — 브릿지로 호출
배포 — 앱 심사 없이 웹만 배포
```

## 답변

저희 서비스도 앱 웹뷰로 웹을 서빙하는 영역이 있어서, 일반 브라우저와의 차이를 세 가지로 체감했습니다.

첫째, **인증이 다릅니다.** 웹뷰에는 로그인 화면이 없습니다 — 사용자는 이미 앱에 로그인했기 때문에, 앱이 가진 인증 상태를 웹뷰에 넘겨줘야 합니다. 저희는 웹은 PHP 세션, 앱 웹뷰는 JWT로 인증이 두 벌로 갈라져 있던 게 문제였고, 이걸 HttpOnly Cookie 기반으로 통합하는 작업을 했습니다("세션과 토큰 혼재" 문항 참고).

둘째, **네비게이션이 다릅니다.** 브라우저의 히스토리 모델과 앱의 화면 스택 모델이 다르기 때문에, 안드로이드 물리 뒤로가기·iOS 스와이프 백이 웹의 `history`와 자연스럽게 맞물리도록 처리해야 합니다.

셋째, **웹이 할 수 없는 일은 브릿지로 앱에 요청합니다.** 네이티브 공유 시트, 앱 내 다른 화면으로 이동, 권한이 필요한 기능 같은 것들입니다.

정리하면 웹뷰 개발은 "웹을 만든다"기보다 **앱과 웹 사이의 계약(인증·네비게이션·브릿지)을 설계하는 일**이 절반이라고 생각합니다.

> ✍️ **확정(2026-08-28)** — 직접 다룬 범위는 **인증 통합과 웹뷰로의 토큰 전달**까지다. 브릿지 설계 전반과 웹뷰 화면 개발은 경험이 얕으므로 "인증 통합 과정에서 웹뷰를 다뤘고, 브릿지 설계는 개념으로 학습했다"고 정직하게 구분한다.

## 브릿지가 무엇인지 설명해주세요

앱과 웹 사이의 **양방향 API**입니다.

- **웹 → 앱**: iOS는 `window.webkit.messageHandlers.<name>.postMessage()`, Android는 `@JavascriptInterface`로 노출된 객체 호출. 앱이 처리할 일(공유, 화면 이동, 토큰 요청)을 메시지로 보냅니다.
- **앱 → 웹**: 앱이 웹뷰에 JavaScript를 주입해서(`evaluateJavascript` 등) 웹의 전역 콜백을 호출합니다.

호출이 비동기 단방향 메시지라서, 실무에서는 **요청에 id를 붙이고 응답 콜백을 매칭해 Promise로 감싸는 래퍼**를 만들어 `await bridge.share(...)`처럼 쓰는 패턴이 일반적입니다.

주의할 점은 브릿지가 **신뢰 경계**라는 것입니다. 웹뷰에 로드된 페이지는 브릿지를 통해 앱 기능에 접근할 수 있으므로, 앱은 허용된 도메인에서만 브릿지를 노출해야 하고, 웹도 브릿지로 받은 데이터를 검증 없이 신뢰하면 안 됩니다.

## 웹뷰 인증은 어떻게 처리하나요

두 가지 방식이 있고, 각각 trade-off가 있습니다.

- **쿠키 주입**: 앱이 로그인 시점에 웹뷰의 쿠키 저장소에 인증 쿠키를 심어줍니다. 웹 입장에서는 일반 브라우저와 코드가 같아지고, HttpOnly라 JS 노출도 없습니다. 저희가 인증을 HttpOnly Cookie로 통일한 것도 웹·웹뷰가 같은 코드 경로를 타게 하려는 목적과 맞닿아 있습니다.
- **브릿지로 토큰 전달**: 웹이 브릿지로 토큰을 받아 Authorization 헤더에 실어 보냅니다. 유연하지만 토큰이 JS 메모리에 존재하므로 XSS 노출면이 생기고, 갱신 타이밍 관리도 웹이 떠안습니다.

가능하면 쿠키 주입 쪽이 낫다고 생각합니다 — **웹과 웹뷰의 인증 코드가 갈라지지 않는 것** 자체가 유지보수에서 가장 큰 이점이기 때문입니다.

## 성능 관점에서는 무엇이 다른가요

웹뷰의 첫 로딩은 **앱 사용자가 느끼는 앱의 속도**입니다. 브라우저 사용자보다 기대 수준이 높습니다 — 네이티브 화면처럼 즉시 뜨길 기대합니다.

- **초기 로딩**: 번들 경량화, 첫 화면 SSR 또는 스켈레톤으로 백지 시간을 없애는 게 우선입니다.
- **웹뷰 프리워밍**: 앱이 웹뷰 인스턴스를 미리 만들어두거나 페이지를 미리 로드해두는 최적화가 가능합니다(앱 팀과의 협업 영역).
- **전환 애니메이션**: 화면 전환이 네이티브처럼 보여야 해서, 당근의 Stackflow 같은 스택 네비게이션 접근이 나옵니다.

## 디버깅은 어떻게 하나요

- iOS: Safari **Web Inspector**로 실기기 웹뷰에 연결
- Android: Chrome `chrome://inspect`로 원격 디버깅
- 환경 차이(앱 UA, 브릿지 유무)가 버그의 원인인 경우가 많아서, 개발 중에는 브릿지 mock을 두고 브라우저에서 개발한 뒤 웹뷰에서 검증하는 흐름이 효율적입니다.

## 꼬리

### 왜 네이티브가 아니라 웹뷰로 만드나요?

키워드: 배포 주기 분리, 앱 심사 없음, 초기 로딩·인터랙션 한계, 화면 성격별 구분

**배포 주기의 분리**가 가장 큽니다. 앱 심사 없이 웹 배포만으로 기능이 즉시 반영되고, iOS·Android를 한 코드로 커버합니다. 실험이 잦은 제품(A/B 테스트, 빠른 개선 루프)일수록 이점이 커집니다.

대가는 초기 로딩 속도와 네이티브 수준 인터랙션의 한계입니다. 그래서 진입 빈도가 높고 인터랙션이 무거운 화면은 네이티브로, 변경이 잦고 콘텐츠 중심인 화면은 웹뷰로 가르는 게 일반적인 기준이라고 이해합니다.

### 웹뷰와 일반 브라우저를 한 코드로 어떻게 대응하나요?

키워드: 환경 감지 한 곳, 기능 단위 어댑터, 호출부는 환경 모름

환경 감지(브릿지 존재 여부·UA)를 한 곳에 모으고, 기능 단위 어댑터로 격리합니다. 예를 들어 `share()`는 웹뷰면 브릿지, 브라우저면 Web Share API나 URL 복사로 동작하게 하고, 호출부는 환경을 모르게 합니다. 분기가 화면 코드 곳곳에 퍼지는 순간 유지보수가 무너지기 때문입니다.

### 안드로이드 물리 뒤로가기는 어떻게 처리하나요?

키워드: 모달은 닫힘 기대, pushState+popstate, UI 상태와 히스토리 동기화

기본 동작은 웹뷰 히스토리 back입니다. 문제는 모달·바텀시트가 열린 상태 — 사용자는 "닫힘"을 기대하는데 페이지가 뒤로 갑니다. 그래서 모달을 열 때 히스토리 엔트리를 쌓고(`pushState`) `popstate`에서 모달을 닫는 식으로, **UI 상태를 히스토리와 동기화**해야 합니다. "SPA URL과 뒤로가기" 문항과 같은 원리이고, 웹뷰에서는 이게 선택이 아니라 필수가 됩니다.

# 당근알바 같은 양면시장에서 프론트엔드가 특별히 신경 쓸 것은 무엇인가요?

## 왜 이 질문이 나오나

당근알바는 **구직자와 사장님**이라는 성격이 완전히 다른 두 사용자가 같은 제품 안에서 만나는 구조입니다. 면접관이 "웹뷰"와 함께 3단계(트레이드오프) 질문을 닫을 때 가장 자주 쓰는 축입니다.

다행히 이건 학습으로 채우는 영역이 아닙니다 — 피터팬은 **방을 내놓는 사람과 구하는 사람**, 아파트스토리는 **관리자와 입주민**이라는 양면 구조였고, 저는 양쪽 제품을 다 만들었습니다. 이 경험을 당근알바의 언어로 옮기는 것이 이 문항의 목적입니다.

## 핵심

```text
두 사용자군은 지표도 화면도 캐시 전략도 다르다
한쪽 최적화가 반대쪽 비용이 될 수 있다
공급(사장님) 쪽이 무너지면 수요(구직자) 쪽도 같이 죽는다
공통은 계약(인증·디자인 시스템·로깅), 분기는 화면
```

## 답변

양면시장에서 프론트엔드가 착각하기 쉬운 게 "사용자 = 한 종류"라고 가정하고 화면을 만드는 것이라고 생각합니다. 저는 세 가지를 다르게 봅니다.

첫째, **두 쪽의 성공 지표가 다릅니다.** 구직자 쪽은 탐색과 지원까지의 마찰을 줄이는 게 목표고, 사장님 쪽은 공고를 끝까지 등록하고 지원자를 빠르게 처리하는 게 목표입니다. 같은 "전환율"이라는 단어를 써도 측정 대상이 완전히 다릅니다. 그래서 이벤트 스키마부터 사용자군을 속성으로 분리해 두지 않으면, 나중에 어떤 지표도 쪼갤 수 없게 됩니다.

둘째, **캐시와 렌더링 전략이 갈립니다.** 구직자가 보는 공고 목록·상세는 다수가 같은 것을 보는 공개 콘텐츠라 캐시와 사전 렌더링이 잘 먹고 SEO도 의미가 있습니다. 반대로 사장님이 보는 지원자 현황은 100% 개인화된 데이터라 공유 캐시를 태울 수 없고, 최신성이 캐시 이득보다 중요합니다. 저희 서비스에서도 매물 목록은 검색 유입을 노려 사전 렌더링을, 중개사·관리자 화면은 요청 시점 데이터를 기준으로 잡았습니다.

셋째, **한쪽의 개선이 반대쪽의 비용이 될 수 있습니다.** 지원 버튼의 마찰을 줄이면 지원 수는 늘지만, 사장님 입장에서는 무성의한 지원이 늘어나 처리 비용이 커집니다. 그래서 양면시장의 실험은 개선한 쪽 지표만 보면 안 되고, **반대쪽의 가드레일 지표를 같이 놓고 봐야 한다**고 생각합니다.

정리하면 양면시장에서 프론트엔드의 일은 화면을 두 벌 만드는 게 아니라, **무엇을 공통 계약으로 묶고 무엇을 갈라 둘지 경계를 정하는 일**에 가깝습니다.

> ✍️ **확정(2026-08-28)** — 피터팬에서 **방 내놓기(공급자)와 방 구하기(수요자) 화면을 둘 다** 개발했다. 아파트스토리도 관리자 어드민과 입주민 서비스를 함께 만들었다. **양면 구조의 양쪽을 다 만든 경험이 실제로 있다** — "B2B 어드민도 했다"가 아니라 **"공급자 제품과 수요자 제품을 같은 플랫폼에서 함께 만들었다"**로 말한다. 이 팀에서 가장 잘 꽂히는 문장이다.

## 꼬리

### 두 사용자군을 한 코드베이스에서 어떻게 나누시겠어요?

키워드: 앱 단위 분리, 공유는 계약만, 컴포넌트 공용화는 신중, 인증·권한은 공통

앱 단위로 가르고 공통은 **계약 수준만** 공유합니다. 아파트스토리에서 마스터 어드민·단지 어드민·사용자 서비스를 한 모노레포에 두면서 잡은 기준이 그대로 적용된다고 봅니다.

공유하는 것은 인증·네트워크 계층, 디자인 토큰과 표시 컴포넌트, 이벤트 로깅 규약처럼 **갈라지면 오히려 사고가 나는 것**입니다. 반대로 도메인 컴포넌트는 쉽게 공용화하지 않습니다 — 겉모습이 비슷하다고 공고 카드를 하나로 합치면, 한쪽 요구사항이 들어올 때마다 분기 props가 붙어서 결국 두 벌보다 읽기 어려워집니다.

기준은 "**변경 이유가 같은가**"입니다. 변경 이유가 다른 두 화면을 코드가 비슷하다는 이유로 합치는 게 양면시장에서 가장 흔한 실수라고 생각합니다.

### 한쪽 지표만 올라가고 반대쪽이 나빠지면 그 실험은 성공인가요?

키워드: 가드레일 지표, 매칭 성사가 최종 지표, 롤백 기준 사전 합의

성공이라고 말하기 어렵다고 봅니다. 양면시장의 최종 지표는 한쪽의 클릭이 아니라 **매칭이 실제로 성사되는 것**이기 때문입니다.

그래서 실험을 설계할 때 개선 지표와 함께 반대쪽 가드레일 지표를 미리 정해 둡니다. 예를 들어 구직자 지원 전환율을 올리는 실험이라면, 사장님 쪽의 지원자 응답률이나 공고 재등록률이 같이 나빠지지 않는지를 봅니다. 그리고 "가드레일이 몇 % 나빠지면 중단한다"는 기준을 **실험 시작 전에** 합의해 둡니다. 끝나고 정하면 결과를 보고 기준을 옮기게 됩니다.

저희에서 문의 전환율 실험을 할 때도 문의 수만 보지 않고, 문의가 실제 응대로 이어지는지를 같이 확인했습니다.

### 트래픽이 한쪽으로 쏠릴 때 프론트엔드가 할 수 있는 일이 있나요?

키워드: 비대칭 규모, 공급자 화면은 데이터 밀도, 수요자 화면은 초기 로딩

양면시장은 보통 규모가 비대칭입니다. 구직자 트래픽이 사장님 트래픽보다 훨씬 크고, 대신 사장님 화면은 사용자당 다루는 데이터가 무겁습니다.

그래서 최적화 대상이 다릅니다. 수요자 화면은 **초기 로딩과 목록 스크롤 성능**이 핵심이라 캐시·사전 렌더링·이미지 최적화가 먼저고, 공급자 화면은 **데이터 밀도와 반복 작업 효율**이 핵심이라 테이블 렌더링 비용·필터 상태 관리·대량 업데이트 후 캐시 무효화 범위가 먼저입니다.

같은 성능 개선이라도 어느 쪽 화면이냐에 따라 손대는 곳이 완전히 달라진다고 생각합니다.

# 지역 기반 서비스에서 위치는 어떻게 다루나요?

## 핵심

```text
위치는 사용자 데이터 — 권한과 실패 경로가 기본값
웹뷰에서는 권한 주체가 앱
위치 없이도 동작하는 화면이 있어야 한다
```

## 답변

위치를 "가져오면 되는 값"으로 보지 않고, **실패할 수 있고 사용자가 거부할 수 있는 입력**으로 다룹니다.

브라우저의 Geolocation API는 권한 프롬프트를 띄우고, 거부·타임아웃·저정밀 결과가 모두 정상 흐름입니다. 그래서 위치를 못 얻었을 때의 대체 경로 — 마지막으로 선택한 지역, 직접 지역 선택 UI — 를 먼저 만들어 두고 위치는 그 위의 편의 기능으로 얹는 게 맞다고 생각합니다.

웹뷰에서는 한 겹이 더 있습니다. 실제 OS 권한은 **앱이 가지고 있고**, 웹뷰는 앱이 허용받은 범위 안에서만 동작합니다. 그래서 웹에서 권한을 요청했을 때 프롬프트조차 뜨지 않고 즉시 거부되는 상황이 생길 수 있고, 이때는 브릿지로 앱에 권한 요청이나 설정 화면 이동을 위임하는 흐름이 필요합니다.

> ✍️ 이 문항은 본인이 직접 구현한 경험이 아니라면 "이렇게 접근하겠다"로 말할 것. 지어내지 않는다.

## 꼬리

### 위치 권한을 언제 요청하나요?

키워드: 진입 즉시 금지, 맥락 있는 시점, 거부하면 회복 불가

진입 즉시 요청하지 않습니다. 맥락 없이 뜬 권한 프롬프트는 거부율이 높고, **한 번 거부되면 브라우저·앱 설정에 들어가야만 되돌릴 수 있어서** 회복 비용이 큽니다.

"내 주변 보기"처럼 사용자가 위치가 필요한 행동을 선택한 시점에 요청하고, 그 직전에 왜 필요한지를 화면에서 먼저 설명하는 순서가 낫다고 봅니다.
