# 4. 왜 레거시를 새로 만들었나요?

## 이력서 근거

- PHP 기반 레거시
- 단지별 DB
- 기능 누적
- 신규 기능 확장 비용 증가
- 마스터 어드민 / 단지 어드민 / 사용자 서비스 신규 구축
- 인수인계자 부재

## 암기 키워드

```text
단지별 DB
PHP 레거시
기능 누적
의존성 높음
변경 영향 파악 어려움
인수인계자 부재
신규 기능 계속 예정
→ 신규 구축
```

## 기본 답변

기존 서비스를 그대로 확장하는 방법도 검토했지만 구조적으로 유지보수 비용이 계속 커지는 상황이었습니다.

단지마다 데이터베이스가 분리되어 있었고, PHP 레거시 코드도 오랫동안 기능이 누적되면서 서로 의존성이 높고 변경 영향 범위를 파악하기 어려웠습니다. 기존 구조를 깊게 알고 있는 인수인계자도 부재했습니다.

앞으로 관리자와 사용자 기능을 계속 추가해야 했기 때문에 기존 코드를 계속 수정하는 것보다, 유지해야 하는 인증과 기존 데이터는 남기고 신규 애플리케이션 영역을 다시 구축하는 것이 장기적으로 더 효율적이라고 판단했습니다.

## Why 1 — 왜 리팩터링이 아니었나요?

리팩터링도 기존 동작과 영향 범위를 충분히 이해한 상태에서 해야 하는데, 당시에는 분석 비용과 변경 리스크가 컸습니다.

그리고 신규 기능이 계속 추가될 예정이라 기존 구조와 신규 구조가 혼재하면 복잡도가 더 커질 가능성이 있었습니다.

## Why 2 — 왜 전체를 다 새로 안 만들었나요?

신규 구축이 목적이 아니었기 때문입니다.

기존 사용자 / 인증 / 데이터처럼 이미 안정적으로 동작하고 사업적으로 연결된 부분은 유지하고, 앞으로 계속 확장해야 하는 애플리케이션 영역만 새 구조로 분리했습니다.

## Why 3 — 다시 한다면?

당시 조건이라면 비슷하게 판단할 것 같습니다.

다만 기존 코드에 충분한 테스트와 명확한 경계가 있었다면 점진적 migration을 먼저 검토했을 것입니다.

# 5. 신규 프로젝트에서 가장 먼저 고민한 것

## 한 줄

> 기술 스택보다 **기존 시스템과 신규 시스템의 경계**를 먼저 정했다.

## 답변

신규 프로젝트라고 해서 모든 시스템을 다시 만들 수는 없었기 때문에 기존 시스템과 신규 시스템의 경계를 먼저 정했습니다.

특히 기존 인증을 그대로 활용해야 했고 여러 도메인이 하나의 API를 사용하고 있어서, 인증 흐름과 API 호출 구조를 먼저 정리한 뒤 프로젝트 구조와 공통 UI 구조를 설계했습니다.

## 꼬리

### 무엇을 기존에 남겼나?

이미 안정적으로 동작하고 사업적으로 연결되어 있던 영역입니다. 인증, 기존 사용자와 데이터가 여기 해당합니다.

이 부분은 바꿔서 얻을 이득보다 잘못 건드렸을 때의 리스크가 훨씬 컸습니다.

### 무엇을 신규화했나?

앞으로 계속 확장해야 하는 애플리케이션 영역입니다.

- 마스터 어드민 / 단지 어드민 / 사용자 서비스 화면
- 프로젝트 구조와 공통 UI
- API 호출 구조

### 가장 먼저 합의한 건?

**경계**입니다. 어디까지 기존 것을 쓰고 어디부터 새로 만들지를 먼저 정했습니다.

이걸 정하지 않으면 화면을 만들다가 "이건 기존 걸 불러와야 하나 새로 만들어야 하나"를 매번 다시 논의하게 됩니다. 경계를 먼저 긋고 나서 인증 흐름을 설계했습니다.

### Backend와 무엇을 협의했나?

크게 두 가지입니다.

1. **기존 인증을 신규 앱에서 어떻게 이어받을지** — 쿠키 도메인 범위와 세션을 어디까지 공유할지
2. **여러 도메인이 하나의 API를 바라볼 때 CORS를 어디서 감당할지** — 백엔드 allowlist로 계속 관리할지, 프론트에서 흡수할지

두 번째는 결과적으로 프론트의 Next 프록시로 흡수하는 쪽으로 정리됐습니다.

# 6. AI Agent를 어떻게 활용했나요?

## 이력서에 적힌 것

- Claude Code
- Cursor
- Figma MCP
- 공통 / 프로젝트 CLAUDE.md
- Command / Memory
- UI 구현
- 구조 설계
- 코드리뷰
- 테스트 / 수정 자동화

## 기본 답변

신규 프로젝트를 빠르게 구축해야 해서 Agent를 코드 탐색, 반복적인 화면 구현, 리팩터링, 테스트 등에 적극적으로 활용했습니다.

처음에는 작업마다 필요한 내용을 프롬프트로 설명했는데 프로젝트가 커지면서 구조와 규칙을 반복해서 설명해야 했고, Agent가 서로 다른 패턴으로 코드를 만드는 문제가 생겼습니다.

그래서 프로젝트 구조와 규칙을 Harness로 명시하고, 반드시 지켜야 하는 규칙은 lint나 타입 같은 방식으로 검증하도록 발전시켰습니다.

## Why 1 — 왜 Harness가 필요했나요?

Agent가 매번 처음부터 프로젝트 맥락을 추론하게 하면 코드 위치, import, 추상화 방식이 흔들릴 수 있었기 때문입니다.

## Why 2 — 왜 프롬프트만 잘 쓰면 안 됐나요?

프롬프트는 작업 단위 지시에는 좋지만, 프로젝트 전체의 지속적인 규칙과 맥락을 매번 반복 설명하는 데는 한계가 있었습니다.

## Why 3 — 사람이 하는 일은?

요구사항 정의, 구조적 판단, 아키텍처, 리뷰, 최종 검증을 가져갑니다.

> 작업은 위임하지만 코드에 대한 책임까지 위임하지 않습니다.

# 7. AI Harness 구조

## 구조

```text
Global
└─ 공통 개발 원칙

Project
├─ 프로젝트 목적
├─ Architecture
├─ Domain Context
├─ Monorepo package 역할
├─ FSD 규칙
├─ import / reuse 규칙
└─ 금지 영역

Commands
├─ 구현
├─ 리뷰
├─ 리팩터링
└─ 테스트

Memory / Context
├─ 반복적으로 필요한 프로젝트 정보
└─ 작업 중 축적된 판단

Validation
├─ lint
├─ type
└─ test
```

## 답변

전역과 프로젝트 단위로 분리했습니다.

전역에는 프로젝트가 바뀌어도 유지할 코드 작성 원칙을 두고, 프로젝트 안에는 아키텍처, 모노레포 패키지 역할, FSD 구조, 도메인 컨텍스트, 금지사항을 넣었습니다.

반복 작업은 Command 형태로 분리했고, 반드시 지켜야 하는 규칙은 문서에만 두지 않고 lint, type, test로 검증했습니다.

## 꼬리

### 왜 하나의 CLAUDE.md에 안 넣나요?

항상 필요한 정보와 특정 작업에서만 필요한 정보가 다르기 때문입니다.

### 어떤 건 lint로 옮기나요?

명확하게 기계적으로 판정 가능한 규칙입니다.

예: import boundary.

### 어떤 건 문서에 남기나요?

불필요한 추상화, 도메인 맥락, 책임 분리처럼 판단이 필요한 것.

# 8. AI 실패 경험

## 키워드

```text
과도한 위임
→ 직접 탐색 감소
→ 구조 이해 시간 감소
→ 문제 인지
→ 리뷰 강화
→ 역할 분리
```

## 답변

초기에는 AI를 적극적으로 사용하는 것 자체에 집중해서 간단한 수정까지 Agent에게 맡겼습니다.

그러다 보니 구현 속도는 빨랐지만 제가 직접 코드를 탐색하고 구조를 이해하는 시간이 줄어드는 문제가 있었습니다.

이후에는 반복 실행은 AI에게 맡기더라도 구조적 판단과 최종 리뷰는 직접 가져가는 방식으로 바꿨습니다.

## 꼬리

### AI 사용량을 줄였나?

총량을 줄이지는 않았습니다. **맡기는 종류를 바꿨습니다.**

반복적인 구현과 대량 변경은 그대로 맡기되, 구조 판단과 최종 리뷰는 제가 다시 가져왔습니다. 문제는 사용량이 아니라 "제가 설명할 수 없는 코드가 쌓이는 것"이었습니다.

### 어떤 작업은 맡기지 않나?

되돌리기 어려운 판단입니다.

- 레이어 / 패키지 경계 같은 구조 결정
- 인증, 권한처럼 틀리면 보안 문제가 되는 영역
- 스키마 변경이나 마이그레이션
- Harness 규칙 자체

반대로 패턴이 정해진 반복 구현, 테스트 케이스 확장, 대량 치환은 적극적으로 맡깁니다.

### AI 결과를 어떻게 검증하나?

타입, lint, 빌드가 1차 방어선입니다. 존재하지 않는 API나 경계 위반은 대부분 여기서 걸립니다.

그다음 리뷰에서 AI 코드에 유독 자주 나오는 것을 먼저 봅니다.

1. 요청하지 않은 코드가 추가됐는가 (쓰지 않는 옵션, 미래를 위한 추상화)
2. 기존 코드를 재사용하지 않고 새로 만들었는가
3. 경계 규칙을 우회했는가

최종 기준은 하나입니다. **제가 설명할 수 없는 코드는 머지하지 않습니다.**

### 테스트 통과하면 믿나?

아니요. **테스트를 누가 썼는지가 중요합니다.**

같은 Agent가 구현과 테스트를 함께 썼다면 그 테스트는 구현을 그대로 옮긴 것일 수 있습니다. 구현의 잘못된 가정이 테스트에도 똑같이 들어가면 둘 다 통과합니다.

그래서 중요한 로직은 테스트가 **무엇을 보장하는지**를 직접 읽고, 필요하면 실패해야 하는 케이스를 추가합니다.

# 9. AI Harness의 실제 효과

## 말하면 좋은 것

- 코드 위치 예측 가능
- 반복 설명 감소
- import / 구조 일관성
- 리뷰의 초점 변화
- 반복 UI 구현 속도 향상

## 주의

정량 측정이 없다면:

```text
개발 속도 2배
리드타임 50% 감소
```

같이 말하지 않는다.

## 답변

정량 지표를 따로 만들지는 않았습니다.

다만 Agent가 예상한 구조와 패턴 안에서 코드를 작성하는 비율이 높아지면서, "이 파일은 어디에 있어야 한다", "이 import는 규칙에 맞지 않는다" 같은 반복적인 리뷰보다 실제 구현 판단에 집중할 수 있게 됐습니다.

# 10. FSD / Public API / lint

## 실제 사례

```text
public API까지만 import
↓
Agent가 내부 파일까지 직접 import
↓
기능은 정상
↓
구조 일관성 깨짐
↓
lint로 강제
```

## 답변

FSD 구조에서 segment의 public API를 통해 import하는 규칙을 사용했습니다.

Agent가 작업하면서 내부 컴포넌트 파일까지 직접 import하는 사례가 반복적으로 생겼고, 기능은 동작하지만 내부 구조와 결합도가 높아지고 import 방식이 파편화됐습니다.

그래서 기계적으로 판정 가능한 규칙이라 보고 lint로 강제했습니다.

## 꼬리

### 왜 FSD?

기능이 계속 추가될 프로젝트에서 **"이 코드를 어디에 둘지"가 매번 개인 판단이 되는 걸 막고 싶었습니다.**

AI Agent에게 맡기는 비중이 커지면서 이유가 하나 더 생겼습니다. 구조가 암묵적이면 Agent는 매번 다른 위치에 코드를 만듭니다. 레이어와 import 규칙이 명시적이면 사람과 Agent가 같은 기준을 씁니다.

### 왜 barrel?

슬라이스의 **공개 API를 한 지점으로 좁히기 위해서**입니다.

내부 파일 경로가 밖으로 새어 나가면 그 순간부터 내부 구조를 바꿀 수 없습니다. `@/features/example/ui`까지만 열어두면 그 아래는 자유롭게 리팩터링할 수 있습니다.

대신 barrel도 공짜가 아니라서, 경계를 만들고 싶은 지점에만 두고 슬라이스 내부에서는 상대 경로로 직접 import했습니다.

### 단점은?

- 작은 기능에도 폴더와 파일이 여러 개 생깁니다
- `entities`인지 `features`인지 경계가 항상 명확하지 않아 논쟁이 생깁니다
- barrel은 tree-shaking이 완벽하지 않으면 불필요한 모듈을 끌고 오고, 순환 참조가 생기기 쉽습니다
- **강제하지 않으면 폴더만 FSD고 실제 의존성은 뒤엉킵니다**

마지막이 실제로 저희에게 일어난 문제라 lint로 막았습니다.

### circular dependency는?

원인은 보통 두 가지입니다. barrel을 서로 참조하는 경우와, 하위 레이어가 상위 레이어를 참조하는 경우입니다.

FSD의 단방향 의존 규칙은 사실상 순환을 구조적으로 막는 장치입니다. 하위가 상위를 못 보게 하면 사이클이 만들어질 수 없어서, 이 방향을 lint로 강제했습니다.

그리고 순환이 필요해 보이면 대부분 **공통으로 내려야 할 코드가 아직 위 레이어에 남아 있다는 신호**로 봤습니다.

> 이 영역은 실제 질문이 나오면 깊게. 처음부터 먼저 꺼내지 않는다.

# 11. Monorepo

## 이력서 주장

- Turborepo
- 여러 앱
- 공통 자산
- 독립 배포
- Build pipeline 표준화

## 기본 답변

마스터 어드민, 단지 어드민, 사용자 서비스가 공통 UI와 인증, 유틸을 공유해야 했기 때문에 모노레포를 선택했습니다.

각 앱은 독립적으로 개발 / 배포하되 공통 모듈은 package로 재사용할 수 있게 경계를 나눴습니다.

## Why 1 — 왜 repo 여러 개가 아니었나요?

공통 UI와 설정이 변경될 때 여러 repository의 버전과 배포를 따로 맞추는 비용이 커질 수 있다고 봤습니다.

## Why 2 — 모노레포 단점은?

- 의존성 경계가 흐려질 수 있음
- 빌드 설정 복잡
- package 간 coupling 가능

그래서 package 역할과 의존 방향을 명확히 나누는 게 중요합니다.

## 꼬리

### 어떤 package를 뺐나?

여러 앱이 실제로 함께 쓰는 것만 뺐습니다.

- 공통 UI 컴포넌트와 디자인 토큰
- 공용 설정 (eslint / tsconfig / prettier)
- 앱 간 공유되는 유틸과 타입

반대로 특정 앱에서만 쓰는 도메인 로직은 그 앱에 남겼습니다. 공통 package에 넣으면 그 앱 사정 때문에 다른 앱이 영향을 받습니다.

### 공통화 기준?

**두 개 이상의 앱에서 같은 형태로 실제 반복될 때** 올립니다. "언젠가 쓸 것 같아서" 미리 올리지 않습니다.

기준을 이렇게 잡은 이유는, 한 곳에서만 쓰는 코드를 공통으로 올리면 그 뒤로 모든 변경이 공통 package 배포를 거쳐야 하기 때문입니다. 얻는 것보다 비용이 큽니다.

### 독립 배포는 어떻게?

앱마다 빌드·배포 단위를 분리하고 공통 부분은 package로 참조합니다. 한 앱을 배포한다고 다른 앱을 같이 올릴 필요는 없습니다.

다만 **완전한 독립은 아닙니다.** 공통 package를 바꾸면 그걸 쓰는 앱은 전부 영향을 받습니다. 그래서 공통 package의 변경은 더 신중하게 봅니다.

### build cache?

Turborepo가 태스크의 입력(소스, 설정, 의존성)을 해시해서 결과를 캐시합니다. 바뀌지 않은 package는 다시 빌드하지 않고 캐시된 결과를 씁니다.

효과가 큰 지점은 CI입니다. 앱 하나만 고쳤는데 모노레포 전체를 다시 빌드하는 상황을 막아줍니다.

### Turborepo를 왜?

필요한 게 **태스크 의존 그래프와 캐시** 두 가지였고, 그 이상은 필요하지 않았습니다.

이미 Next 기반이라 설정이 가볍게 붙었고, 새로운 빌드 시스템을 팀이 따로 배우지 않아도 됐습니다. 더 강력한 도구도 있지만 지금 규모에서는 학습·운영 비용이 이득보다 크다고 봤습니다.

# 12. Design System

## 기본 답변

여러 관리자와 사용자 서비스에서 같은 UI 패턴을 반복 구현해야 했기 때문에 공통 디자인 토큰과 컴포넌트를 분리했습니다.

목적은 컴포넌트 수를 늘리는 게 아니라 여러 앱에서 동일한 규칙을 재사용하고, 변경 시 한 곳에서 관리하는 것이었습니다.

## 꼬리

### 언제 공통 컴포넌트로 올리나?

두 가지가 동시에 만족될 때 올립니다.

1. 두 개 이상의 앱이나 화면에서 **같은 형태로** 반복된다
2. 그 컴포넌트가 **표시 책임만** 갖는다 (도메인 상태를 모른다)

두 번째가 중요합니다. 도메인을 아는 컴포넌트를 공통으로 올리면 다른 앱이 쓸 때마다 그 도메인이 딸려 옵니다.

### 너무 빨리 공통화하면?

케이스가 하나씩 늘 때마다 prop과 분기가 붙습니다. 결국 **어느 화면에도 딱 맞지 않는데 모두가 의존하는 컴포넌트**가 됩니다.

그 시점엔 고치는 것도 어렵습니다. 바꾸면 모든 앱이 영향을 받으니까요.

그래서 확신이 없으면 중복을 그대로 두는 쪽을 택했습니다. 중복은 나중에 합칠 수 있지만, 잘못 뽑은 추상화는 되돌리기 어렵습니다.

### Design Token이 뭔가?

색, 간격, 타이포그래피 같은 값을 **이름으로 고정한 것**입니다.

`#3B82F6` 대신 `primary`, `16px` 대신 `spacing-md`를 참조하게 합니다. 값이 아니라 의미를 참조하기 때문에

- 라이트/다크 테마 전환이 토큰 교체로 끝나고
- 브랜드 색을 바꿀 때 한 곳만 고치면 되고
- "이 파랑은 어떤 파랑인가"를 매번 정하지 않아도 됩니다

저희는 토큰을 source of truth로 두고 거기서 CSS 변수를 생성하는 방식으로 관리했습니다.

### Storybook은 왜?

목적은 **컴포넌트를 앱 밖에서 상태별로 확인**하는 것입니다. 로딩·에러·빈 상태처럼 실제 화면에서 재현하기 번거로운 경우를 바로 볼 수 있고, 디자이너·기획자와 같은 화면을 두고 이야기할 수 있습니다.

다만 도입 자체가 목적이 되면 스토리를 유지하는 비용만 남습니다. 컴포넌트가 바뀌었는데 스토리가 안 따라오면 오히려 잘못된 참조가 됩니다.

> ✍️ 실제로 도입했는지 / 어디까지 썼는지를 사실대로 말할 것. 안 썼다면 "필요성은 알지만 당시엔 앱에서 바로 확인이 가능해 우선순위를 뒤로 뒀다"가 정직한 답.

# 13. 인증 구조

## 이력서 주장

- Session/Cookie
- HttpOnly
- SSO
- 서브도메인
- 세션 / 토큰 혼재 구조 통합

## 기본 답변

신규 서비스라고 인증까지 새로 만들지는 않았습니다.

기존 사용자 인증 체계를 그대로 활용해야 했고, 서비스 간 인증 상태를 공유해야 해서 서브도메인 기반의 세션 쿠키 인증 구조를 사용했습니다.

프론트에서 인증 정보를 직접 관리하는 범위를 줄이고, 인증 상태와 만료를 서버 중심으로 관리하는 방향이었습니다.

## Why 1 — 왜 Session?

기존 인증 체계를 재사용해야 했고 서버에서 세션 상태와 무효화를 관리하고 있던 구조였기 때문에 자연스러운 선택이었습니다.

## Why 2 — 왜 HttpOnly?

JavaScript에서 인증 쿠키를 직접 읽지 못하게 해서 XSS 상황에서 토큰 값 자체가 노출되는 경로를 줄이기 위해서입니다.

## 주의

> "Session이 JWT보다 무조건 안전하다"라고 말하지 않는다.

## 깊게 들어오면

- Secure
- SameSite
- CSRF
- XSS
- cookie domain
- 만료

# 14. Reverse Proxy

## 이력서 주장

- 100+ 도메인
- 하나의 Backend API
- CORS 운영 복잡도
- Next reverse proxy

## 기본 답변

100개가 넘는 도메인이 하나의 Backend API를 사용하는 구조였는데, 모든 도메인을 Backend CORS allowlist에서 관리하면 도메인 추가 때마다 Backend 설정과 배포가 필요했습니다.

인프라 레벨 프록시도 검토할 수 있었지만, 당시에는 기존 Next 서버를 활용하면 별도 인프라 없이 일관된 API 경로를 만들 수 있었습니다.

API hop과 Next 서버 의존성이 늘어난다는 단점은 알고 있었지만 당시 규모에서는 운영 단순성의 이점이 더 크다고 판단했습니다.

## Why 1 — CORS가 왜 문제?

기술적으로 어렵다는 뜻이 아니라 변경 주기가 다른 두 시스템이 결합되는 문제였습니다.

## Why 2 — 왜 Nginx / Gateway가 아니었나요?

추가 인프라의 설정, 배포, 모니터링, 운영 포인트가 생기기 때문입니다.

## Trade-off

- hop 증가
- Next server 부하
- 장애 전파 가능

## 깊게 들어오면

- cookie forwarding
- Set-Cookie
- timeout
- retry
- idempotency

# 15. Amplitude / A/B 테스트 — 가장 위험한 영역

## 이력서에 적힌 주장

- 이벤트 정의
- 공통 logging
- PM과 데이터 분석
- 개선 가설
- A/B 테스트 운영
- CTA / gallery 개선
- 문의 클릭 전환율 23% 개선

## 반드시 사실 기준으로 정리

### 내 역할

아래 중 실제 한 것만 말한다.

- 이벤트 schema 설계
- 이벤트 구현
- variant 구현
- PM / marketer와 데이터 확인
- 결과 분석 참여
- 실험 운영

## 안전한 답변 방향

실험 전체를 제가 단독으로 리드했다기보다는 PM / 마케터와 함께 가설을 보고, 프론트에서는 variant 구현과 이벤트 계측, Amplitude에서 비교할 수 있는 기반을 만드는 역할을 했습니다.

## 23% 질문 대비

반드시 확인해야 한다.

```text
무엇의 23%?
절대값인가 상대 개선율인가?
기존 값?
개선 값?
기간?
표본?
누가 분석?
```

기억나지 않으면 지어내지 않는다.

> 정확한 baseline 수치는 지금 기억나지 않지만, 이력서의 23%는 문의 클릭 전환율의 상대 개선으로 정리한 수치입니다.

※ 위 문장은 실제 정의가 맞을 때만 사용.

## 꼬리

### 어떤 이벤트를 수집?

기준은 **가설을 검증할 수 있는 최소 단위**였습니다. 화면에서 일어나는 모든 걸 수집하면 나중에 어떤 이벤트가 무슨 의미인지 아무도 모르게 됩니다.

- 진입 (어떤 화면에 들어왔는가)
- 노출 (검증 대상 UI를 실제로 봤는가)
- 클릭 (문의 CTA 등 전환 직전 행동)
- 전환 (목표 행동 완료)

그리고 이벤트 이름과 속성을 임의로 만들지 않도록 공통 logging 유틸을 두고 schema를 맞췄습니다. 여기가 흐트러지면 나중에 비교 자체가 안 됩니다.

> ✍️ 실제로 정의한 이벤트 이름 2~3개를 말할 수 있으면 훨씬 강해진다. 기억나는 것만.

### A/B 그룹 어떻게?

프론트에서는 **주어진 그룹에 따라 variant를 렌더링하고, 어떤 그룹이었는지를 이벤트에 실어 보내는 것**이 역할이었습니다.

여기서 중요하게 본 건 두 가지입니다.

1. **같은 사용자가 계속 같은 그룹을 봐야 한다** — 새로고침할 때마다 화면이 바뀌면 실험이 무의미해집니다
2. **그룹 정보가 전환 이벤트까지 따라붙어야 한다** — 안 그러면 나중에 어느 그룹의 전환인지 붙일 수 없습니다

> ✍️ 그룹 배정을 프론트에서 했는지, 서버/툴에서 내려줬는지는 사실대로. 모르면 "배정 로직 자체는 제가 설계한 부분이 아닙니다"가 맞는 답.

### 통계적 유의성?

**제가 직접 판단한 영역은 아닙니다.** 이 부분은 솔직하게 말하는 게 맞다고 생각합니다.

제가 이해하고 있는 범위에서는, 표본이 충분히 쌓이기 전의 차이는 우연일 수 있어서 기간과 표본을 정해두고 봐야 하고, 중간에 좋아 보인다고 실험을 일찍 끝내면 결과가 왜곡됩니다.

프론트에서 제가 책임진 부분은 **판단의 근거가 되는 데이터가 신뢰할 수 있게 쌓이는 것**이었습니다. 이벤트 누락이나 중복이 있으면 그 위의 분석은 전부 무의미해지니까요.

### PM과 역할?

실험 전체를 제가 단독으로 리드했다기보다는, PM·마케터와 함께 가설을 보고 프론트에서 검증 가능한 형태로 만드는 역할이었습니다.

- **PM / 마케터**: 가설 수립, 지표 정의, 결과 해석
- **저**: 이벤트 schema 설계와 구현, variant 구현, Amplitude에서 비교 가능한 기반 만들기, 결과 확인에 참여

역할을 부풀리지 않는 게 중요하다고 생각합니다. 과장하면 바로 다음 질문에서 드러납니다.

### 실험 실패 경험?

가설이 기각된 것 자체는 실패가 아니라 결과입니다. 실제로 문제가 되는 건 **결론을 못 내리는 실험**입니다.

계측이 빠져 있거나, 그룹 정보가 전환 이벤트까지 안 붙거나, 노출 이벤트가 없어서 "봤는데 안 눌렀다"와 "아예 못 봤다"를 구분할 수 없는 경우입니다.

그래서 실험을 시작하기 전에 **결과가 어떻게 나오든 해석이 가능한지**를 먼저 확인하는 게 프론트의 몫이라고 봅니다.

> ✍️ 실제로 겪은 계측 누락·재실험 사례가 있으면 그걸로 교체.

# 17. SEO / 동네생활백서

## 이력서 주장

- App Router
- SSR / SSG 전략 분리
- IA / URL
- metadata
- indexing
- Search Console

## 기본 답변

모든 페이지를 같은 렌더링 방식으로 두지 않고 콘텐츠 특성과 변경 주기를 기준으로 SSR과 SSG를 나눴습니다.

검색 유입이 중요한 서비스였기 때문에 URL 구조, metadata, sitemap, indexing 여부를 함께 봤습니다.

## Why 1 — SSR / SSG 기준?

```text
자주 변함 / 요청 시점 데이터 필요 → SSR
변경 적음 / 미리 생성 가능 → SSG
```

## 꼬리

### sitemap 어떻게?

정적으로 고정된 페이지는 빌드 시점에 생성하고, 콘텐츠처럼 계속 늘어나는 URL은 데이터에서 가져와 생성했습니다.

요청마다 전체를 훑어 만들면 크롤러가 자주 요청할 때 그대로 부하가 되기 때문에, 캐시하거나 주기적으로 생성하는 쪽이 맞다고 봤습니다.

sitemap은 **최신일 필요는 있어도 실시간일 필요는 없습니다.** 검색엔진이 반영하는 데 어차피 시간이 걸립니다.

### canonical?

같은 내용이 여러 URL로 존재할 때 **어떤 URL이 대표인지** 알려주는 표시입니다.

정렬 파라미터, 페이지네이션, `?utm_...` 같은 추적 파라미터, www 유무처럼 사실상 같은 페이지가 여러 주소를 갖는 경우가 흔합니다. 그대로 두면 평가가 분산됩니다.

주의할 점은 canonical이 **강제가 아니라 힌트**라는 것과, sitemap에는 canonical URL만 넣어야 한다는 것입니다. 둘이 서로 다른 URL을 가리키면 신호가 충돌합니다.

### robots.txt?

크롤러에게 **어디를 크롤링하지 말라고 알리는 파일**입니다. sitemap이 "여기 있으니 와서 봐라"는 안내라면 robots.txt는 제한입니다.

자주 혼동되는 지점이 하나 있습니다. robots.txt로 막은 경로는 크롤러가 접근하지 않으므로 **그 안의 `noindex`도 읽히지 않습니다.**

색인에서 빼고 싶으면 robots.txt로 막는 게 아니라 페이지에 `noindex`를 두고 크롤링은 허용해야 합니다.

### indexing 확인?

sitemap에 넣었다고 색인이 보장되지는 않기 때문에, 제출한 URL 수와 실제 색인된 URL 수를 비교해서 격차가 큰 그룹을 찾는 방식으로 봤습니다.

색인이 안 되는 경우는 보통 원인이 정해져 있습니다.

- `noindex`가 남아 있거나 robots.txt에 막혀 있음
- canonical이 다른 URL을 가리키고 있음
- 콘텐츠가 얇거나 다른 페이지와 사실상 중복

### Search Console에서 무엇을 봤나?

주로 **색인 상태와 검색 유입**입니다. 어떤 페이지가 색인됐는지, 제외됐다면 이유가 무엇인지, 어떤 검색어로 노출되고 클릭되는지를 봤습니다.

> ✍️ 여기서 구체적으로 무엇을 발견하고 무엇을 고쳤는지 한 가지만 말할 수 있으면 답변이 훨씬 강해진다. 기억나는 사례가 없으면 "정기적으로 색인 상태를 확인하는 수준이었다"고 정직하게 말하는 편이 낫다.

# 18. Sitemap

## 한 줄

검색엔진에게 발견할 URL을 알려주는 XML 목록.

## Why

동적 URL이 많으면 내부 링크만으로 모든 페이지를 발견하기 어려울 수 있기 때문입니다.

## 꼬리

### robots.txt와 차이?

역할이 반대에 가깝습니다. robots.txt는 "여기는 크롤링하지 마라"는 **제한**이고, sitemap은 "여기 있으니 와서 봐라"는 **안내**입니다.

그리고 robots.txt로 막은 경로는 크롤러가 들어가지 않으므로 그 안의 `noindex`도 읽히지 않습니다. 색인에서 빼고 싶으면 크롤링은 허용하고 `noindex`를 둬야 합니다.

### canonical?

같은 내용이 여러 URL로 존재할 때 대표 URL을 알려주는 힌트입니다. 파라미터나 페이지네이션 때문에 중복이 생겼을 때 평가가 분산되는 걸 막습니다.

sitemap에는 **canonical URL만** 넣습니다. 둘이 다른 URL을 가리키면 신호가 충돌합니다.

### URL 100만 개?

sitemap 한 파일에는 URL 5만 개, 압축 전 50MB라는 상한이 있어서 나눠야 합니다.

```text
sitemap index (최상위)
→ sitemap-1.xml
→ sitemap-2.xml
```

실무적으로는 단순히 개수로 쪼개는 것보다 **의미 단위로 나누는 게** 낫습니다. 카테고리별이나 갱신 주기별로 나누면 어떤 그룹이 색인되고 있는지 파악하기 쉽고, 자주 바뀌는 그룹만 다시 만들면 됩니다.

### 모두 sitemap에 넣나?

아니요. **색인시키고 싶은 페이지만** 넣습니다.

- 로그인, 마이페이지처럼 개인화된 화면
- 검색 결과처럼 조합이 무한한 페이지
- `noindex`를 건 페이지 (넣으면 신호가 모순됩니다)
- canonical이 아닌 중복 URL

가치 없는 URL을 많이 넣으면 크롤링 예산만 낭비됩니다.

# 20. 상태관리

## 첫 문장

> 라이브러리보다 상태의 소유권과 수명을 먼저 봅니다.

## 분류

```text
Local State
Server State
Global Client State
URL State
```

## 답변

- 컴포넌트 안 → useState
- 서버 데이터 → TanStack Query
- 여러 영역 공유 client state → Zustand / Redux
- 공유 / 복원 / 뒤로가기 → URL

## 꼬리

### Redux와 Zustand는 어떻게 다른가요?

큰 차이는 **강제하는 구조의 양**입니다.

- **Redux**: action / reducer로 흐름이 명확하고 도구가 강력합니다. 대신 boilerplate가 생기고, 규모가 작으면 구조 비용이 이득보다 큽니다
- **Zustand**: API가 단순하고 자유도가 높습니다. 대신 기준 없이 쓰면 store가 비대해지고 server state까지 들어가기 쉽습니다

저는 팀 규모와 상태의 복잡도로 나눈다고 생각합니다. 흐름 추적이 중요한 큰 상태 기계라면 Redux 쪽 구조가 도움이 되고, 화면 몇 개가 공유하는 가벼운 client state라면 Zustand로 충분합니다.

### Context는 언제 쓰나요?

**자주 바뀌지 않는 전역 값**에 씁니다. theme, 인증 컨텍스트, 로케일 같은 것들입니다.

주의할 점은 Context가 상태관리 도구가 아니라 **전달 수단**이라는 것입니다. 값이 바뀌면 그 Context를 구독하는 모든 컴포넌트가 리렌더됩니다.

그래서 자주 바뀌는 값이나 넓게 쓰이는 값을 Context에 넣으면 성능 문제가 생깁니다. 그런 건 별도 store로 빼서 필요한 컴포넌트만 구독하게 하는 게 맞습니다.

### Query가 상태관리인가?

관리하는 대상이 다르다고 봅니다. React Query는 client global state 라이브러리라기보다 **server state 관리 도구**입니다.

서버 데이터는 client state와 성격이 다릅니다. 내가 소유한 값이 아니라 **원본이 서버에 있는 값의 복사본**이라서, 캐시·stale 판단·재요청·무효화가 필요합니다.

이걸 직접 store에 넣고 관리하면 로딩·에러·중복 요청·경쟁 상태를 전부 손으로 짜게 됩니다. 그래서 서버에서 오는 데이터는 Query에 맡기고, store에는 진짜 client state만 남깁니다.

### URL state 단점?

- **길이 제한과 가독성** — 상태가 많아지면 URL이 지저분해지고 브라우저·서버마다 상한이 있습니다
- **민감한 값을 넣으면 안 됩니다** — URL은 로그, 히스토리, Referer로 새어 나갑니다
- **타입이 없습니다** — 전부 문자열이라 파싱과 검증이 필요하고, 사용자가 직접 고칠 수 있으니 신뢰할 수 없는 입력으로 다뤄야 합니다
- 변경 빈도가 높은 상태에는 부적합합니다. 타이핑마다 URL을 바꾸면 히스토리가 오염됩니다

그래서 **공유하거나 뒤로가기로 복원해야 하는 상태만** URL에 둡니다.

# 23. Browser Rendering / CSS 성능

## Pipeline

```text
HTML → DOM
CSS → CSSOM
Render Tree
→ Layout
→ Paint
→ Composite
```

## 핵심

CSS 성능은 "어떤 CSS 문법"보다 변경이 브라우저 어느 단계를 다시 실행시키는지를 본다.

## 꼬리

### reflow는 언제 일어나나요?

요소의 **위치나 크기를 다시 계산해야 할 때** 일어납니다. `width`, `height`, `top`, `font-size`, DOM 추가·삭제 등이 유발합니다.

한 요소가 바뀌면 주변과 자식까지 영향을 받기 때문에 비용이 큽니다. 그래서 애니메이션에서 레이아웃을 건드리는 속성을 바꾸는 걸 피합니다.

### repaint와는 뭐가 다른가요?

repaint는 **위치는 그대로고 픽셀만 다시 칠하는 것**입니다. `color`, `background-color`, `visibility` 같은 속성이 해당합니다.

관계는 한 방향입니다. **reflow가 일어나면 repaint도 따라오지만, 반대는 아닙니다.** 그래서 레이아웃을 건드리지 않고 색만 바꾸는 변경이 더 쌉니다.

### layout thrashing이 뭔가요?

**쓰기와 읽기를 번갈아 하면서 강제로 레이아웃 계산을 반복시키는 것**입니다.

```js
// 나쁨: 매 반복마다 강제 동기 레이아웃
for (const el of items) {
  el.style.width = el.offsetWidth + 10 + 'px';
}
```

브라우저는 스타일 변경을 모아서 처리하려 하는데, `offsetWidth`처럼 레이아웃 결과가 필요한 값을 읽으면 그 자리에서 계산을 강제합니다.

해결은 **읽기를 먼저 다 하고 쓰기를 나중에 몰아서** 하는 것입니다.

### transform / opacity는 왜 유리한가요?

레이아웃과 페인트를 건너뛰고 **합성 단계에서 처리될 수 있기** 때문입니다.

다만 "transform은 무조건 GPU라 빠르다"는 과장입니다. 레이어 승격 조건에 따라 달라지고, 레이어가 많아지면 합성 비용과 메모리가 늘어 오히려 느려질 수 있습니다.

정확하게는 **"레이아웃을 유발하는 속성보다 유리한 경우가 많다"** 정도로 말하고, 실제로는 측정해서 확인합니다.

### will-change는?

"이 속성이 곧 바뀔 테니 미리 준비해라"라고 브라우저에 알리는 힌트입니다. 보통 해당 요소를 별도 레이어로 승격시킵니다.

주의할 점이 많습니다.

- **레이어마다 메모리를 씁니다.** 남발하면 오히려 느려집니다

# 25. API 3회 호출 문제

## 첫 문장

> 먼저 세 요청이 서로 의존적인지 확인하겠습니다.

## 사고

```text
의존성?
→ 병렬 가능?
→ 중복?
→ cache?
→ 첫 화면 필수?
→ BFF?
→ 일부 실패 허용?
```

## 꼬리

### Promise.all 중 하나가 실패하면?

**즉시 reject됩니다.** 첫 번째 실패가 그대로 전체 결과가 됩니다.

주의할 점은 나머지 요청이 취소되지는 않는다는 것입니다. 이미 보낸 요청은 계속 진행되고 결과만 버려집니다.

그래서 "하나가 실패해도 나머지 화면은 보여줘야 한다"면 `Promise.all`은 맞지 않습니다.

### allSettled?

**모든 프로미스가 끝날 때까지 기다리고, 각각의 성공/실패를 배열로 돌려줍니다.**

```js
const results = await Promise.allSettled([apiA(), apiB(), apiC()]);
// [{status:'fulfilled', value}, {status:'rejected', reason}, ...]
```

일부가 실패해도 나머지를 렌더링해야 하는 화면에 적합합니다. 대신 호출한 쪽에서 각 결과의 상태를 직접 확인해야 하고, **실패한 영역을 UI에서 어떻게 보여줄지**를 결정해야 합니다.

### 하나만 느리면?

먼저 그 응답이 **첫 화면에 꼭 필요한지**를 봅니다.

- 필요 없다면 → 나머지를 먼저 렌더하고 느린 부분만 나중에 채웁니다 (Suspense, 스트리밍, 스켈레톤)
- 필요하다면 → 왜 느린지 봅니다. 백엔드 쿼리인지, 응답이 과하게 큰지, 왕복이 많은지

그리고 **타임아웃을 둡니다.** 하나가 무한정 기다리면 전체 화면이 인질이 됩니다.

전부 모아서 한 번에 보여주는 것보다 **먼저 보여줄 수 있는 걸 먼저 보여주는 게** 체감상 훨씬 빠릅니다.

### cache stale?

캐시는 **오래된 데이터를 보여줄 위험을 감수하고 속도를 얻는 것**입니다. 그래서 데이터마다 허용 가능한 낡음의 정도를 먼저 정합니다.

- 거의 안 바뀌는 데이터 → 길게 캐시
- 자주 바뀌지만 조금 늦어도 되는 데이터 → stale-while-revalidate. 캐시를 먼저 주고 뒤에서 갱신
- 항상 최신이어야 하는 데이터 → 캐시하지 않거나 매우 짧게

그리고 **변경이 일어난 쪽에서 무효화**하는 게 핵심입니다. 시간 만료에만 의존하면 사용자가 방금 수정한 값이 이전 값으로 보이는 상황이 생깁니다.

### BFF trade-off?

**장점**

- 요청 한 번으로 필요한 데이터를 받습니다. 왕복 횟수와 waterfall이 줄어듭니다
- 화면에 필요한 형태로 가공해서 내려줄 수 있어 클라이언트가 가벼워집니다
- 여러 백엔드의 차이를 한 곳에서 흡수합니다

**단점**

- 배포하고 운영할 서버가 하나 늘어납니다. 장애 지점도 늘어납니다
- 화면이 바뀔 때마다 BFF도 같이 바꿔야 해서 배포 결합이 생깁니다
- 캐시 전략이 한 겹 더 복잡해집니다

프록시를 도입할 때와 같은 종류의 판단입니다. **단순함과 통제력 사이의 trade-off**입니다.
