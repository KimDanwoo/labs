# 면접 하브루타 — 2026-10 당근 핵심

지난 면접에서 실제로 받은 질문 12개. 한 바퀴 20분.

질문마다 **키워드 3줄 → 30초 답변 → 오답 1장 → 꼬리 최대 2개**. 키워드만 보고 먼저 말해본 뒤 답변을 연다.

> `⟨…⟩`는 아직 채우지 않은 칸이다. 2차 이력서 문답·JD 대조·가정형 질문은 `havruta-2-v1`(확장)에 있다.

```text

대표 사례 = 거주후기 신규 구축
```

> 매물을 찾은 뒤 앱을 계속 사용할 이유가 부족하다는 문제를 거주후기 신규 구축으로 풀었고, 후기 등록·탐색 프론트엔드 전반을 주도했습니다.

# 2. 거주후기를 신규 구축한 배경과 본인 역할은?

## 키워드

```text
매물 찾은 뒤 방문 이유 부족 → 거주후기
피터팬 카페 실제 후기를 데이터화
등록·탐색 프론트 주도 · 기획은 PM
```

## 답변

> 매물을 찾은 뒤 앱을 계속 쓸 이유가 부족해서, 사용자 간 정보 공유를 위한 거주후기를 신규 도입했습니다. 피터팬 카페의 실제 거주후기를 데이터화해 연동했습니다.
> 기획은 PM이 주도했고, 저는 후기 등록·탐색 프론트엔드 전반을 주도했습니다.

## 오답 — 카페 데이터 수집·가공이나 예시 후기 아이디어도 내가 했다

내 범위는 등록·탐색 프론트엔드다. 데이터 수집·가공도, 예시 후기 제안도 내 것이라고 하지 않는다.

## 꼬리

### 거주후기를 왜 도입했나요?

키워드: 재방문 목적, 후기-매물 연결, 카페 콘텐츠 활용

매물 탐색 외 재방문 목적, 다른 주거 정보 수요, 후기-매물 연결, 기존 카페 콘텐츠 활용. **도입 의도**이지 재방문 성과 수치가 아니다.

### 출시 후에는 뭘 했나요?

키워드: 진입점 확장, 예시 후기, 진입·작성 이벤트

홈에만 있던 진입점을 매물 등록 완료·매물 상세·지도로 넓혔다. 후기가 없으면 예시 후기와 작성 유도 버튼을 보여주고, 진입 경로·작성 단계 이벤트를 계측했다.

# 3. 복잡한 필터 상태는 어떻게 설계했나요?

## 키워드

```text
필터별 매핑 규칙 → 공통 함수가 URL 쿼리 갱신
쿼리 키 변환은 보조 함수
URL 공유 = 같은 조건으로 탐색
```

## 답변

> 복잡한 필터를 필터별 매핑 규칙으로 구조화했습니다. 공통 함수에 필터 종류와 값을 넘기면 규칙대로 URL 쿼리를 갱신하고, 쿼리 키 변환은 보조 함수로 뺐습니다. 조건을 추가·수정할 때 바꿀 곳이 명확해졌습니다.

## 오답 — 매핑 = JavaScript Map

필터별 규칙 구조라는 뜻이지 `Map` 자료구조가 아니다.

## 꼬리

### 왜 URL 쿼리에 두었나요?

키워드: 공유가 많은 부동산, 같은 조건 ≠ 같은 매물

공유받은 사용자도 같은 필터 조건으로 탐색하게 하려고. 같은 조건이지 같은 매물이 영구 보장되는 건 아니다.

# 4. 지도 클러스터가 깜빡이는 문제는 어떻게 해결했나요?

## 키워드

```text
필터 변경·지도 이동 때 깜빡임
클러스터 고유 key로 기존·신규 비교
신규만 추가 / 기존만 제거 / 양쪽 유지
```

## 답변

> 필터를 바꾸거나 지도를 움직이면 클러스터가 깜빡였습니다. 클러스터 고유 key로 기존과 신규 목록을 비교해서 신규에만 있으면 추가, 기존에만 있으면 제거, 양쪽에 있으면 유지해 불필요한 교체를 줄였습니다.

## 꼬리

### key가 같은데 개수가 바뀌면요?

키워드: 데이터 수신 ≠ 지도 객체 속성 반영

유지한 객체에 바뀐 정보를 따로 반영해야 한다. 당시 속성 갱신까지 구현했는지는 ⟨확인 필요⟩ — 확인 전엔 "확인해보지 않았습니다".

# 5. 지도를 움직일 때 요청이 겹치는 문제는요?

## 키워드

```text
AbortController로 이전 요청 취소
마지막으로 "보낸" 요청의 응답 반영
스로틀 ≠ 취소, 같이 쓸 수 있음
```

## 답변

> 응답이 느리면 요청이 겹칠 수 있어서, 새 요청을 보낼 때 AbortController로 이전 요청을 취소했습니다. 그래서 이동이 멈추면 마지막으로 보낸 요청의 응답이 반영됩니다.

## 꼬리

### 스로틀을 쓰면 되지 않나요?

키워드: 빈도 제어 vs 이전 요청 정리

스로틀은 빈도 제어, 취소는 이전 요청 정리라 대체 관계가 아니고 함께 쓸 수 있다.

# 6. 참여한 A/B 실험과 본인 역할은?

## 키워드

```text
PC 리스트 패널 토글 버튼 툴팁 유무
디자이너가 Amplitude 설정, 나는 클래스·툴팁 구조
결과는 공유받지 못함
```

## 답변

> PC 매물 리스트 패널의 열기·닫기 버튼을 알아보기 어려워서 "누르면 닫혀요/열려요" 툴팁 유무를 실험했습니다. 디자이너가 Amplitude에서 실험을 설정했고, 저는 비주얼 편집기에서 다루기 쉽게 버튼 클래스와 툴팁 구조를 정리했습니다.
> 결과는 공유받지 못했고, 이후 툴팁이 빠진 걸로 기억하지만 승패는 단정하지 않습니다.

## 오답 — SDK variant로 분기했다 / 툴팁이 져서 제거됐다

비주얼 편집기 실험이었다. 종료 기록은 control 100%·이유 공란이라 승패를 말할 근거가 없다.

## 꼬리

### 성공 지표는 뭘로 봐야 하나요?

키워드: 토글 사용률 = 직접 효과, 문의 완료율 = 이후 성과

토글 사용률로 직접 효과를, 문의 완료율로 이후 성과·악화를 본다. 집단별 수·비율·기간을 함께 비교한다.

# 7. 이벤트 계측은 어떻게 설계했나요?

## 키워드

```text
지도·리스트 공존 → 페이지 조회로는 부족
```

> PC 홈은 지도와 리스트가 함께 있어서 페이지 조회로는 리스트 진입을 알 수 없었고, 그래서 첫 마우스 패널 진입을 따로 재자고 제안했습니다. 페이지 방문당 한 번만, 플래그로 관리했습니다.

## 오답 — 스크롤·디바운스·mouseleave 초기화로 설명한다

정정된 설명이다. 쓰지 않는다.

## 꼬리

### 어떻게 검증했나요?

키워드: 실시간 수집 내역, 재진입·새로고침 시나리오, 교차 확인

Amplitude 실시간 수집 내역을 보며 반복 진입·새로고침·재진입을 직접 돌렸고 마케터와 교차 확인했다.

# 8. 특정 단지만의 요구사항은 어떻게 처리했나요?

## 키워드

```text
단지 전용 말고 공통 기능
신청·유료 계약에 따라 단지별 개방
모든 요청을 공통화하진 않음
```

## 답변

> 요구사항을 공통 기능으로 만들고, 단지의 신청·계약 조건에 따라 열어서 다른 단지도 재사용할 수 있게 했습니다. 예를 들어 수영장 이용 기능도 한 단지 전용이 아니라 공통으로 만들고 계약에 따라 개방했습니다.

## 오답 — 수영장 기능을 코드 세부까지 설명한다

권한·설정 구조는 ⟨확인 필요⟩. 확인 전엔 구조까지 말하지 않는다.

## 꼬리

### 모든 요청을 다 공통화하나요?

키워드: 공통 문제로 다듬고 검증 후 구현

아니다. 요구를 공통 문제로 다듬고 검증한 뒤 구현한다.

# 9. AI가 팀 코드 규칙을 지키게 하려고 어떻게 했나요?

## 키워드

```text
문서 지침 → 위반 확인 → lint로 강제 → CI
AI가 네이밍·barrel 규칙을 빠뜨림
index.ts 공개 경로를 lint로 강제
```

## 답변

> 코드 구조·네이밍·import 지침을 규칙 파일로 나눠 전역 설정에 뒀습니다. 그런데 AI가 네이밍과 barrel 규칙을 실제로 빠뜨려서, 그 규칙을 lint로 강제하고 CI에서도 돌렸습니다.
> 문서 지침 → 위반 확인 → 기계 검사 → CI 순서입니다.

## 오답 — 규칙 파일을 AI가 항상 읽는다

보장 못 한다. 그래서 lint로 강제했다.

## 꼬리

### 도메인 지식은 어떻게 줬나요?

키워드: 약어-라벨 매핑, 상수·타입, UI에도 사용

별도 문서 대신 부동산 약어를 상수·타입 매핑으로 관리했다(`V2 → 홍보확인서 V2`). 같은 매핑을 UI 표시에도 써서 불일치를 줄였다.

# 10. 디자인 시스템 컴포넌트는 어떤 기준으로 설계했나요?

## 키워드

```text
재사용 · 단일 책임 · 조합
Compound Component + Context
서비스 전용은 감싸서 확장
```

## 답변

> 재사용·단일 책임·조합 가능을 기준으로 Compound Component 패턴을 썼습니다. Input의 prefix나 clear 버튼을 props로 늘리지 않고 하위 요소로 합성하게 해서 쓰는 쪽에서 구성이 보이게 했고, 내부 상태는 Context로 공유했습니다.

## 오답 — 합성 패턴이 항상 낫다

장점만으로 항상 맞다고 단정하지 않는다.

## 꼬리

### 서비스마다 요구가 다르면요?

키워드: 감싼 전용 컴포넌트, 반복되면 공통화

공통 props에 다 넣지 않고 감싼 전용 컴포넌트에서 조합한다. 여러 서비스에서 반복되면 공통화를 검토한다.

# 12. 점검: 면접에서 말하지 않을 것은?

## 키워드

```text
문의 전환율 23% · 후기 20건 · 100자→30자 — 근거 없음
회사 AI 사주 추천 — 회사 경험 아님
가정형 실험·회사 실험 존재 ≠ 내 성과
```

확인된 것만 말한다. 계측·실험에서 확인된 내 경험은 **툴팁 UI 준비와 이벤트 계측**뿐이다.

근거 없는 기재다. 툴팁·계측 경험을 이 수치의 근거로 연결하지 않는다.
