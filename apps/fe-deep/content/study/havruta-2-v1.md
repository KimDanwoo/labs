# 3. 거주후기 출시 후에는 무엇을 개선하고 어떻게 측정했나요?

## 키워드

```text
진입점: 홈 → 매물 등록 완료·매물 상세·지도
후기 있음 = 실제 후기 / 없음 = 예시 후기 + 작성 유도
진입 경로·작성 단계 이벤트
```

## 답변

> 출시 후에는 홈에 있던 진입점을 매물 등록 완료·매물 상세·지도로 확장했습니다. 후기가 있으면 실제 후기를, 없으면 예시 후기와 작성 유도 버튼을 노출했습니다.
> 등록과 탐색, 진입 경로·작성 단계 이벤트를 계측했습니다.

## 오답 — 예시 후기는 내 아이디어였다

키워드: PM 기획 주도, 방향 논의·구현·계측 참여

PM이 기획을 주도했고 본인은 작업 방향 논의와 구현·계측에 참여했다. 예시 후기 제안을 본인의 아이디어라고 하지 않는다.

도입 목적은 의도다. 재방문 성과를 검증한 수치가 아니다.

# 10. 문의 전환을 개선한다면 어떤 실험을 설계하겠어요? (가정형)

이번에 함께 만든 가정형 실험이다. 실제 수행 사례가 아니다.

## 키워드

```text
'문의하기'는 다음 동작이 불명확
전화·문자·채팅으로 문의하기 명시
문구 외 위치·색상·크기·연결 동작 유지
주요 지표 = API 성공 사용자 / 노출 사용자
클릭 증가만으로 성공 판단 금지
```

## 답변

> 일반적인 "문의하기" 문구는 다음 동작이 불명확해 망설임이 있을 수 있다는 가설입니다. "전화로 문의하기 / 문자로 문의하기 / 채팅으로 문의하기"로 알려주면 부담과 불확실성을 줄일 수 있습니다.
> A는 일반 문구, B는 연결 방식 명시로 두고 위치·색상·크기·연결 동작은 유지합니다. 사용자 단위로 무작위 배정해 동일 그룹을 유지하고, 문의 방식별로 비교합니다.
> 주요 지표는 실제 문의 접수를 확인하는 API 성공 이벤트 사용자를 대상 화면 노출 사용자로 나눈 값입니다. 버튼 클릭률과 클릭 후 API 성공률은 보조 지표입니다.

## 오답 — 이 실험으로 23% 성과를 설명한다

가정형 제안이다. 실제 23% 성과로 연결하지 않고, 과거 경험이나 그 수치의 근거로 쓰지 않는다.

## 꼬리

### 문의 완료는 어떻게 정의하나요?

키워드: API 성공 응답 후 이벤트, 클릭·요청 전송 ≠ 완료, 열람·응답과 구분

문의 이벤트는 API 성공 응답 후에 보낸다고 확인했다. API 요청 전송·버튼 클릭만으로 문의 완료라 부르지 않는다. 전화·문자에서 API 성공이 실제 통화·문자 발송을 의미하는지는 ⟨확인 필요⟩. 상대방 열람·응답과도 구분한다.

### 전화 클릭이 줄면 실패인가요?

키워드: 예기치 않은 연결 감소, 해석 필요

버튼 클릭 증가만으로 성공을 판단하지 않듯, 전화 클릭 감소도 예기치 않은 연결의 감소일 수 있어 해석이 필요하다.

### 표본과 기간은 어떻게 정하나요?

키워드: 기초 전환율 확인, 사전 결정

표본·기간·최소 개선 폭은 기초 전환율을 확인한 뒤 사전에 결정한다.

# 11. 코드 기반 A/B 실험은 어떻게 구현하나요? (학습)

이번에 학습한 내용이다. 아래 코드는 실제 사용자 구현 코드가 아니다.

## 키워드

```text
비주얼 편집 = CSS·문구 / 코드 기반 = 컴포넌트·폼·동작
초기화 → 식별 → fetch → variant → 분기 → 노출·결과 수집
flag key ≠ variant value
배정은 식별자·설정 기준
```

## 답변

> 비주얼 편집은 디자이너가 대상 DOM의 CSS·문구 등을 설정하는 방식이고, 실제 툴팁 사례가 여기에 해당합니다. 복잡한 컴포넌트·폼 단계·동작 변경에는 코드 기반 실험이 적합합니다.
> Amplitude에 대상·배정 비율·variant를 정의하면 user_id/device_id와 설정을 기준으로 사용자를 배정합니다. Amplitude가 좋은 화면을 미리 판단하는 것이 아닙니다.
> 흐름은 SDK 초기화 → 사용자 식별 → 실험값 fetch → flag key로 variant 조회 → variant.value로 UI 분기 → 실제 노출과 결과 이벤트 수집입니다.

```ts
await experiment.fetch();
const variant = experiment.variant('review-flow-test');
// variant.value가 설정한 treatment이면 변경 폼, control이면 기존 폼
```

flag key와 variant value는 서로 다르다. 키·값은 Amplitude 설정에 맞춘다.

## 꼬리

### 같은 사용자는 계속 같은 그룹인가요?

키워드: 동일 식별자·설정, 로그인 전후 식별자 변경, 설정 변경

동일 식별자·설정에서는 같은 그룹을 유지한다. 로그인 전후 식별자 변경과 설정 변경은 따로 고려한다.

### 노출은 언제 기록하나요?

키워드: 조회 시점 ≠ 실제 노출, 자동 노출 기록, 수동 exposure

variant 조회 시점과 실제 노출이 다를 수 있다. SDK 설정에 따라 자동 노출 기록이 있으므로 실제 노출 시점과 정합성을 맞춘다. 자동 기록을 끄고 수동 exposure를 쓰는 선택도 있다.

# 12. 실험 화면이 A에서 B로 깜빡이지 않게 하려면? (학습)

## 키워드

```text
A를 먼저 보여주고 B로 바꾸지 않는다
진입 초기에 실험값 조회
크기를 확보한 로딩·스켈레톤
값 확정 후 최초 렌더링
```

## 답변

> A를 먼저 보여주고 나중에 B로 바꾸지 않습니다. 진입 초기에 실험값을 조회하고, 대기 중에는 대상 영역의 크기를 확보한 로딩·스켈레톤을 씁니다. 값이 확정된 뒤 해당 화면을 최초 렌더링합니다.
> 전체 페이지를 기다리게 할 필요는 없고, 실험 대상 영역만 기다립니다.

## 꼬리

### 실험값 조회가 실패하거나 늦으면요?

키워드: 실패·시간 초과 = 기본안, 늦은 응답으로 교체 금지

실패·시간 초과 시 기본안을 선택한다. 이미 표시한 화면은 늦은 응답으로 교체하지 않는다.

### 작은 툴팁 하나도 기다려야 하나요?

키워드: 값 확정 후 노출 여부만 적용

작은 툴팁은 값 확정 후 노출 여부를 적용해도 된다.

실제 사례가 없는 가정형 질문이다.

## 키워드

```text
목적·항목·기한 확인
기존 DB 조합으로 추출 가능한지 담당자와 협의
화면 일부 데이터로 추론 금지
```
