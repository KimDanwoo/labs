### **React 앱의 상태 관리 방법**

React의 상태 관리는 **상태의 범위와 성격에 따라 도구를 선택하는 것**이 중요합니다.

크게 보면 상태는 **로컬 상태**, **전역 클라이언트 상태**, **서버 상태**로 나눌 수 있습니다.

---

### **useState**

`useState`는 가장 기본적인 상태 관리 방법으로, **하나의 컴포넌트 안에서 사용하는 단순한 로컬 상태**를 관리할 때 사용합니다.

주로 다음과 같은 경우에 적합합니다.

- 모달 열림 여부
- 입력값
- 체크박스 상태
- 간단한 카운트
- 특정 컴포넌트에서만 사용하는 UI 상태

즉, **상태를 사용하는 범위가 좁고 로직이 단순하다면 useState가 가장 적합**합니다.

---

### **useReducer**

`useReducer`는 여러 상태가 서로 연관되어 있거나, 상태 변경 규칙이 복잡한 경우 사용합니다.

`useState`가 단순히 값을 변경하는 방식이라면, `useReducer`는 **action을 전달하고 reducer가 상태 변경 로직을 처리하는 구조**입니다.

주로 다음과 같은 경우에 적합합니다.

- 하나의 상태에 여러 변경 방식이 존재하는 경우
- 여러 상태가 서로 연결되어 있는 경우
- 상태 변경 로직을 한곳에 모으고 싶은 경우

즉, **로컬 상태이지만 상태 변경 로직이 복잡할 때 useReducer를 고려할 수 있습니다.**

---

### **Context API**

`Context API`는 여러 컴포넌트에서 공통으로 필요한 값을 **props로 계속 전달하는 Prop Drilling 문제를 줄이기 위해** 사용합니다.

대표적으로 다음과 같은 값에 적합합니다.

- 테마
- 로그인 사용자 정보
- 언어 설정
- 전역 설정값

다만 Context의 값이 변경되면 해당 Context를 사용하는 컴포넌트들이 다시 렌더링될 수 있기 때문에, **변경이 매우 잦은 복잡한 전역 상태를 모두 Context로 관리하는 것은 주의해야 합니다.**

따라서 Context는 보통 **자주 변경되지 않는 전역 데이터**에 적합합니다.

---

### **Zustand**

`Zustand`는 **전역 클라이언트 상태를 간단하게 관리하기 위한 상태 관리 라이브러리**입니다.

Redux에 비해 보일러플레이트가 적고 구조가 단순해서 비교적 쉽게 사용할 수 있습니다.

주로 다음과 같은 상태에 적합합니다.

- 여러 페이지에서 공유하는 상태
- 로그인 상태
- 장바구니
- 필터 조건
- 공통 UI 상태
- 여러 컴포넌트에서 공유해야 하는 클라이언트 데이터

특히 상태와 상태 변경 함수를 하나의 Store에서 관리할 수 있어서 **중소 규모 프로젝트에서 전역 상태 관리가 필요할 때 많이 사용**합니다.

---

### **Jotai**

`Jotai`는 **Atom이라는 작은 상태 단위를 조합해서 관리하는 상태 관리 라이브러리**입니다.

하나의 큰 Store를 중심으로 관리하는 방식보다는, 필요한 상태를 작은 Atom 단위로 나누고 컴포넌트가 필요한 Atom만 구독하는 방식입니다.

주로 다음과 같은 경우에 적합합니다.

- 상태를 작게 나누어 관리하고 싶은 경우
- 컴포넌트별로 필요한 상태만 구독하고 싶은 경우
- 복잡한 전역 Store보다 유연한 상태 조합이 필요한 경우

즉, Zustand가 **Store 중심의 상태 관리**라면 Jotai는 **Atom 중심의 상태 관리**라고 이해하면 좋습니다.

---

### **TanStack Query**

`TanStack Query`는 일반적인 전역 상태 라이브러리와 목적이 조금 다릅니다.

주로 API를 통해 가져오는 **서버 상태를 관리**하는 데 사용합니다.

서버 상태는 클라이언트가 직접 생성한 값이 아니라 **서버에 원본이 존재하는 데이터**이기 때문에 캐싱, 재요청, 동기화 같은 기능이 중요합니다.

TanStack Query는 다음과 같은 기능을 제공합니다.

- API 데이터 캐싱
- 로딩 상태 관리
- 에러 상태 관리
- 데이터 재요청
- stale 상태 관리
- 서버 데이터 동기화

따라서 API 응답 데이터를 Zustand나 Context에 직접 넣어서 관리하기보다는 **TanStack Query 같은 서버 상태 관리 도구를 사용하는 것이 일반적**입니다.

---

### **핵심 구분**

| 상태 관리 방법 | 주 용도 | 특징 |
|---|---|---|
| `useState` | 단순한 로컬 상태 | 가장 기본적인 상태 관리 |
| `useReducer` | 복잡한 로컬 상태 | 상태 변경 로직을 reducer로 관리 |
| `Context API` | 전역 설정 및 공유 값 | Prop Drilling 해결 |
| `Zustand` | 전역 클라이언트 상태 | Store 기반, 간단한 구조 |
| `Jotai` | 전역 클라이언트 상태 | Atom 기반, 작은 상태 단위 조합 |
| `TanStack Query` | 서버 상태 | 캐싱 및 서버 데이터 동기화 |

---

### **클라이언트 상태와 서버 상태 구분**

현대 React에서는 **클라이언트 상태와 서버 상태를 구분해서 관리하는 것이 중요**합니다.

클라이언트 상태는 프론트엔드에서 직접 관리하는 상태입니다.

예를 들어:

- 모달 상태
- 선택된 탭
- 필터 조건
- 로그인 UI 상태
- 사용자 입력값

이런 상태는 `useState`, `Context`, `Zustand`, `Jotai` 등을 사용할 수 있습니다.

반면 서버 상태는 **API를 통해 서버에서 가져온 데이터**입니다.

예를 들어:

- 사용자 목록
- 게시글 목록
- 상품 정보
- 주문 내역

이러한 데이터는 보통 `TanStack Query`를 사용해서 관리합니다.

---

### **요약**

React에서는 **상태의 범위와 성격에 따라 상태 관리 방법을 선택합니다.**

컴포넌트 내부의 단순한 상태는 `useState`를 사용하고, 상태 변경 로직이 복잡하다면 `useReducer`를 사용할 수 있습니다.

여러 컴포넌트에서 공유해야 하는 테마나 인증 정보처럼 비교적 단순한 전역 값은 `Context API`를 사용할 수 있고, 전역 클라이언트 상태가 복잡해지면 `Zustand`나 `Jotai` 같은 외부 상태 관리 라이브러리를 사용할 수 있습니다.

`Zustand`는 **Store 기반으로 전역 상태를 간단하게 관리하는 방식**이고, `Jotai`는 **Atom 단위로 상태를 나누어 필요한 상태만 조합하고 구독하는 방식**이라는 차이가 있습니다.

그리고 API에서 가져오는 데이터는 일반적인 클라이언트 상태와 성격이 다르기 때문에 `TanStack Query`를 사용해 **캐싱, 재요청, 로딩 및 에러 상태, 서버와의 동기화**를 관리하는 것이 일반적입니다.

결국 중요한 것은 하나의 상태 관리 도구로 모든 상태를 관리하는 것이 아니라, **로컬 상태, 전역 클라이언트 상태, 서버 상태를 구분하고 각각에 적절한 도구를 사용하는 것**입니다.
