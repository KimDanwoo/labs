### **React 컴포넌트는 언제 리렌더링되나요?**

React 컴포넌트는 대표적으로 다음과 같은 경우에 리렌더링됩니다.

1. **state가 변경될 때**
2. **props가 변경될 때**
3. **부모 컴포넌트가 리렌더링될 때**
4. **구독하고 있는 Context 값이 변경될 때**

여기서 중요한 점은 **부모 컴포넌트가 리렌더링되면 자식 컴포넌트도 기본적으로 다시 렌더링된다는 것**입니다.

자식의 props 값이 실제로 변경되지 않았더라도, 부모가 다시 렌더링되면 자식 컴포넌트 함수도 다시 실행될 수 있습니다.

---

### **state가 변경될 때**

컴포넌트의 state가 변경되면 React는 해당 컴포넌트의 **새로운 UI 결과를 계산하기 위해 리렌더링**을 수행합니다.

다만 state setter를 호출했다고 해서 항상 리렌더링되는 것은 아니고, **이전 상태와 새로운 상태가 동일하다고 판단되면 업데이트가 생략될 수 있습니다.**

---

### **props가 변경될 때**

부모로부터 전달받는 props가 변경되면 자식 컴포넌트도 새로운 props를 기준으로 다시 렌더링됩니다.

특히 객체, 배열, 함수는 값의 내용이 같아 보여도 **새로운 참조가 생성되면 다른 값으로 판단될 수 있다는 점**을 주의해야 합니다.

이런 경우 필요하다면 `useMemo`, `useCallback`, `React.memo` 등을 이용해 참조를 안정적으로 유지할 수 있습니다.

---

### **부모 컴포넌트가 리렌더링될 때**

React에서는 부모 컴포넌트가 리렌더링되면 **자식 컴포넌트도 기본적으로 함께 리렌더링**됩니다.

그래서 특정 state가 부모에 너무 높은 위치에 존재하면, 그 state와 직접 관련 없는 자식 컴포넌트까지 리렌더링될 수 있습니다.

이런 경우 상태를 실제 사용하는 컴포넌트 가까이에 두는 **State Colocation**을 통해 리렌더링 범위를 줄일 수 있습니다.

즉, 상태를 무조건 최상위로 끌어올리는 것이 아니라 **필요한 범위까지만 상태를 공유하는 것이 중요**합니다.

---

### **Context 값이 변경될 때**

컴포넌트가 특정 Context를 구독하고 있다면 해당 **Context의 value가 변경될 때 리렌더링**됩니다.

Context를 너무 큰 범위로 사용하거나 하나의 Context에 많은 상태를 넣으면 작은 상태 하나가 변경되어도 여러 컴포넌트가 다시 렌더링될 수 있습니다.

따라서 필요한 경우 Context를 역할별로 분리하거나 외부 상태 관리 라이브러리를 고려할 수 있습니다.

---

### **불필요한 리렌더링을 줄이는 방법**

#### **React.memo**

`React.memo`는 부모 컴포넌트가 리렌더링되더라도 **자식에게 전달되는 props가 변경되지 않았다면 자식의 리렌더링을 생략**할 수 있도록 해줍니다.

특히 렌더링 비용이 큰 컴포넌트에서 효과적일 수 있습니다.

다만 props로 객체나 함수가 전달되고 매번 새로운 참조가 만들어진다면 `React.memo`만으로는 효과가 없을 수 있습니다.

---

#### **useMemo / useCallback**

`useMemo`는 **값의 참조를 유지**하고, `useCallback`은 **함수의 참조를 유지**하는 데 사용할 수 있습니다.

주로 `React.memo`가 적용된 자식 컴포넌트에 객체나 함수를 props로 전달할 때 불필요한 props 변경을 줄이기 위해 사용합니다.

---

#### **State Colocation**

상태는 **실제로 사용하는 컴포넌트와 최대한 가까운 곳에 두는 것**이 좋습니다.

상태를 너무 상위 컴포넌트에 두면 그 상태가 변경될 때 필요하지 않은 영역까지 리렌더링될 수 있습니다.

따라서 공유할 필요가 없는 상태라면 굳이 부모로 끌어올리지 않고 해당 영역 내부에서 관리하는 것이 좋습니다.

---

#### **children 패턴**

컴포넌트의 내부 상태가 변경되더라도, 외부에서 이미 생성되어 전달된 `children`을 활용하면 **불필요하게 하위 컴포넌트를 다시 생성하는 구조를 피할 수 있습니다.**

다만 `children`을 사용한다고 해서 항상 자식의 리렌더링이 무조건 방지되는 것은 아닙니다.

핵심은 **컴포넌트 트리 구조와 state의 위치를 적절하게 설계해서 리렌더링 범위를 줄이는 것**입니다.

---

#### **key를 안정적으로 사용**

리스트에서는 각 요소를 구분하기 위해 `key`를 사용합니다.

가능하면 배열의 `index`보다는 **데이터를 고유하게 식별할 수 있는 안정적인 id를 key로 사용**하는 것이 좋습니다.

`key`가 불안정하면 React가 기존 요소를 재사용하지 못하고 새롭게 생성하거나 상태를 잘못 연결할 수 있습니다.

다만 `key`는 일반적인 리렌더링 자체를 막는 최적화 수단이라기보다는 **리스트 reconciliation에서 요소의 identity를 정확하게 판단하기 위한 값**이라고 이해하는 것이 더 정확합니다.

---

### **성능 최적화 시 주의점**

리렌더링 자체가 반드시 성능 문제를 의미하는 것은 아닙니다.

React에서 리렌더링은 **컴포넌트 함수를 다시 실행해 새로운 UI 결과를 계산하는 과정**이고, 실제 DOM이 무조건 변경되는 것은 아닙니다.

React는 이전 결과와 새로운 결과를 비교한 뒤 **실제로 변경이 필요한 부분만 DOM에 반영**합니다.

따라서 무조건 `React.memo`, `useMemo`, `useCallback`을 적용하기보다는 **React DevTools Profiler 등을 통해 실제 병목을 확인한 뒤 최적화하는 것이 중요**합니다.

---

### **핵심**

React 컴포넌트는 대표적으로 **state가 변경되거나, props가 변경되거나, 부모 컴포넌트가 리렌더링되거나, 구독하고 있는 Context 값이 변경될 때 리렌더링**됩니다.

특히 부모가 리렌더링되면 자식도 기본적으로 다시 렌더링되기 때문에, 불필요한 리렌더링을 줄이기 위해 `React.memo`를 사용하거나 `useMemo`, `useCallback`을 통해 props의 참조를 안정적으로 유지할 수 있습니다.

또한 상태를 너무 상위에 두지 않고 **실제로 사용하는 컴포넌트 가까이에 배치하는 State Colocation**도 중요합니다.

리스트에서는 안정적인 `key`를 사용해 React가 각 요소의 identity를 정확하게 판단할 수 있도록 해야 합니다.

다만 **리렌더링 자체가 항상 성능 문제는 아니기 때문에**, 무조건 최적화를 적용하기보다는 React DevTools Profiler 등을 이용해 실제 병목을 측정한 뒤 필요한 부분만 최적화하는 것이 좋습니다.
