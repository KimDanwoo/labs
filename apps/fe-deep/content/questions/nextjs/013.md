Next.js는 React 기반 **풀스택 프레임워크**입니다. React는 UI 라이브러리일 뿐이라 라우팅·번들링·SSR·데이터 패칭을 직접 조립해야 하는데, Next.js는 이것들을 **의견을 가진 기본값**으로 통합 제공합니다.

### **핵심 장점**

**1. 렌더링 전략을 페이지·컴포넌트 단위로 선택**

정적 콘텐츠는 SSG, 주기적으로 갱신되는 목록은 ISR, 개인화 화면은 SSR, 인증 뒤 상호작용 화면은 CSR — **한 앱 안에서 섞어 쓸 수 있다는 것**이 핵심입니다.

**2. React Server Components**

서버에서만 실행되는 컴포넌트로 DB에 직접 접근하고, 그 코드는 **클라이언트 번들에 포함되지 않습니다.** 무거운 파서나 유틸 라이브러리를 서버에 두면 번들이 그만큼 줄어듭니다.

**3. 파일 기반 라우팅** — 폴더 구조가 곧 URL이고, layout.tsx로 중첩 레이아웃이 상태를 유지한 채 공유됩니다.

**4. 내장 최적화** — Image(포맷 변환·반응형·lazy·CLS 방지), next/font(셀프 호스팅·레이아웃 시프트 제거), 자동 코드 스플리팅.

**5. 백엔드 통합** — Route Handlers와 Server Actions로 별도 서버 없이 API·폼 처리가 가능하고, API 키를 서버에만 두는 구조가 자연스럽습니다.

**6. SEO** — 서버 렌더링된 HTML에 Metadata API로 메타 태그·사이트맵·오픈그래프를 타입 안전하게 담아 보냅니다.

### **트레이드오프**

- SSR·ISR은 정적 호스팅보다 **서버 비용**이 듭니다.
- App Router의 **캐싱 계층이 복잡**하고, 서버/클라이언트 경계 개념의 학습 곡선이 있습니다.
- Pages → App Router 전환, 캐싱 기본값 변경처럼 **버전 간 변화가 큽니다.**
- 일부 최적화는 Vercel에서 가장 매끄러워 **종속 우려**가 있습니다.

### **언제 쓰고 언제 안 쓰나**

SEO가 중요한 서비스, 콘텐츠 중심, 초기 로딩이 성과와 직결되는 서비스에 적합합니다. 반대로 **전부 인증 뒤에 있는 사내 어드민·대시보드**는 SEO가 무의미하므로 Vite + React가 더 가볍고, 순수 정적 문서는 Astro 같은 선택지가 있습니다. "React 쓰니까 무조건 Next"가 아니라 **서비스 성격으로 판단**하는 것이 좋습니다.
