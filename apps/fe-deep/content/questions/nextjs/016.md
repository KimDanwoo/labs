### **먼저 출력 모드부터 정합니다**

- **Node 서버(기본)** — SSR·ISR·Route Handlers·Middleware 등 모든 기능을 지원합니다. Vercel이나 자체 Node 서버에 올립니다.
- **Standalone** — 같은 기능을 지원하면서 의존성을 최소로 묶은 번들을 만듭니다. **Docker로 배포할 때** 씁니다.
- **Static Export** — 순수 정적 파일만 내보냅니다. SSR·ISR·Middleware·이미지 최적화를 **못 쓰므로**, 나중에 SSR이 필요해지는 흔한 실수를 피하려면 기능 요구사항을 먼저 확정해야 합니다.

### **배포 체크리스트**

- **환경변수(보안 직결)** — `NEXT_PUBLIC_` 접두사가 붙은 값은 **빌드 시 클라이언트 번들에 인라인되어 브라우저에 노출**됩니다. 공개 전제인 값만 붙이고, 시크릿에는 절대 붙이면 안 됩니다. 또 빌드 타임에 고정되므로 환경별로 재빌드가 필요합니다.
- **캐싱 전략** — App Router의 여러 캐시 계층이 각각 언제 무효화되는지 정하고, revalidatePath·revalidateTag로 갱신 경로를 마련합니다. 배포 후 "데이터가 안 바뀐다" 문제의 대부분이 여기서 나옵니다.
- **이미지 최적화** — next/image는 서버 런타임이 필요합니다. 정적 export라면 최적화를 끄거나 외부 이미지 CDN을 붙여야 합니다.
- **런타임 선택** — Edge는 콜드 스타트가 거의 없지만 Node API와 대부분의 DB 드라이버를 못 씁니다. Middleware에 무거운 로직을 넣지 않습니다.
- **보안 헤더** — CSP, HSTS, X-Content-Type-Options 등을 next.config의 headers로 설정합니다.
- **관측 가능성** — 에러 추적(Sentry), Core Web Vitals 실사용자 측정. 배포 후 문제를 모르는 것이 가장 큰 리스크입니다.
- **빌드 재현성** — Node 버전 고정, 락파일 커밋, CI에서 lint·타입체크·빌드를 게이트로 둡니다.

### **플랫폼 선택**

- **Vercel** — Next.js 제작사라 ISR·이미지·프리뷰 배포가 무설정으로 동작합니다. 대신 트래픽에 따라 과금이 커질 수 있고 종속 우려가 있습니다.
- **Docker + Cloud Run/ECS** — 이식성과 비용 예측이 장점이고, standalone 모드가 이 시나리오를 위해 존재합니다. ISR·이미지 최적화는 직접 챙겨야 합니다.
- **Cloudflare·Netlify** — 저렴하거나 간편하지만 어댑터와 기능 지원 시차를 확인해야 합니다.
- **정적 호스팅(S3 등)** — SSG 전용이면 가장 저렴합니다.

### **실무 판단**

팀이 작고 빠르게 가야 하면 Vercel — 설정에 쓸 시간을 제품에 쓰는 쪽이 대체로 이깁니다. 비용 예측이나 사내 인프라 정책이 중요하면 Docker(standalone)입니다.
