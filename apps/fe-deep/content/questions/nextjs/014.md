Next.js 13에서 도입된 App Router(`app/`)는 **React Server Components 기반의 새 라우팅 모델**이고, Pages Router(`pages/`)는 기존 방식입니다. 한 프로젝트에 **공존이 가능**해서 라우트 단위로 점진 이전할 수 있습니다.

### **주요 차이**

- **기본 컴포넌트** — Pages는 전부 클라이언트 컴포넌트, App은 **기본이 서버 컴포넌트**입니다.
- **레이아웃** — Pages는 전역 `_app` 하나였지만, App은 **layout.tsx를 중첩**할 수 있고 페이지 이동 시 리렌더 없이 유지됩니다.
- **데이터 패칭** — Pages는 `getServerSideProps`·`getStaticProps`를 페이지 최상단에서만 쓰고 props로 내려보냈지만, App은 **필요한 컴포넌트가 직접 async/await로** 가져옵니다. prop drilling이 사라지고, 같은 요청 안의 중복 fetch는 자동 메모이제이션됩니다.
- **로딩·에러** — Pages는 직접 구현했지만 App은 loading.tsx(Suspense)·error.tsx(Error Boundary)가 **세그먼트별로 자동** 적용됩니다.
- **파일 규칙** — Pages는 폴더 안 모든 파일이 라우트가 되어 컴포넌트를 같이 못 뒀지만, App은 **특수 파일명만 라우트**라서 콜로케이션이 가능합니다.
- **스트리밍** — App Router만 지원합니다.

### **App Router의 이점**

중첩 레이아웃 유지, 느린 부분만 나중에 채우는 스트리밍, 서버 컴포넌트로 인한 번들 감소, 세그먼트별 에러 격리, Server Actions.

### **마이그레이션 난점**

- **`'use client'` 경계 이해가 필수**입니다. 상태·이벤트·브라우저 API는 클라이언트 컴포넌트에서만 동작하고, 클라이언트 전용 라이브러리는 래퍼가 필요합니다.
- **캐싱이 어렵습니다.** 계층이 여러 개이고 Next 15에서 기본값이 "캐시 안 함"으로 바뀌는 등 버전별 변화가 잦았습니다.
- 기존 데이터 패칭 함수들은 App Router에서 동작하지 않습니다.

### **선택 기준**

신규 프로젝트는 App Router입니다 — 신규 기능이 전부 여기에 들어갑니다. 기존 Pages Router 대규모 앱은 계속 지원되므로 급하게 옮길 필요 없이 점진 이전하면 됩니다.
