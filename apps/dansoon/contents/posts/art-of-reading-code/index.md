### 들어가며

나는 코드 작성보다 **코드를 읽는 일**에 훨씬 더 많은 시간을 쓰는 개발자다.

새로운 기능을 붙이기 전에 전체 구조를 파악하고, 레거시 코드의 의도를 이해하며, 코드 리뷰에서는 설계의 맥락을 읽어내야 한다. 대부분의 시간은 이런 일에 쓰인다.

그리고 매번 드는 생각은 이렇다. “왜 읽는 게 이렇게 어려울까?” 무엇이 독해를 어렵게 만들까?

어떻게 하면 더 빠르고 정확하게 읽을 수 있을까?

이런 고민이 쌓이던 중에 한 권의 책을 만났다. 『프로그램을 읽는 기술』은 단순히 코드 독해 요령을 나열하는 책이 아니다. **코드 읽기를 하나의 기술(skill)**로 정의하고, 이를 체계적으로 설명한다. 특히 실무에서 기존 코드를 처음 마주할 때 겪는 문제를 구조적으로 풀어낸다.

### 코드 읽기가 어려운 이유

책은 **다른 사람의 코드를 읽기 어려운 이유**를 먼저 진단한다. 처음에는 단순히 난해한 코드 때문이라 생각했지만, 실제로는 다음과 같은 본질적인 요인이 있다.

-   사고 방식의 차이
-   사용하는 언어나 스타일의 차이
-   함수나 변수명이 의도를 충분히 전달하지 못함
-   프로그램의 **입력과 출력**에 대한 사고가 불분명함

여기서 중요한 통찰이 있다. 실무에서 접하는 대부분의 코드는 ‘내가 쓰지 않았기 때문에’ 낯설고 어렵다. 이 책은 단지 “코드가 복잡하다”는 평가로 끝내지 않고, **무엇이 읽히지 않게 만드는지를 체계적으로 분류**해 준다. 이 접근법은 독해를 감각이 아닌 **논리적 사고의 대상**으로 바꿔 놓는다.

또한 **가독성(readability)**이나 **유지보수성(maintainability)** 같은 모호한 개념을, **읽는 관점에서 재정의**한다.

좋은 코드란 결국 다른 개발자도 빠르게 이해할 수 있는 코드이기 때문이다.

### 전체에서 세부로: 읽기의 새로운 패러다임

가장 실용적이었던 부분은 **읽는 순서**에 대한 조언이다. 많은 개발자는 함수 한 줄, 조건문 하나씩 파고드는 식으로 세부부터 읽기 시작한다. 반면 이 책은 **입력 → 처리 → 출력**이라는 흐름을 먼저 파악하라고 조언한다.

이 패러다임 전환은 간단하지만 효과적이다.

1.  문서와 설계서를 먼저 본다.
2.  프로그램의 메인 흐름을 훑는다.
3.  핵심 데이터 구조를 파악한다.
4.  마지막에 세부 조건과 반복문, 함수 내부로 들어간다.

이처럼 **목적 중심의 틀을 먼저 세운 뒤 세부로 들어가는 방식**은 시니어 개발자에게는 자연스럽지만, 경험이 부족한 팀원에게는 낯설다. 그러나 이 구조는 **체계적으로 훈련되지 않으면 결코 몸에 배지 않는다.**

### 코드 읽기에 생긴 변화: 나만의 루틴

이 책을 읽고 난 후, 내 코드 독해 방식은 훨씬 더 **의식적이고 계량적**으로 변했다.

### 1) 목적 중심 읽기

처음 코드를 접할 때 던지는 질문은 다음과 같다.

“이 코드의 입력은 무엇인가?”, “출력은 무엇인가?”, “어떤 흐름으로 처리되는가?”

나는 줄 단위가 아니라 **의도와 아이디어 중심으로** 코드를 본다. 이 방식은 리팩토링 과정에서 영향을 추적할 때 특히 유용했다.

### 2) 인터페이스에서 시작하기

API, 함수 시그니처, 도메인 엔티티를 먼저 확인하고, 그것이 전체 흐름에 어떤 영향을 주는지 본다.

이 책이 제안하는 ‘입력 → 처리 → 출력’ 방식은 **인터페이스 중심 사고**와 직결된다.

### 3) 세부는 나중에 보기

조건문, 반복문, 변수명 등에 주의를 기울이기 전에, 그것이 전체 구조에서 어떤 역할을 하는지를 먼저 파악한다. 이런 접근은 **레거시 코드**나 **테스트가 없는 코드**를 분석할 때 특히 효과적이다.

### 책의 한계: 실전에서의 적용

책은 체계적인 독해 전략을 제시하지만, 몇 가지 현실적인 제약도 있다.

-   예제 대부분이 파이썬 기반이며, 언어 특성 덕분에 다소 단순화돼 있다. 현실의 엔터프라이즈 시스템은 멀티 레이어, 비동기, 도메인 설계가 복잡하다. 이런 환경에서는 **전체 설계 맥락**까지 함께 읽어야 이해가 가능하다.
-   책은 주로 내부 코드 중심으로 독해를 설명하지만, 실제 실무에서는 **도메인 지식과 외부 문서**가 더 중요할 때가 많다.
-   코드 독해란 결국 도메인 이해 → 아키텍처 파악 → 코드로 연결되는 과정이다. 이 점에 대한 확장이 아쉽다.

### 결론: 프로그램 읽기는 **판단의 기술**이다

『프로그램을 읽는 기술』은 단순한 코드 읽기 요령서가 아니다.

코드 독해를 **판단 능력**과 **구조적 사고 과정**으로 정의하고, 그 훈련법을 체계적으로 제시한다.

내가 얻은 가장 큰 인사이트는 다음과 같다.

> 전체 목적과 흐름을 먼저 파악하는 능력이 개발자의 생산성으로 직결된다.
> 
> 세부부터 파고들면 속도는 낼 수 있지만, **정확성과 구조적 이해** 없이 오류에 빠지기 쉽다.

AI가 코드를 생성하는 시대에는, 오히려 **코드를 읽고 평가하며 판단하는 능력**이 더 중요해진다.

이 책은 그 능력을 체계적으로 훈련할 수 있는 드문 실전서다.
