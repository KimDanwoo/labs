## 함수 이름과 주석도 읽는 사람을 위한 문장이다

변수와 함수의 이름, 주석, 리뷰 설명은 모두 다른 사람이 코드를 이해할 때 읽는 글입니다. 《개발자의 글쓰기》를 읽으며 이런 문장을 어떻게 다듬을지 살펴봤습니다.

문장과 단락의 구조, 띄어쓰기와 문장 부호, 네이밍과 주석 가운데 개발할 때 참고할 내용을 정리합니다.

## 1\. 문장과 단락을 구조화하는 법

### 간단한 문장의 힘

글쓰기를 어렵게 만드는 가장 큰 이유는 불필요하게 긴 문장입니다.

핵심만 담은 간단한 문장을 먼저 쓰고, 필요하면 부가 설명으로 확장하는 것이 기본 원칙입니다.

첫 문장의 주어를 소제목으로 끌어내면 문단 구조가 자연스럽게 만들어집니다.

### 서술식 · 개조식 · 도식의 차이

개발자가 글을 쓰는 방식에는 세 가지가 있습니다.

-   **서술식**: ~다로 끝나는 완전한 문장. 설명·논증에 적합. (가이드 문서, 매뉴얼 등)
-   **개조식**: 항목을 나열하는 방식. 중복·누락에 주의. (회의록, TODO 등)
-   **도식**: 관계를 시각적으로 보여주는 표·도표. (기능 비교, 프로세스 설계 등)

규칙은 단순합니다.

-   줄거리가 있는 설명 → 서술식
-   반복되는 항목 정리 → 개조식
-   관계를 비교/정리 → 도식

### 개조식에 필수적인 글머리 기호

개조식 문단은 반드시 기호가 있어야 읽기 쉽습니다.

-   설명: 기호
-   서사(순서): 1. 2. 3.
-   논증(흐름): → 화살표
-   묘사(그림 요소): ① ② ③

### 문단의 위계

업무용 글은 위계가 있어야 합니다.

들여쓰기, 글자 크기, 굵기, 줄간격으로 레벨을 표현하지 않으면 단순한 ‘소설’이 되어버립니다.

## 2\. 띄어쓰기와 문장 부호

### 가장 쉬운 띄어쓰기 규칙

외우기 쉬운 규칙 하나면 충분합니다.

> 조사, 순서, 숫자, ‘하다’, 기호만 붙이고 나머지는 띄운다.

### 따옴표의 규칙

-   큰따옴표 " " : 대화, 직접 인용
-   작은따옴표 ' ' : 인용 안의 인용, 마음속 말

비즈니스 문서에서는 조금 다르게 응용됩니다.

-   책·신문 이름: 큰따옴표
-   법률·규정·상호: 작은따옴표
-   강조·비교: 작은따옴표

## 3\. 영어 단어 선택과 외래어 표기법

### 단어 선택의 원칙

정확성보다 중요한 것은 일관성과 개연성입니다.

예를 들어 조회 함수의 접두사를 get으로 쓸지 fetch로 쓸지는 어느 쪽이든 괜찮습니다. 팀이 하나로 합의해 끝까지 같은 단어를 쓰는 것이 중요합니다.

### 외래어 표기

외산 제품 이름, 기술 용어는 반드시 일관되게 써야 합니다.

React를 어떤 문서에는 리액트, 어떤 곳에는 ReactJS라고 적으면 혼란만 생깁니다.

## 4\. 이름 짓기와 네이밍 컨벤션

### 이름 짓기는 창조가 아니라 조합

변수명은 무에서 창조하는 것이 아니라, 이미 있는 패턴을 조합하는 행위입니다.

### 영어 표기법을 상속한 네이밍 컨벤션

영어의 대문자 규칙 → PascalCase, camelCase → 코딩 컨벤션으로 이어졌습니다.

-   PascalCase: 클래스, 타입
-   camelCase: 함수, 변수
-   UPPER\_CASE: 상수

같은 이름 규칙이라도 언어와 생태계마다 관례가 다릅니다. JavaScript와 TypeScript는 변수와 함수에 camelCase를 씁니다. Python은 PEP 8에서 함수와 변수에 snake\_case를 권장합니다. CSS 클래스와 URL 경로에는 kebab-case가 흔히 쓰입니다. 그래서 이름 규칙은 쓰는 언어의 관례를 먼저 따르고 린터 설정으로 고정해 두면 팀 안에서 흔들리지 않습니다.

### 변수 이름 짓는 팁

-   i는 괜찮지만 d는 피합니다 (맥락 불명확)
-   검색이 잘 되도록 긴 이름도 두려워하지 않습니다
-   복수형은 userNames 또는 userList처럼 명확하게
-   약어는 보편적이지 않으면 쓰지 않습니다
-   중요한 단어는 앞에 배치 (예: visitorTotal > totalVisitor)

### SMART한 이름의 5가지 기준

좋은 이름은 다음 5가지 조건을 충족합니다.

-   **Searchable** 검색하기 쉽고
-   **Mixable** 조합하기 쉽고
-   **Agreeable** 모두가 수긍할 수 있고
-   **Rememberable** 기억하기 쉽고
-   **Typable** 입력하기 쉬워야 합니다

## 5\. 주석 줄일 것, 하지만 없앨 수는 없다

### 이름이 곧 주석

```typescript
// 나쁜 예
// 스크린 최대 높이를 480으로 지정
const h = 480

// 좋은 예
const screenHeightMax = 480
```

나쁜 예는 주석이 없으면 `h`가 무엇인지 알 수 없지만, 좋은 예는 변수 이름만으로 의미가 드러납니다. 좋은 이름을 지으면 이런 주석은 필요 없습니다.

`screenHeightMax`는 가장 중요한 대상인 screen에서 시작해 점점 구체적인 속성으로 좁혀지는 순서입니다. 앞서 본 "중요한 단어는 앞에 배치"하는 팁이 적용된 이름이라서 `screenWidthMax`처럼 짝이 되는 변수와 접두사가 같아 검색해 묶어 보기도 쉽습니다.

《프로그램을 읽는 기술》도 함수나 변수명이 의도를 충분히 전달하지 못하는 것을 코드가 읽히지 않는 이유로 꼽습니다. 이 내용은 [프로그램을 읽는 기술을 읽고](/posts/art-of-reading-code/)에 정리했습니다.

### 하지만 주석은 여전히 필요하다

-   이유 설명
-   새로 발견한 사실 기록
-   예상 질문에 대한 답
-   TODO / HACK / XXX 주석
-   다른 사람에게 보완 요청

```typescript
// TODO: 동영상 확장자 체크 기능 추가
// HACK: 확장자 검사를 건너뛰고 우선 통과시킴
```

위 두 주석은 태그를 붙인 예입니다. TODO는 앞으로 할 일을, HACK은 정석 대신 임시로 넘어간 부분을 표시하는 관례로 쓰입니다. 비슷한 태그로 결함을 뜻하는 FIXME와 위험하거나 주의가 필요한 곳을 뜻하는 XXX도 흔히 보입니다. 에디터와 린터가 이런 태그를 모아 보여주는 경우가 많아서 나중에 한꺼번에 찾기 좋습니다. 태그만 남기지 않고 무엇을 왜 해야 하는지까지 적어야 읽는 사람에게 의미가 전달됩니다.

주석은 코드가 무엇을 하는지보다 왜 그렇게 했는지를 적을 때 가치가 큽니다. 무엇을 하는지는 이름과 구조로 드러낼 수 있지만 결정의 이유는 코드에 남지 않기 때문입니다.

## 코드와 설명을 다시 읽을 때

문장을 짧게 쓰고 문단의 주제를 나누는 방법은 리뷰 설명에도 적용할 수 있습니다. 함수 이름으로 동작을 드러내고, 이름으로 알 수 없는 결정의 이유는 주석에 남깁니다.

이 책에서 정리한 기준을 다음 코드와 문서를 다시 읽을 때 참고하려 합니다. 읽는 사람이 문장 하나에서 여러 뜻을 추측해야 하는지, 코드와 설명이 같은 말을 하는지부터 확인해 볼 수 있겠습니다.
