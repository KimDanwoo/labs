## 들어가며

“개발자는 코드만 잘 짜면 된다”는 말, 이제는 절반만 맞는 이야기입니다.

현대의 개발자는 **코드와 문서를 동시에 설계하는 사람**입니다.

변수 하나, 함수 이름 하나, 주석 한 줄에도 팀 전체의 생산성과 유지보수성이 달라집니다.

따라서 글쓰기와 코딩은 별개의 영역이 아니라, 같은 **‘의미를 전달하는 기술’**로 이어져 있습니다.

이 글에서는 《개발자의 글쓰기》에서 다룬 내용을 바탕으로,

-   문장과 단락을 구조화하는 법
-   띄어쓰기와 문장 부호
-   네이밍과 주석의 원칙

위 내용을 개발자의 관점에서 정리해보겠습니다.

## 1\. 문장과 단락을 구조화하는 법

### 간단한 문장의 힘

글쓰기를 어렵게 만드는 가장 큰 이유는 불필요하게 긴 문장입니다.

핵심만 담은 **간단한 문장** → 필요 시 **부가 설명**으로 확장하는 것이 기본 원칙입니다.

그리고 첫 문장의 주어를 소제목으로 끌어내면 문단 구조가 자연스럽게 만들어집니다.

### 서술식 · 개조식 · 도식의 차이

개발자가 글을 쓰는 방식에는 세 가지가 있습니다.

-   **서술식**: ~다로 끝나는 완전한 문장. 설명·논증에 적합. (가이드 문서, 매뉴얼 등)
-   **개조식**: 항목을 나열하는 방식. 중복·누락에 주의. (회의록, TODO 등)
-   **도식**: 관계를 시각적으로 보여주는 표·도표. (기능 비교, 프로세스 설계 등)

규칙은 단순합니다.

-   줄거리가 있는 설명 → 서술식
-   반복되는 항목 정리 → 개조식
-   관계를 비교/정리 → 도식

### 개조식에 필수적인 글머리 기호

개조식 문단은 반드시 기호가 있어야 읽기 쉽습니다.

-   설명: 기호
-   서사(순서): 1. 2. 3.
-   논증(흐름): → 화살표
-   묘사(그림 요소): ① ② ③

### 문단의 위계

업무용 글은 위계가 있어야 합니다.

들여쓰기, 글자 크기, 굵기, 줄간격으로 레벨을 표현하지 않으면 단순한 ‘소설’이 되어버립니다.

## 2\. 띄어쓰기와 문장 부호

### 가장 쉬운 띄어쓰기 규칙

외우기 쉬운 규칙 하나면 충분합니다.

**→ 조사, 순서, 숫자, ‘하다’, 기호만 붙이고 나머지는 띄운다.**

### 따옴표의 규칙

-   큰따옴표 " " : 대화, 직접 인용
-   작은따옴표 ' ' : 인용 안의 인용, 마음속 말

비즈니스 문서에서는 조금 다르게 응용됩니다.

-   책·신문 이름: 큰따옴표
-   법률·규정·상호: 작은따옴표
-   강조·비교: 작은따옴표

## 3\. 영어 단어 선택과 외래어 표기법

### 단어 선택의 원칙

정확성보다 중요한 것은 **일관성과 개연성**입니다.

예를 들어 모든 함수 이름을 doSomething()으로 통일해도, 팀이 합의했다면 문제 없습니다.

### 외래어 표기

외산 제품 이름, 기술 용어는 반드시 일관되게 써야 합니다.

React를 어떤 문서에는 리액트, 어떤 곳에는 ReactJS라고 적으면 혼란만 생깁니다.

## 4\. 이름 짓기와 네이밍 컨벤션

### 이름 짓기는 창조가 아니라 조합

변수명은 무에서 창조하는 것이 아니라, 이미 있는 패턴을 조합하는 행위입니다.

### 영어 표기법을 상속한 네이밍 컨벤션

영어의 대문자 규칙 → PascalCase, camelCase → 코딩 컨벤션으로 이어졌습니다.

-   PascalCase: 클래스, 타입
-   camelCase: 함수, 변수
-   UPPER\_CASE: 상수

### 변수 이름 짓는 팁

-   i는 괜찮지만 d는 피하자 (맥락 불명확)
-   검색이 잘 되도록 긴 이름도 두려워하지 말자
-   복수형은 userNames 또는 userList처럼 명확하게
-   약어는 보편적이지 않으면 쓰지 말자
-   중요한 단어는 앞에 배치 (예: visitorTotal > totalVisitor)

### SMART한 이름의 5가지 기준

좋은 이름은 다음 5가지 조건을 충족합니다.

-   **Searchable** 검색하기 쉽고
-   **Mixable** 조합하기 쉽고
-   **Agreeable** 모두가 수긍할 수 있고
-   **Rememberable** 기억하기 쉽고
-   **Typable** 입력하기 쉬워야 한다

## 5\. 주석 줄일 것, 하지만 없앨 수는 없다

### 이름이 곧 주석

```typescript
// 나쁜 예
// 스크린 최대 높이를 480으로 지정
const h = 480

// 좋은 예
const screenHeightMax = 480
```

좋은 이름을 지으면 주석은 필요 없다.

### 하지만 주석은 여전히 필요하다

-   이유 설명
-   새로 발견한 사실 기록
-   예상 질문에 대한 답
-   TODO / HACK / XXX 주석
-   다른 사람에게 보완 요청

```typescript
// TODO: 동영상 확장자 체크 기능 추가
// HACK: null 입력 시 무한 루프 발생 가능
```

## 마무리하며

개발자의 글쓰기는 **코드와 글을 동시에 구조화하는 기술**입니다.

-   문장은 단순하게, 문단은 위계 있게
-   일관성 있는 띄어쓰기와 따옴표
-   네이밍은 창조가 아닌 조합, SMART 기준으로
-   주석은 최소화하되 의도와 맥락을 기록

코드와 문서 모두 결국은 **팀 전체를 위한 소통 도구**입니다.

좋은 글쓰기 습관이 곧 좋은 코드 습관으로 이어진다는 점을 기억하면, 개발 생산성은 자연스럽게 올라갈 것입니다.
