## 코드는 맡겨도, 판단까지 맡길 수는 없었다

최근 Thoughtworks의 「[Should we still design code for humans?](https://www.thoughtworks.com/insights/blog/programming-languages/should-still-design-code-humans)」라는 글을 읽었다.

AI가 코드를 작성하고 다시 AI가 그 코드를 읽고 수정하는 일이 자연스러워진 지금, 여전히 사람이 읽기 좋은 코드를 만드는 일이 중요하냐는 질문에서 시작하는 글이다. 조금 더 밀어붙이면 이런 상상도 가능하다.

사람은 요구사항과 제약만 정의하고 구현과 테스트, 수정은 Agent에게 넘긴다. 코드가 문제가 되면 다시 Agent가 읽고 고친다. 그렇게 된다면 코드는 사람이 직접 관리해야 하는 산출물이 아니라, Agent 사이에서 소비되는 중간 결과물이 될 수도 있다. 나 역시 AI에게 코딩을 꽤 많이 맡기고 있기 때문에 낯선 이야기는 아니었다.

오히려 생산성만 놓고 보면 이미 이전 방식으로 돌아가기 어렵다고 느낀다. 그런데 글에서 더 오래 생각하게 된 부분은 따로 있었다. Agent가 만드는 코드의 문제는 각각의 구현이 틀려서가 아니라, 각각의 구현이 너무 그럴듯해서 생길 수도 있다는 점이었다.

## 각각은 맞는데, 전체가 틀어질 수 있다

AI에게 개발을 맡길 때 우리가 던지는 요청은 대체로 feature 단위다.

"필터를 하나 추가해줘."

"이 API를 연결해줘."

"여기서도 같은 데이터를 사용할 수 있게 해줘."

"이 화면에서는 예외적으로 이 경우를 처리해줘."

Agent는 현재 코드베이스를 읽고 기존 패턴을 찾고 요구사항을 만족하는 방법을 빠르게 만든다. 대부분 잘 동작한다. 타입도 맞고 테스트도 통과하고 화면도 원하는 대로 나온다.

문제는 이 작업을 열 번, 스무 번, 백 번 반복했을 때다. 첫 번째 기능에서는 조건 하나를 추가한다. 두 번째에서는 비슷한 로직이 필요해 helper를 만든다.

세 번째에서는 기존 모델이 애매해서 상태를 하나 더 만든다. 네 번째에서는 기존 abstraction으로는 표현하기 어려워 별도의 경로를 만든다. 다섯 번째에서는 기존 구조에 예외 처리를 넣는다.

```text
Feature A → 조건 하나 추가
Feature B → 유사한 로직 추가
Feature C → 상태 하나 추가
Feature D → 새로운 추상화
Feature E → 기존 구조의 예외 처리
```

각각의 변경만 리뷰하면 크게 이상하지 않을 수 있다. 그 순간에는 오히려 가장 비용이 적은 선택일 수도 있다. 그런데 어느 시점에 전체를 다시 보면 이야기가 달라진다.

같은 개념이 서로 다른 이름으로 존재하고 하나였던 책임이 여러 위치에 흩어지고 처음에는 명확했던 경계가 조금씩 흐려져 있다. 사람이 개발한다고 이런 일이 생기지 않는 것은 아니다. 우리는 오래전부터 이것을 기술 부채나 소프트웨어 엔트로피 같은 이름으로 불러왔다.

차이는 속도다. Agent는 기능을 훨씬 빠르게 만든다. 그렇다면 국소적으로 합리적인 선택이 누적되는 속도 역시 빨라질 수 있다. Thoughtworks의 글에서도 Agent가 개별 feature를 해결하며 만들어낸 예외와 local optimization이 전체 복잡도로 누적되고 누군가 주기적으로 뒤로 물러나 시스템을 다시 보지 않으면 그 효과가 더 빨리 복리처럼 쌓일 수 있다고 지적한다.

여기서 한 가지를 분리해서 생각할 필요가 있다고 느꼈다. 코드를 빠르게 만드는 능력과, 시스템이 계속 변경될 수 있도록 만드는 능력은 같은 것이 아니다. 전자는 이제 Agent가 매우 잘한다.

후자는 여전히 어렵다.

## 처음에는 프롬프트의 문제라고 생각했다

AI를 개발에 사용하기 시작했을 때 결과가 마음에 들지 않으면 대부분 설명을 더 붙였다. 우리 프로젝트는 이런 구조를 사용한다. 상태는 이런 기준으로 나눈다.

이 패턴은 사용하지 않는다. 이 라이브러리를 우선한다. 테스트는 이런 방식으로 작성한다.

설명을 자세히 할수록 결과는 좋아졌다. 하지만 AI를 사용하는 빈도가 높아지면서 다른 문제가 보이기 시작했다. 나는 계속 같은 설명을 반복하고 있었다.

TypeScript에서는 어떤 타입 전략을 사용할지. React에서는 서버 상태와 로컬 상태를 어떻게 구분할지. 컴포넌트와 feature의 책임을 어디까지 볼지.

레이어 사이의 의존 방향을 어떻게 제한할지. 이미 사용하는 라이브러리가 있는데 비슷한 역할의 다른 라이브러리를 새로 가져오지 않게 할지. 어떤 명령은 실수라고 해도 절대 실행되면 안 되는지.

이런 것들은 매번 새롭게 판단하는 내용이 아니었다. 이미 팀이나 프로젝트에서 합의했고 반복해서 적용해야 하는 기준에 가까웠다. 그때부터 질문이 조금 달라졌다.

이미 정한 기준을 매번 다시 설명하는 일을 줄이고 싶어서 프론트엔드용 하네스인 [my-fe-harness](https://github.com/KimDanwoo/my-fe-harness)를 만들기 시작했다. 여기서 하네스는 규칙을 전달하고 위험한 행동을 막고 결과를 다시 검사하는 장치를 가리킨다.

## 판단을 Agent의 기억력에 맡기지 않기

초기 아이디어는 단순했다. 프로젝트에서 반복적으로 사용하는 기준을 rule로 만들고 필요한 프로젝트에 설치한다. TypeScript, React, 테스트, 접근성, 폴더 구조, 모노레포 같은 기준을 한곳에서 관리하고 Claude Code가 관련 파일을 다룰 때 자동으로 읽게 했다.

예를 들어 React 코드를 수정할 때 React 규칙을 읽고 TypeScript 파일을 수정할 때 타입 규칙을 읽는다. 그런데 직접 사용하다 보니 모든 규칙을 같은 방식으로 다루면 안 된다는 것이 보였다.

"렌더 중 계산할 수 있는 값을 굳이 state로 복사하지 않는다."

"사용자의 이벤트에서 시작된 일은 가능하면 이벤트 핸들러에서 끝낸다."

"전역 상태는 필요한 경우에만 사용한다."

이런 것은 중요한 기준이지만 여전히 문맥이 개입한다. 예외가 있을 수 있고 다른 선택이 더 나을 수도 있다. 반대로 이런 것은 다르다.

실제 secret을 코드에 쓰는 것. 민감한 파일을 커밋하는 것. 루트나 홈 디렉터리를 재귀적으로 삭제하는 것.

이건 "되도록 하지 않는다"가 아니다. 아예 실행되면 안 된다. 그래서 하네스에서도 둘을 나눴다.

```text
Rules
→ 판단할 때 참고할 기준

Guard
→ 해서는 안 되는 행동을 실행 전에 차단
```

현재 하네스는 convention을 .claude/rules를 통해 context로 주입하고 안전과 관련된 확실한 위반은 PreToolUse 단계에서 막는다. PreToolUse는 Claude Code가 도구를 실행하기 직전에 호출되는 훅이다. 여기서 꽤 중요한 차이를 느꼈다. 문서에 적어두는 것과 시스템이 보장하는 것은 다르다.

이건 AI가 등장해서 새로 생긴 교훈도 아니다. 오랫동안 개발하면서 lint, type system, CI, branch protection 같은 도구를 써온 이유와 크게 다르지 않다. 사람에게 "조심해서 지켜주세요"라고 말하는 것보다, 지켜야 하는 규칙이라면 시스템으로 만들 수 있는 부분을 시스템으로 옮기는 편이 낫다.

Agent에게도 마찬가지였다.

## 그런데 규칙을 넣었다고 끝난 게 아니었다

처음 하네스를 만들 때는 입력 쪽을 많이 봤다. Agent에게 어떤 context를 줄 것인가. 어떤 규칙을 보여줄 것인가.

무엇을 강제로 막을 것인가. 하지만 프로젝트는 설치한 날에 멈춰 있지 않는다. 코드는 계속 변한다.

dependency가 추가되고 폴더가 생기고 alias가 바뀌고 feature가 늘어난다. Agent에게 "우리는 이런 구조를 쓴다"고 알려줬다고 해서 3개월 뒤에도 그 구조가 그대로 유지된다는 보장은 없다. 오히려 그동안 수십 개의 feature가 추가됐다면 다시 확인하는 편이 자연스럽다.

그래서 최근에는 하네스에 세 번째 축을 넣었다. 되읽기(Read-back)다. 현재 check는 실제 src 코드를 다시 훑으면서 설치된 구조 팩의 의존 방향이 아직 지켜지고 있는지를 검사한다.

아래 레이어에서 위 레이어를 참조하는지. 같은 레이어의 다른 slice 내부를 직접 참조하는지. 공개 API를 두고 내부 구현으로 deep import하고 있는지.

이처럼 답을 기계적으로 결정할 수 있는 것만 검사한다. 위반하면 파일과 줄을 보여주고 CI에서는 실패시킬 수도 있지만 코드를 알아서 고치지는 않는다. 이 기능을 넣으면서 하네스에 대한 생각이 한 번 더 바뀌었다.

```text
Rules
    ↓
Agent가 구현
    ↓
Guard
    ↓
Code
    ↓
Check
    ↓
다시 확인
```

규칙을 한 번 넣고 끝내는 것이 아니라 결과를 다시 읽는 루프가 필요했다. Thoughtworks 글에서 인상적이었던 주장 중 하나도 비슷했다. 좋은 설계를 markdown이나 harness에 한 번 정의해놓고 영원히 위임할 수는 없으며 요구사항이 바뀌면 설계 역시 계속 다시 협상되어야 한다는 것이다. 나도 하네스를 만들면서 같은 결론에 가까워졌다.

규칙은 설계의 끝이 아니라, 현재까지 내린 판단의 스냅샷에 가깝다.

## 그래서 모든 것을 검사하려 하지 않았다

check를 만들면서 오히려 중요하게 생각한 것은 무엇을 검사할지가 아니라 무엇을 검사하지 않을지였다. 예를 들어 이런 질문들이 있다. 이 컴포넌트는 너무 큰가.

이 abstraction은 과한가. 두 feature를 하나로 합쳐야 하는가. 이 중복은 제거해야 하는가.

이 상태를 URL로 보내는 편이 나은가, 전역 상태로 두는 편이 나은가. 이런 것들을 LLM에게 평가하게 만들 수도 있다. 자동으로 점수를 매기고 warning을 띄우는 것도 가능하다.

하지만 하지 않았다. 이 문제들은 같은 코드를 보고도 제품의 방향, 팀의 상황, 앞으로의 변경 가능성에 따라 답이 달라진다. 반면 레이어의 의존 방향처럼 이미 우리가 선택했고 판정도 결정론적인 것은 자동화하기 좋다.

그래서 지금은 대략 이렇게 경계를 나누고 있다.

```text
Agent
→ 구현, 탐색, 반복 작업

Harness
→ 이미 결정된 기준의 전달과 검증

Human
→ trade-off가 필요한 판단
```

개인적으로는 이 경계가 꽤 중요하다고 생각한다. 자동화할 수 있다는 이유와 자동화해야 한다는 이유는 다르다. 특히 판단의 정확도를 검증하기 어려운 영역까지 자동화하기 시작하면, 생산성은 높아 보여도 시스템을 이해하는 사람이 점점 사라질 수 있다.

## 코드베이스의 사실과 좋은 설계도 구분해야 했다

하네스를 고도화하면서 또 하나 분리하게 된 것이 있다. 규칙과 사실이다.

"상태관리는 Jotai를 써야 한다."

이것은 보편적인 좋은 규칙이 아니다. 하지만 이미 어떤 프로젝트에서 Jotai를 사용하고 있다면

"이 프로젝트는 Jotai를 사용하고 있다."

는 사실이다. 둘은 전혀 다르다. Agent가 코드를 수정할 때 필요한 것은 일반적인 Best Practice만이 아니다.

현재 코드베이스가 이미 어떤 선택을 했는지도 알아야 한다. 그래서 지금은 프로젝트를 읽어서 실제 사용하는 상태관리, 폼, 스타일, 테스트, API 라이브러리와 source directory, import alias 같은 정보를 \_stack.md에 남긴다. 그리고 설치 이후 dependency나 디렉터리 구조가 변해서 이 정보가 낡으면 status에서 다시 감지한다.

이 기능을 만들면서 한 가지 생각이 더 명확해졌다. 좋은 Agent 경험을 만들려면 정답을 많이 알려주는 것보다 현재 상황을 정확하게 알려주는 편이 더 중요할 때가 있다. 이미 React Query가 있는데 비슷한 데이터 패칭 도구를 새로 가져오는 것.

이미 alias가 있는데 갑자기 깊은 상대 경로를 만드는 것. 프로젝트에 정해진 구조가 있는데 새로운 최상위 디렉터리를 만드는 것. 이런 문제는 React를 얼마나 잘 아느냐와 크게 관련이 없다.

그 프로젝트의 맥락을 놓쳤기 때문에 생긴다.

## 결국 하네스도 판단의 결과다

여기까지 만들고 나면 이런 생각을 할 수도 있다. 규칙을 충분히 잘 만들고 위험한 행동은 Hook으로 막고 결과는 다시 검사한다면 이제 구현을 거의 전부 Agent에게 맡겨도 되는 것 아닐까. 일부는 맞다고 생각한다.

나 역시 앞으로 더 많은 구현을 위임할 생각이다. 그런데 여기에는 한 가지 전제가 있다. 하네스에 들어가는 판단이 괜찮은 판단이어야 한다.

만약 내가 잘못된 기준을 넣으면 어떻게 될까. 예를 들어 모든 공유 상태를 전역 상태로 만들라는 규칙을 넣었다고 하자. Agent는 아주 성실하게 지킬 수 있다.

```text
잘못된 판단
    ↓
Harness
    ↓
Agent
    ↓
일관된 잘못된 코드
```

자동화하지 않았다면 한두 번의 잘못된 선택으로 끝났을 일이 전체 코드베이스에서 일관되게 반복될 수도 있다. 그래서 지금은 하네스를 이렇게 생각한다. 하네스는 좋은 판단을 대신 내려주는 장치가 아니다.

내가 이미 내린 판단 중 반복할 가치가 있는 것을 시스템으로 옮겨놓는 장치다. 그렇다면 가장 중요한 문제는 여전히 그 앞에 남는다. 무엇을 rule로 만들 것인가.

무엇을 guard로 강제할 것인가. 무엇을 check로 검증할 것인가. 무엇은 끝까지 사람의 판단으로 남길 것인가.

이 경계를 만드는 것 자체가 엔지니어링이다.

---

## 그래서 AI를 쓸수록 공부의 방향이 바뀌었다

AI를 많이 사용하면 개발자가 공부해야 할 것이 줄어들 수 있다는 생각을 종종 한다. 어느 정도는 맞다. 라이브러리의 API를 전부 기억할 필요는 확실히 줄었다.

옵션 이름을 잊어도 된다. 처음 보는 syntax도 바로 설명받을 수 있다. boilerplate를 익숙하게 작성하는 능력의 가치도 예전과 같지는 않다.

구현 방법을 찾는 비용은 정말 많이 떨어졌다. 대신 내가 공부하고 싶은 것은 조금 달라졌다. Zustand의 API를 외우기보다,

어떤 상태를 애플리케이션 상태로 만들어야 하는지를 더 보고 싶다. React Query의 옵션을 외우기보다, 서버 상태를 왜 별도의 클라이언트 상태로 복사하면 문제가 되는지를 이해하고 싶다.

[FSD](/posts/fsd-guide/)의 폴더 이름을 외우기보다,

왜 의존 방향을 제한하고 무엇을 얻으려 하는지가 더 중요하다. 테스트 도구의 mocking API보다, 어떤 경계를 검증해야 변경에 대한 신뢰가 생기는지가 더 궁금하다.

결국 공부의 방향이 조금씩 이렇게 변하고 있다.

```bash
How     → Why
문법     → 원리
구현     → 구조
사용법   → Trade-off
정답 찾기 → 선택 기준 만들기
```

How가 필요 없다는 뜻은 아니다. 원리를 이야기하려면 구현을 알아야 하고 좋은 구조를 판단하려면 코드가 실제로 어떻게 움직이는지도 알아야 한다. 다만 지금은 암기할 내용보다 판단할 때 참고할 지식을 우선하게 됐다.

## AI의 제안에 반론할 수 있는가

요즘 AI와 코딩하면서 꽤 중요하게 보는 기준이 하나 있다. AI의 제안에 반론할 수 있는가. Agent는 대부분의 선택을 그럴듯하게 설명할 수 있다.

"여러 컴포넌트에서 사용하는 상태이므로 전역 상태로 분리하겠습니다."

"중복을 제거하기 위해 공통 Hook으로 추출하겠습니다."

"확장성을 고려해 abstraction layer를 추가하겠습니다."

틀린 문장은 아니다. 문제는 현재 코드에서도 맞는 문장이냐는 것이다. 여러 곳에서 사용한다고 반드시 전역 상태일 필요는 없다.

두 코드가 현재 비슷하다고 해서 앞으로 같은 이유로 변경된다는 보장도 없다. 언젠가 확장될 수 있다는 이유만으로 오늘 복잡성을 미리 지불할 필요도 없다. 이 개념들을 모르면 선택지는 사실 하나뿐이다.

"좋아. 그렇게 해줘."

하지만 알고 있으면 다시 물을 수 있다. 이 상태는 URL이 source of truth가 되는 편이 낫지 않을까. 이 중복은 우연한 중복과 지식의 중복 중 어느 쪽일까.

이 abstraction이 해결하는 현재의 문제가 정확히 무엇일까. 기존 dependency로 해결할 수 있는데 하나를 더 들고 와야 할 이유가 있을까. Agent가 코드를 생성하는 속도와 경쟁할 필요는 없다고 생각한다.

그건 이미 게임이 끝난 영역에 가깝다. 대신 Agent가 만들어낸 선택을 검토하고 다른 선택지를 만들고 필요하면 반론하는 능력은 더 중요해지고 있다. 그리고 이 능력은 프롬프트 테크닉보다 기본적인 소프트웨어 설계 지식에서 나온다고 생각한다.

---

## 위임한 뒤에도 내가 확인할 것

지금은 세 가지를 의식적으로 확인한다.

- 테스트 통과와 함께 변경이 기존 구조에 어떤 영향을 주는지 본다.
- dependency를 추가할 때는 기존 도구로 해결할 수 있는지, 업데이트와 운영 비용을 감당할 수 있는지 따진다.
- 이해하지 못하는 코드는 다음에도 AI가 고칠 것이라는 이유로 넘기지 않는다. 시스템의 방향을 바꿔야 할 때 검토할 수 있어야 하기 때문이다.

하네스 자체에도 같은 기준을 적용하고 있다. core rule을 대조 형태로 바꾸고 path-scoped rule의 토큰 비용을 측정했다. 구조 규칙은 주입하는 데서 끝내지 않고 실제 코드에서 다시 검사하도록 바꿨다. 아직 측정하지 않은 부분은 측정하지 않았다고 남겨 두었다.

이 작업은 [my-fe-harness](https://github.com/KimDanwoo/my-fe-harness)에서 이어 가고 있다. 이미 합의한 기준은 Rule로 전달하고, 금지한 행동은 Guard로 막고, 코드가 기준을 지키는지는 Check로 확인한다. 그 기준을 유지할지 고칠지는 프로젝트가 변할 때 다시 판단한다.

앞으로도 구현은 더 많이 맡길 것 같다. 매번 같은 설명을 반복하는 시간이 줄면, 지금의 규칙이 이 프로젝트에도 필요한지와 어떤 예외를 허용할지에 더 시간을 쓸 수 있다.

하네스 자체의 규칙과 모델 설정을 다시 살펴본 과정은 [Claude Code는 바뀌는데, 내 하네스는 그대로였다](/posts/removing-omc-ponytail/)에 정리했다.
