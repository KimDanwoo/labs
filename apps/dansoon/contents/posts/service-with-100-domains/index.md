최근 하나의 프로젝트가 100개가 넘는 도메인에서 동작하는 구조를 마주했다.

하나의 Next.js 애플리케이션이 있고, 사용자는 서로 다른 도메인으로 서비스에 접근한다. 하지만 내부적으로는 같은 프론트엔드 애플리케이션을 바라보고 사용하는 API 서버도 동일한 구조였다.

예를 들면 이런 형태에 가까웠다.

```bash
a-service.com      ─┐
b-service.com      ─┤
c-service.com      ─┤
...                ─┼─> Next.js App
z-service.com      ─┘
```

처음에는 이 구조가 단순해 보였다.

도메인별로 라우팅만 잘 처리하고 API 서버에서 CORS를 열어주면 되지 않을까 생각했다. 몇 개의 도메인이라면 그렇게 관리할 수도 있었을 것이다.

하지만 도메인이 100개를 넘는 순간 이야기가 달라졌다.

새로운 도메인이 추가될 때마다 백엔드 CORS 허용 목록을 수정해야 하고 도메인이 변경되거나 제거될 때도 설정을 함께 관리해야 한다. 당장은 단순한 설정 문제처럼 보여도, 시간이 지나면 운영 복잡도가 계속 쌓이는 구조였다.

무엇보다 로그인 상태가 필요한 API 요청이 들어오는 순간부터 문제가 더 커졌다.

브라우저는 어떤 도메인의 쿠키를 포함해서 요청해야 할까?  
백엔드는 100개가 넘는 Origin 중 어떤 요청을 신뢰해야 할까?  
인증이 필요한 요청을 매번 브라우저에서 백엔드 API로 직접 보내는 구조가 맞을까?

이 고민은 여러 도메인에서 하나의 로그인 상태를 공유하는 SSO 문제가 아니었다.

핵심은 **100개가 넘는 도메인에서 발생하는 API 요청과 인증 흐름을 어느 계층에서 정리할 것인가**였다.

---

## 도메인이 100개면 API 요청과 인증에서 무엇이 어려워질까

도메인이 여러 개라는 사실만 보면 크게 어려운 문제처럼 보이지 않을 수 있다.

프론트엔드 애플리케이션은 동일하고 API 서버도 동일하다면 각 도메인에서 같은 앱을 보여주면 된다. 실제 화면을 렌더링하는 것만 생각하면 단순한 Host 기반 라우팅 문제처럼 보인다.

하지만 API 호출이 들어오면 이야기가 달라진다.

특히 로그인 상태가 필요한 API라면 브라우저, 쿠키, CORS, 세션 정책이 함께 얽힌다. 여기서 Origin은 프로토콜, 도메인, 포트의 조합이며 CORS는 다른 Origin에서 받은 응답을 그 요청을 보낸 스크립트가 읽어도 되는지 브라우저가 서버의 응답 헤더로 확인하는 정책이다. 단순한 요청은 서버까지 도달하고, PUT·DELETE 같은 메서드나 `Content-Type: application/json`처럼 단순 요청 조건을 벗어나는 요청은 본 요청 전에 preflight(OPTIONS) 요청으로 먼저 허용 여부를 묻는다. CORS가 CSRF 방어를 대신해 주지는 않는다.

```bash
Browser
  ↓
Backend API
```

브라우저가 백엔드 API를 직접 호출하는 구조에서는 백엔드가 각 도메인의 요청을 직접 상대해야 한다.

도메인이 몇 개라면 괜찮을 수 있다. 하지만 도메인이 100개를 넘으면 백엔드 입장에서는 100개가 넘는 Origin을 관리해야 한다.

여기서 중요한 건 단순히 “CORS 설정을 할 수 있느냐”가 아니다.

도메인이 계속 늘어나는 구조에서 이 방식을 안정적으로 운영할 수 있느냐가 더 중요한 문제였다.

---

## CORS 허용 목록을 계속 늘리는 방식의 부담

처음에는 백엔드에서 허용할 Origin 목록을 관리하면 된다고 생각했다.

```text
Access-Control-Allow-Origin: https://a-service.com
Access-Control-Allow-Origin: https://b-service.com
Access-Control-Allow-Origin: https://c-service.com
...
```

하지만 도메인이 100개를 넘는 상황에서는 이 방식이 부담스럽게 느껴졌다.

도메인이 추가될 때마다 백엔드 설정이 바뀌어야 한다.  
도메인이 제거되거나 변경될 때도 마찬가지다.  
환경별로 개발, 스테이징, 운영 도메인을 따로 관리해야 할 수도 있다.

이런 구조에서는 CORS 설정이 단순 보안 설정이 아니라 운영 관리 대상이 된다.

또한 인증이 필요한 요청에서는 credentials 설정까지 고려해야 한다. 브라우저가 쿠키를 포함해서 요청하려면 프론트엔드 요청 설정, 백엔드 CORS 설정, 쿠키 정책이 모두 맞아야 한다.

결국 문제는 CORS 하나로 끝나지 않았다.

CORS, 쿠키, 세션, 인증 흐름이 모두 도메인 수만큼 복잡해지는 구조가 될 수 있었다.

---

## 세션 쿠키는 도메인 경계를 넘지 못한다

로그인 상태를 유지하기 위해 가장 먼저 떠올릴 수 있는 방식은 세션 쿠키다.

같은 도메인 안에서는 세션 쿠키가 자연스럽게 동작한다. 브라우저는 요청을 보낼 때 해당 도메인에 맞는 쿠키를 자동으로 포함하고 서버는 그 쿠키를 기준으로 사용자를 식별할 수 있다.

하지만 도메인이 달라지면 쿠키는 자연스럽게 공유되지 않는다.

```text
a-service.com
b-service.com
c-service.com
```

브라우저 입장에서 이 도메인들은 서로 다른 출처다. 각 도메인의 쿠키는 각자의 경계 안에서 관리된다.

물론 쿠키 설정을 조정하거나, 특정 조건을 맞추면 가능한 방식들이 있을 수 있다. 하지만 이번 고민의 핵심은 “기술적으로 가능하냐”가 아니었다.

100개가 넘는 도메인에서 세션과 인증 흐름을 일관되게 운영할 수 있느냐가 문제였다.

도메인마다 인증 흐름이 흩어지고 백엔드가 모든 Origin을 직접 상대해야 한다면 문제가 생겼을 때 추적하기도 어려워진다.

어떤 도메인에서는 쿠키가 포함되고, 어떤 도메인에서는 누락된다.  
어떤 요청은 CORS에서 막히고, 어떤 요청은 인증 실패로 떨어진다.  
이런 문제가 생기면 원인을 찾는 데도 시간이 오래 걸릴 수밖에 없다.

## 토큰을 브라우저 저장소에 두면 생기는 문제

다른 선택지도 있었다.

로그인 후 발급받은 토큰을 브라우저 저장소에 저장하고 API 요청마다 Authorization 헤더에 실어 보내는 방식이다.

```text
localStorage
sessionStorage
in-memory state
cookie
```

구현만 보면 이 방식은 단순해 보일 수 있다.

로그인 후 토큰을 저장하고 API 요청 시 토큰을 꺼내 헤더에 넣으면 된다.

하지만 인증 정보를 브라우저 쪽에서 직접 관리하는 순간 고민해야 할 것들이 많아진다.

localStorage나 sessionStorage는 JavaScript에서 접근할 수 있기 때문에 XSS(악성 스크립트 삽입 공격)에 더 민감하다. 인메모리 상태는 새로고침이나 탭 이동에 취약하다. 토큰 만료, 갱신, 로그아웃, 동시 탭 처리 같은 흐름도 클라이언트 코드에서 직접 관리해야 한다.

물론 토큰 기반 인증이 항상 나쁘다는 의미는 아니다. 서비스 구조에 따라 충분히 좋은 선택이 될 수 있다.

하지만 이번 상황에서는 인증 정보를 브라우저 저장소에서 직접 다루는 방식을 피하고 싶었다.

도메인이 100개를 넘는 상황에서 인증 상태까지 클라이언트 코드 곳곳에 흩어지면, 오히려 복잡도가 더 커질 수 있다고 느꼈다.

## 이상적인 구조: Gateway와 Edge 계층에서 도메인 인입 처리

가장 이상적인 구조만 놓고 보면, 100개가 넘는 도메인을 Next.js 애플리케이션이나 백엔드 API가 직접 하나하나 상대하지 않는 방향이 더 자연스럽다.

도메인이 많아질수록 이 문제는 애플리케이션 코드 안에서 해결해야 할 문제가 아니라, 서비스로 들어오는 요청을 가장 앞에서 정리하는 인입 계층의 문제에 가까워진다.

구조로 보면 이런 형태다.

```text
100+ Domains
  ↓
CDN / Edge / WAF / API Gateway / Reverse Proxy
  ↓
Next.js App
  ↓
Backend API
```

이 구조에서는 앞단의 Gateway나 Edge 계층이 먼저 요청을 받는다.

이 계층에서는 요청이 들어온 Host가 유효한지 확인하고 어떤 서비스나 테넌트에 연결된 도메인인지 판단할 수 있다. TLS 인증서, WAF, rate limit, 공통 보안 정책도 이 계층에서 관리할 수 있다.

그 뒤 Next.js 애플리케이션은 이미 정리된 요청을 받아 화면을 렌더링하고 필요한 경우 프론트엔드 요구사항에 맞게 API 요청을 조합한다.

백엔드 API는 100개가 넘는 브라우저 Origin을 직접 상대하기보다, Gateway나 Next.js 서버를 통해 정리된 내부 요청을 받는다.

책임을 나누면 이렇게 볼 수 있다.

```text
Gateway / Edge
- 100개 이상의 도메인 인입 처리
- TLS 인증서 관리
- Host 기반 라우팅
- 유효한 도메인인지 검증
- WAF, rate limit, 공통 보안 정책 처리

Next.js App
- 화면 렌더링
- Host 기반 UI / 설정 분기
- 프론트엔드에 필요한 데이터 조합
- API 요청 경계 정리

Backend API
- 비즈니스 로직
- 데이터 처리
- 인증 / 권한 검증
- 도메인 자체보다 내부 식별자 기준으로 처리
```

이 구조가 깔끔한 이유는 복잡도를 각 계층의 역할에 맞게 나누기 때문이다.

---

## 이상적인 구조의 비용: 인프라·운영·학습 부담

문제는 비용이다.

Gateway, CDN, Edge Function, WAF, 로그 수집, 모니터링, 인증서 관리까지 고려하면 구조는 선명해지지만 그만큼 비용도 늘어난다.

여기서 말하는 비용은 단순히 인프라 비용만이 아니다.

새로운 계층을 도입하면 그 계층을 이해하고 운영해야 한다. 장애가 발생했을 때 어느 계층에서 문제가 생겼는지 추적해야 하고 배포와 모니터링 방식도 함께 정리해야 한다.

가장 이상적인 구조에는 다음과 같은 비용이 함께 따른다.

```text
인프라 비용
운영 비용
모니터링 비용
장애 대응 비용
팀의 학습 비용
구조 전환 비용
```

반대로 백엔드에서 모든 Origin을 직접 관리하는 방식은 초기 비용이 낮다. 이미 있는 CORS 설정을 수정하면 되기 때문이다.

하지만 도메인이 추가되거나 변경될 때마다 백엔드 설정과 배포가 함께 따라가야 한다면, 시간이 지날수록 사람의 운영 비용이 커진다.

단순화하면 이렇게 볼 수 있다.

```text
백엔드 CORS 직접 관리
- 초기 비용 낮음
- 인프라 단순함
- 도메인이 늘어날수록 운영 비용 증가

Gateway / Edge 계층 분리
- 구조적으로 가장 깔끔함
- 확장성과 보안 정책 관리에 유리함
- 초기 도입 비용과 운영 비용 증가

Next.js 프록시 / BFF 활용
- 별도 인프라 도입 없이 시작 가능
- 요청 경계를 어느 정도 정리할 수 있음
- 대신 Next.js 서버의 책임과 부하 증가
```

비용 관점에서 보면 중요한 것은 “무엇이 가장 멋진 구조인가”가 아니었다.

현재 프로젝트에서 감당할 수 있는 비용 안에서, 어떤 계층이 어떤 복잡도를 책임지는 것이 가장 현실적인가가 더 중요했다.

## Next.js 서버를 API 요청의 중간 계층(프록시)으로 두는 접근

이런 맥락에서 고민한 방식은 Next.js 서버를 API 요청의 중간 계층으로 두는 것이었다.

브라우저가 백엔드 API를 직접 호출하는 대신, 먼저 Next.js 서버로 요청을 보낸다. 그리고 Next.js 서버가 필요한 요청 정보를 정리한 뒤 백엔드 API를 호출한다.

구조로 보면 이런 형태다.

```text
Browser
  ↓
Next.js Server
  ↓
Backend API
```

이 방식에서 브라우저는 현재 접근한 도메인의 Next.js 애플리케이션과 통신한다.

백엔드 API를 직접 바라보지 않는다.

반대로 백엔드는 100개가 넘는 브라우저 Origin을 직접 상대하기보다, Next.js 서버를 통해 정리된 요청을 받게 된다.

프록시 코드보다 요청의 방향과 신뢰 경계를 바꾼다는 점이 중요하다.

기존 구조에서는 브라우저가 백엔드 API를 직접 호출했다.

```text
Browser
  ↓
Backend API
```

이 구조에서는 백엔드가 브라우저 Origin을 직접 신뢰해야 한다.

반면 Next.js 서버를 중간 계층으로 두면 요청 흐름은 이렇게 바뀐다.

```text
Browser
  ↓
Next.js Server
  ↓
Backend API
```

이제 브라우저와 백엔드 API 사이에 Next.js 서버라는 경계가 생긴다.

즉, 백엔드가 100개가 넘는 Origin을 직접 상대하는 대신, 프론트엔드 서버에서 요청을 한 번 정리할 수 있다.

## Next.js Route Handler로 만든 간단한 프록시 예시

예를 들어 Next.js App Router에서는 Route Handler를 통해 API 프록시를 구성할 수 있다. Route Handler는 app 디렉터리 안에서 HTTP 메서드별 요청 처리 함수를 export하는 서버 코드다. App Router의 layout과 서버 렌더링이 운영에 미치는 영향은 [Next.js App Router 레이아웃·라우팅과 SEO](/posts/nextjs-app-router-layout-seo/)에서 다뤘다.

```typescript
// app/api/proxy/[...path]/route.ts

import { NextRequest } from 'next/server';

const API_BASE_URL = process.env.API_BASE_URL;

type Context = {
  params: Promise<{
    path: string[];
  }>;
};

async function proxy(request: NextRequest, context: Context) {
  const { path } = await context.params;

  // new URL(path, base)는 path가 절대 주소면 base를 무시한다.
  // 세그먼트를 인코딩해 이어 붙이고, 만든 주소가 백엔드 주소 아래를 벗어나면 거절한다.
  const baseUrl = `${API_BASE_URL}`.replace(/\/*$/, '/');
  const targetUrl = new URL(path.map(encodeURIComponent).join('/'), baseUrl);
  if (!targetUrl.href.startsWith(baseUrl)) {
    return new Response(null, { status: 400 });
  }
  targetUrl.search = request.nextUrl.search;

  const headers = new Headers();

  const cookie = request.headers.get('cookie');
  const contentType = request.headers.get('content-type');
  const host = request.headers.get('host');

  if (cookie) headers.set('cookie', cookie);
  if (contentType) headers.set('content-type', contentType);
  if (host) headers.set('x-forwarded-host', host);

  const response = await fetch(targetUrl, {
    method: request.method,
    headers,
    body: ['GET', 'HEAD'].includes(request.method)
      ? undefined
      : request.body,
    cache: 'no-store',
  });

  // fetch가 이미 압축을 풀어 준 본문이라 원본의 압축·길이 헤더는 넘기지 않는다
  const responseHeaders = new Headers(response.headers);
  responseHeaders.delete('content-encoding');
  responseHeaders.delete('content-length');

  return new Response(response.body, {
    status: response.status,
    headers: responseHeaders,
  });
}

export const GET = proxy;
export const POST = proxy;
export const PUT = proxy;
export const PATCH = proxy;
export const DELETE = proxy;
```

물론 실제 서비스에서는 이보다 더 많은 처리가 필요하다.

메서드별 처리, 쿼리스트링 전달, 요청 바디 전달, 에러 처리, 인증 실패 처리, 응답 헤더 제어 등을 함께 고려해야 한다.

특히 받은 경로로 요청 주소를 만들 때는 그 주소가 백엔드를 벗어나지 않는지 확인해야 한다. 확인 없이 합치면 경로 자리에 다른 사이트 주소가 들어왔을 때 쿠키를 실은 요청이 그쪽으로 나간다.

그래서 이 코드는 정답이 아니다.

이 예시가 보여주려는 것은 브라우저가 백엔드 API를 직접 호출하지 않도록 요청 경계를 조정할 수 있다는 점이다.

## Next.js 프록시 구조가 해결해주는 것

Next.js 서버를 프록시 계층으로 두면 몇 가지 장점이 생긴다.

첫 번째로, 브라우저가 백엔드 API를 직접 바라보지 않아도 된다.

브라우저는 현재 접근한 도메인의 Next.js 서버로 요청을 보낸다. 그러면 백엔드 API의 CORS 정책과 브라우저가 직접 맞닿는 면이 줄어든다.

두 번째로, 백엔드가 100개가 넘는 Origin을 직접 관리해야 하는 부담이 줄어든다.

도메인이 추가될 때마다 백엔드 CORS 허용 목록을 계속 수정하는 방식은 운영 부담이 크다. Next.js 서버를 요청 경계로 두면 도메인 변화가 백엔드 설정에 직접적으로 영향을 주는 범위를 줄일 수 있다.

세 번째로, 인증이 필요한 요청 흐름을 한 곳에서 정리할 수 있다.

로그인 여부 확인, 인증 실패 처리, 세션 만료 응답 처리 같은 흐름을 브라우저 코드 곳곳에 흩뿌리는 대신, Next.js 서버 계층에서 한 번 정리할 수 있다.

네 번째로, 프론트엔드 요구사항에 맞게 API 응답을 가공할 수 있다.

백엔드 API 응답을 그대로 화면에서 사용하기 어려운 경우가 있다. 이때 Next.js 서버 계층에서 필요한 형태로 데이터를 정리하면, 클라이언트 컴포넌트는 화면에 필요한 데이터에 더 집중할 수 있다.

다섯 번째로, 로깅과 에러 처리를 모으기 쉬워진다.

어떤 API에서 실패가 많이 발생하는지, 특정 도메인에서만 문제가 생기는지, 인증 실패가 어떤 흐름에서 발생하는지 등을 서버 계층에서 더 일관되게 추적할 수 있다.

이 관점에서 Next.js 서버는 단순히 화면을 렌더링하는 서버가 아니다.

프론트엔드와 백엔드 사이에서 요청을 정리하는 계층에 가까워진다.

## 프록시는 복잡도의 위치를 옮길 뿐이다

여기서 조심해야 할 점이 있다.

Next.js 서버를 프록시로 둔다고 해서 모든 문제가 사라지는 것은 아니다.

오히려 정확히 말하면 문제의 위치가 바뀌는 것에 가깝다.

브라우저와 백엔드 사이에 있던 복잡도를 Next.js 서버 쪽으로 옮기는 것이다. 그 대신 프론트엔드 서버가 API 라우팅, 인증 실패 처리, 캐시 정책, 에러 응답, 로깅 같은 책임을 가져가게 된다.

즉, 프록시는 문제를 없애는 도구가 아니다.

복잡도를 어느 계층에서 감당할 것인지 선택하는 방식이다.

서비스 구조에 따라 더 나은 방식은 달라질 수 있다.

API Gateway나 Nginx 같은 인프라 계층에서 요청을 정리하는 방식이 더 적합할 수도 있다. 백엔드에서 동적으로 Origin을 검증하는 방식이 더 맞을 수도 있다. 도메인 구조 자체를 정리할 수 있다면 그게 더 좋은 방향일 수도 있다.

하지만 이번 상황에서 중요하게 본 것은 “가장 멋진 구조가 무엇인가”가 아니었다.

이미 Next.js 애플리케이션이 사용자 요청의 진입점 역할을 하고 있었고 100개가 넘는 도메인이 이 애플리케이션을 바라보고 있었다.

그렇다면 브라우저가 백엔드 API를 직접 호출하게 두기보다, Next.js 서버를 요청 경계로 두고 API 호출과 인증 흐름을 한 번 정리하는 방식을 현실적인 선택지로 고민해볼 수 있었다.

## 프록시 계층에서 대신 책임져야 하는 것들

Next.js 서버를 프록시 계층으로 둔다면 책임도 분명히 늘어난다.

먼저 API 라우팅 규칙을 관리해야 한다.

어떤 요청을 어떤 백엔드 API로 전달할지, 메서드별로 어떻게 처리할지, 쿼리스트링과 헤더를 어디까지 전달할지 기준이 필요하다.

```bash
GET    /api/proxy/users
POST   /api/proxy/orders
PATCH  /api/proxy/profile
DELETE /api/proxy/items/:id
```

단순히 모든 요청을 그대로 넘기는 방식은 편해 보일 수 있다. 하지만 시간이 지나면 프록시 계층이 또 다른 레거시가 될 수 있다.

인증 실패 처리도 명확히 정해야 한다.

백엔드에서 401을 내려줬을 때 Next.js 서버는 그 응답을 그대로 전달할 것인지, 로그인 페이지로 보낼 것인지, 클라이언트가 처리할 수 있는 공통 에러 형태로 변환할 것인지 결정해야 한다.

캐시 전략도 조심해야 한다.

로그인 사용자마다 달라지는 응답을 잘못 캐시하면 심각한 문제가 될 수 있다. 반대로 캐시할 수 있는 응답까지 모두 no-store로 처리하면 성능상의 이점을 놓칠 수 있다.

또한 Next.js 서버가 장애 지점이 될 수도 있다.

브라우저와 백엔드 사이에 Next.js 서버가 추가되기 때문에, 이 계층에서 문제가 생기면 전체 API 호출 흐름이 영향을 받는다.

타임아웃, 에러 로깅, 응답 포맷, 재시도 여부를 신중하게 다뤄야 한다.

이 구조는 단순한 우회로가 아니다.

프론트엔드 서버가 요청 흐름의 일부를 책임지겠다는 선택이다.

## 정리: 100개 도메인에서 요청의 경계를 어디에 둘까

이번 고민의 결론은 Next.js 프록시가 모든 상황의 정답이라는 것이 아니었다.

오히려 이 고민을 통해 더 분명해진 것은 요청의 경계를 의식적으로 정해야 한다는 점이었다.

도메인이 몇 개 수준이라면 백엔드 CORS 설정으로 관리할 수 있다. 하지만 하나의 프로젝트가 100개가 넘는 도메인에서 동작한다면 이야기가 달라진다.

도메인이 늘어날수록 백엔드는 더 많은 Origin을 직접 신뢰해야 한다. 인증이 필요한 요청에서는 쿠키와 세션 정책까지 함께 관리해야 한다. 이 복잡도를 백엔드 CORS 설정에 계속 쌓을 것인지, Next.js 서버 같은 중간 계층에서 정리할 것인지, 아니면 Gateway나 Edge 계층으로 분리할 것인지 선택해야 한다.

가장 이상적인 구조는 앞단의 Gateway나 Edge 계층에서 도메인 인입을 정리하고 Next.js는 화면 렌더링과 프론트엔드 데이터 조합에 집중하며 백엔드는 비즈니스 로직과 권한 검증에 집중하는 구조일 수 있다.

하지만 가장 이상적인 구조가 항상 가장 현실적인 구조는 아니다.

구조를 나누면 책임은 선명해지지만, 그만큼 비용도 생긴다. 인프라 비용, 운영 비용, 모니터링 비용, 장애 대응 비용, 팀의 학습 비용까지 함께 고려해야 한다.

그래서 이번 고민에서 중요했던 것은 특정 기술을 선택하는 것이 아니었다.

현재 프로젝트에서 감당할 수 있는 비용 안에서, 요청의 책임을 어느 계층에 둘 것인가였다.

중요한 것은 프록시 자체가 아니다.

브라우저, Next.js 서버, Gateway, 백엔드 API 중 어디에 요청의 경계를 둘 것인가.

그리고 그 경계를 선택했을 때 어떤 계층이 어떤 책임과 비용을 가져갈 것인가.

프론트엔드는 이제 화면만 그리는 영역이 아니다.

Next.js 같은 프레임워크를 사용하는 순간, 프론트엔드 서버는 사용자 요청의 진입점이 될 수 있고, 때로는 백엔드 API와 브라우저 사이의 경계를 정리하는 역할도 하게 된다.

도메인이 100개를 넘는 구조에서 내가 마주한 문제는 결국 이것이었다.

**API를 어디서 호출할 것인가가 아니라, 요청의 책임을 어디에 둘 것인가.**
