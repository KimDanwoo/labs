> 아내의 한마디에서 시작해 매주 자동으로 생성되는 베스트셀러 리포트를 만든 과정

아내는 책을 좋아한다.

새로운 책을 발견하는 것도 좋아하고 서점에 들어가 요즘 사람들이 어떤 책을 많이 읽는지 구경하는 것도 좋아한다.

어느 날 아내가 이런 이야기를 했다.

> 서점마다 베스트셀러가 다른데, 한곳에서 같이 볼 수 있으면 좋겠다.

듣고 보니 그랬다.

알라딘에도 베스트셀러가 있고 교보문고와 YES24, 리디에도 있다. 정보가 없는 것은 아니었다. 다만 여러 곳에 흩어져 있었다.

한 서점의 목록만 보면 그 서점에서 인기 있는 책은 알 수 있다. 하지만 여러 서점의 목록을 함께 보면 조금 다른 흐름이 보인다.

여러 곳에서 동시에 높은 순위에 오른 책은 무엇인지, 특정 서점에서만 유독 주목받는 책은 무엇인지 확인할 수 있다.

문제는 이 흐름을 보려면 매번 여러 서점에 들어가 목록을 하나씩 확인해야 한다는 것이었다.

그렇다면 사람이 반복해서 확인하던 일을 대신하고 결과를 한 페이지에 정리해주면 어떨까.

그렇게 주간 베스트셀러 리포트를 만들기 시작했다.

---

## 알라딘 API로 가장 작은 결과부터 만들었다

처음부터 모든 서점을 연결하지는 않았다.

여러 서점의 데이터를 가져오려면 페이지 구조와 데이터 형식, 수집 실패 처리, 동일 도서 판별까지 한꺼번에 고민해야 했다.

실제로 유용한지도 확인하지 않은 상태에서 처음부터 큰 구조를 만들고 싶지는 않았다.

그래서 공식 API를 제공하는 알라딘부터 시작했다.

알라딘 API를 사용하면 제목, 저자, 순위, 카테고리 같은 정보를 일정한 구조로 받을 수 있었다. 화면의 HTML을 분석할 필요도 없고 필요한 필드를 골라 바로 사용할 수 있었다.

```text
알라딘 API 호출
→ 필요한 데이터 변환
→ 베스트셀러 페이지 생성
```

첫 번째 결과는 금방 만들 수 있었다.

책의 제목과 저자, 순위를 정리해 하나의 페이지에 보여줬다. 정해진 주기에 실행하도록 연결하니 새로운 리포트도 자동으로 생성됐다.

생각했던 자동화는 일단 동작했다.

하지만 결과를 직접 보고 나니 처음 해결하려던 문제와 조금 다르다는 것을 알게 됐다.

아내가 원했던 것은 알라딘 베스트셀러를 편하게 보는 페이지가 아니었다.

서점마다 다른 베스트셀러를 한곳에서 비교하는 페이지였다.

첫 번째 버전은 구현으로서는 완성돼 있었지만 처음의 문제에는 절반만 답하고 있었다.

그렇다고 첫 구현이 잘못된 것은 아니었다.

작은 결과를 빠르게 만들었기 때문에 실제로 무엇이 부족한지 확인할 수 있었다.

## 한 서점의 목록에서 여러 서점의 비교로

다음 목표는 분명했다.

```text
한 서점의 베스트셀러
→ 여러 서점의 베스트셀러 비교
```

알라딘 외에 교보문고 YES24, 리디를 추가하기로 했다.

여기서부터는 알라딘 API처럼 한 가지 방법으로 해결할 수 없었다.

각 서점의 페이지가 데이터를 제공하는 방식이 달랐기 때문이다.

처음에는 모든 서점을 같은 방식으로 수집하면 구조가 깔끔할 것이라고 생각했다.

하지만 수집 방식을 통일하는 것 자체는 사용자에게 아무런 가치가 없었다.

중요한 것은 각 서점에서 신뢰할 수 있는 데이터를 가져오는 일이었다.

알라딘은 공식 API를 그대로 사용하는 편이 가장 안정적이었다.

교보문고와 YES24는 실제 브라우저가 페이지를 렌더링한 뒤에야 필요한 정보를 확인하기 쉬웠다.

리디는 오히려 headless 브라우저 접근이 차단돼 서버에서 렌더링된 HTML을 직접 읽는 방식이 더 적합했다.

Playwright는 실제 브라우저를 코드로 조작해 페이지를 렌더링하는 도구이고 SSR HTML은 서버가 미리 완성해서 내려주는 HTML이다.

결국 서점마다 다른 방법을 사용하게 됐다.

```text
알라딘
→ 공식 API

교보문고·YES24
→ Playwright로 페이지 렌더링
→ 페이지 내부 데이터 확인

리디
→ SSR HTML 요청
→ 도서 링크와 텍스트 직접 파싱
```

모든 서점을 하나의 도구로 처리하려고 억지로 맞추지 않았다.

각 사이트에서 가장 적합한 접근 방법을 사용하고 수집이 끝난 뒤의 데이터 형태만 통일했다.

이 과정에서 구현 방식의 일관성과 데이터의 일관성은 다른 문제라는 것을 알게 됐다.

수집 방법이 서로 달라도 이후 단계에서 같은 형태로 다룰 수 있다면 리포트는 일관된 기준으로 만들 수 있었다.

## 외부 페이지의 차이는 수집 단계에 남겼다

각 서점의 원본 데이터를 그대로 리포트 코드로 넘기면, 화면을 만드는 코드가 모든 사이트의 사정을 알아야 한다.

교보문고에서는 어떤 필드가 제목인지 알아야 하고 YES24에서는 다른 구조를 처리해야 한다. 리디의 HTML 구조가 바뀌면 집계와 화면 코드까지 영향을 받을 수 있다.

그래서 서점별 수집 로직은 분리하되, 결과는 비슷한 형태로 반환하도록 맞췄다.

```json
{
    "rank": 1,
    "title": "책 제목",
    "author": "저자",
    "cover": "표지 URL",
    "link": "상세 페이지 URL",
    "genre_key": "novel",
    "source": "알라딘",
}
```

알라딘이 API를 사용했는지, 교보문고가 브라우저에서 데이터를 찾았는지, 리디가 HTML을 직접 파싱했는지는 집계 단계에서 중요하지 않았다.

집계 코드가 알아야 하는 것은 어떤 책이 어느 서점에서 몇 위였는지였다.

처음부터 복잡한 수집기 프레임워크나 클래스 계층을 만들지는 않았다.

실제로 달라지는 부분은 서점별 함수로 분리하고 이후 단계에 필요한 데이터 계약만 맞췄다.

추상화를 먼저 설계하기보다 변경이 발생하는 지점을 확인한 뒤 필요한 만큼만 경계를 나눴다.

## 구조화된 데이터를 찾지 못하면 AI를 폴백으로 사용했다

교보문고와 YES24에서는 먼저 페이지 내부에 구조화된 데이터가 있는지 확인했다.

웹페이지는 사람에게 화면을 보여주기 위해 만들어지지만 내부에서는 렌더링을 위해 JSON 형태의 데이터를 사용하는 경우가 있다.

이 데이터를 찾을 수 있다면 화면에 표시된 문자열을 다시 해석하지 않고 제목, 저자, 상품 식별자 같은 정보를 직접 가져올 수 있다.

하지만 외부 페이지의 구조를 항상 기대할 수는 없었다.

구조화된 값을 찾지 못하는 경우에는 Playwright로 렌더링한 페이지의 텍스트를 읽고 Gemini가 책의 순위와 제목, 저자를 JSON 형태로 정리하는 폴백 경로를 뒀다.

```text
Playwright
→ 실제 페이지 렌더링
→ 페이지 텍스트 추출

Gemini
→ 책의 순위·제목·저자 구조화

코드
→ 응답 형식 확인
→ 공통 데이터로 변환
```

AI가 직접 웹사이트에 접속해 리포트를 만드는 구조는 아니었다.

브라우저 접근은 Playwright가 담당하고 Gemini는 이미 읽어온 텍스트를 정해진 형태로 변환하는 역할을 맡았다.

이 방법은 DOM 선택자 하나가 변경될 때마다 수집 코드 전체가 깨지는 문제를 줄여줬다.

하지만 AI를 사용한다고 페이지 변화에 완벽하게 대응할 수 있는 것은 아니었다.

메뉴와 버튼 문구가 책 정보로 섞일 수 있고 장르를 잘못 판단할 수도 있다. 응답이 자연스럽게 보인다고 해서 실제 데이터가 정확하다는 보장도 없었다.

AI를 붙이는 것보다 중요한 것은 AI가 만든 결과를 어디까지 신뢰할 것인지 정하는 일이었다.

## 네 개의 목록을 모은다고 바로 비교할 수는 없었다

서점별 수집이 가능해지자 네 개의 베스트셀러 목록을 한 페이지에 표시할 수 있게 됐다.

처음에는 순위를 모아 점수를 계산하면 종합 순위를 쉽게 만들 수 있을 것이라고 생각했다.

예를 들어 1위에는 높은 점수를 주고 순위가 내려갈수록 낮은 점수를 주는 방식이었다.

계산 자체는 어렵지 않았다.

문제는 서로 다른 목록의 숫자가 모두 같은 의미인지 확인하지 않았다는 점이었다.

리디에서는 장르별 베스트셀러 목록을 수집하고 있었다.

소설 1위, 경제경영 1위, 자기계발 1위가 각각 존재했다.

이를 다른 서점의 전체 베스트셀러 순위와 함께 합산하자, 리디 1위가 여러 권 생겼다.

코드에서는 모두 같은 숫자 1이었지만 실제 의미는 달랐다.

```text
전체 베스트셀러 1위
≠ 소설 분야 1위
≠ 자기계발 분야 1위
```

값의 타입과 범위가 같다고 해서 같은 데이터는 아니었다.

종합 순위에는 각 서점의 전체 베스트셀러 순위만 사용하고 장르별 순위는 장르별 비교에만 사용하도록 계산 경로를 분리했다.

리디 전체 베스트셀러는 페이지에서 확인할 수 있는 범위가 다른 서점보다 적었다.

이를 억지로 같은 개수까지 맞추기보다, 리디는 제공되는 범위까지만 집계된다는 사실을 리포트에 표시했다.

서로 다른 데이터를 비교할 때는 차이를 감추지 않고 어디까지 같은 기준으로 비교할 수 있는지 명확하게 보여줘야 했다.

## 자동화가 첫 번째 리포트를 만들었다

여러 서점의 데이터를 수집하고 순위를 합산한 뒤, 처음으로 네 개 서점이 포함된 리포트가 생성됐다.

표에는 책의 제목과 저자, 장르, 각 서점의 순위가 함께 표시됐다.

이제 아내는 여러 사이트를 돌아다니지 않고 한 페이지에서 베스트셀러를 비교할 수 있었다.

처음 생각했던 결과에 가까워졌다.

하지만 실제 리포트를 읽어보니 이상한 부분들이 보이기 시작했다.

에세이 목록에 파크골프 표준교재가 1위로 올라와 있었다.

코스모스와 코스모스 100만 부 기념판은 서로 다른 책으로 계산됐다.

유럽 도시 기행 3과 부제, 사인본 정보가 포함된 제목 역시 별개의 책으로 잡혔다.

제목에 `|`가 포함된 책은 마크다운 표의 열까지 깨뜨렸다.

자동화는 정상적으로 실행됐고 오류도 발생하지 않았다.

하지만 결과는 정확하지 않았다.

자동화는 실패하지 않았다.

내가 작성한 잘못된 기준을 매주 반복하고 있었다.

## 페이지가 열렸다는 것과 데이터가 맞다는 것은 다르다

파크골프 표준교재가 에세이 1위에 들어간 원인은 알라딘의 에세이 카테고리 ID를 잘못 사용한 것이었다.

API 호출은 성공했다.

응답도 정상적인 JSON이었고 제목과 저자도 모두 존재했다.

단지 내가 잘못된 카테고리를 요청하고 있었다.

기술적인 성공 여부만 확인했다면 발견하기 어려운 문제였다.

장르를 분류하는 방식에도 문제가 있었다.

초기에는 제목과 카테고리 문자열에 특정 키워드가 포함돼 있는지를 기준으로 장르를 판단했다.

그러자 과학>천문학이라는 카테고리가 문학이라는 일부 문자열 때문에 소설로 분류되는 일이 생겼다.

건강/취미>스포츠는 건강이라는 단어 때문에 과학기술로 분류됐다.

키워드를 더 추가한다고 해결될 문제는 아니었다.

오히려 조건이 많아질수록 우연히 겹치는 문자열도 늘어났다.

그래서 장르를 판단하는 순서를 바꿨다.

먼저 공식 카테고리 경로를 확인하고 명확하게 매핑할 수 있는 대분류가 있다면 그 값을 사용했다.

리포트의 장르에 포함하지 않을 카테고리는 먼저 제외했다.

카테고리 정보만으로 판단할 수 없을 때만 제목과 텍스트의 키워드를 폴백으로 사용했다.

```text
카테고리 경로 확인
→ 명시적 장르 매핑
→ 제외 대상 판정
→ 판단할 수 없을 때 키워드 사용
```

더 신뢰할 수 있는 정보에 우선순위를 부여하자 조건을 계속 추가할 때보다 정확도가 높아졌다.

## 같은 책을 같은 책으로 판단하는 기준: 제목 정규화

여러 서점의 데이터를 비교하려면 같은 책을 하나로 묶어야 했다.

하지만 같은 책도 서점마다 다르게 표시됐다.

```text
코스모스

코스모스 (100만 부 기념판)

개정판 | 빅터 프랭클의 죽음의 수용소에서

빅터 프랭클의 죽음의 수용소에서
```

문자열이 완전히 같을 때만 동일한 책으로 판단하면 같은 책이 여러 개로 분리된다.

반대로 괄호와 부제, 에디션 정보를 모두 제거하고 제목이 비슷하면 무조건 합치는 것도 위험했다.

서로 다른 책이나 판본을 하나로 합칠 수 있기 때문이다.

사용자에게 보여줄 원본 제목과 비교에 사용할 제목을 분리했다.

비교용 제목에서는 공백과 특수문자를 정리하고 개정판, 특별판, 기념판, 리커버, 사인본 같은 에디션 표현을 제거했다.

괄호 안에 들어간 판본 정보도 비교용 키에서는 제외했다.

다만 제목이 일부 비슷하다는 이유만으로 합치지는 않았다.

저자가 같은 경우에만 제목의 접두사가 일치하는지 확인했고 너무 짧은 제목은 다른 책과 잘못 합쳐질 가능성이 있어 최소 길이 조건을 뒀다.

```text
원본 제목
→ 에디션 표현 제거
→ 공백·특수문자 정리
→ 비교용 제목 생성
→ 저자 확인
→ 충분히 긴 제목만 접두사 비교
```

같은 서점에서 일반판과 특별판이 동시에 잡히는 경우에는 가장 높은 순위만 반영했다.

두 항목의 점수를 모두 더하면 한 서점이 같은 책에 두 번 투표한 것처럼 계산되기 때문이다.

정규화는 문자열을 깨끗하게 만드는 작업이 아니었다.

서로 다른 표현을 어디까지 같은 의미로 볼 것인지 정하는 일이었다.

---

## 수집이 끝나도 파이프라인은 끝나지 않았다

수집과 집계가 끝난 결과는 마크다운 표로 생성됐다.

여기서도 예상하지 못한 문제가 생겼다.

책 제목에 `|`가 포함되면 마크다운이 이를 표의 열 구분자로 해석했다.

```text
개정판 | 빅터 프랭클의 죽음의 수용소에서
```

데이터는 정상적으로 수집됐지만 최종 화면에서는 표가 깨졌다.

마크다운 셀에 들어가는 제목과 저자의 파이프 문자를 이스케이프해 해결했다.

링크도 그대로 사용하지 않았다.

교보문고와 YES24에서 개별 도서 링크를 찾지 못한 경우, 베스트셀러 목록 페이지의 주소가 들어올 수 있었다.

목록 페이지를 책의 상세 링크처럼 표시하지 않도록 상세 페이지라고 판단할 수 있는 링크만 제목에 연결했다.

외부 페이지에서 가져온 제목과 저자도 안전한 문자열이라고 가정할 수 없었다.

수집한 문자열이 HTML이나 마크다운으로 렌더링되는 구조라면 사용자 입력을 다루는 것과 비슷한 수준으로 경계해야 했다.

자동화의 품질은 데이터를 가져오는 단계에서 끝나지 않았다.

사용자가 실제로 보게 되는 마지막 화면까지 포함해야 했다.

---

## 결과물의 성격을 보고 Astro를 선택했다

리포트를 어떤 방식으로 제공할지도 고민했다.

익숙한 React 기반 프레임워크로 애플리케이션을 만들 수도 있었다.

하지만 사용자가 이 페이지에서 하는 일은 대부분 이미 생성된 결과를 읽는 것이었다.

로그인도 없고 사용자의 입력에 따라 데이터가 실시간으로 바뀌지도 않는다.

베스트셀러 데이터는 일주일에 한 번 갱신된다.

사용자가 페이지에 들어올 때마다 네 서점에 다시 접근하거나, 서버에서 같은 순위를 반복해서 계산할 이유가 없었다.

이 서비스는 실시간 애플리케이션보다 매주 새롭게 발행되는 문서에 가까웠다.

그래서 Astro를 선택했다.

```text
주간 자동화 실행
→ 서점별 데이터 수집
→ 정규화와 순위 계산
→ 마크다운 리포트 생성
→ Astro 정적 페이지 빌드
```

사용자가 페이지에 접근하는 시점에는 모든 작업이 이미 끝나 있다.

브라우저는 완성된 HTML을 받아 보여주면 된다.

이번 프로젝트에서 Astro가 빨랐던 이유를 단순히 프레임워크의 성능으로만 설명하고 싶지는 않다.

더 중요한 것은 실행 시점을 옮긴 일이었다.

```text
사용자 접속 후 실행
수집 → 계산 → 렌더링

대신

자동화 실행 시점
수집 → 계산 → 페이지 생성

사용자 접속 시점
완성된 결과 전달
```

빠른 페이지는 실행 속도를 계속 최적화하는 것만으로 만들어지는 것이 아니었다.

사용자가 기다리는 동안 실행할 필요가 없는 일을 제거하는 것에서 시작했다.

빌드 시점에 미리 만들어 두는 접근은 [링크 미리보기 이미지를 빌드할 때 만들기](/posts/build-time-og-images/)에서도 썼고 Astro로 블로그를 옮긴 과정은 [티스토리 글 29편을 Astro 블로그로 옮기며](/posts/tistory-to-astro/)에 적었다.

---

## GitHub Actions로 매주 한 번 실행하고 기록으로 남겼다

기술적으로는 매일 새로운 리포트를 만들 수도 있었다.

하지만 실행 횟수가 많다고 더 좋은 자동화는 아니다.

베스트셀러는 실시간 주가처럼 몇 분 단위의 변화가 중요한 데이터가 아니다.

이 프로젝트의 목적은 지금 이 순간의 순위를 보여주는 것이 아니라, 여러 서점에서 어떤 책이 주목받고 있는지를 주기적으로 확인하는 것이었다.

그래서 매주 월요일 한 번 실행하도록 했다.

GitHub Actions가 Python 환경과 Playwright 브라우저를 준비하고 수집 스크립트를 실행한다.

리포트가 생성되면 날짜가 포함된 브랜치를 만들고 변경된 콘텐츠를 커밋한 뒤 PR을 생성해 머지한다.

```text
매주 자동 실행
→ 데이터 수집
→ 마크다운 생성
→ 브랜치와 커밋 생성
→ PR 생성
→ 머지
```

결과 파일은 날짜별 경로에 저장된다.

```text
contents/book/2026-07-27-bestseller/index.md
```

Astro는 콘텐츠를 읽어 각각의 정적 페이지를 생성한다.

```text
/book/2026-07-27-bestseller/
```

매번 최신 페이지를 덮어쓰지 않고 각 주의 결과가 하나의 콘텐츠로 축적된다.

자동화의 결과가 JSON이나 실행 로그에서 끝나는 것이 아니라, 사람이 읽고 다시 확인할 수 있는 기록으로 남는다.

---

## 자동화가 새로운 문제를 보여줬다

처음에는 자동화의 목적을 반복 작업을 없애는 것이라고 생각했다.

사람이 매주 네 서점에 들어가 목록을 확인하지 않아도 되는 것.

하지만 실제로 리포트가 반복해서 생성되자 자동화는 다른 역할을 하기 시작했다.

내가 만든 기준을 검증하는 피드백 루프가 됐다.

```text
자동화 실행
→ 실제 리포트 생성
→ 이상한 결과 발견
→ 분류·집계 기준 수정
→ 다음 결과에서 다시 확인
```

파크골프 표준교재가 에세이 목록에 들어간 것도 실제 페이지가 만들어졌기 때문에 발견할 수 있었다.

동일한 책이 판본 차이로 분리되는 문제와 장르별 순위가 전체 순위를 왜곡하는 문제도 결과를 직접 읽는 과정에서 보였다.

처음부터 모든 예외를 예상해 완벽한 구조를 만든 것은 아니었다.

작은 결과를 만들고 실제로 사용하고 이상한 결과를 발견한 뒤 기준을 다시 세웠다.

프로젝트가 커졌다기보다 실제로 사용하면서 책임져야 할 기준이 하나씩 생겼다.

---

## 실패하지 않았다고 성공한 것은 아니었다

브라우저 자동화는 언제든 실패할 수 있다.

페이지 응답이 느릴 수 있고 내부 데이터 구조가 바뀔 수도 있다. 봇 차단 방식이 달라지거나 Gemini가 예상과 다른 형식으로 응답할 수도 있다.

현재는 하나의 서점에서 수집이 실패해도 다른 서점의 데이터로 리포트를 생성할 수 있도록 실패 범위를 나눠뒀다.

하지만 이것만으로 충분한 것은 아니다.

네 서점 중 하나만 정상적으로 수집돼도 종합 리포트라고 부를 수 있는지, 수집된 도서가 지나치게 적을 때도 페이지를 발행해야 하는지 별도의 기준이 필요하다.

앞으로는 다음과 같은 검증을 추가할 수 있다.

```text
서점별 최소 수집 개수
빈 제목과 저자의 비율
순위 중복과 누락
이전 결과 대비 비정상적인 변화
필수 서점의 수집 성공 여부
```

페이지를 정상적으로 열었다는 것과 올바른 데이터를 가져왔다는 것은 다르다.

GitHub Actions가 초록색으로 끝났다는 것과 사용자에게 정확한 리포트를 제공했다는 것도 다르다.

자동화의 성공 조건은 프로세스가 오류 없이 종료됐는지가 아니라, 결과가 사용할 수 있는 품질인지까지 포함해야 했다.

---

## 마무리: 모으는 일보다 기준을 정하는 일

처음에는 아내가 여러 서점의 베스트셀러를 한곳에서 보고 싶다고 했다.

가장 작은 결과를 확인하기 위해 알라딘 API로 첫 페이지를 만들었다.

실제로 사용해보니 한 서점의 목록만으로는 처음의 문제를 해결할 수 없었다.

교보문고와 YES24, 리디를 추가했고 각 사이트의 상황에 맞춰 API와 Playwright, SSR HTML 파싱을 함께 사용했다.

서점별로 다른 수집 방식은 수집 단계에 남기고 이후에는 같은 형태의 데이터로 비교할 수 있도록 맞췄다.

하지만 데이터를 모으는 것만으로 리포트가 완성되지는 않았다.

전체 순위와 장르별 순위는 같은 숫자여도 의미가 달랐다.

같은 책은 서점마다 다른 제목으로 표시됐고 단순한 키워드 분류는 예상하지 못한 오분류를 만들었다.

자동화는 내가 작성한 기준을 그대로 반복했다.

기준이 잘못돼 있으면 잘못된 결과도 더 빠르고 꾸준하게 만들어졌다.

그래서 이 프로젝트에서 가장 중요했던 것은 어떤 기술을 사용했는지가 아니었다.

어떤 데이터가 더 신뢰할 수 있는지, 서로 다른 값을 어디까지 같은 기준으로 비교할지, 같은 책을 어떤 조건에서 하나로 묶을지 결정하는 일이었다.

알라딘 API는 가능성을 빠르게 확인하기 위해 사용했다.

Playwright는 브라우저에서만 확인할 수 있는 정보를 읽기 위해 사용했다.

Gemini는 구조화된 데이터를 찾지 못했을 때 페이지 텍스트를 정리하는 폴백으로 사용했다.

리디에는 브라우저 자동화를 고집하지 않고 SSR HTML 파싱을 선택했다.

Astro는 익숙한 프레임워크여서가 아니라, 미리 생성되고 빠르게 읽혀야 하는 리포트의 성격에 맞는 선택이었다.

처음부터 이 기술들을 모두 사용하려고 계획하지는 않았다.

실제 결과를 만들고 부족한 부분을 확인하는 과정에서 각 기술이 필요한 자리가 생겼다.

매주 새로운 베스트셀러 리포트가 생성된다.

아내는 여러 서점의 순위를 한곳에서 확인할 수 있다.

그리고 나는 이 프로젝트를 통해 다시 확인했다.

자동화는 단순히 반복 작업을 대신 실행하는 코드가 아니다.

사람이 해오던 판단을 코드로 옮기고 그 판단이 틀렸을 때 실제 결과를 통해 발견하고 다시 고칠 수 있도록 만드는 구조다.

아직 고도화 중인 프로젝트로, 실제로 사용하면서 필요한 기능과 데이터 검증 기준을 계속 보완해나갈 예정이다. 사용하면서 불편한 점이나 개선 아이디어가 있다면 편하게 의견을 남겨 주면 감사하겠다.
