## 1. 설치할 때의 이유가 계속 유효한지 궁금해졌다

OMC(oh-my-claudecode)는 오케스트레이션을 기대하며 설치했다. 작업을 나누고 적절한 에이전트에 맡기는 과정을 도와주면 좋겠다고 생각했다. 포니테일(Ponytail)에는 토큰 사용량 최적화를 기대했다. AI에게 맡기는 일이 늘어나는 상황에서 둘 다 써볼 만한 도구였다.

그런데 시간이 지나면서 다시 살펴볼 이유가 생겼다. Claude Code 자체에서 오케스트레이션을 지원하는 범위가 늘었다. 내 하네스에 이미 적어둔 YAGNI 원칙과 포니테일의 규칙이 겹치는 부분도 있었다. 기존 하네스를 구축하는 과정에서 서브에이전트가 Sonnet 4.6을 사용하도록 설정돼 있다는 점을 확인한 것도 크게 걸렸다. 특히 리뷰와 검증을 어느 모델에 맡길지는 내가 확인하고 선택하고 싶었다.

실제로 동작이 꼬이거나 작업이 실패한 일은 없었다. 여러 설정과 기본 기능의 변화를 함께 살펴본 뒤 OMC와 포니테일의 사용을 중단하고 환경을 정리했다. 제거 전후의 토큰 사용량을 같은 조건으로 비교하지는 않았으므로 비용이 줄었다는 결론도 낼 수 없다.

그 과정에서 도구를 설치하는 것으로 구성이 끝나지는 않는다고 느꼈다. 여기서 말하는 하네스는 프로젝트 지침, 스킬, 훅, 에이전트 설정처럼 AI의 작업 방식을 정하는 환경이다. 설치할 때 필요했던 구성이 지금도 내 작업에 맞는지는 계속 확인할 일이다.

## 2. 기본 도구가 발전하면 추가 도구의 역할도 다시 봐야 한다

OMC를 다시 본 이유 중 하나는 Claude Code의 기본 오케스트레이션이었다. 공식 [서브에이전트 문서](https://code.claude.com/docs/en/sub-agents#understand-automatic-delegation)는 Claude가 요청한 작업, 에이전트의 설명과 현재 문맥을 보고 자동으로 위임한다고 설명한다. 메인 세션이 일을 나눠 맡기고 결과를 받는 흐름을 기본으로 지원한다.

여러 세션을 조율하는 Agent Teams도 있다. [공식 변경 기록](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md#2132)에는 2.1.32에서 연구 미리보기로 도입했다고 적혀 있다. 작성 시점에도 기본으로 꺼진 실험 기능이며 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`로 활성화한다. 활성화한 대화형 세션에서는 Claude가 이름을 붙여 호출한 에이전트가 팀원으로 실행되는 등 팀을 명시적으로 요청하지 않아도 팀이 만들어질 수 있다. [Agent Teams 문서](https://code.claude.com/docs/en/agent-teams)는 작업 목록과 메시지를 통한 협업 방식도 설명한다.

이 변화만으로 OMC의 역할을 전부 설명할 수는 없다. OMC의 [공식 저장소](https://github.com/Yeachan-Heo/oh-my-claudecode)는 작업 실행 흐름과 팀 조율 같은 기능을 제공한다. 기본 도구에 위임 기능이 생겼더라도 계획부터 실행과 검증까지 반복하는 방식을 미리 갖추고 싶다면 추가 도구의 도움이 남을 수 있다.

그래서 현재는 Claude Code와 Codex의 기본 실행 환경에 내가 관리하는 지침과 스킬을 연결하는 구성을 택했다. Claude Code가 기본으로 제공하는 작업 위임을 먼저 살펴보고 이미 둔 YAGNI와 프로젝트 구조 규칙을 정리하며 리뷰·검증에 적용되는 모델 설정을 직접 확인하려는 선택이다.

추가 도구에는 미리 갖춘 개발 절차와 편의 기능이 있다. 그만큼 그 도구가 더하는 규칙, 모델 선택과 실행 절차도 내 설정과 함께 검토해야 한다. 지금은 공통 지침의 원본과 도구별 진입점을 직접 관리하면서 어떤 설정을 바꿨는지 추적할 수 있는 범위부터 정리하기로 했다. 반복해서 필요한 기능이 드러나면 그 기능을 제공하는 도구를 다시 검토할 수 있다.

기본 도구를 사용하면 성능이나 비용이 더 좋다는 비교 결과가 있는 것은 아니다. 기본 도구의 업데이트도 계속 확인해야 한다. 우선 이 구성을 기준으로 실제 작업을 비교해 추가 도구가 줄여주는 일과 새로 관리할 설정을 함께 판단하려 한다.

## 3. 도구 이름보다 맡길 역할부터 나눠봤다

공식 문서로 범위를 넓혀보니 같은 하네스라고 부르는 도구들도 맡는 일이 달랐다. 개발 절차를 정하거나 작업 상태를 남기는 도구가 있고 명세·기억·도구 출력을 관리하는 도구도 있었다. 여러 역할을 함께 제공하기도 하므로 내가 필요한 역할과 그 결과를 확인할 질문을 짝지어 봤다.

| 필요한 역할           | 살펴본 도구·구성           | 다시 검증할 질문                                     |
| --------------------- | -------------------------- | ---------------------------------------------------- |
| 작업 위임과 실행 조율 | Claude Code 기본 기능, OMC | 필요한 일을 나눠 맡기고 결과를 빠짐없이 모으는가     |
| 개발 절차와 진행 상태 | [Superpowers](https://github.com/obra/superpowers), [GSD](https://github.com/gsd-build/get-shit-done/blob/main/docs/ARCHITECTURE.md) | 작업 규모에 맞는 절차이며 세션이 바뀌어도 이어지는가 |
| 규칙과 개발 환경 구성 | [ECC](https://github.com/affaan-m/ECC), 포니테일 | 기존 규칙과 어떻게 합쳐지고 어떤 범위에 적용되는가 |
| 명세와 변경 관리 | [OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/overview.md) | 요구사항·명세·코드가 같은 동작을 설명하는가 |
| 세션 간 기억 | [Claude-Mem](https://github.com/thedotmack/claude-mem) | 필요한 기억을 찾으며 바뀐 결정을 구분할 수 있는가 |
| 도구 출력과 문맥 관리 | [Context Mode](https://github.com/mksglu/context-mode) | 필요한 근거를 조회하면서 실제 진단 품질을 유지하는가 |

포니테일도 로컬의 4.8.4 버전 [스킬 정의](https://github.com/DietrichGebert/ponytail/blob/16f29800fd2681bdf24f3eb4ccffe38be3baec6b/skills/ponytail/SKILL.md)를 읽어봤다. 구현 필요성을 검토하고 기존 코드·표준 라이브러리를 우선하는 원칙이 있었다. 파일 수 최소화 지침은 컴포넌트마다 파일을 나누는 내 FSD 규칙과 함께 살펴볼 부분이었다. 명시한 요구사항을 보존하라는 지침도 있으므로 충돌을 단정하기보다 실제 결과가 프로젝트 구조를 지키는지 확인해야 한다.

예를 들어 세션을 넘길 때마다 결정의 배경을 다시 설명하는 일이 문제라면 작업 상태나 기억을 남기는 방식부터 볼 수 있다. 작은 수정에도 긴 계획 절차를 거치는 일이 부담이라면 그 절차를 적용하는 조건을 봐야 한다. 필요한 역할을 정하면 설치할 도구뿐 아니라 생략하거나 조정할 기능도 고를 수 있다.

## 4. 업데이트는 버전 숫자 외의 동작도 바꾼다

공식 문서의 변경 사례를 보면 재검토할 이유가 더 구체적으로 드러난다. 아래는 내가 직접 겪은 장애가 아니라 각 프로젝트가 설명한 변경 내용이다.

Superpowers의 [릴리스 노트](https://github.com/obra/superpowers/blob/main/RELEASE-NOTES.md)는 7.0.1에서 질문 전에 프로젝트 문맥을 살피도록 브레인스토밍 절차를 조정했다고 설명한다. 같은 버전에서 긴 스킬이 Claude Code의 문맥 압축 이후 잘리는 문제를 다루기 위해 일부 내용을 참조 문서로 분리한 변경도 기록한다. 질문 방식이나 규칙을 읽는 구조도 업데이트 대상인 셈이다.

이런 업데이트를 적용했다면 내 작업에서도 달라진 동작을 봐야 한다. 이미 문서에 답이 있는 질문을 다시 하는지, 작은 수정에 어떤 절차를 적용하는지, 긴 작업에서 리뷰와 종료 조건을 계속 따르는지 확인할 수 있다. 도구가 업데이트됐다는 사실과 내가 원하는 동작이 유지된다는 판단은 각각 확인해야 한다.

ECC의 [1.x에서 2.0으로의 이전 안내](https://github.com/affaan-m/ECC/blob/main/docs/MIGRATION-1X-TO-2.0.md)에는 저장소 이름과 플러그인 식별자가 바뀐 내용이 있다. 기존 `everything-claude-code@everything-claude-code`와 새 `ecc@ecc`를 함께 남겨두면 서로 다른 플러그인으로 인식돼 스킬·명령·훅 실행이 중복된다고 안내한다. 이 경우 업데이트 검증에는 새 버전의 기능 확인과 이전 설치 상태 확인이 모두 포함된다.

프로젝트 안에 생성된 파일까지 업데이트해야 하는 경우도 있다. OpenSpec의 [업그레이드 안내](https://github.com/Fission-AI/OpenSpec/blob/main/docs/faq.md#how-do-i-upgrade)는 패키지를 올린 뒤 각 프로젝트에서 `openspec update`를 실행해 생성된 스킬과 명령을 갱신하도록 설명한다. 프로그램 버전 확인만으로는 프로젝트가 읽는 절차까지 갱신됐는지 알 수 없는 사례다.

기반 도구의 설정 해석도 바뀐다. Claude Code의 [모델 선택 문서](https://code.claude.com/docs/en/sub-agents#choose-a-model)는 2.1.251 이전에는 `CLAUDE_CODE_SUBAGENT_MODEL` 환경변수가 호출별 모델과 에이전트 정의보다 우선했다고 설명한다. 현재 문서의 기본 우선순위는 호출별 지정, 에이전트 정의, 해당 환경변수, 메인 모델 순서다. 설정 파일을 바꾸지 않았더라도 버전에 따라 적용되는 값이 달라질 수 있는 사례다.

내 로컬의 `code-reviewer.md`와 `verifier.md`에도 `model: sonnet`이 남아 있다. 이 별칭만으로 당시 실제 실행 모델의 정확한 버전을 증명할 수는 없다. 기존 하네스에서 Sonnet 4.6 설정을 확인한 경험을 현재 도구 전체의 기본값으로 일반화해서도 안 된다. 모델 이름을 적어둔 파일과 실행에 적용된 모델을 함께 확인해야 한다.

## 5. 직접 만든 지침도 프로젝트보다 늦어질 수 있다

![규칙 카드와 노트를 펼쳐 놓고 설정을 정리하는 모습](./settings-ownership.webp)

외부 도구와 같은 기준으로 내가 만든 지침도 봐야 한다. 직접 작성했다는 사실이 현재 프로젝트와 계속 맞는다는 보장은 없다.

이번 글을 작성하면서 확인한 예가 블로그 이미지 규칙이다. 이 저장소는 본문과 표지 이미지를 WebP로 바꿨다. 썸네일 생성 스크립트 `make-thumbnails.ts`도 `cover.webp`를 읽는다. 그런데 글 작성 절차를 담은 `dansoon-post/SKILL.md`에는 여전히 `cover.jpg`와 JPG 변환 안내가 남아 있었다. 목록과 링크 미리보기에 쓰는 `thumbnail.jpg`는 따로 유지하고 있다.

실제 자산과 스크립트는 바뀌었는데 에이전트가 읽는 절차는 이전 형식을 설명하고 있었다. 이런 차이를 찾아 지침도 함께 고쳐야 한다. 구현 파일을 고치는 것과 AI가 다음 작업에서 참고할 지침을 맞추는 일을 한 변경으로 생각할 필요가 있다.

YAGNI 규칙도 같은 맥락이다. 여러 곳에 같은 원칙이 있으면 어디에서 관리할지, 프로젝트별 예외를 어디에 둘지 정할 수 있다. 중복 자체가 오류는 아니지만 프로젝트의 기준을 바꿀 때 함께 검토할 곳은 알아야 한다. 지금 남아 있는 `AGENTS.md`, 글 작성 스킬과 패키지 매니저 사용을 제한하는 훅도 계속 점검할 대상이다.

## 6. Claude와 Codex가 읽을 지침도 함께 정리했다

설정을 다시 보는 동안 Claude에 둔 지침을 Codex도 읽는지 확인했다. 공통으로 적용하고 싶은 규칙이 있어도 각 도구가 읽는 파일과 적용 범위를 맞춰야 했다.

Codex의 [프로젝트 지침 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md)는 전역 지침과 저장소부터 현재 작업 디렉터리까지의 `AGENTS.md`를 읽는 순서를 설명한다. Claude Code는 [메모리 문서](https://code.claude.com/docs/en/memory#imports)에 나온 `@경로` 문법으로 `CLAUDE.md`에서 다른 파일을 가져올 수 있다. 이 저장소에서는 `CLAUDE.md`에 `@AGENTS.md`를 두어 공통 문서를 읽도록 연결했다.

일반적인 프론트엔드 규칙은 직접 관리하는 하네스의 `.claude/rules/`를 원본으로 두고 `AGENTS.md`의 정해진 영역에 생성하도록 했다. 저장소의 구체적인 규칙은 그 영역 밖에 남겼다. 일반 규칙에서 쓰는 `pages` 대신 이 저장소에서 쓰는 `views`처럼 프로젝트의 선택이 분명한 부분은 프로젝트 규칙을 우선하도록 적었다. 공통 원칙을 바꿀 때 수정할 원본과 프로젝트의 예외를 둘 위치를 구분했다.

문서 크기도 확인했다. 전역·저장소·가장 큰 앱 지침을 합치면 약 54KB였다. Codex의 기본 지침 한도인 32KiB보다 커서 저장소 설정의 `project_doc_max_bytes`를 64KiB로 늘렸다. 다만 읽을 수 있는 분량을 늘렸다고 규칙을 더 잘 따른다는 뜻은 아니다. Claude 문서도 긴 지침의 문맥 비용을 설명하며 특정 작업에만 필요한 내용은 범위를 나누도록 권한다. 공통 규칙을 연결한 뒤에도 중복과 불필요한 내용을 줄일 여지는 남는다.

규칙 문서를 공유하는 것과 훅을 실행하는 것은 별개다. 이 저장소의 Claude용 패키지 매니저 검사 훅을 `AGENTS.md`에서 언급한다고 Codex에도 같은 검사가 등록되지는 않는다. 도구마다 읽을 지침, 발견할 스킬, 실제로 실행할 훅을 따로 확인해야 한다.

현재 확인한 범위는 설치 상태, 생성된 규칙의 일치 여부, 업데이트를 다시 실행해도 기존 프로젝트 규칙이 유지되는지까지다. 새 Claude·Codex 세션에서 같은 작업을 수행해 지침 준수까지 비교한 것은 아니다. 파일을 연결한 결과와 실제 행동을 검증한 결과는 구분해서 남기려 한다.

## 7. 변경 전후를 비교할 작업을 남겨두려 한다

설정 파일을 읽는 것만으로는 부족하다. [Anthropic의 에이전트 평가 글](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)도 에이전트를 평가할 때 모델과 하네스가 함께 작동한 결과를 본다고 설명한다. 내 환경에서도 무엇을 설치했는지와 함께 실제로 어떤 결과를 내는지 확인해야 한다.

개인 프로젝트라면 평소 반복하는 작업 몇 개를 비교 대상으로 삼는 데서 시작할 수 있다. 아래는 점검을 구성하는 예시다. 아직 이 과정을 반복 측정하는 체계까지 만든 것은 아니다.

| 비교할 작업                    | 확인할 결과                                  | 함께 기록할 부분                                    |
| ------------------------------ | -------------------------------------------- | --------------------------------------------------- |
| 범위가 정해진 작은 수정        | 요청한 동작을 고치고 관련 검사를 통과하는지  | 불필요한 변경, 확인 요청과 사람이 다시 고친 내용    |
| 여러 파일을 바꾸는 리팩터링    | 기존 동작과 프로젝트 구조를 유지하는지       | 위임 범위, 누락된 요구사항, 리뷰 후 수정량          |
| 알려진 문제가 있는 변경의 리뷰 | 문제를 근거와 함께 찾고 잘못된 지적은 없는지 | 실제 실행 모델, 발견·누락·오탐한 항목               |
| 과거 결정이 필요한 후속 작업   | 관련 근거를 찾고 현재 바뀐 조건을 반영하는지 | 조회된 기억의 출처, 오래된 결정으로 생긴 재작업     |
| 긴 로그를 분석하는 작업        | 원문 근거를 찾아 같은 문제를 진단하는지      | 조회한 출력의 범위, 누락된 근거, 진단 결과와 사용량 |

가령 폼의 빈 입력값 검증을 추가하는 작은 수정을 비교 대상으로 정할 수 있다. 같은 커밋에서 시작해 요청과 완료 조건을 같게 주고 기존 하네스와 변경한 하네스로 각각 실행한다. 입력 검증이 동작하는지와 관련 검사를 통과하는지 본 뒤 요청하지 않은 추상화, 다른 파일의 수정, 사람이 다시 고친 부분을 비교한다. 에이전트가 계획을 길게 작성했는지보다 그 절차가 실제 누락을 줄였는지 확인하는 방식이다. 아직 수행하지 않은 비교 예시이므로 결과 수치는 없다.

비교할 때는 바꾸기 전 설정을 남겨둘 생각이다. 기반 도구와 플러그인 버전, 적용한 규칙, 실행 모델도 함께 기록해야 나중에 차이를 해석할 수 있다. 모델과 규칙, 실행 절차를 한꺼번에 바꾸면 무엇 때문에 결과가 달라졌는지 알기 어려우니 가능한 한 변경 범위를 나눠보려 한다.

결과 코드와 검증 명령뿐 아니라 전체 작업 시간, 제공되는 토큰 사용량, 사람이 다시 검토하고 수정한 내용도 볼 필요가 있다. 리뷰를 한 번 더 수행해 토큰은 늘었지만 사람이 놓칠 문제를 찾았다면 그 검토가 내게 가치 있는지도 판단할 수 있다. 병렬 실행 역시 팀원마다 문맥을 사용하므로 속도와 사용량을 함께 봐야 한다. [Agent Teams 문서](https://code.claude.com/docs/en/agent-teams#token-usage)도 단일 세션보다 토큰을 더 사용한다고 설명한다.

한 번 잘된 결과를 기준으로 삼기도 어렵다. 비슷한 작업을 반복하고 실행 기록과 산출물을 같이 보면서 개선인지 우연인지 판단하려 한다. 문제가 생겼을 때 이전 설정으로 돌아가 비교할 수 있도록 변경 내역도 남겨두려 한다.

## 정리

OMC와 포니테일을 설치할 때는 필요한 역할이 있었다. 이후 Claude Code의 기본 기능이 늘었고 내 규칙과 모델 설정도 다시 살펴보게 됐다. 이번에는 두 도구를 걷어냈지만 다른 상황에서는 설정을 조정하거나 추가 도구를 유지하는 선택이 맞을 수 있다.

이번에 손댄 것도 공통 지침의 원본과 Claude·Codex의 진입점이다. 다음에는 같은 작업에서 그 지침이 적용되는지, 빠뜨리는 요구사항과 사람이 다시 고치는 부분이 줄어드는지 확인하려 한다.

[AI에게 코드를 맡기기 위한 위임의 조건](/posts/delegating-code-to-ai/)에서는 프로젝트의 기준과 결과 검증을 다뤘다. 그 기준은 내가 고른 하네스에도 적용된다. 설치할 때의 기대를 적어두고 업데이트 뒤에도 그 역할을 하는지 확인하려 한다. OMC와 포니테일을 뺀 결정도 다음에 필요한 기능이 생기면 다시 검토할 수 있다.
