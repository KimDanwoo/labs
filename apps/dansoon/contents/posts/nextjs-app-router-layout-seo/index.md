## 레이아웃과 라우팅 설계가 운영에 미치는 영향

Next.js App Router를 사용하다 보면, 폴더 구조나 컴포넌트 분리보다 먼저 고민하게 되는 부분이 있습니다.

바로 레이아웃 설계와 라우팅 방식이 실제 서비스 운영에 어떤 영향을 주는지에 대한 문제입니다.

처음에는 저도 UI 구조만 고민했습니다.

어떤 컴포넌트를 어디에 둘지, 레이아웃을 얼마나 세분화할지 같은 것들이었습니다.

하지만 실제 운영 환경에 배포해보니, 이 선택들이 SSR 타이밍, 데이터 패칭 위치, 캐시 전략, 그리고 SEO까지 전부 좌우하는 요소임을 체감하게 됐습니다.

레이아웃 트리는 한 번 틀어지면 나중에 되돌리기 쉽지 않은 구조이기도 합니다.

그래서 지금은 UI 구성 요소가 아니라 서비스의 뼈대라는 관점으로 레이아웃과 라우팅을 설계하는 편입니다.

## 1\. Nested Layout은 공통 UI만 묶는 게 아니다

App Router의 layout은 처음에는 단순히 공통 UI를 묶는 용도로 보일 수 있습니다.

하지만 실제 서비스 규모가 커질수록 layout 트리가 SSR 트리로 그대로 연결된다는 점을 실감하게 됩니다.

어떤 레이어에서 SSR이 돌고, 어떤 데이터가 언제 패칭되는지, 페이지 이동 시 어떤 부분이 유지되고 어떤 부분이 재평가되는지가 모두 layout 레벨에서 결정됩니다.

실무에서 느낀 장점은 분명했습니다.

-   공통 데이터는 상위 레이아웃에서 한 번만 패칭할 수 있고
-   페이지 이동 시 상위 구조가 유지되니 UX가 안정적이며
-   반복되는 UI를 정리하기에도 좋습니다

하지만 단점은 더 크게 다가왔습니다.

-   상위 레이아웃에 지나치게 많은 책임을 올리면
-   동적으로 렌더링되는 페이지는 어디로 들어오든 첫 진입과 새로고침 때마다 그 레이아웃의 SSR 비용을 함께 치르고
-   TTFB(요청을 시작한 때부터 브라우저가 응답의 첫 바이트를 받기까지 걸리는 시간)가 매 요청마다 흔들리고
-   URL마다 책임져야 할 문서의 의미도 흐려집니다

그래서 지금은 기준을 명확히 나눠서 설계하고 있습니다.

-   레이아웃(layout)
    -   전체 골격
    -   모든 페이지에서 정말 공통으로 필요한 최소 데이터
-   페이지(page)
    -   해당 URL이 대표해야 하는 문서
    -   그 문서를 설명하는 실제 데이터와 메타데이터

‘이 데이터가 정말 모든 페이지 입장에서 공통인가?’

이 질문 하나로 많은 실수를 미리 막을 수 있었습니다.

## 2\. Root Layout에는 무엇을 올려야 할까

app/layout.tsx는 앱 전반의 SSR이 시작되는 지점입니다.

그만큼 여기에 어떤 요소를 올리느냐의 무게가 매우 큽니다.

초기에 저는 단순히 “어디서든 쓰니까 여기에 두자”라는 판단으로 여러 요소를 root layout에 올렸습니다.

-   특정 페이지에서만 쓰는 모달
-   무거운 컴포넌트
-   대시보드 전용 UI
-   지도, 차트, 에디터 등 큰 라이브러리

결과는 명확했습니다.

-   초기 TTFB가 눈에 띄게 무거워지고
-   어떤 URL로 들어오든 첫 진입 시 부담이 컸으며
-   동적으로 렌더링되는 요청은 매번 root layout에서 시작하기 때문에 전체적인 성능이 불안정해졌습니다

지금은 기준을 이렇게 두고 있습니다.

-   html/body 구조
-   전역 Provider
-   모든 페이지에 공통적으로 필요한 UI

그 외의 요소들은 아래로 내려 특정 경로에서만 로드되도록 구조를 조정합니다.

root layout은 “편하니까 올리는 공간”이 아니라 “올리는 순간 앱 전체의 초기 성능과 번들을 함께 책임지는 공간”이라는 점을 몸으로 배웠습니다.

## 3\. Navigation Cache와 BFCache가 만드는 체감 속도

Next.js Navigation Cache는 Link 기반 페이지 이동에서 큰 장점을 제공합니다.

리스트 → 상세 → 뒤로가기 같은 흐름은 캐시 덕분에 매우 빠르게 동작합니다.

문제는 브라우저 단위의 BFCache입니다.

이 기능은 페이지 전체를 스냅샷처럼 저장했다가 뒤로가기 시 그대로 복원하는데, 생각보다 쉽게 비활성화됩니다.

실제로 어떤 페이지에서만 뒤로가기가 유독 느려지는 문제가 있었는데, 원인은 저희 쪽의 가벼운 이벤트 하나였습니다.

-   beforeunload
-   새로고침 감지 코드
-   히스토리 조작
-   특정 unload 훅

이런 코드가 들어가면 BFCache가 꺼질 수 있습니다. 가장 확실한 원인은 unload 리스너입니다. beforeunload는 최신 브라우저에서는 BFCache를 막지 않지만 예전에는 막았고 지금도 안정적이지 않아서 [web.dev의 BFCache 문서](https://web.dev/articles/bfcache)는 꼭 필요할 때만 붙이라고 안내합니다.

지금은 아래 기준으로 판단합니다.

-   기본적인 페이지 이동은 Next Navigation Cache를 활용
-   BFCache를 꺼트릴 수 있는 코드는 정말 필요한 조건에서만 사용
-   새로고침 감지나 beforeunload는 UX 영향까지 고려해 도입

“빠른 뒤로가기”는 렌더링 속도가 아니라 캐시 전략이 만드는 UX라는 점을 깨달았습니다.

## 4\. 시멘틱 URL과 Query로 문서의 의미와 상태 분리하기

SEO와 유지보수성을 함께 고려할 때 가장 명확한 기준은 이겁니다.

-   Path에는 문서의 정체성을
-   Query에는 문서를 보는 방식을

예를 들면:

-   /buildings/경기도-화성시-신동 → “이 문서 자체”
-   ?page=2&sort=price-desc&view=list → “이 문서를 어떻게 보고 있는지”

초반에는 필터가 많아서 query에 모든 것을 몰아넣었는데, 나중 가니 canonical 처리도 어려워지고 문서 의미도 모호해졌습니다. canonical은 같은 내용의 URL이 여러 개일 때 검색 엔진에 대표 URL을 알려주는 설정입니다. query로 URL에 상태를 싣는 방식은 [URL 상태관리는 문제를 해결했다](/posts/url-state-management/)에서도 다뤘습니다.

지금은 아래처럼 정리해서 사용하고 있습니다.

-   Path: 실제 리소스를 대표할 수 있는 식별 정보
-   Query: 필터, 정렬, 뷰 타입, 페이지네이션 등의 상태 정보
-   리스트 페이지는 canonical을 Path 기준으로 지정해 색인 안정성을 유지

다만 페이지네이션은 따로 봐야 합니다. 구글은 2페이지 이후를 1페이지로 canonical 처리하지 말고 페이지마다 자기 URL을 canonical로 두라고 [안내합니다](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading). 정렬이나 뷰 타입처럼 같은 문서를 다르게 보여 주는 값만 Path 기준으로 모읍니다.

이 기준 하나만으로도 URL 구조가 굉장히 명확해지고, SEO 이슈가 발생했을 때의 원인 추적도 쉬워졌습니다.

## 5\. generateMetadata는 URL과 같은 의미 체계를 가져야 한다

Dynamic route에서 generateMetadata()를 사용할 때 가장 중요했던 점은 URL, 페이지 데이터, 메타데이터가 동일한 도메인 모델을 바라봐야 한다는 것이었습니다.

예를 들어 /buildings/\[buildingId\]라면:

-   실제 buildingId 기반 데이터를 패칭하고
-   title, description, OG 이미지도 같은 데이터에서 생성해야 하며
-   본문 내용 역시 동일한 모델을 표현해야 합니다

이 세 가지가 맞지 않으면 검색 엔진은 페이지 의미를 정확히 해석하지 못합니다.

실제 운영 서비스에서 이를 일관되게 맞춰두니 검색 안정성이 확실히 좋아졌습니다. 크롤러가 HTML을 읽는 방식과 SSR이 SEO에 주는 영향은 [SEO의 구조적 진화](/posts/seo-structural-evolution/)에서 정리했습니다.

## 새 페이지를 만들 때 먼저 정리하는 네 가지

App Router를 처음 사용할 때는 레이아웃과 라우팅을 단순한 UI 구조 정도로 생각했습니다.

하지만 실제 서비스에 적용하면서 느낀 건, 이 부분이 성능, SEO, 데이터 흐름, UX까지 모든 핵심 요소를 좌우한다는 점이었습니다.

그래서 지금은 새로운 페이지를 만들 때 와이어프레임을 그리기 전에 먼저 아래를 정리합니다.

-   레이아웃 트리 구조
-   데이터 패칭 위치
-   URL의 의미 체계
-   메타데이터 구성 방식

한 번 구조가 꼬이면 나중에 되돌리기 쉽지 않기 때문입니다.

지금은 이렇게 생각하고 있습니다.

> 레이아웃과 라우팅은 단순한 화면 분리가 아니라 서비스 전체의 구조와 문서 체계를 정의하는 레이어입니다.
