### 다만 더 많은 문제를 해결하는 것이 항상 더 좋은 선택은 아니었다

예약 조건을 입력하고, 조건에 맞는 옵션을 선택한 뒤 예약 내용을 확인하는 플로우를 구현했다.

```text
예약 조건 입력
→ 옵션 조회
→ 옵션 선택
→ 예약 내용 확인
```

기능의 흐름은 단순했다.

첫 화면에서 입력한 값을 다음 화면으로 넘기고, 사용자가 선택한 옵션을 예약 확인 화면까지 전달하면 됐다.

조금 더 고민이 필요했던 것은 상태를 어디에 둘 것인지였다.

예약 확인 화면에서 옵션만 다시 선택하더라도 앞에서 입력한 조건은 유지되는 편이 자연스러워 보였다. 옵션 목록에서 새로고침하거나 주소로 직접 진입했을 때도 현재 화면을 다시 구성할 수 있다면 사용자 흐름이 더 안정적일 것 같았다.

명시적으로 정해진 동작은 아니었다.

화면의 흐름을 해석하면서 내가 추가로 중요하다고 본 조건에 가까웠다.

여러 화면에서 같은 값을 사용한다는 점만 보면 익숙한 상태관리 방식을 선택할 수 있었다. 하지만 이번에는 현재 화면을 주소로 설명할 수 있다면 상태의 흐름도 더 명확해질 것이라고 생각했다.

그래서 URL을 상태의 원본으로 사용하기로 했다.

---

## 화면을 공유하는 것보다 다시 구성하는 것

예약 과정에서 유지해야 했던 값은 다음과 같았다.

```text
예약 날짜
이용 인원
예약 유형
선택한 옵션
```

상태관리 라이브러리를 사용한다면 어렵지 않게 표현할 수 있다.

```ts
type ReservationState = {
  date: string | null;
  participants: number;
  category: ReservationCategory;
  selectedOptionId: number | null;
};
```

각 화면에서는 필요한 상태를 읽고, 정해진 액션을 통해 값을 변경하면 된다.

```ts
updateReservationConditions(nextConditions);
clearSelectedOption();
```

객체를 그대로 저장할 수 있고, 값을 문자열로 변환하거나 다시 파싱할 필요도 없다.

충분히 익숙하고 단순한 방법이었다.

다만 브라우저 메모리에만 존재하는 상태는 새로고침하면 사라진다. 옵션 목록의 주소로 직접 진입했을 때 어떤 조건으로 데이터를 조회해야 하는지도 알 수 없다.

Storage에 상태를 남길 수도 있지만, 저장 시점과 초기화 조건을 별도로 정해야 한다. 새로운 예약을 시작할 때 기존 값을 유지할 것인지, 여러 탭에서 같은 상태를 공유해도 되는지, 오래된 상태는 언제 제거할 것인지 같은 정책이 추가된다.

이번에는 별도의 저장소보다 현재 주소가 화면을 설명하도록 만들기로 했다.

```text
/options
  ?date=2026-08-01
  &participants=2
  &category=standard
```

옵션 목록 화면은 이전 화면에서 전달된 메모리 상태에 의존하지 않는다.

URL을 읽으면 어떤 조건으로 데이터를 조회해야 하는지 알 수 있다. 새로고침하더라도 동일한 요청을 다시 보낼 수 있고, 주소로 직접 접근해도 필요한 상태를 구성할 수 있다.

내가 중요하게 본 것은 여러 화면이 값을 공유하는 것보다, **현재 화면을 다시 만들어낼 수 있는가**였다.

## 선택한 옵션은 ID만 남겼다

예약 조건을 URL에 두는 것은 비교적 자연스러웠다.

날짜와 인원, 예약 유형은 현재 어떤 옵션 목록을 보고 있는지 설명한다.

조금 더 애매했던 것은 사용자가 선택한 옵션이었다.

선택한 옵션은 조회 조건이라기보다 예약을 진행하면서 만들어진 결과에 가깝다.

상태관리 라이브러리를 사용한다면 객체를 그대로 저장할 수 있다.

```ts
setSelectedOption(option);
```

Router State를 사용해 다음 화면으로 전달하는 것도 가능하다.

하지만 예약 확인 화면에서도 주소만으로 현재 선택을 다시 구성하려면 최소한의 식별자가 필요했다.

그래서 선택한 옵션의 ID까지 URL에 남겼다.

```text
/confirm
  ?date=2026-08-01
  &participants=2
  &category=standard
  &selectedOptionId=120
```

대신 옵션 객체 전체를 저장하지는 않았다.

```ts
{
  id: 120,
  title: '예약 옵션 A',
  startAt: '2026-08-01T10:00:00',
  price: 48000,
}
```

옵션의 이름과 가격, 예약 가능 여부는 서버가 관리하는 정보다.

객체 전체를 URL에 저장하면 이전에 조회한 데이터의 복사본이 만들어진다. 서버의 정보가 변경되더라도 URL에 남은 값은 그대로다.

따라서 URL에는 사용자가 무엇을 선택했는지만 기록하고, 그 선택이 현재도 유효한지는 서버 데이터로 다시 확인했다.

```ts
const selectedOption = options.find(
  option => option.id === selectedOptionId,
);
```

존재하는 ID라고 해서 현재 조건에서도 유효한 선택이라는 보장은 없다.

사용자가 주소를 직접 수정했을 수도 있고, 이전에는 가능했던 옵션이 더 이상 예약할 수 없는 상태가 됐을 수도 있다.

URL은 선택을 복원하고, 서버는 사실을 확인한다.

두 역할을 분리하고 싶었다.

## URL은 상태이면서 외부 입력이었다

구현하면서 가장 먼저 부딪힌 부분은 신뢰의 문제였다.

로컬 상태나 전역 상태는 대부분 애플리케이션 코드가 변경한다.

```ts
setParticipants(2);
```

반면 URL은 사용자가 직접 수정할 수 있다.

```text
?participants=-10
&category=UNKNOWN
&selectedOptionId=hello
&date=2026-99-99
```

TypeScript에서 타입을 선언하더라도 URL에서 읽은 값은 문자열일 뿐이다.

숫자로 변환할 수 있다는 것과 도메인에서 사용할 수 있는 값이라는 것도 다르다.

```ts
Number('hello'); // NaN
Number('-10');   // 숫자지만 유효한 인원은 아님
```

URL을 상태의 원본으로 선택한 순간, 동시에 URL을 외부 입력으로 다뤄야 했다.

그래서 애플리케이션으로 들어오는 경계에서 값을 파싱하고 검증했다.

```ts
const reservationParamsSchema = z.object({
  date: z
    .string()
    .regex(/^\d{4}-\d{2}-\d{2}$/)
    .nullable(),

  participants: z.coerce
    .number()
    .int()
    .min(1)
    .max(9)
    .catch(1),

  category: z
    .enum(['standard', 'premium'])
    .catch('standard'),

  selectedOptionId: z.coerce
    .number()
    .int()
    .positive()
    .optional(),
});
```

하지만 스키마를 통과했다고 모든 화면에서 바로 사용할 수 있는 것은 아니었다.

예약 조건을 입력하는 화면에서는 날짜가 없어도 정상이다. 반면 옵션을 조회하는 화면에서는 날짜가 반드시 필요하다.

```ts
type ReservationQuery = {
  date: string | null;
  participants: number;
  category: ReservationCategory;
};

type ReadyReservationQuery = {
  date: string;
  participants: number;
  category: ReservationCategory;
};
```

URL에서 읽은 상태와 기능을 실행할 수 있는 상태를 분리했다.

```ts
function toReadyReservationQuery(
  query: ReservationQuery,
): ReadyReservationQuery | null {
  if (query.date == null) {
    return null;
  }

  return {
    date: query.date,
    participants: query.participants,
    category: query.category,
  };
}
```

타입과 함수는 늘어났다.

대신 URL의 불완전함이 애플리케이션 전체로 퍼지는 것은 막을 수 있었다.

URL을 상태로 사용한다는 것은 Query String에 값을 넣는 일이 아니었다.

외부에서 들어온 문자열을 내부에서 신뢰할 수 있는 상태로 바꾸는 일이었다.

---

## 같은 값이어도 확정 시점은 달랐다

인원은 최종적으로 URL에 저장했다.

그렇다고 사용자가 인원을 변경하는 모든 순간을 URL에 반영하지는 않았다.

인원 선택 UI를 열고 값을 올리거나 내리는 과정은 아직 예약 조건으로 확정된 상태가 아니다. 사용자는 수정을 취소하거나 원래 값으로 돌아갈 수 있다.

편집 중인 값은 로컬 상태로 관리했다.

```ts
const [draftCount, setDraftCount] =
  useState(initialCount);
```

사용자가 확인했을 때만 URL에 반영했다.

```text
편집 중인 인원
→ 로컬 상태

확정된 예약 조건
→ URL 상태
```

처음에는 같은 인원 값이 두 곳에 존재하니 중복 상태처럼 보였다.

하지만 둘은 같은 상태의 복사본이 아니었다.

하나는 사용자가 아직 결정하지 않은 값이고, 다른 하나는 현재 옵션 조회에 실제로 적용된 값이다.

값의 모양보다 언제 만들어지고 언제 확정되는지가 저장 위치를 결정했다.

모든 상태를 URL에 넣으려 한 것이 아니라, 현재 화면을 구성하는 데 필요한 확정된 상태만 URL에 남겼다.

## URL을 바꾸는 일은 History를 설계하는 일이었다

URL을 사용하면 뒤로가기도 자연스럽게 해결될 것이라고 생각했다.

이전 URL로 돌아가면 이전 조건을 복원할 수 있으니 완전히 틀린 생각은 아니었다.

하지만 어떤 변경을 브라우저 History에 남길지는 URL이 대신 결정해주지 않았다.

같은 화면에서 인원을 변경할 때마다 새로운 History를 추가한다고 해보자.

```text
/reservation?participants=1
/reservation?participants=2
/reservation?participants=3
```

사용자는 같은 화면 안에서 조건을 수정했을 뿐이다.

그런데 화면을 나가기 위해 뒤로가기를 누르면 2명과 1명 상태를 차례대로 지나가게 된다.

URL이 달라졌다고 해서 모든 변경이 새로운 탐색인 것은 아니었다.

변경을 두 종류로 나눴다.

```text
push
- 새로운 단계로 이동
- 뒤로가기로 돌아와야 하는 탐색

replace
- 같은 화면 안에서 조건 수정
- 탐색 기록으로 남길 필요가 없는 변경
```

예약 조건을 수정할 때는 replace를 사용했다.

옵션 목록이나 예약 확인 화면으로 이동할 때는 push를 사용했다.

```text
예약 조건 수정
→ replace

옵션 목록 진입
→ push

예약 확인 진입
→ push

예약 완료
→ replace
```

조건이 바뀌면 이전에 선택한 옵션도 제거해야 했다.

날짜와 인원이 변경됐는데 과거 조건에서 선택한 옵션 ID가 남아 있다면 URL은 더 이상 하나의 일관된 상태를 표현하지 못한다.

URL 상태관리는 값 몇 개를 주소에 저장하는 방식이 아니었다.

어떤 변경을 새로운 탐색으로 볼 것인지, 여러 파라미터가 어떤 관계를 가져야 하는지까지 함께 설계하는 일이었다.

## 선택하며 생긴 복잡성을 한곳에 모았다

각 화면이 URL을 직접 읽고 수정하도록 두면 규칙은 빠르게 흩어진다.

한 화면에서는 기본값을 URL에 남기고 다른 화면에서는 제거할 수 있다. 조건이 바뀌었는데 이전의 선택값이 남을 수도 있다. 파라미터 이름이 변경되면 여러 화면을 함께 수정해야 할 수도 있다.

그래서 파싱과 직렬화, 경로 생성을 하나의 경계에 모았다.

```ts
parseReservationParams();
toReservationParams();
toOptionsPath();
toConfirmPath();
```

컴포넌트에서는 Query Parameter의 구체적인 구조보다 사용자의 행동이 보이도록 했다.

```text
navigate(
  toConfirmPath(query, selectedOptionId),
);
```

URL을 선택하며 생긴 복잡성을 없애지는 못했다.

대신 그 복잡성이 애플리케이션 전체로 퍼지지 않게 만들었다.

주소만으로 조회 조건을 다시 구성할 수 있었고, 선택한 옵션도 ID를 통해 복원할 수 있었다. 새로고침과 직접 진입, 브라우저 탐색도 하나의 흐름 안에서 설명할 수 있었다.

선택한 방식 안에서는 필요한 규칙을 일관되게 만들었다고 생각한다.

---

## 구현을 끝낸 뒤 다시 비교해본 선택

URL을 기준으로 예약 흐름을 구성하는 방식은 의도대로 동작했다.

처음 중요하게 보았던 문제는 실제로 해결됐다.

다만 구현을 정리하며 다른 방법과 다시 비교하자 처음에는 잘 보이지 않던 부분이 눈에 들어왔다.

나는 화면을 얼마나 완전하게 다시 구성할 수 있는지를 중심으로 방법을 비교했다.

그 기준에서는 URL의 장점이 분명했다.

반면 새로고침 이후의 복원이나 중간 화면으로의 직접 진입은 처음부터 반드시 해결해야 했던 문제라기보다, 사용자 흐름을 해석하면서 내가 추가한 조건에 가까웠다.

이 조건들이 불필요했다는 뜻은 아니다.

실제로 지원했을 때의 장점도 분명했다.

다만 익숙한 상태관리 방식을 사용했다면 이 조건을 모두 만족시키지 않더라도 예약의 핵심 흐름은 더 단순하게 표현할 수 있었다.

이미 알고 있는 방식으로 상태 변경을 구성하고, URL의 파싱과 직렬화, History 정책을 별도로 설계하지 않아도 됐을 것이다.

URL이 문제를 잘 해결하지 못한 것은 아니었다.

오히려 내가 중요하게 본 문제를 예상보다 충실하게 해결했다.

다만 더 많은 상황을 해결할 수 있다는 사실과, 현재 흐름에 가장 적절한 선택이라는 사실은 같지 않았다.

## 익숙함은 단순한 편의가 아니었다

새로운 방식을 선택할 때는 보통 학습 시간이나 코드 작성량을 비용으로 생각한다.

직접 사용해보니 더 큰 비용은 따로 있었다.

익숙한 도구에서는 이미 지나간 판단을 다시 해야 했다.

어디까지 URL에 둘 것인지, 기본값을 주소에 남길 것인지, 어떤 변경을 History에 기록할 것인지, 잘못된 파라미터를 복구할 것인지 거부할 것인지 하나씩 정해야 했다.

처음 사용하는 방식에서는 무엇을 모르는지도 처음부터 알기 어렵다.

반대로 익숙한 방식에서는 구현하기 전부터 복잡성의 범위를 어느 정도 예상할 수 있다.

어디에서 문제가 생길지 알고 있고, 어떤 추상화가 필요한지 판단할 수 있으며, 예상하지 못한 문제를 만났을 때도 이미 갖고 있는 경험으로 대응할 수 있다.

익숙함은 코드를 빠르게 작성하게 해주는 편의에 그치지 않았다.

불확실성을 줄이고, 중요한 곳에 시간을 집중하며, 결과의 완성도를 안정적으로 높일 수 있게 해주는 기반에 가까웠다.

새로운 방법을 선택하는 것과 익숙한 방법을 선택하는 것은 도전과 타협의 관계가 아니었다.

둘은 서로 다른 목적을 가진 선택이었다.

새로운 구조를 탐색하는 것이 중요할 때는 낯선 방법을 선택할 수 있다. 반대로 핵심 흐름을 안정적으로 완성하는 것이 중요할 때는 이미 충분히 알고 있는 방법이 더 나은 선택일 수 있다.

중요한 것은 어떤 선택이 더 어려워 보이는지가 아니었다.

지금 무엇을 해결해야 하는지에 가까운 선택인가였다.

---

## 다시 같은 흐름을 구현한다면

화면 복원이 실제로 중요한 요구사항이라면 URL을 다시 선택할 수 있다.

주소만으로 화면을 구성해야 하고, 새로고침이나 직접 진입이 사용자 흐름의 일부라면 URL은 여전히 강한 선택지다.

다만 먼저 확인할 것이 늘어났다.

```text
반드시 유지해야 하는 상태는 무엇인가
사용자 흐름을 해석하며 추가한 조건은 무엇인가
추가한 조건이 실제 복잡성을 감수할 만큼 중요한가
팀에 이미 비슷한 규칙과 도구가 존재하는가
선택한 방식의 복잡성을 구현 전에 예상할 수 있는가
```

반대로 화면 간 상태 전달이 핵심이고 복원은 부가적인 가치라면 익숙한 상태관리 방식을 먼저 선택할 것이다.

일단 핵심 플로우를 단순하게 완성하고, 복원의 필요성이 커질 때 URL과의 역할을 다시 나눌 수도 있다.

```text
조회 조건
→ URL

임시 입력과 선택 상태
→ 상태관리

서버가 책임지는 사실
→ 서버 상태
```

모든 상태를 하나의 장소에 두는 것보다 각 상태의 생명주기와 책임에 맞게 나누는 편이 더 자연스러울 수 있다.

이제는 어떤 기술이 더 많은 문제를 해결하는지만 보지 않으려 한다.

그 선택으로 새롭게 책임져야 하는 것은 무엇인지, 이미 가지고 있는 구조와 경험을 활용했을 때 무엇에 더 집중할 수 있는지도 함께 보려고 한다.

---

## 마무리

URL을 상태의 원본으로 사용한 경험을 후회하지는 않는다.

주소를 외부 입력으로 바라보게 됐고, 불완전한 상태가 애플리케이션 안으로 퍼지지 않도록 경계를 만드는 방법을 고민할 수 있었다.

선택한 옵션의 ID와 서버가 관리하는 정보를 분리했고, 브라우저 History를 단순한 라우터 기능이 아니라 사용자 흐름의 일부로 다뤄볼 수 있었다.

직접 선택하고 부딪혔기 때문에 얻을 수 있었던 기준도 분명히 있다.

다만 기술을 선택할 때 문제와 도구의 관계만 보는 것으로는 충분하지 않았다.

현재 흐름에서 반드시 해결해야 하는 문제와 내가 더 나은 경험을 위해 추가한 조건을 구분해야 했다. 새로운 방식이 제공하는 가능성뿐 아니라, 익숙한 방식이 줄여주는 불확실성도 선택의 일부로 봐야 했다.

URL은 내가 중요하게 본 문제를 해결했다.

그럼에도 다시 구현한다면 같은 방법을 선택한다고 단정할 수는 없다.

조건이 달라지면 더 단순한 상태관리 방식을 선택할 수도 있고, 복원이 중요하다면 URL을 다시 선택할 수도 있다.

중요한 것은 특정 도구를 선택했다는 사실이 아니었다.

**더 많은 문제를 해결하는 방법보다, 지금 중요한 문제를 가장 안정적으로 해결하는 방법을 선택할 수 있는가였다.**
