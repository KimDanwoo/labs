## 과제 개요: 프레임워크 없이 SPA 구현하기

이번 과제에서는 Vanilla JavaScript로 SPA(Single Page Application)를 구현했다. 주요 요구사항은 History API로 라우터를 구현하는 것, LocalStorage를 사용한 사용자 관리 기능, 컴포넌트 기반 구조 설계, 초기 상태 관리 구현, 그리고 테스트 코드 통과였다.

이전에 react-router를 사용해본 경험은 있지만, 내부적으로 어떻게 동작하는지는 구체적으로 알지 못했다. 이번 과제에서 SPA 라우팅이 어떻게 작동하는지 직접 구현하면서 더 깊이 이해할 수 있었다.

## 시도한 것들

### 1. History API로 라우터 직접 구현

기존에 사용하던 라우터 라이브러리 대신 브라우저의 History API로 페이지 전환 기능을 구현했다. history.pushState와 popstate 이벤트를 관리해 클라이언트 사이드 라우팅을 처리했고, URL이 바뀔 때마다 컴포넌트를 렌더링하고 브라우저 내비게이션 이벤트에 반응하도록 했다.

pushState는 페이지를 새로 불러오지 않고 주소와 히스토리 항목만 바꾸는 메서드이고, popstate는 뒤로 가기나 앞으로 가기로 히스토리 항목이 바뀔 때 발생하는 이벤트다. 두 가지를 짝지으면 새로고침 없이 URL을 바꾸고 그에 맞는 화면을 그릴 수 있다. 상태를 URL에 두는 경우 히스토리에 무엇을 남길지까지 설계해야 했던 경험은 [URL 상태관리는 문제를 해결했다](/posts/url-state-management/)에서 다뤘다.

pushState는 상태 객체, 제목 자리의 인자, URL을 받으며 URL은 현재 문서와 같은 출처여야 한다. 한 가지 주의할 점은 pushState를 호출해도 popstate 이벤트는 발생하지 않는다는 것이다. popstate는 뒤로 가기·앞으로 가기처럼 사용자가 히스토리를 이동할 때 발생하므로, 링크를 눌러 직접 경로를 바꿀 때는 pushState를 호출한 뒤 화면을 다시 그리는 코드를 따로 실행해야 한다. 그래서 라우터는 보통 이동 함수와 popstate 핸들러가 같은 렌더링 함수를 부르는 구조가 된다.

주소창에 경로를 직접 입력하거나 새로고침하면 브라우저는 서버에 그 경로를 요청한다. 서버가 `/profile` 같은 경로를 모르면 404가 나므로, History API 방식의 SPA는 서버가 알 수 없는 경로에도 index.html을 돌려주도록 설정해야 한다. 이 설정이 필요 없는 대안이 해시(`#`) 기반 라우팅이다. 해시 뒤의 값은 서버로 전송되지 않고 `hashchange` 이벤트로 감지하지만 URL에 `#`이 붙는다.

### 2. 경로 보호(Route Guard)

사용자 로그인 여부에 따라 특정 경로에 접근할 수 있도록 경로 보호 로직을 추가했다. 로그인하지 않은 사용자가 보호된 경로로 접근하려 하면 로그인 페이지로 리다이렉트하고, 로그인 상태일 때는 프로필 페이지에 접근할 수 있도록 했다. 사용자 상태에 따른 라우팅 처리를 이렇게 구현했다.

리다이렉트에서는 pushState 대신 replaceState를 쓰는 방법이 있다. replaceState는 히스토리 항목을 새로 쌓지 않고 현재 항목을 바꾼다. 보호된 경로에서 로그인 페이지로 보낼 때 이 방식을 쓰면 뒤로 가기를 눌렀을 때 다시 보호된 경로로 돌아가 같은 리다이렉트가 반복되는 일을 피할 수 있다.

클라이언트에서 하는 경로 보호는 화면 접근을 안내하는 장치일 뿐 보안 장치가 아니다. LocalStorage의 값은 사용자가 개발자 도구에서 바꿀 수 있으므로 로그인 여부를 거기서 읽는 가드는 우회할 수 있다. 실제 권한 검증은 서버가 해야 하고 민감한 토큰을 LocalStorage에 두면 XSS가 발생했을 때 탈취될 수 있다는 점도 알고 있어야 한다.

### 3. 상태 관리(Store) 구현

싱글톤 패턴으로 전역 상태 관리 스토어를 구축했다. 싱글톤은 인스턴스를 하나만 만들어 어디서든 같은 객체를 쓰게 하는 패턴이라, 스토어가 사용자 정보와 로그인 상태를 한 곳에서 관리하고 페이지가 바뀌어도 상태가 유지되도록 처리할 수 있었다. 프레임워크 없이 상태 관리 시스템을 직접 구현하면서 상태 변경에 따른 UI 업데이트를 처리하는 방식을 배웠다.

싱글톤 스토어는 자바스크립트에서 모듈 하나가 한 번만 실행되고 그 결과가 캐시된다는 성질을 이용하면 간단히 만들 수 있다. 모듈 안에 상태 객체를 두고 getState와 setState 같은 함수만 내보내면 어디서 import하든 같은 객체를 가리킨다. 상태가 바뀔 때 화면을 갱신하려면 구독 함수를 등록해 두고 setState에서 등록된 함수를 모두 호출하는 옵저버 패턴을 흔히 쓴다. 전역 상태이므로 테스트마다 초기값으로 되돌리는 처리가 없으면 테스트 사이에 상태가 새어 나갈 수 있다.

### 4. 클린업 처리(Cleanup)

페이지 전환 시 기존 컴포넌트의 리소스를 정리해야 한다는 점을 깨닫고, 메모리 관리와 이벤트 리스너 제거로 불필요한 리소스가 남지 않도록 신경 썼다. 성능 최적화와 리소스 관리가 중요하다는 것도 체감했다.

정리해야 하는 대상은 크게 세 가지다. 이전 화면이 등록한 이벤트 리스너는 `removeEventListener`로 해제하고 `setInterval`이나 `setTimeout` 같은 타이머는 해제 함수로 멈추며 진행 중인 fetch 요청은 `AbortController`로 취소한다. 페이지 전환 때 DOM만 교체하고 이 작업을 빼먹으면 보이지 않는 화면의 코드가 계속 실행된다. React의 `useEffect`가 반환하는 정리 함수도 같은 문제를 다루는 장치다.

### 5. 이벤트 위임(Event Delegation)

전역 클릭 이벤트를 감지해 이벤트 위임 방식으로 링크 클릭을 처리했다. 클릭 이벤트로 브라우저 새로고침 없이 경로를 바꾸는 방식을 구현했고, DOM 이벤트 처리 패턴을 더 깊이 이해할 수 있었다. 이벤트 위임은 가상 DOM을 구현한 과제에서도 다시 다뤘다. 자세한 내용은 [내가 리액트를 직접 만들어봤다?](/posts/build-my-own-react/)에 있다.

이벤트 위임은 DOM 이벤트가 자식에서 부모로 전파되는 버블링에 기반한다. 링크마다 리스너를 붙이는 대신 상위 요소(보통 document)에 리스너를 하나만 두고 핸들러에서 `event.target.closest('a')`로 클릭된 요소 자신이나 그 요소를 감싸는 가장 가까운 링크를 찾는다. 나중에 동적으로 추가된 링크도 따로 등록하지 않고 처리할 수 있다는 점이 장점이다. 링크를 가로챌 때는 같은 출처의 내부 경로인지, `target="_blank"`나 Ctrl·Cmd 키가 함께 눌린 클릭이 아닌지를 확인해야 한다. 이 경우를 걸러내지 않으면 새 탭으로 열기 같은 브라우저 기본 동작이 깨진다.

## 배운 것들: History API, 상태 관리, 에러 바운더리

이번 과제에서 History API로 페이지 새로고침 없이 URL을 바꾸고, 브라우저의 뒤로 가기와 앞으로 가기를 관리하는 방법을 배웠다. pushState와 popstate 이벤트로 페이지 전환을 처리하는 점이 특히 흥미로웠다.

컴포넌트 기반 구조로 코드를 설계하면서 유지 보수성과 확장성이 얼마나 중요한지도 실감했다. React 같은 프레임워크 없이 상태 관리를 직접 구현해보니, 프레임워크가 얼마나 많은 복잡한 작업을 대신 처리해주는지 알게 되었다. 전역 상태 관리나 상태 변경에 따른 UI 업데이트를 모두 수동으로 처리해야 했기 때문이다. 덕분에 상태 관리 최적화를 고민해볼 기회가 됐다.

에러 바운더리를 구현하면서 에러 처리 방식과 사용자 경험을 보호하는 방법도 배웠다. 특히 센트리 같은 도구로 사용자의 피드백 없이도 에러를 자동으로 캐치하는 방식이 매우 매력적으로 다가왔다. 실무에서도 꼭 사용해보고 싶은 기능이었다.

React의 에러 바운더리는 자식 컴포넌트를 렌더링하다 생긴 오류를 잡아 대체 화면을 보여 주는 컴포넌트다. 클래스 컴포넌트의 `getDerivedStateFromError`와 `componentDidCatch`로 구현한다. 프레임워크 없이 만들 때는 이런 장치가 없으므로 렌더링 함수를 try/catch로 감싸 대체 화면을 그리고 잡히지 않은 오류는 `window`의 `error` 이벤트와 처리되지 않은 Promise 거부를 받는 `unhandledrejection` 이벤트로 수집한다. 센트리 같은 도구도 이 이벤트를 이용해 오류를 자동으로 수집한다.

## History API 라우터의 한계와 다른 선택지

직접 만든 라우터는 구조가 단순한 대신 중첩 라우트, 경로 파라미터(`/users/:id`) 매칭, 쿼리스트링 처리, 스크롤 위치 복원, 코드 분할 같은 기능을 직접 채워야 한다. react-router 같은 라이브러리가 이 부분을 맡는다. 브라우저에는 History API를 대체하려는 Navigation API도 도입되고 있지만 지원 범위는 브라우저와 버전마다 다르므로 사용하기 전에 MDN의 호환성 표를 확인해야 한다.
